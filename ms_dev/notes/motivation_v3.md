## 0. 이 문서를 읽는 법

### 0.1 논증을 한 문단으로

여러 종류의 요청을 GPU 함대 하나에서 같이 서빙하면, **그 함대가 감당할 수 있는 도착률이
하드웨어로 정해지지 않고 라우터가 요청을 어떻게 나눠 놓았는지로 정해진다.** 이유는 연속
배칭(continuous batching)에 있다 — 인스턴스 하나는 자기 위의 모든 요청에게 같은 속도로
토큰을 만들어 주므로, 그 인스턴스가 얼마나 빨라야 하는지는 거기 있는 요청 중 가장 급한 것이
정한다. 그래서 요청 하나를 어디에 놓느냐가 그 요청의 자원만 쓰는 것이 아니라 **거기 이미
있던 요청들의 여유까지 바꾼다.** 측정하면, 엔진·모델·요청 구성·지연 규칙을 전부 고정하고
컨트롤플레인만 바꿔도 90% 달성률을 유지하는 도착률이 15.8에서 28.1 req/s로 1.78배 벌어지고
(정적 sweep), 같은 함대가 같은 양의 토큰을 만들면서 규칙 안에 도착하는 토큰은 6.9배 차이가
난다(한 시간 trace). **그러므로 라우팅 계층의 목표는 부하를 고르게 펴는 것이 아니라,
지연 규칙을 지키면서 감당할 수 있는 도착률을 크게 만드는 것이다.**

### 0.2 논증의 단계

| | 단계 | 절 |
|---|---|---|
| 1 | 워크로드가 이질적이고 지연 규칙의 **형태가 둘**이다 — 토큰당 예산과 전체 시간 예산 | §2.1 |
| 2 | 그래서 배포가 다중 인스턴스이고, 요청은 **라우팅 계층을 먼저 지나** 엔진 스케줄러로 간다 | §2.2 |
| 3 | 라우팅 계층의 목표를 **함대의 serving capacity를 유지하는 것**으로 정의하고, 그 값을 재는 방법을 정한다 | §2.3 |
| 4 | 실측: **라우터만 바꿔도 결과가 크게 달라지고**, 엔진은 거의 같은 양의 일을 한다 | §3.1 |

| 6 | 어려움 셋: **예산이 batch에 묶인다 / 단일 부하 신호가 없다 / 신호가 정책 자신의 결정에 따라 움직인다** | §3.2 |
| 7 | 기존 시스템을 **admission 축과 routing 축**으로 놓으면 각 칸의 실패가 같은 메커니즘으로 설명된다 | §3.3 |
| 8 | 그래서 해법이 반드시 가져야 하는 것 넷, 그리고 우리 설계의 어느 부분이 각각에 대응하는가 | §3.4 |

### 0.3 용어 — 뜻이 겹치는 말 넷만 여기 적는다

| 말 | 이 문서에서의 뜻 |
|---|---|
| **배치(placement)** | 요청 **하나**를 어느 인스턴스에 놓는 것 |
| **batch** | 엔진이 디코드 스텝 하나에서 같이 진행시키는 요청 집합. 영어 그대로 쓴다 |
| **배정(allocation)** | 어떤 **클래스**가 결과적으로 인스턴스 몇 대를 쓰게 되었는가 |
| **배분(partition)** | 클래스마다 인스턴스를 몇 대씩 **미리 떼어 주는 것**. 2.5대 같은 값을 줄 수 없다 |

**그리고 우리 시스템의 부품 이름이 §3.4 전에 몇 번 나오므로 여기서 한 번씩 풀어 둔다.**

| 이름 | 무엇인가 |
|---|---|
| **게이트(gate)** | 인스턴스 하나가 지금 지켜야 하는 **디코드 스텝 시간의 상한**과, 새 요청을 하나 더 받았을 때 실제로 나올 스텝 시간을 비교하는 조건. 상한은 지금 그 인스턴스에서 처리되고 있는 요청들이 각자 허용하는 값 중 가장 작은 것이다 |
| **`overIncumbents`** | 새 요청을 받으면 **이미 그 인스턴스에서 처리되고 있던 요청들**이 자기 예산을 넘기게 되는지를 보는 조건 |
| **ROUTE / PEND / SHED / FORCE** | 같은 판정 조건을 네 인스턴스에 각각 적용한 결과가 만드는 네 가지 답이다. 통과하는 인스턴스가 있으면 그중 하나로 **보내고**(ROUTE), 지금은 하나도 없지만 곧 생길 수 있으면 요청을 아직 어느 엔진에도 넘기지 않은 채 **라우터에 붙들어 두었다가 다시 판정하고**(PEND, 문헌 용어로는 router-side queueing), 붙들고 기다려도 안 될 것으로 판정되면 **거절하고**(SHED), 그럴 수도 없으면 조건을 가장 덜 어기는 인스턴스로 **강제로 보낸다**(FORCE) |
| **명목 예산 / 남은 예산** | 인스턴스의 스텝 시간 상한을 구하는 방법이 둘이다. **명목 예산**은 클래스별 목표를 그대로 쓴다(chat이 하나라도 있으면 50 ms). **남은 예산**은 각 요청이 지금까지 쓴 시간을 빼고 남은 시간을 남은 출력 토큰 수로 나눈다 — 예산보다 빨리 진행된 요청은 앞으로 조금 느려져도 되므로 값이 더 느슨하다 |
| **오라클 고정 배분** | 실험이 끝난 뒤에 그 run에서 실제로 나온 클래스별 출력 토큰 비중을 보고, 인스턴스 네 대를 클래스에 정수로 나누는 방법 중 가장 좋았을 것을 고른 것. **실험 중에는 알 수 없는 정보를 쓰므로 배포할 수 있는 정책이 아니고**, 정수 배분이 낼 수 있는 값의 상한을 재려고 계산한 참조선이다 |
| **tier 키** | 워크로드 설정 파일의 `tbt_ms` 값이고, **세 클래스를 구별하려고 붙인 이름(25 / 50 / 100)이지 그 클래스의 목표가 아니다.** swe의 실제 목표는 전체 30초다 |
| **클래스당 유효 인스턴스 수 (`N_eff`)** | 그 클래스의 요청이 실제로 **몇 대의 인스턴스에 나뉘어 갔는지**를 인스턴스 개수 단위로 나타낸 값. 창 하나 안에서 클래스 c의 요청이 인스턴스 i로 간 비율을 s_i라 할 때 `N_eff = 1/Σ s_i²`이고, 창마다 계산해 중앙값을 쓴다. **네 대에 고르게 갔으면 4.0, 한 대에만 갔으면 1.0, 두 대에 반씩이면 2.0이다.** 지어낸 지표가 아니라 inverse Simpson index와 같은 양이다 |
| **chat을 하나도 처리하지 않고 있던 인스턴스의 시간 비율** | 일정 간격으로 인스턴스 네 대를 각각 들여다봤을 때, 그 순간 그 인스턴스에서 처리되고 있는 chat 요청이 하나도 없었던 경우의 비율. 네 대 중 평균 한 대가 계속 그랬으면 25%다 |

**SLO 달성률(attainment)**은 자기 지연 규칙을 지킨 채 완료된 요청의 비율이고, 분모를 두 개
쓴다 — `admitted`(시스템이 받아들인 것)와 `offered`(도착한 모든 것, **거절은 위반으로 센다**).
이 문서의 수치는 따로 밝히지 않는 한 **offered 분모이고 요청 하나를 하나로 세는 집계**다.

그 밖의 용어(`gateAllowance`, `tightestAllowance` 등)는
`motivation_v2.md` §0.4에 정의가 있고, 이 문서는 처음 쓰는 자리에서 한 번씩 풀어 쓴다.

# 2 Background

## 2.1 Heterogeneous LLM workloads and SLOs

> **A single fleet now serves request classes whose latency contracts differ in
> kind, not only in magnitude: some are bounded per output token, others end to
> end.**

같은 모델을 쓰는 서비스라도 요청의 성격이 크게 다르다. 사람이 화면을 보며 기다리는 대화형
질의응답은 첫 토큰이 빨리 나와야 하고 그 뒤로 글자가 읽는 속도로 흘러야 한다. 검색 결과를
모아 긴 보고서를 쓰는 요청은 첫 토큰이 조금 늦어도 되고 토큰당 속도도 느슨해도 된다. 코딩
에이전트가 도구를 호출하는 사이에 넣는 LLM 호출은 사람이 중간 출력을 읽지 않으므로 토큰당
속도에는 요구가 없고, 대신 **호출 전체가 정해진 시간 안에 끝나야** 다음 단계로 넘어간다.

우리 실험은 이 셋을 쓴다. 아래 값은 실제로 돌린 워크로드에서 잰 것이다.

| 클래스 | 무엇인가 | 첫 토큰까지 | 그 뒤의 규칙 | 평균 입력 | 평균 출력 | 요청 비중 |
|---|---|---|---|---|---|---|
| chat | 대화형 질의응답 | 5초 | 출력 **토큰 하나당 평균 50 ms** | 649 토큰 | 428 | **76.9%** |
| deepresearch | 검색 결과로 긴 보고서 작성 | 10초 | 토큰 하나당 **100 ms** | 4,639 | 985 | 15.4% |
| swe | 코딩 에이전트의 한 호출 | 11.8초 | **전체가 30초 안에** 끝날 것 | 5,557 | 520 | 7.7% |

⚠ **요청 비중 76.9%는 정적 조건의 값이다.** 위 비율 10:2:1을 요청 수로 그대로 돌리면
76.9 / 15.4 / 7.7%가 되고, 정적 sweep이 그것이다. **한 시간 trace는 구성이 15분마다
바뀌므로 전체를 합친 실측이 78.1 / 11.9 / 10.0%**로 조금 다르다. 이 문서는 정적 조건의
수치 옆에는 76.9%를, 한 시간 trace의 수치 옆에는 78.1%를 쓴다.

**여기서 논문이 써야 하는 사실은 "예산의 크기가 다르다"가 아니라 "예산의 형태가 둘이다"라는
것이다.** chat과 deepresearch는 토큰당 시간으로 판정되고 swe는 전체 시간으로 판정된다.
**전체 시간 예산은 토큰당 임계 하나로 표현되지 않는다** — 남은 토큰이 많으면 느려도 되고
적으면 빨라야 하므로, 같은 요청이라도 진행 정도에 따라 허용되는 속도가 달라지기 때문이다.
이 사실이 뒤에서 두 번 쓰인다. 한 번은 기존 정책이 왜 swe를 잘못 다루는지(§3.2.2), 또 한 번은
우리 실험이 왜 두 정책에만 다른 워크로드 설정을 주는지(§3.1의 Approaches)다.

**그리고 도착률과 구성비가 둘 다 시간에 따라 움직인다.** 우리 한 시간 trace는 Azure 실측
도착률을 그대로 쓰고 대역만 옮기는데, 그 안에서 **가장 한가한 때와 가장 바쁜 때가 10.8 대
45.0 req/s로 4.17배** 차이난다. 구성비는 그것과 따로 움직인다 — Azure의 2024년 공개 trace에서
대화형 요청 대비 코드 요청의 비가 시각대별로 **12.0%에서 56.7%까지 4.71배** 움직이고, 곡선이
봉우리 하나짜리라 하루 주기다. 우리 한 시간 trace는 같은 자릿수의 이동을 합성해서 넣는다(swe의 입력 토큰 비중
14~57%, 4.07배). **즉 "믹스가 움직인다"는 우리가 고른 설정이 아니라 실측에 근거가 있다** —
다만 **수준 자체(10:2:1)는 우리가 고른 값이다.**

## 2.2 LLM serving infrastructure: a routing plane over independent engines

> **Deployments scale out to many instances, so a request first passes a routing
> plane that chooses an instance, and only then an engine scheduler that chooses
> an order.**

하나의 GPU 인스턴스가 감당할 수 있는 부하에는 한계가 있으므로 실제 배포는 인스턴스를 여러 대
둔다. 그러면 요청 하나가 두 번의 결정을 지난다. **첫 번째는 라우팅 계층**이 "이 요청을 어느
인스턴스로 보낼 것인가, 혹은 보내지 않을 것인가"를 정하고, **두 번째는 그 인스턴스의 엔진
스케줄러**가 "지금 batch에 무엇을 넣을 것인가"를 정한다. vLLM과 SGLang이 두 번째 계층이고,
Llumnix·llm-d·vLLM production stack router 같은 것이 첫 번째 계층이다.

**엔진 계층은 지연 목표를 맞추려고 여러 기법을 이미 쓰고 있다.** 첫 토큰까지의 시간은
prefill이 정하므로, prefill 계산을 작은 단위(chunk)로 쪼개서 다른 요청의 디코드를 오래 막지
않게 하고, 마감이 급한 요청의 prefill을 먼저 하거나 진행 중인 것을 preemption한다. 토큰당
시간은 batch가 커질수록 나빠지므로 batch 크기나 batch가 들고 있는 KV 캐시 양에 상한을 둔다.

**그런데 엔진 하나가 아무리 잘해도 자기에게 이미 온 요청밖에 다루지 못한다.** 엔진
스케줄러의 결정 변수는 **이미 자기에게 커밋된 요청들의 순서와 batch 구성**이고, 라우팅
계층의 결정 변수는 **아직 어느 엔진에도 속하지 않은 요청의 목적지**다. 요청은 라우팅
계층에서 엔진 스케줄러로 한 방향으로만 넘어가고 되돌아오지 않는다 — 라우팅 계층이 인스턴스
하나를 골라 그 엔진에 요청을 넘기고 나면, 그 엔진의 스케줄러는 받은 요청을 다른 엔진으로 다시
보낼 수 없다. **그러므로 요청이 잘못된 인스턴스에 가 있으면 엔진 안에서는 어떤 순서로도 고칠
수 없다.** 이 구분이 §3.1.4의 측정으로 확인된다.

## 2.3 What the routing plane is for

> **The routing plane's job is to keep the fleet at its serving capacity: the
> highest arrival rate at which arriving requests still meet their own latency
> rule.**

**요청이 모두 같은 지연 규칙을 따르면 이 목표는 부하 분산과 같은 말이다.** 인스턴스 하나가
초당 K건을 감당하면 N대는 NK건을 감당하고, 라우터가 할 일은 그 NK를 낭비하지 않는 것 —
한 인스턴스가 놀고 다른 인스턴스가 밀리는 상태를 만들지 않는 것이다. 이것이 **부하 분산이
옳은 목적함수인 조건**이고, 이 분야의 라우터 대부분이 그 조건 아래에서 설계됐다.

**지연 규칙이 클래스마다 다르면 그 등식이 깨진다.** 함대의 capacity가 하드웨어의 성질이
아니라 **배치의 함수**가 되기 때문이고, 그 메커니즘은 §3.2.1에 적는다. 여기서는 목표를
어떻게 **잴 것인지**만 정한다.

### 2.3.1 capacity를 무엇으로 정의하는가

> **We report the highest offered request rate at which at least 90% of arriving
> requests meet their own per-class latency rule, counting rejections as
> violations, interpolated between the two measured rates that bracket the
> threshold.**

거절을 위반으로 세는 것이 핵심이다. **그렇게 하지 않으면 전부 거절하는 정책이 만점을 받는다.**

**후보 정의 넷을 쓰지 않기로 했고, 이유는 각각 다르다.**

| 후보 | 왜 쓰지 않는가 |
|---|---|
| 포화 시점의 token goodput | 단위가 토큰이라 **출력이 긴 요청을 지키고 짧은 요청을 거절하는 정책이 높게 나온다.** 실제로 한 조건에서 토큰으로 세면 Llumnix SLO가 1위이고 요청으로 세면 PolyServe가 1위로 뒤집힌다. **보조 지표로 반드시 같이 싣되 주 지표로는 쓰지 않는다** |
| admitted 분모의 달성률이 90%를 지나는 도착률 | **전부 거절하는 정책이 무한대를 받는다** |
| 각 클래스 단독 포화 도착률의 가법 결합 | 자원이 하나뿐이고 클래스마다 고정 비율로 소비한다는 가정 위에 있는데, **그 가정이 틀렸다는 것이 이 논문의 주장이므로 주 정의로 쓰면 순환이다** |
| 배치의 모든 경우를 탐색했을 때의 최대 도착률 | 이론적으로는 이것이 정확한 뜻이지만 **측정할 방법이 없다** |

**이 정의가 주장하는 것과 주장하지 않는 것을 갈라 적는다.**

- **주장한다**: 하드웨어·모델·요청 구성·지연 규칙을 전부 고정하고 컨트롤플레인만 바꿨을 때
  이 값이 얼마나 움직이는가. 그 차이는 컨트롤플레인의 것이다.
- **주장하지 않는다**: 이 값이 함대의 물리적 상한이라는 것. 우리 값도 상한이 아니고, 사후에
  계산한 오라클 배분이 우리를 이기는 조건이 실제로 있다(§3.3.3).
- **주장하지 않는다**: 90%가 특별한 값이라는 것. 통과 기준을 70·80·90·95% 어디에 그어도
  **우리가 네 통과 기준 전부에서 1위**다. 다만 **기준선끼리의 순서는 통과 기준에 따라 뒤집히므로**
  (§3.1의 표 2) 기준선의 순위를 말할 때는 통과 기준을 같이 밝힌다.

**⚠ 이 정의에 약점이 둘 있고, 심사에서 지적당하기 전에 우리가 먼저 적어야 한다.**

**① 요청 수로 가중한 90% 문턱은 한 클래스의 요청을 거의 전부 거절해도 통과한다.** chat과 deepresearch가
요청의 90%이므로, **swe를 100% 거절하는 정책도 이 기준을 넘을 수 있다.** 이것은 이질적인
SLO를 다룬다면서 스칼라 하나로 합쳐 버린 것이고, 하필 우리 정책이 한 시간 trace에서 swe를 34.1%
거절한다. → **그러므로 이 값을 쓸 때는 반드시 클래스별 달성률 벡터를 같이 싣고,
"클래스별 하한"으로 잰 값(가장 낮은 클래스의 달성률)도 같이 보고한다.** §3.1.2가 그 값이다.

**② 이 값을 선형 보간으로 구하는데, 두 arm에서는 달성률이 한 단계 사이에서 급격히 떨어지는
구간을 사이에 두고 보간한다.** Llumnix SLO는
20 req/s의 95.4에서 25의 34.4로, PolyServe는 15의 99.9에서 20의 39.9로 떨어진다. **그 사이를
직선으로 이으면 측정이 아니라 가정이다.** → **논문에는 보간값 대신 구간으로 적는 것이 옳다**
(PolyServe는 (15, 20], Llumnix SLO는 (20, 25]). 그리고 15.8과 20.4처럼 소수 첫째 자리까지 적혀
있다고 해서 그만큼 촘촘한 간격으로 도착률을 재 봤다는 뜻이 아니다 — 실제로 잰 도착률은
10·15·20·25·35·45·55·70 req/s 여덟 단계뿐이다. 그 구간을 더 촘촘하게 재는 것이 §5.2의 E4다.

# 3 Motivation

## 3.1 Problems with existing routing schemes

기존 라우팅 방식의 한계를 드러내려고 실험을 하나 돌렸다. 설정은 다음과 같다.

**Testbed.** vLLM V1 인스턴스 **네 대**, 각각 `meta-llama/Meta-Llama-3.1-70B-Instruct`를
tensor parallel 2로 올린다(총 **NVIDIA B200 8장**, 한 노드. 파드에서 확인한 값이다). 인스턴스마다 KV 캐시가 584,928 토큰이고 최대 문맥이 8,192 토큰이다.
엔진 스케줄러는 **따로 밝히지 않는 한 vLLM 기본 FIFO**다. 컨트롤플레인은 Llumnix의
게이트웨이와 스케줄러이고, **정책만 갈아 끼운다** — 즉 네 arm이 같은 게이트웨이·같은 엔진·
같은 워크로드를 쓰고 라우팅/admission 정책만 다르다.

⚠ **이식 충실도에 대해 두 가지만 여기 적고, 이유는 §5.1에서 적는다.** 하나, **두 Llumnix
arm에서는 migration이 결정만 되고 실제로 실행되지는 않으므로 재배치가 없는 구성으로 읽어야
한다.** 둘, **PolyServe 이식본은 원문 전체가 아니라 "고정 함대 위의 정적 클래스 파티션"으로
이름을 좁혀 부른다** — 원문의 과부하 대응 셋(오토스케일링, lazy promotion, DSLO 채점)이 빠져
있고, 셋 다 그 arm에 불리한 방향이다(§5.1의 ④).

**Workloads.** §2.1의 세 클래스를 10:2:1(요청 수 기준)로 섞는다. 두 가지 형태로 돌린다 —
**정적 sweep**은 도착률을 8분씩 고정하고 10·15·20·25·35·45·55·70 req/s 여덟 단계로 올리고,
**한 시간 동적 trace**는 Azure 실측 도착률을 10.8~45.0 req/s 대역으로 옮기고 클래스 구성을
15분마다 바꾼다.

**Approaches.** 라우팅 계층에 있는 기존 시스템 셋과 우리 것을 놓는다.

| arm | 무엇을 하는 정책인가 |
|---|---|
| **Llumnix** | 인스턴스별 대기 prefill 토큰 수가 가장 적은 곳으로 보낸다. 거절이 없다 |
| **Llumnix SLO** | TTFT와 토큰당 시간을 추정해서 판정하고, 아무 데도 안 되면 거절한다 |
| **PolyServe** | 클래스별로 인스턴스를 정수 개씩 미리 떼어 준다(정적 파티션). 거절이 없다 |
| **llm-d** | 요청마다 지연을 예측하고, **인스턴스 위 가장 빡빡한 TPOT 예산을 판정 조건에 넣는다.** 통과한 후보 중 부하가 적은 곳을 고른다 |
| **FluidServe** | 우리 것. §3.4 |

⚠ **Llumnix SLO와 llm-d에는 다른 워크로드 설정(`m1f`)을 준다.** 두 정책 모두 **전체 시간
예산을 표현할 수 없어서**, 그냥 두면 swe의 tier 키 25 ms(§0.3)를 토큰 하나당 목표로 곧이곧대로
읽는다. 그 값은 유휴 상태에서 잰 디코드 시간의 중앙값이라 부하가 걸리면 거의 항상 초과되고,
그 상태에서 Llumnix SLO가 그 클래스의 98%를 거절한 적이 있다. `m1f`는 같은 30초 안에 들어가는
다른 (첫 토큰까지, 토큰당) 쌍을 준다. **채점은 어느 설정으로 돌렸든 항상 전체 30초다.**
⚠ 다만 이 대체에 비대칭이 하나 남아 있고, 그것은 **§5.1의 ⑤**에 적었다.

⚠ **Llumnix 부하 균등화는 수정 후 워크로드에서 재측정되지 않았고, vLLM production stack
router는 이식돼 있지 않다.** 그래서 수정 후 표의 arm이 넷이고 여섯이 아니다.

**Metrics.** 다섯을 항상 같이 싣는다.

1. **총 출력 토큰/초** — 엔진이 규칙과 무관하게 만들어 낸 토큰 전부.
2. **token goodput** — 그중 자기 규칙을 지킨 요청에서 나온 것.
3. **SLO 달성률, offered 분모** — 도착한 모든 요청이 분모이고 거절은 위반이다.
4. **SLO 달성률, admitted 분모** — 시스템이 받아들인 것만 분모다.
5. **거절률**, 그리고 그것을 풀어 쓴 **세 갈래 분해**(규칙 안에 완료 / 받았지만 못 지킴 /
   거절).

**왜 다섯이 다 필요한가.** 거절률 없이 admitted만 보면 **전부 거절하는 정책이 만점을 받는다.**
goodput 없이 달성률만 보면 **출력이 짧은 요청만 지키는 정책이 높게 나온다.** 총 출력 없이
goodput만 보면 **엔진이 일을 적게 해서 낮은 것인지, 엔진은 일했는데 그 결과가 늦게 도착해서
낮은 것인지 구분되지 않는다.** 세 갈래 분해가 없으면 **"거절해서 진 정책"과 "받아 놓고 못 지켜서 진 정책"이 같은
수로 보인다.**

### 3.1.1 Routing changes the result, and the engine is not what changes

> **On the same four engines, with the same request mix and the same latency
> rules, changing only the control plane moves the sustainable arrival rate by
> 1.78x; the engines produce almost the same number of tokens either way.**

**표 1 — 90% 달성률을 유지하는 최대 도착률** (정적 sweep, EXP-68·69·70·72).

| | **90% 유지 도착률** (보간) |
|---|---|
| **FluidServe** | **28.1 req/s** |
| Llumnix SLO | 20.4 |
| llm-d | 18.7 |
| PolyServe | 15.8 |

**표 2 — 같은 값을 다른 통과 기준에서 잰 것.** 이 표를 같이 실어야 하는 이유는 아래에 있다.

| 통과 기준 | PolyServe | Llumnix SLO | llm-d | **FluidServe** |
|---|---|---|---|---|
| 95% | 15.4 | 20.0 | **12.2 (꼴찌)** | **25.4** |
| 90% | 15.8 | 20.4 | 18.7 | **28.1** |
| 80% | 16.7 | 21.3 | **22.7 (2위)** | **33.7** |
| 70% | 17.5 | 22.1 | **25.8 (2위)** | **39.2** |

> **FluidServe는 네 통과 기준 전부에서 1위인데, 기준선 셋의 순서는 통과 기준에 따라 뒤집힌다.**
> 이유는 곡선의 모양이다 — llm-d는 완만하게 내려가고(95.8 → 88.7 → 72.4 → 42.9) 나머지 둘은
> 한 단계 사이에서 급격히 떨어진다(Llumnix SLO는 20 req/s의 95.4에서 25의 34.4로, PolyServe는 15의 99.9에서
> 20의 39.9로). **그러므로 capacity 하나로 우리와 기준선을 비교하는 것은 튼튼하고, 기준선끼리
> 순서를 매기는 것은 그 통과 기준에서만 유효하다.** 기준선 순서가 중요한 자리에서는 막대가 아니라
> 곡선 그림을 쓴다.

⚠ **반복이 고르지 않다.** FluidServe와 llm-d는 35~70 req/s에서 2반복이고 10~25에서
1반복이며, PolyServe와 Llumnix SLO는 **전 구간 1반복**이다(EXP-72). **네 arm의 90% 유지 도착률이 전부 1반복
구간에 떨어지므로 논문에 싣기 전에 두 번째 반복이 필요하다**(§5.2의 E4).

**표 3 — 같은 sweep에서 엔진이 실제로 만든 토큰과 그중 규칙 안에 도착한 토큰** (수정 후
워크로드. 10~25 req/s는 1반복, 35~70은 FluidServe와 llm-d만 2반복이고 나머지 둘은 1반복).
**논문 그림의 (a) throughput / (b) goodput / (c) attainment 세 패널이 이 표다.**

| req/s | 지표 | **FluidServe** | llm-d | Llumnix SLO | PolyServe |
|---|---|---|---|---|---|
| 20 | 총 출력 tok/s | 9,095 | 8,762 | 9,106 | 9,017 |
| | goodput tok/s | 9,040 | 8,383 | 8,994 | **4,159** |
| | offered | 99.6 | 88.7 | 95.4 | **39.9** |
| 45 | 총 출력 tok/s | **13,077** | 6,847 | 8,045 | 10,548 |
| | goodput tok/s | **11,836** | 6,298 | 2,132 | **1,325** |
| | offered | **59.4** | 24.9 | 6.4 | 9.6 |
| 70 | 총 출력 tok/s | **13,952** | 7,102 | 8,825 | 8,443 |
| | goodput tok/s | **11,897** | 6,663 | 747 | 424 |
| | offered | **38.2** | 17.7 | 1.3 | 1.2 |

**이 표에서 읽을 것 셋.**

1. **도착률 45 req/s에서, 네 컨트롤플레인 중 엔진이 가장 많이 만든 경우와 가장 적게 만든
   경우가 13,077과 6,847 tok/s로 1.9배 차이난다. 그런데 그렇게 만든 토큰 중 자기 클래스의
   지연 규칙을 지킨 채 완료된 요청에 속하는 것만 세면 11,836과 1,325로 8.9배 차이난다.**
   즉 정책 사이의 차이는 엔진이 만든 토큰의 양에서보다 **그 토큰이 규칙 안에서 완료됐는가**에서
   훨씬 크게 벌어진다.
2. **총 출력은 어느 정책에서도 무너지지 않는다.** 정적 파티션은 10 req/s의 4,610에서
   35 req/s의 10,628까지 올라간 뒤 평평하고, 그동안 goodput은 4,607에서 2,003으로 내려간다.
   **처리량만 보는 관측으로는 이 문제가 보이지 않는다.**
3. **다만 "throughput은 정책과 무관하게 최대화된다"고 쓰면 안 된다.** llm-d는 25 req/s의
   8,985에서 45의 6,847로 **내려간다** — 도착의 71.5%를 거절하기 때문이다. 그리고 FluidServe는
   70 req/s까지 13,952로 단조 증가한다. **총 출력의 모양이 정책마다 다르고, 그 모양 자체가
   거절 정책의 함수다.**

⚠ **goodput의 측정 구간 정의가 스크립트마다 1.65% 다르다**(첫 요청부터 세는 것과 0부터 세는
것). 위 표는 **0부터**다. 다른 문서의 같은 조건 값이 이보다 조금 크면 그 차이다.

**표 4 — 한 시간 동적 trace** (EXP-71, **네 arm 모두 2반복**, 괄호가 두 반복의 폭).

| | offered | admitted | 거절률 | token goodput | **총 출력 토큰/초** |
|---|---|---|---|---|---|
| **FluidServe** | **81.0** (1.5) | 96.2 | 15.8% | **10,865** (219) | 11,501 |
| llm-d | 56.7 (1.8) | 92.5 | 38.7% | 8,367 (142) | 8,864 |
| Llumnix SLO | 37.6 (0.2) | 54.7 | 31.3% | 5,503 (65) | 10,007 |
| **PolyServe** | **11.2** (0.0) | 11.2 | 0.0% | **1,566** (10) | **11,145** |

**이 표에서 가장 중요한 것은 마지막 두 열이다.** 정적 파티션은 우리의 **96.9%**에 해당하는
출력 토큰을 만든다(11,145 대 11,501). 그런데 자기 지연 규칙 안에 도착하는 것은 **6.9배
적다**(1,566 대 10,865). **엔진은 거의 같은 양의 계산을 했다. 다른 것은 그 계산 결과가 규칙
안에 도착했는가다.**

**한 시간 trace는 표 3의 정적 조건이 보여 준 것을 한 문장으로 만들어 준다** — 정적 조건에서는
총 출력의 폭이 1.9배라 "거의 같다"고 쓸 수 없는데, 이 trace에서는 두 arm의 총 출력이 3.1%
안이라 **다른 모든 것을 고정했을 때 남는 것이 컨트롤플레인 하나**라고 말할 수 있다.

⚠ **그러므로 두 문장을 하나로 합치면 안 된다.** "1.78배"는 정적 sweep에서 잰 유지 도착률의
비이고 "3%와 6.9배"는 한 시간 trace에서 PolyServe에 대해 잰 것이다. 그 정적 sweep에서 우리와
llm-d의 총 출력은 3% 안이 아니라 70 req/s에서 13,952 대 7,102로 두 배 가까이 차이난다.

### 3.1.2 The aggregate hides which class each policy sacrifices — so all three aggregations are reported

> **Every policy in this comparison, ours included, buys its aggregate score by
> sacrificing one class, and which class that is differs between policies. The
> per-request aggregate therefore has to be reported beside the class-equal mean
> and beside the worst class, because the three disagree about the size of the
> advantage.**

**이것을 먼저 적는 이유는, 이 값을 우리가 먼저 적지 않으면 심사위원이 적기 때문이다.**
한 시간 trace의 클래스별 offered 달성률과 클래스별 거절률이다(EXP-71, 네 arm 모두 2반복.
이 워크로드에서 요청의 실제 구성비는 chat 78.1 / deepresearch 11.9 / swe 10.0%다).

| | chat (78.1%) | deepresearch (11.9%) | swe (10.0%) | 거절률 chat / dr / swe |
|---|---|---|---|---|
| **FluidServe** | **84.7** | 75.8 | 57.9 | 14.0 / 12.0 / **34.1** |
| llm-d | 51.3 | **81.8** | **69.3** | **43.7** / 18.1 / 23.7 |
| Llumnix SLO | 32.6 | 72.0 | 35.8 | 39.8 / 0.0 / 2.1 |
| PolyServe | 3.6 | 23.3 | 54.5 | 0.0 / 0.0 / 0.0 |

**우리와 llm-d의 24.3점 차이를 클래스별로 분해하면 이렇다.**

```
   chat   (78.1% × +33.5) = +26.1
   dr     (11.9% ×  −6.1) =  −0.7
   swe    (10.0% × −11.4) =  −1.1
                     합계  = +24.3   (실측 격차 +24.3)
```

> **즉 격차 전부가 chat 항에서 나오고, llm-d는 나머지 두 클래스에서 우리를 이긴다.**
> 그리고 같은 값을 다른 방식으로 모으면 크기가 크게 달라진다 — **클래스마다 같은 무게를 주는
> 평균으로는 +5.3점**(72.8 대 67.5)이고, **가장 낮은 클래스끼리 비교하면 +6.6점**
> (우리의 최저는 swe 57.9, llm-d의 최저는 chat 51.3)이다.

**이것을 어떻게 읽어야 하는가.** 두 가지를 갈라야 한다.

**하나, 방어할 수 있는 부분.** llm-d가 deepresearch와 swe에서 앞서는 것은 **chat의 43.7%를
거절해서 산 것**이다. 요청의 78.1%인 클래스를 절반 가까이 거절하면 남은 요청들에게 돌아가는
자원이 늘어난다. **요청 하나를 하나로 세는 집계가 그 거래를 그대로 반영하는 것이고, 실제
서비스가 보는 것도 그 집계다.** 우리도 같은 거래를 하지만 반대쪽에서 한다 — swe를 34.1%
거절한다.

**둘, 방어할 수 없는 부분.** 그 집계의 크기가 **우리가 고른 믹스 비율(10:2:1)의 함수**다.
믹스가 **움직인다**는 것은 Azure 실측으로 뒷받침되지만(§2.1), **수준 자체는 운영 데이터
근거가 없고 한 번도 바꿔 가며 재지 않았다.** chat의 비중이 절반으로 내려가면 24.3점의 절반이
사라진다.

→ **그러므로 논문은 (a) 세 집계를 모두 싣고, (b) 믹스 비율 sweep을 반드시 돌려야 한다.**
그것이 §5.2의 E2이고, 이 논증에서 **가장 급한 미측정 항목**이다.

⚠ **그리고 우리가 swe를 34.1% 거절하는 원인이 아직 안 갈렸다.** 하필 그 클래스만 arm마다
다른 예산 설정을 받으므로(위의 `m1f` 비대칭), **정책의 성질인지 설정의 결과인지 지금은
구분할 수 없다.** 2조건이면 갈린다(§5.1의 ⑤와 §5.2의 E3).

### 3.1.3 Rejection is present in the routing layer, and it fails in two opposite ways

> **Two of the baselines have a rejection mechanism and two do not, and both
> groups leave the fleet unable to serve what it is holding — one by never
> refusing anything, the other by refusing more than a third of arrivals while
> its engines run at a third of their batch size.**

**거절을 하나도 안 하는 쪽.** PolyServe는 어느 도착률에서도 0%를 거절한다. 그래서 offered와
admitted가 같고, 무너진 값이 그대로 사용자가 본 값이다. 한 시간 trace의 중앙값 시점에 엔진
셋이 KV 99% 이상에서 각각 152~2,130건을 큐에 세우고 있는 동안 **네 번째 엔진은 KV 17.7%에
큐가 비어 있다**(EXP-71 pass 1, 1반복. pass 2에서도 같은 엔진이 KV 16.6%에 큐 0으로
재현된다). 정적 파티션에서 이것은 설계의 직접적 결과다 — 그 인스턴스는 수요가 적은 클래스에
배정돼 있고, 다른 클래스의 요청은 그 인스턴스를 후보로 볼 수 없다.

**거절을 많이 하는 쪽.** llm-d는 같은 trace에서 도착의 **38.7%를 거절하면서** 네 엔진 전부
KV 중앙값 32~34%, 대기 요청 최대 18건이다(2반복). 정적 55 req/s에서도 거절률 76.5%인데 네
엔진의 실행 batch 크기 합이 llm-d 318 대 우리 775다. **그 거절률이 "받을 자리가 없어서"의
결과가 아니다.**

**도착한 요청에 실제로 무슨 일이 있었는지를 세 갈래로 나누면 두 실패가 한 표에서 갈린다.**
`analysis_scripts/request_level/three_way_split.py`가 계산한다. 첫 열은 offered 달성률과
같은 값이다(같은 분자, 같은 분모).

| | 규칙 안에 완료 | **받았지만 못 지킴** | 거절 | ⚠ 결과를 모름 |
|---|---|---|---|---|
| **한 시간 trace** (2반복) | | | | |
| FluidServe | **81.0** | **3.2** | 15.8 | 0.1 |
| llm-d | 56.7 | 4.6 | **38.7** | 0.1 |
| Llumnix SLO | 37.6 | **31.1** | 31.3 | 0.1 |
| PolyServe | 11.2 | **88.8** | **0.0** | **7.4** |
| **정적 45 req/s** | | | | |
| FluidServe | **59.4** | 4.5 | 36.0 | 1.7 |
| llm-d | 24.9 | 3.1 | **71.9** | 0.5 |
| Llumnix SLO | 6.4 | **20.9** | **72.8** | 2.5 |
| PolyServe | 9.6 | **90.4** | 0.0 | **35.9** |

**두 번째 열이 이 표의 요점이다.** 거절하는 세 정책은 받아 놓고 못 지키는 비율이 3~5%로
작은데(Llumnix SLO만 21~31%로 예외다) **정적 파티션은 88.8~90.4%다.** 엔진 시간을 다 쓰고
위반을 돌려주는 것이다. 그리고 그 정책은 **거절을 하나도 하지 않는다** — 세 번째 열이 0.0이다.

**Llumnix SLO가 두 실패를 동시에 한다는 것도 이 표에서만 보인다.** 72.8%를 거절하면서 남은
것 중에서도 20.9%포인트를 놓친다. 거절이 "못 지킬 것을 미리 자른다"는 일을 하고 있지 않다.

⚠ **네 번째 열을 먼저 읽는다.** run이 끝날 때 아직 처리 중이던 요청은 결과를 알 수 없어 두
분모에서 모두 빠지는데, **정적 45 req/s의 PolyServe에서 그 비율이 35.9%다**(다른 셋은
0.5~2.5%). 그 요청들은 깊은 큐 뒤에 있던 것이므로 **빼는 것이 그 arm에 유리하게 작용한다.**
즉 표의 9.6은 낙관적인 값이다.

**그리고 거절은 자기가 만든 실패를 지표에서 가린다.** 거절률이 오르면 **admitted 분모의
달성률은 올라가고 offered는 단조로 내려간다.** Llumnix SLO의 정적 sweep에서 거절률이
7.5 → 21.8 → 35.8 → 49.2 → 69.2%로 오르는 동안 offered는 52.4 → 34.2 → 31.0 → 26.3 → 21.4로
내려가고 admitted는 56.8에서 71.3까지 올라간다(EXP-53, 2반복, **수정 전 워크로드**).
**그 71.3%는 도착한 요청의 30.0% 위에서 계산된 값이다.** 그래서 이 논문은 두 분모를 항상 같이
싣는다.

**거절이 클래스에 대해 중립도 아니다.** 같은 정책이 45 req/s에서 chat의 9.8%를, 70 req/s에서
88.8%를 거절하는 동안 deepresearch는 어느 도착률에서도 0%다. **예산이 가장 빡빡한 클래스가
먼저 잘리는데, 하필 그 클래스가 요청의 76.9%다.** 그래서 admitted 분모의 인구 구성 자체가
바뀐다 — chat이 76.9%에서 29.8%로 줄어든다.

**거절이 §3.2.1의 상태를 고치지도 못한다.** 거절은 "이 요청을 서빙하지 않는다"는 답이지
"다른 요청들을 다른 곳에 놓았어야 했다"는 답이 아니다. 네 인스턴스가 전부 chat을 들고 있으면
deepresearch는 네 번 다 같은 답을 받는다. **네 인스턴스가 모두 같은 이유로 거절하므로 재시도 횟수를 늘려도 답이 달라지지 않는다.**

⚠ **"함대의 절반이 쓰이지 않고 있다"고 쓰면 안 된다.** 정책마다 남는 자원이 다르고, 함대를 실제로
채우면서도 점수가 낮은 arm이 있다 — Llumnix SLO는 같은 trace에서 네 엔진 KV 중앙값
56.6~58.8%, p95가 99.6~99.9%, preemption 1,985회인데 offered가 37.6이다. **쓸 수 있는 문장은
정책마다 따로다**: 정적 파티션은 메모리와 연산을 한 인스턴스에 남긴 채 다른 인스턴스에 큐를
쌓고, llm-d는 네 엔진을 3분의 1만 쓰면서 38.7%를 거절하며, 완전 혼합은 메모리를 절반 남긴 채
메모리는 남아 있는데 디코드 스텝 시간이 먼저 예산을 넘긴다. 근거는 `motivation_v2.md` §1.5에 다 있다.

### 3.1.4 SLO-centric engine schedulers do not close the gap

> **A deadline-aware engine scheduler recovers 2.8 points inside an instance
> whose queue the router should not have created, in the same session in which
> the placement itself costs 60 points.**

엔진 계층에도 SLO를 아는 스케줄러들이 있다. 그것을 쓰면 되지 않느냐는 반론이 심사에서 반드시
나오므로, **세 실험이 각각 다른 상태에서 답한다.** 셋 다 같은 이식본(Niyama/QoServe)을
FIFO 대신 넣고 컨트롤플레인을 고정한 것이다.

| 어떤 상태의 arm 위에서 | 마감 인식 스케줄러로 바꾼 결과 |
|---|---|
| **엔진 큐가 비어 있는 arm** (FluidServe, Llumnix SLO) | 격차 변화가 반복 간 편차 안이다 — 45 req/s에서 +4.1점(편차 11.4), 60에서 +1.4점(편차 1.8). **이 두 arm은 엔진의 대기 큐가 거의 비어 있으므로, 마감을 보고 순서를 다시 매기는 스케줄러를 넣어도 순서를 바꿀 대상 자체가 없다** (EXP-40, 24조건, 2반복) |
| **큐가 네 엔진에 고르게 깊은 arm** (Llumnix, 거절 0%) | **오히려 조금 뒤로 간다** — −1.14 / −0.93 / −0.45점, goodput −3 / −10 / −14%. 50 req/s의 −0.93은 반복 폭 0.29보다 크다 (EXP-61, 2반복) |
| **큐가 한 엔진에만 쌓인 arm** (PolyServe) | **도움이 되고, 그 이득의 크기가 이 질문에 대한 답이다** — +0.98 / +2.65 / +2.79점. 이득이 **전부 chat**이고 나머지 둘은 이미 99~100%다 (EXP-62) |

**세 번째 줄이 결론을 만든다.** 배치가 틀려서 한 엔진에 큐가 쌓인 상태에서 마감 인식
스케줄러는 그 인스턴스 안에서 2.8점을 되찾는데, **같은 세션에서 배치가 만든 손실은 60점**
이다(FluidServe 94.76 대 PolyServe 34.10, 정적 45 req/s).

**공정하게, 엔진 계층이 잘하는 것도 하나 적는다.** 엔진은 자기 batch를 직접 보므로 스텝
예산을 줄여 가장 빡빡한 디코드를 보호할 수 있다 — 실제로 그렇게 하면 chat의 토큰당 시간이
48.2에서 47.2 ms로 내려간다(EXP-40). **컨트롤플레인은 그것을 할 수 없다.** 두 계층이 대체
관계가 아니라는 뜻이고, 이 논문의 주장은 "엔진 스케줄러가 필요 없다"가 아니라 **"엔진
스케줄러로는 배치가 만든 손실을 되찾을 수 없다"**이다.

**왜 못 고치는지는 §2.2에 이미 적었다** — 두 계층의 결정 변수가 다르고, 요청은 한 방향으로만
넘어간다. **거절을 받아 다른 엔진으로 재시도하는 조합도 같은 벽에 걸린다**: 재시도는 갈 곳을
찾을 수는 있어도 만들 수는 없고, 갈 곳이 있는지는 그 요청이 도착하기 전에 **다른 요청들을
어디에 놓았는가**로 이미 정해져 있다. 조합 일곱 개를 하나씩 해부한 것은
`related-works-review.md` §9가 정본이다.

### 3.1.5 Goal

> **This paper asks how a routing plane should decide where to place a request
> and whether to admit it, so that the fleet sustains the highest arrival rate
> at which arriving requests still meet their own latency rule.**

§3.1의 측정이 말하는 것은 셋이다. **(1)** 같은 함대에서 라우팅/admission 정책만 바꿔도 유지
가능한 도착률이 1.78배 달라진다. **(2)** 그 차이가 엔진이 한 일의 양으로 설명되지 않는다.
**(3)** 엔진 안의 마감 인식 스케줄러로는 그 차이의 5%도 못 되찾는다. 그러므로 문제는 라우팅
계층에 있고, 이 논문은 그 계층을 다시 설계한다.

## 3.2 Challenge

목표를 그렇게 세우고 나면 다음 질문은 왜 기존 시스템이 그 목표를 달성하지 못했는가이다.
어려움이 셋 있고, 셋은 서로 독립이 아니라 하나가 다른 하나를 더 어렵게 만든다.

1. **토큰당 예산이 요청 하나가 아니라 batch 전체에 걸린다** (§3.2.1).
2. **인스턴스에 얼마나 여유가 있는지를 스칼라 하나로 말할 수 없다** (§3.2.2).
3. **라우터가 볼 수 있는 신호 대부분이 라우터 자신의 직전 결정이 만든 결과다** (§3.2.3).

### 3.2.1 Bound budgets: the per-token budget is shared by the whole batch

> **Continuous batching gives every request resident on an instance the same
> token-generation rate, so a per-token budget is not a quantity the router can
> hand out per request: admitting one request changes the rate every other
> resident receives.**

**먼저 첫 토큰까지의 시간과 갈라서 봐야 한다.** 첫 토큰까지의 시간은 그 요청이 큐에서 기다린
시간과 그 요청 자신의 prefill 시간으로 되어 있다. **한 번 지불되고 끝나며, 어느 요청 때문에
생긴 비용인지 대체로 가릴 수 있다.** 그래서 도착 시점에 한 번 판정하는 것으로 어느 정도
지킬 수 있다.

**토큰당 시간은 그렇지 않다.** 디코드 스텝 하나가 그 인스턴스의 활성 요청 전부를 한 토큰씩
진행시키므로, 토큰당 시간은 요청마다 따로 정해 줄 수 있는 양이 아니다. **여기서 세 가지가
따라 나오고, 셋 다 첫 토큰까지의 시간에는 없는 성질이다.**

1. **그 인스턴스가 지켜야 하는 스텝 시간 상한은, 지금 거기서 처리되고 있는 요청들이 각자
   허용하는 값 중 가장 작은 것으로 정해진다.**
2. **위반의 원인이 미래에 있다.** 어떤 요청의 토큰당 시간을 망가뜨리는 것은 **그 요청이
   배치된 뒤에 도착한 요청들**이다. 도착 시점의 판정만으로는 이 예산을 지킬 수 없고, **그 뒤의
   도착까지 통제해야 한다.** 이것이 admission을 routing과 같은 결정으로 묶어야 하는 첫 번째
   이유다.
3. **비용이 그 요청이 머무는 시간에 비례한다.** 출력이 985 토큰인 deepresearch 하나는 428
   토큰인 chat 하나보다 **2.3배 오래** 그 인스턴스의 속도를 자기 예산 안으로 묶어 둔다.

**그래서 함대의 capacity를 "요청 하나가 이만큼을 쓴다"는 값의 합으로 계산할 수 없다.**
디코드 스텝 시간을 실제로 적합하면

```
t = 16.361 + 1.2822e-5·M + 0.07643·n
        M = 그 순간 인스턴스가 들고 있는 KV 토큰 수, n = batch 안의 요청 수
        R² = 0.952, 표본 377,838
```

이고 **두 변수 모두 그 인스턴스에 무엇을 보냈는지로 정해진다.** 보통의 부하 분산에서는 작업
하나를 놓으면 그 서버의 남은 용량이 **작업 크기만큼** 준다. 여기서는 줄어드는 양이 작업
크기가 아니라 **누구 옆에 놓았는지**에 달려 있다.

⚠ **여기까지가 물리이고, "그러므로 그 인스턴스는 새 요청을 받으면 안 된다"는 여기서 자동으로
따라 나오지 않는다.** 그것은 admission 규칙이 정하는 것이고 규칙마다 답이 다르다. 우리
스케줄러 안에도 상한을 구하는 방법이 둘 있고(§0.3의 명목 예산과 남은 예산), 같은 순간에 두
값이 크게 다르다. **명목 예산으로 재면 50.0 ms이고 남은 예산으로 재면 68.3~72.7 ms인데, 그때
함대가 실제로 내주고 있던 스텝 시간은 55.6 ms였다.** 즉 첫 번째 방법으로 재면 네 인스턴스가
모두 이미 상한을 넘긴 상태이고, 두 번째 방법으로 재면 아직 여유가 있는 상태다. **새 요청을
받을지 말지의 답이 어느 쪽으로 재느냐에 따라 통째로 뒤집힌다.**

> **이 구분을 안 하면 우리가 만든 제약을 세상의 성질로 소개하는 것이 된다.** 그리고 이 축에는
> 조절할 수 있는 설정값(`gateSlack`)이 있어서, 실제로 움직여 보면 정적 조건에서 +10.6점,
> 한 시간 trace에서 −4.4점이다(EXP-50, 각 1반복). 자세한 것은 `motivation_v2.md` §1.2.2.

#### Spreading a class across instances binds every instance to the tightest budget in the mix

> **The obvious rule — send each request to an instance that can meet its own
> budget, and among those pick the least loaded — drives the whole fleet to the
> tightest budget in the mix.**

chat이 요청의 76.9%이므로 chat은 곧 모든 인스턴스에 도달한다. 그리고 판정을 명목 예산의
최솟값으로 하는 정책에서는, 어떤 인스턴스든 chat을 하나라도 들면 그 인스턴스의 허용 스텝
시간이 chat 예산인 50 ms가 된다. 그러면 deepresearch(100 ms)나 swe(전체 30초)를 받을 수 있는
인스턴스가 함대 어디에도 없다 — **그 요청들 자신은 여유가 있는데, 그들을 받아 줄 인스턴스가
50 ms에 묶여 있어서 받을 수 없다.**

**측정한다.** "그 순간 chat 요청을 하나도 처리하고 있지 않은 인스턴스"의 비율을 센다. 네 대
중 평균 한 대가 계속 chat 없이 있었으면 25%다.

| 정적 45 req/s (**수정 전 워크로드**, 반복 3) | chat 없는 인스턴스의 시간 비율 | offered |
|---|---|---|
| Llumnix SLO | 1.0 / 1.0% | 51.9 / 53.0 |
| Llumnix | 1.0% | 32.2 |
| **FluidServe, 클래스 선호만 끔** | **1.0 / 1.0 / 1.0%** | 86.7 / 86.5 / 87.0 |
| **FluidServe** | **30.9 / 23.7 / 4.4%** | **98.9 / 93.4 / 90.4** |
| PolyServe | 67.9 / 67.9% | 35.6 / 35.5 |

**세 번째 줄이 결정적이다** — 우리 바이너리에서 클래스 선호 항 하나만 끄면 완전 혼합 정책들과
같은 상태가 된다. **즉 이 값은 어느 시스템인지에 따라 정해지는 것이 아니라, 그 시스템이 요청을 인스턴스에 어떻게 나눠 놓았는지에 따라 정해진다.**

같은 현상이 수정 후 워크로드의 한 시간 trace에서 현대적인 기준선에 대해서도 재현된다
(EXP-71, 네 arm 모두 2반복. 왼쪽은 클래스가 실제로 나뉘어 간 인스턴스 수 `N_eff = 1/Σs²`이고,
네 대에 고르면 4.0, 한 대면 1.0, 두 대에 반씩이면 2.0이다).

| | 유효 인스턴스 chat / dr / swe | chat 없는 인스턴스의 시간 비율 | offered |
|---|---|---|---|
| PolyServe | **1.00 / 1.00 / 1.00** | 56.4% | 11.2 |
| **FluidServe** | **2.00 / 2.03 / 2.14** | 29.7% | **81.0** |
| Llumnix SLO | 3.94 / 3.88 / 3.74 | 4.6% | 37.6 |
| **llm-d** | **3.66 / 3.86 / 3.89** | **0.2%** | 56.7 |

> **llm-d에서 chat 없는 인스턴스의 시간 비율이 0.2%다.** 요청 하나하나에 대해 지연을 예측하고 그
> 예측으로 목적지를 고르는, 이 목록에서 가장 정교한 기준선이 **네 인스턴스 전부에 chat을
> 올려 두고 있다.** 예측의 정확도 문제가 아니다 — 요청 하나씩 보면 각 결정이 옳고, 그
> 결정들이 쌓인 상태가 느슨한 예산을 받을 수 있는 자리를 함대에서 없앤다.

#### Isolating instead removes that failure and introduces an integral one

> **Giving each class its own instances removes that failure and introduces a
> different one: the allocation is integral, so a class that needs 2.56 of four
> instances receives one — and that class is 78.1% of the requests.**

클래스마다 인스턴스를 따로 떼어 주는 방식은 비교를 위해 상상한 대안이 아니라 실제로 발표되고
배포된 시스템들이 쓰는 방식이다(PolyServe, 그리고 QoServe를 클래스별로 분리해 배치하는 구성).
그리고 이 방식은 바로 앞에서 본 실패, 즉 모든 인스턴스가 chat을 하나씩 갖게 되어 예산이 느슨한
요청을 받을 인스턴스가 없어지는 상태를 실제로 없앤다. 대신 문제가 셋 새로 생긴다.

1. **배분 단위가 인스턴스 한 대, 즉 함대의 25%다.** 네 대를 세 클래스에 나누면 가능한 배분이
   (2,1,1)·(1,2,1)·(1,1,2)뿐이다. chat이 2.56대만큼을 필요로 해도 1이나 2로 반올림된다.
   실제로 **1.00대**를 받는다.
2. **그 반올림이 클래스별 수요 추정값 위에서 이루어진다.** deepresearch는 평균 입력이 4,639
   토큰이라 요청 하나당 prefill 비용이 크고, 그래서 요청 수가 훨씬 많은 chat과 수요 추정값이
   비슷해지는 구간이 생긴다. **두 값이 비슷하면 추정값이 조금만 움직여도 남는 인스턴스 한 대가
   어느 클래스로 갈지가 뒤집히고, 인스턴스 한 대는 함대의 25%이므로 그 뒤집힘이 곧바로 큰
   성능 차이가 된다.**
3. **바꿀 수 있는 주기가 분 단위다.** 한 시간 run에서 배분이 세 가지 사이를 여섯 번 오간다
   (8분 정적 조건에서는 한 번도 안 바뀐다). **"한 번 정하면 절대 안 바뀐다"고 쓰면 안 되고**,
   옳은 서술은 **"바꿀 수 있는 단위가 인스턴스 한 대이고 주기가 분 단위여서 그 사이에는 배분이
   정수로 고정된다"**이다.

**그 결과가 §3.1.3의 비어 있는 엔진이고, 한 시간 trace의 chat 달성률 3.6%다.**

⚠ **이 실패가 "우리만 좋은 정보를 갖고 있어서"가 아니다.** 2026-08-05부터 PolyServe의 tier별
디코드 토큰 수가 **우리 정책이 읽는 것과 같은 파일의 클래스별 평균에서 유도된다.** 즉 **정적
파티션에 우리와 동일한 길이 프로파일을 주었는데도 chat에 한 대를 준다.** 남는 차이는 그 정보를
**어떻게 쓰는가**다 — 저쪽은 tier별 수요 추정치로 모아 정수 배분을 고르고, 이쪽은 요청
하나하나의 판정에 넣는다.

#### The two failures are the same decision, missed from opposite sides

**완전 혼합과 정적 파티션은 서로 반대되는 설계처럼 보이지만, 둘 다 "각 클래스가 인스턴스를
몇 대씩 쓰게 할 것인가"라는 같은 결정에서 틀린 것이고 틀리는 방향만 반대다.** 그 결정에는
질문이 둘 있다.

- **수준** — 각 클래스가 지금 함대의 몇 대를 쓰고 있는가.
- **해상도** — 그 수준을 얼마나 잘게, 얼마나 자주 바꿀 수 있는가.

**완전 혼합은 수준에서만 틀린다**(모든 클래스에 네 대를 주므로 수요에서 가장 멀다. 바꿀 배정이
없으니 해상도는 문제가 안 된다). **정적 파티션은 둘 다에서 틀린다.** 그리고 **두 축은 독립이
아니다** — 수준을 연속으로 맞추려면 해상도가 연속이어야 하고, 수요가 2.56인데 배분 단위가 1
이면 반올림 오차가 최소 0.44대다.

> **그러므로 수준을 맞추는 메커니즘과 해상도를 높이는 메커니즘을 따로 만들 수 없다. 배분
> 단위를 요청 한 건으로 줄이는 것 자체가 수준을 연속으로 맞추는 유일한 방법이다.**

⚠ **두 축의 증거 강도가 다르다.** 수준 축은 우리 시스템 안의 ablation으로 21점을 갈라 놓았고
(EXP-59: 같은 고정 메커니즘에서 배분만 바꿔 72.29 대 93.20), **해상도 축은 한 시간 trace의 네
구간 중 한 구간(−9.4점)이 전부다.** 이 워크로드가 해상도 축을 거의 시험하지 않기 때문이다.

### 3.2.2 Heterogeneous load signals

> **Because requests are heterogeneous, no single scalar tells the router how
> much room an instance has: different classes exhaust different resources, and
> the load a request creates is not a property it carries but a property of the
> instance it is placed on.**

**하나. 클래스마다 먼저 한계에 닿는 자원이 다르고, 그 자원의 단위가 다르다.** 클래스를
하나씩 따로 돌려 보면 chat은 메모리를 73% 남긴 채 디코드 스텝 시간이 먼저 예산을 넘기고,
deepresearch는 정반대로 스텝 시간은 예산 안인데 KV 캐시가 먼저 찬다.

**즉 어떤 클래스가 왜 자기 규칙을 지키지 못하게 되는지를 결정하는 양이 클래스마다 다르고, 그
단위가 각각 토큰당 밀리초, KV 토큰 개수, 초로 서로 다르다. 그러므로 스칼라 하나에 문턱을 두는
방식으로는 세 클래스가 각자 얼마나 여유가 있는지를 동시에 판정할 수 없다.**

⚠⚠ **이 문단의 세 수치는 지금 인용할 수 없다** — 그 실험(EXP-55)이 수정 전 워크로드에서
돌았고 재측정이 §5.1의 ⑥이다. **결론이 뒤집힐 것 같지는 않지만 숫자 자체는 다시 재야 한다.**

**둘. 한 요청이 만드는 부하는 그 요청이 들고 다니는 스칼라가 아니다.** 위 스텝 법칙에서 요청
하나가 더하는 시간은 어느 인스턴스로 보내든 같다. 그런데 **그것이 문제가 되는지 아닌지는 그
인스턴스에서 지금 무엇이 처리되고 있는가에 달려 있다.** 같은 deepresearch 요청이 deepresearch만
있는 인스턴스에서는 여유 안이고, chat이 하나 있는 인스턴스에서는 그 인스턴스의 속도를 chat의
예산 쪽으로 끌어내린다. **"이 요청은 얼마나 무거운가"는 답이 없는 질문이고, 답이 있는 질문은
"이 요청을 이 인스턴스에 놓으면 거기 있는 것들이 예산을 넘기는가"다.**

**셋. 지금 보이는 값에는 미래가 빠져 있다.** 인스턴스의 현재 KV 점유량은 지금 그
인스턴스에서 처리되고 있는 요청들이 **이미 쓴 것**이고, 그들이 앞으로 만들어 낼 토큰은 들어 있지 않다. 출력이 985 토큰인
deepresearch가 방금 시작했으면 그 인스턴스는 곧 그만큼을 더 쓸 예정인데 현재 게이지는 그것을
모른다.

**기존 신호를 하나씩 놓고 보면 이렇다.**

| 신호 | 쓰는 시스템 | 무엇을 놓치나 |
|---|---|---|
| 대기 중 prefill 토큰 수 최소 선택 | Llumnix | 예산이 전혀 안 들어간다. 세 클래스 어디에 대해서도 간접 지표이고, 위의 수렴을 그대로 만든다 |
| KV 점유율 문턱 | 여러 admission 정책 | deepresearch에 대해서는 맞는 신호다. 그러나 **chat은 KV 점유율이 27%일 때 이미 토큰당 시간 예산을 넘기기 시작하므로**, KV가 문턱에 닿았을 때는 chat 위반이 이미 일어난 뒤다 |
| 대기열 깊이 | 대부분의 라우터 | 셋 다에 대해 간접 지표. 요청을 붙들거나 거절하는 정책에서는 **0에 붙어 있어서 정보가 없다** |
| 전역 (TTFT, TPOT) 임계 한 쌍 | Llumnix SLO, llm-d | **전체 시간 예산을 표현할 수 없다.** 우리 실험이 그 두 arm에 `m1f` 설정을 주는 이유다 |
| tier별 수요 추정치 | PolyServe | 클래스별 도착률이 이미 반영되어 있으므로 부하 자체는 본다. 놓치는 것은 **그 추정값을 인스턴스 정수 개로 반올림하는 단계**이고, 두 클래스의 추정값이 비슷할 때 반올림이 어느 쪽으로 가느냐에 따라 결과가 크게 달라진다 |
| 요청 단위 지연 예측기 | llm-d, Scorpio, AdaGen | 예측 자체는 우리보다 세밀하다. 놓치는 것은 **그 예측이 목적지의 현재 최솟값과 결합되는 방식**이다 |

⚠ **마지막 줄이 이 논문에서 가장 조심해야 하는 자리다.** llm-d의 판정 조건은 "그 엔드포인트
에서 돌고 있는 요청들의 TPOT 예산 중 최솟값"을 포함하고, 그것은 **우리 판정 조건과 같은
형태다**(소스에서 확인했다). **그러므로 "인스턴스 위 가장 빡빡한 예산을 본다"는 것 자체는
우리의 차별점이 아니다.** 무엇이 남는 차이인지는 §3.3.2에 적는다.

### 3.2.3 The signals move with the policy's own decisions

> **Most of what the router can observe is the result of what the router just
> did, so feeding it back into the decision closes a loop.**

이 프로젝트에서 **세 가지 형태로 실제로 겪었다.** 셋 다 사후에 알았고, 셋 다 처음에는
합리적으로 보였다.

| 형태 | 무엇이 일어났나 |
|---|---|
| **한 번 들어가면 스스로는 빠져나오기 어려운 상태** | 모든 인스턴스가 chat을 하나씩 들면 모든 인스턴스의 허용 속도가 50 ms가 되고, 분리를 다시 만들려면 어떤 인스턴스를 chat에서 비워야 하는데 새로 오는 chat은 어디로든 가야 한다 |
| **양의 되먹임 — 한쪽으로 조금 치우치면 그 치우침이 스스로 더 커진다** | 클래스 선호가 어떤 인스턴스를 다음 요청에게 더 매력적으로 만든다. 그 결과 **같은 바이너리·같은 설정·같은 도착률의 세 반복이 90.4 / 93.4 / 98.9로 8.5점 흔들린다.** 선호를 끄면 배정과 점수가 같이 고정된다 — **이득과 편차가 같은 메커니즘에서 나온다** |
| **보정 계수가 자기가 만든 값을 입력으로 받은 것** | 청구액 `charge = raw × κ`인데 갱신을 `κ ← 계산량 / Σ charge`로 썼다. 평형이 `κ² = 계산량/raw`라 **κ가 참값이 아니라 참값의 제곱근으로 수렴한다.** 실측 κ 0.53~0.59, 역산한 참값 0.28~0.35 |

**그리고 예측을 쓰는 항은 예측 자체를 먼저 재야 한다.** 우리도 일정 시간 뒤의 KV 점유량을
예측하는 항을 만들었는데, 오차를 실제로 재 보니 **88.5%가 과소예측이고 평균절대오차가 아무
예측도 안 하는 것의 3.6배**였다.

> **그러므로 신호를 고를 때 조건이 하나 더 붙는다. 그 신호가 정책 자신의 결정에 따라 얼마나
> 움직이는지를 알고 골라야 하고, 예측값을 쓰는 항은 그 예측의 오차를 먼저 재야 한다.**

## 3.3 Where existing systems sit

### 3.3.1 Two axes: where rejection is decided, and when a class is bound to an instance

> **Existing routing-layer systems are separated by two questions -- whether
> rejection comes from the same test as placement, and when the binding between
> a class and an instance is fixed -- and not by whether they isolate or mix,
> which a measurement contradicts.**

**가장 먼저 떠오르는 분류는 격리 대 혼합인데, 측정된 반례가 있으므로 쓰면 안 된다.**
"가장 빡빡한 클래스가 모든 인스턴스에 있으면 안 된다"를 직접 재는 값에서 **정적 파티션이
우리보다 훨씬 잘 만족하는데 달성률이 절반 이하다**(67.9% 대 4.4~30.9%, 35.6 대 90~99). 그리고
완전히 섞는 구성 셋이 그 축 위에서 사실상 같은 자리인데 점수가 **86.7 / 52.4 / 32.1로 54점**
벌어진다. **그 축을 주 축으로 쓰면 논문의 첫 표가 자기 결론을 반증한다.**

**대신 두 축을 쓴다. 고른 이유는 대칭적이거나 예뻐서가 아니라, 각각에 대해 다른 축을 고정한
측정이 있기 때문이다.**

**축 A (admission) — 거절이 있는가, 배치와 같은 판정 조건에서 나오는가, 보유할 수 있는가.**

```
A0   거절이 없다 — 과부하는 큐잉과 SLO 위반으로만 나타난다
A1   거절이 있으나 이미 자기에게 커밋된 요청에 대해서만 판정한다 (엔진 또는 replica 로컬)
A2a  거절이 라우팅 계층에 있으나 배치 판정과 **다른 양**을 쓴다
A2b  거절이 배치와 같은 양을 쓰지만 **도착 시점에 결정이 끝난다** (보유가 없다)
A3   거절이 배치와 같은 판정 조건에서 나오고, "지금은 아무 데도 못 놓지만 아직 기다릴 수
     있다"(PEND)라는 세 번째 답이 있다
```

⚠ **A2를 둘로 쪼갠 것이 v2와 다른 점이고, 쪼개야 하는 이유가 있다.** v2는 이 둘을 A2 하나로
묶어 놓고 우리 바이너리의 `--fluidserve-enable-pend=false` arm이 그 칸을 채운다고 적었는데,
**코드를 보면 그 arm은 A2b이지 A2a가 아니다.** 보유를 끄면 결정이 곧바로 SHED로 내려가는데
SHED의 판정은 여전히 배치와 **같은** 후보 평가에서 나온다(`fluidserve.go:1298`의
`best.missesOwnBudget`). 즉 **EXP-73이 재는 것은 "세 번째 답이 값을 갖는가"이고,
"거절과 배치가 같은 양을 써야 하는가"는 아직 아무도 재지 않았다.** 후자를 재려면 SHED의
판정만 다른 스칼라(예: 함대 평균 KV 문턱)로 바꾼 arm이 필요하고, 그것이 §5.2의 E2다.

**축 B (routing) — 클래스와 인스턴스의 결합이 언제, 어느 단위로 정해지는가.**

```
B0  해당 없음 — 인스턴스가 하나이거나 클래스가 하나다
B1  사전에 정한다. 단위가 인스턴스 정수 개이고 변경 주기가 분 단위다
B2  정하지 않는다. 모든 클래스가 모든 인스턴스에 갈 수 있고, 목적함수가 그것을 균등으로 민다
B3  요청 하나하나의 판정 결과로 정해진다. 단위가 요청 1건이고 되돌리는 비용이 0이다
```

| | **B0** 해당 없음 | **B1** 사전 정수 배분 | **B2** 결합 없음 / 균등 | **B3** 판정 결과, 연속 |
|---|---|---|---|---|
| **A0** 거절 없음 | AdaGen, LMetric | **PolyServe** | **Llumnix**, vLLM router\* | 원리적으로 없음 |
| **A1** 엔진/replica 로컬 거절 | Scorpio, SLOs-Serve | QoServe silo 구성 | QoServe (섞는 구성) | 원리적으로 없음 |
| **A2a** 거절이 배치와 다른 양을 쓴다 | SLOs-Serve 라우팅, JITServe | (문헌에 없음) | **Llumnix SLO**, **llm-d** | ★ shed 신호 교체 — **미측정**(§5.2의 E2) |
| **A2b** 같은 양이나 도착 시점에 결정이 끝남 | — | — | — | ★ `pend=off` **93.8 / 64.0 / 35.4** (EXP-73, 2반복) |
| **A3** 배치와 같은 조건 + 보유 | — | ★ class-pin 72.29 / 93.20 | ★ affinity=off **93.5 / 74.7 / 65.3** (EXP-73, 2반복) | **FluidServe** **96.1 / 78.7 / 57.9** (EXP-73, 2반복) |

★ = 발표된 시스템이 아니라 우리 바이너리 안의 ablation.
\* vLLM production stack router는 이식돼 있지 않다 — 측정 없음.

**이 분류 표에서 읽을 것 셋.**

1. **문헌이 왼쪽 위에 몰려 있다.** 발표된 시스템 10개 중 7개가 A0~A2 × B0·B2에 있다.
2. **오른쪽 위 두 칸이 비어 있는 것은 탐색이 안 된 것이 아니라 원리적인 것이다.** B3은 결합이
   요청마다의 판정으로 정해진다는 뜻인데, 그 판정이 **함대 전체에 대한 것이어야** 결합을
   만들 수 있다. A0은 판정이 결정을 바꾸지 못하고, A1은 자기에게 온 것 밖을 보지 못한다.
   **거절이란 "이 요청을 받을 수 있는 인스턴스가 하나도 없다"는 뜻이므로, 그 판정을 내리려면
   인스턴스를 하나씩 놓고 물어봐야 한다. 그러므로 축 B의 오른쪽은 축 A의 아래쪽을 요구한다.**
3. **이 분류 표는 문헌 지도이면서 동시에 우리 ablation 행렬의 좌표계다.** A3×B1은 클래스를
   인스턴스에 고정하는 플래그, A3×B2는 클래스 선호를 끄는 플래그, A2b×B3은 보유를 끄는
   플래그이고 **셋 다 같은 바이너리에서 그 축 하나만 바뀐다.** 두 역할이 같은 축을 쓴다는 것이
   이 분류를 고르는 가장 강한 이유다.

⚠ **3번은 이 분류를 고른 이유이면서 동시에 이 분류의 가장 큰 약점이다.** A3과 B3의 정의가
사실상 우리 시스템의 서술이므로, **"우리 칸이 좋다"를 이 표로 보이면 순환이다.** 이 표가
할 수 있는 것은 **각 칸의 실패를 서로 다른 문장으로 설명하는 것**까지이고, 어느 칸이 좋은지는
표 밖의 측정(§3.1)이 정해야 한다. 논문에서 이 표를 **관련 연구를 정리하는 자리**에 놓고
**주장의 근거로 쓰지 않는 것**이 안전하다.

### 3.3.2 The strongest baseline in this table is llm-d, and it is the test of our claim

> **Testing a candidate instance against the tightest budget resident on it is
> necessary but not sufficient. It says the current placement is bad; what
> placement to build instead is decided by the tie-break among the candidates
> that pass — and every existing system breaks that tie by load.**

llm-d는 §3.2.2에서 본 대로 **우리와 같은 형태의 판정 조건**을 갖는다. 즉 §3.2.1의 메커니즘을
알고 있다. 그런데 축 B에서 B2다 — 결합을 만들지 않고, 판정을 통과한 후보 중 부하가 적은 곳을
고른다. 그러면 같은 클래스가 흩어지고, chat이 요청의 78.1%이므로 곧 네 인스턴스 전부에 chat이
올라간다. **그 상태가 되고 나면 같은 판정 조건이 이번에는 거절을 만든다 — 한 시간 trace에서
38.7%다.**

**그리고 그 항 하나를 끄면 우리도 같은 상태가 된다** — 클래스 선호를 끄면 chat 없는
인스턴스-시각이 30.9%에서 1.0%로, 클래스당 유효 인스턴스가 3.9로 가고 달성률이 7.5점
떨어진다(EXP-56, 정적 45 req/s, 3반복). **축 B의 값을 우리 바이너리 안에서 확인할 수 있고,
그 결과가 llm-d가 서 있는 자리와 같다.**

⚠ **수정 이전 워크로드에서는 결과가 반대였고, 원인을 안다.** 2026-08-08 이전에는 llm-d가
50~60 req/s에서 우리보다 9.7~13.0점 앞섰다. 원인은 클래스 분리가 아니라 **prefix cache
재사용**이었고(엔진 hit rate 93.5% 대 75.1%), **그 hit rate 자체가 부하 생성기의 결함으로
부풀려져 있었다.** 고친 뒤 순서가 뒤집힌다. ⚠ 그래도 이것은 "축 B가 결과를 정한다"의 증거가
아니라 **"그 구간에서 우리가 진 원인이 축 B가 아닌 다른 것이었다"의 증거**다.

### 3.3.3 Two things this classification does not do, stated before anyone asks

> **The axes place the existing systems, but they neither predict that our cell
> is the best one nor account for where our own advantage comes from.**

**하나. 축 B에서 우리가 이기지 못하는 칸이 있다.** 같은 실험(EXP-59)에서 **사후에 계산한
오라클 고정 배분이 정적 55 req/s에서 16.4점, 한 시간 trace에서 7.7점 우리를 이긴다**(84.79 대
68.42, 76.76 대 69.02).

⚠ **v2는 이것을 "메커니즘의 실패가 아니라 편차의 실패"로 설명했는데, 그 설명은 같은 표가
반박한다.** 편차 설명이 성립하려면 우리가 진 두 조건에서 우리 값이 크게 흔들려야 하는데,
**그 두 조건에서 우리 반복 폭은 1.5점(67.68~69.17)과 0.5점(68.77~69.27)이다.** 8.5점이
흔들리는 것은 우리가 **이긴** 조건(정적 45 req/s)이다. **그러므로 지금 쓸 수 있는 정직한
문장은 "원인을 모른다"이고, 이 결과는 다음 둘 중 하나를 뜻한다** — 배분을 요청 단위로 연속
조정하는 것이 이 워크로드·이 함대 크기에서 정수 배분보다 낫지 않거나, 우리의 온라인 배정이
사후 최적 배분에서 그만큼 떨어져 있거나. **어느 쪽인지 가르는 실험은 §5.2의 E5(함대 크기)과
온라인 수요 추정기를 붙인 arm이다.**

⚠ 그리고 **"사후 계산이라 배포할 수 없다"는 방어도 약하다.** 그 배분은 실현된 출력 토큰
비중에서 나오고, 그것은 지나간 창에서 온라인으로 계산할 수 있는 양이다. **우리가 만들지
않았을 뿐이다.**

⚠ 한 시간의 7.7점은 요청 수로 잰 것이고 **토큰으로는 1.9%**다. **두 값 중 하나만 적으면 안
되고 같이 적어야 한다.**

**둘. 이 분류는 기존 시스템을 나누는 데는 맞지만 우리 우위를 분해하는 좌표계로는 불완전하다.**
가장 큰 단일 기여는 **prefill 비용 회계**(+10.2~13.5점)인데 그것은 두 축 어느 쪽도 아니다.
분해는 §3.4.2에 따로 적는다.

## 3.4 Requirements, and what our design does about them

### 3.4.1 Four requirements, and the part of the design each one names

> **The three difficulties above translate into four requirements, and each of
> them names one part of the design.**

| # | 요구 조건 | 어느 어려움에서 나오나 | 우리 설계의 어느 부분 |
|---|---|---|---|
| **1** | **판정이 "이 인스턴스가 이 요청을 받으면 거기 있던 것들이 예산을 넘기는가"여야 한다** — 요청 하나의 무게가 아니라 | §3.2.1의 1번, §3.2.2의 2번 | 인스턴스 하나하나에 대해 따로 계산하는 판정 조건 둘(§0.3의 게이트와 `overIncumbents`). **한 시간 trace 1반복에서, 거절된 요청 전체를 분모로 놓으면 그중 90.8%는 게이트에서 걸려 거절됐고 2.0%는 `overIncumbents`에서 걸렸다** |
| **2** | **admission이 배치와 같은 결정이어야 하고, 엔진에 커밋되기 전에 내려져야 한다** | §3.2.1의 2번(위반의 원인이 미래에 있다) | 같은 판정 조건 하나가 네 갈래(ROUTE / PEND / SHED / FORCE)를 만든다. **PEND는 요청이 아직 아무 인스턴스에도 속하지 않았을 때만 성립하므로 엔진 계층은 이 선택지를 원리적으로 가질 수 없다** |
| **3** | **부하를 스칼라 하나가 아니라 요청 자신의 예산과 인스턴스의 상태로 나눠 봐야 한다** | §3.2.2 | 요청마다의 남은 예산, 클래스별 출력 길이 분포에서 얻는 조건부 기댓값, 계수 셋짜리 해석적 스텝 모델, **인스턴스별 prefill 비용(prefix 인식)** |
| **4** | **결합을 미리 정하지 않고 판정의 결과로 얻어야 하며, 그 신호가 정책 자신의 결정에 되먹임되지 않아야 한다** | §3.2.1의 두 실패, §3.2.3 | 클래스 선호가 **필터가 아니라 정렬 키**다. 그리고 되먹임이 닫히는 신호 둘을 실제로 제거했다 |

**요구 조건 4의 "정렬 키"라는 점이 이 설계에서 가장 중요한 자리다.** 선호가 필터였다면
정적 파티션과 같아진다. 정렬 키이므로 두 방향이 자동으로 걸린다 — **위쪽**으로는 같은
클래스가 모이고, **아래쪽**으로는 한 인스턴스가 그 클래스로 차면 판정을 통과하지 못해 후보에서
빠지므로 무한정 몰리지 않는다. **되돌리는 장치도 따로 필요 없다**: 조건이 바뀌면 다음 판정부터
다르게 나오고, 부하가 오르면 판정을 통과하는 후보가 하나로 줄어 선호가 작동할 자리 자체가
없어지므로 분리가 저절로 풀린다. 실제로 한 시간 trace에서, 창별로 잰 클래스별 집중 정도
(§0.3의 클래스당 유효 인스턴스 수)와 그 창의 도착률 사이의 상관계수가 **−0.613**이다 —
도착률이 높아질수록 클래스가 여러 인스턴스에 고르게 퍼진다는 뜻이다.

> **그러므로 우리는 "격리와 혼합의 중간"에 있는 것이 아니다.** 중간이라는 말은 두 끝점 사이의
> 어느 지점을 고른다는 뜻인데, 우리는 축 위의 지점을 고르는 것이 아니라 **그 축을 만드는 결정
> 자체를 다른 것으로 바꾼다** — "어떤 요청들이 한 인스턴스를 같이 써도 되는가"에 미리 답하지
> 않고, 요청이 올 때마다 인스턴스 하나씩에 대해 판정한다.

### 3.4.2 The order of the story is not the order of the measured effects

> **The design element with the largest measured effect is the one the argument
> above spends the least time on, and we say so rather than reordering the
> measurements to match the narrative.**

**ablation이 있는 것끼리 비교할 수 있는 것은 셋이다.**

| | 효과 (정적 25 / 35 / 45 req/s) | 실험·반복 |
|---|---|---|
| **prefill 비용을 인스턴스별로 정확히 매기는 것** | 35·45·55에서 **+13.5 / +10.2 / +10.3점**, goodput +14~22%, 거절 −9.2 / −7.8 / −7.4 %p | EXP-69, 3 rate × **2반복** |
| **보유(PEND)** | **+2.3 / +14.6 / +22.5점** | **EXP-73, 3 rate × 2반복** |
| **클래스 선호** | **+2.6 / +4.0 / −7.3점** ⚠ **45에서 부호가 반대다** | **EXP-73, 3 rate × 2반복** |

⚠ **클래스 선호의 값이 예전에 적어 두었던 것과 다르다.** `motivation.md`와 v2가 인용하는
"정적 45 req/s에서 +7.5점"은 **수정 전 워크로드에서 prefix 회계를 끈 바이너리로** 잰
것이다(EXP-56, 3반복). **지금 배포된 구성에서 같은 도착률을 다시 재면 선호를 끈 쪽이 7.3점
높다**(EXP-73, 2반복, 폭 0.1과 0.7). 두 측정은 조건이 다르므로 EXP-56이 틀린 것이 아니라,
**배포 구성의 값으로 +7.5를 인용하면 안 된다.**

**45 req/s에서 선호가 해로운 이유를 엔진이 직접 말해 준다.** 선호는 같은 클래스를 적은 수의
인스턴스에 모으고, 그렇게 모인 인스턴스의 KV가 먼저 차고, **vLLM V1은 KV가 부족하면
recompute로 요청을 쫓아낸다** — 이미 한 prefill을 버리고 다시 하는 것이라 어떤 요청 단위
지표도 그 비용을 청구하지 않는다. **선호를 끄면 함대의 preemption이 35 req/s에서 128건에서
0건이 되고, 45에서 272건에서 46건이 된다**(반복당 함대 합계, 2반복 평균). 판정 실패의 사유도
같은 방향이다 — 메모리 때문인 것이 18.8%에서 3.4%로 내려간다.
**분리가 만드는 이득보다 KV가 한쪽에 몰려 생기는 preemption과 거절이 더 커지는 도착률이 있고,
이 워크로드에서 그 교차점이 35와 45 req/s 사이에 있다.**

⚠ **그리고 선호는 엔진의 prefix hit rate를 올리지 않는다** — 25 / 35 / 45 req/s에서 대조군
42.1 / 37.2 / 35.3%, 선호 끔 38.4 / 38.1 / 37.3%로, 낮은 도착률에서는 오히려 끈 쪽이 높다.
**"클래스 선호가 접두사 재사용을 돕는다"고 쓰면 안 된다.**

**두 메커니즘을 조건부로 읽으면 순위가 분명해진다.**

| | 35 req/s | 45 |
|---|---|---|
| **보유의 값** (선호 켠 상태 / 끈 상태) | +14.6 / +9.6 | +22.5 / +28.2 |
| **클래스 선호의 값** (보유 켠 상태 / 끈 상태) | **+4.0** / −1.1 | **−7.3** / −1.7 |

> **보유는 네 칸 전부에서 9.6~28.2점의 값을 갖고, 클래스 선호는 네 칸 중 한 칸에서만
> 양수다.** 그러므로 이 설계에서 큰 메커니즘은 보유이고, 클래스 선호는 작고 조건에 크게
> 의존하며 preemption이라는 대가를 치른다. **두 항이 같은 자원(KV) 위에서 반대 방향으로
> 작용하므로 손해가 가법적이지 않고, 그것이 §5.1의 ②에 적은 sub-additivity의 정체다.**

**그리고 두 메커니즘의 값이 사실상 전부 chat 항이다.** 대조군 대비 차이를 요청 비중으로
가중해 분해하면 보유 끔 @ 45가 −22.5 중 chat −21.5, 선호 끔 @ 45가 +7.3 중 chat +7.6이고
deepresearch와 swe는 어느 arm에서도 1점 안에서 움직인다. **그러므로 이 두 값도 chat이 요청의
76.9%라는 것에 비례해 커진 값이고, 믹스를 바꾸면 같이 줄어들 것으로 보아야 한다**(§5.1의 ①).

**보유(PEND)가 하는 일도 이 실험이 처음 갈랐다.** 보유를 끄면 그 결정이 거절과 강제 배치로
나뉘고(45 req/s에서 shed 19.0 → 49.7%, force 1.7 → 13.4%), **엔진에 큐가 생긴다** — 큐 p95가
8.8에서 23.7건으로, KV 점유 중앙값이 57.6에서 69.9%로, preemption이 272에서 732건으로 간다.
그리고 **두 분모가 같이 무너진다**: admitted가 92.1에서 71.9로 내려가고 "받았지만 못 지킴"이
4.9에서 13.9%로 세 배가 된다. **즉 더 많이 거절하면서 받아들인 것도 더 많이 놓친다** — 거절이
는 것이 "못 지킬 것을 미리 잘라서"가 아니다.

> **그러므로 보유는 admission 규칙이기 전에 back-pressure다.** 게이트웨이에 붙들고 있는 동안
> KV가 비워지고, 그래서 엔진이 preemption 구간에 들어가지 않는다. **"잠깐 기다렸다가 같은
> 곳에 넣는 것"이 아니다.**

손해는 chat에 집중된다(61.6 → 33.6). **deepresearch는 오히려 견딘다** — 첫 토큰까지가 중앙값
2초에서 8초로, 토큰당 시간이 47.9에서 70.4 ms로 나빠지는데 **둘 다 자기 예산(10초, 100 ms)
안**이라 달성률이 57.4에서 57.2로 거의 그대로다. **예산이 느슨한 클래스는 back-pressure가
없어져도 버티고, 예산이 빡빡한 chat이 전부 떠안는다.**

**게이트는 ablation이 없지만 거절의 90.8%를 만든다**(한 시간, 1반복). `overIncumbents`는
**2.0%**다. ⚠ **코드 주석은 `overIncumbents`를 "한 클래스를 다른 클래스의 인스턴스에서 막는
조건"이라고 부르는데, 계수기는 그 인과를 확인해 주지 않는다. 설명의 중심에 이 항을 놓으면
측정과 어긋난다.**

**이 순위를 "우아한 부분은 별것 아니었다"로 읽으면 안 된다. 두 가지 이유가 있다.**

**하나. 게이트가 설계 자체다.** 게이트가 하는 일이 §3.2.1의 메커니즘을 결정으로 바꾸는
일이고, 클래스 선호는 게이트를 대신하는 것이 아니라 **게이트가 어디에 걸릴지를 바꾸는
것**이다. 둘은 경쟁 관계가 아니다.

**둘. 판정 조건만으로는 안 된다는 것이 측정돼 있다.** llm-d는 **같은 형태의 판정 조건을
갖고도** 유지 도착률이 18.7 대 28.1이고 한 시간 trace에서 네 인스턴스 전부에 chat을 올려 둔다.
**판정 조건은 필요조건이고 충분조건이 아니다.**

**그래도 정직하게 남는 것이 있다.** 클래스 선호의 한 시간 이득 +1.6~+2.1점은 우리와 llm-d의
한 시간 격차 24.3점에 비하면 작고, **나머지가 어디서 오는지는 아직 다 분해되지 않았다.**

| **게이트** | §3.2.1 | **없다** (축 `gateSlack`만 있다) | 거절의 **90.8%**를 만든다 (1반복) | **WEAK** — 가장 크게 작용하는데 통제된 값이 1반복이다 |
| **prefill 비용을 인스턴스별로 정확히 매김** | §3.2.2 | `--fluidserve-prefix-aware` | **+13.5 / +10.2 / +10.3점** (3 rate × 2반복) | 효과는 **SOLID**, **동기가 MISSING** |
| **클래스 선호** (정렬 키) | §3.2.1 | `--fluidserve-enable-affinity` 외 둘 | 배포 구성에서 **+2.6 / +4.0 / −7.3점**(EXP-73, 2반복). 한 시간은 +1.6~2.1(대조군 2 대 ablation 1) | **SOLID, 그런데 45 req/s에서 부호가 반대다** |
| **보유(PEND)** | §3.2.1의 "위반의 원인이 미래에 있다" | `--fluidserve-enable-pend` | 정적 25 / 35 / 45 req/s에서 **+2.3 / +14.6 / +22.5점** | **SOLID** (EXP-73, 3 rate × 2반복) |
| **이미 못 지키는 요청을 용량 모델에서 제외** | §3.2.3 | **플래그도 arm도 없다** | 일화 하나 | **MISSING** |
| **되먹임을 피해 고른 신호** | §3.2.3 | **arm이 없다** | 개발 중 관측 | **MISSING (설계 주장으로는)** |
| **요청마다의 남은 예산** | §3.2.2 | **없다** | 간접 하나(프로파일 3.4배 오류 시 −20.2점) | **MISSING** |

**여기서 읽어야 하는 것 둘.**

1. **가장 크게 측정된 설계 요소(prefill 회계, +10.2~13.5점)가 motivation에서 가장 약하게
   동기부여된 항목이다**(§3.2.2의 "부하는 스칼라가 아니다"에 측정이 없다). **가장 싼 수선은
   실험이 아니라 서술이다** — 그 주장을 어려움의 한 갈래로 올리고, 증거를 EXP-69의 거절률
   감소로 직접 세운다.
2. **어느 설계 요소도 답하지 않는 주장이 하나 있다** — "옳은 배정이 시간에 따라 움직인다"
   (해상도 축). 우리 대응은 "배분 단위가 요청 한 건"인데, **이 워크로드는 그 축을 거의
   시험하지 않는다**(구간마다 수요를 반올림하면 네 구간 전부 같은 배분이 된다). 함대 크기를
   바꾸는 것이 유일한 경로다(§5.2의 E5).

계산하는 것이 없었고, **초고의 지표 넷에도 이것과 거절률이 빠져 있다.**

# 5. 심사에서 나올 반론과, 그것을 닫는 실험

**이 절이 이 문서에서 가장 실용적인 부분이다.** 왼쪽은 지금 이 논증에 대해 던질 수 있는
가장 아픈 질문이고, 오른쪽은 그것을 닫는 실험이다. **급한 순서로 놓았고, 순서를 정한 기준은
"그 반론이 논문의 주장 자체를 무너뜨리는가"다.**

### 5.1 반론 여섯

**① 우위 전체가 chat 한 클래스이고, 그 클래스의 비중은 당신들이 고른 값이다.**
→ **2026-08-10에 닫혔다 (EXP-76, 2 믹스 × 2 arm × 2반복).** 아래 진단은 그대로 맞지만,
**믹스를 바꿔도 우위가 줄지 않는다는 것을 쟀다.** 자세한 것은 이 항목 끝에 있다.
§3.1.2가 그것이다. 요청 단위 24.3점을 클래스별로 분해하면 chat이 +26.1점이고 나머지 둘은
**음수**다(deepresearch −0.7, swe −1.1) — 즉 **llm-d가 두 클래스에서는 우리를 이긴다.**
같은 값을 클래스마다 같은 무게를 주어 모으면 +5.3점이고, 각 정책의 가장 낮은 클래스끼리
비교하면 +6.6점이다. **믹스가 움직인다는 것은 Azure 실측으로
뒷받침되지만 수준(10:2:1)은 근거가 없고 한 번도 바꿔 재지 않았다.**
→ **닫혔다. EXP-76이 두 믹스에서 두 정책을 각각 2반복으로 쟀다.**

| | m4 (chat 요청의 **57.2%**, 30 req/s) | m5 (chat **33.3%**, 20 req/s) |
|---|---|---|
| **요청 단위 우위** | **+31.2** | **+29.0** |
| 두 arm 중 큰 반복 폭 | 12.1 (llm-d) | 6.3 (llm-d) |
| 클래스 균등 평균 | +15.7 | **+28.9** |
| 최저 클래스끼리 | +5.2 | **+16.7** |
| token goodput | +3,556 tok/s | +2,740 tok/s |

**chat을 요청의 78%에서 33%로 내려도 우위가 줄지 않고**(+31.2 → +29.0, 반복 폭의 4.6배),
**m5에서는 세 집계 전부에서 유지된다** — 한 시간 trace에서 +5.3과 +6.6이던 클래스 균등과 최저
클래스가 여기서는 +28.9와 +16.7이다.

**왜 줄지 않는지도 같은 표에 있다.** 한 시간 trace에서 우위가 전부 chat 항이었던 것은 사실인데,
**그 원인이 chat의 비중이 아니라 llm-d가 chat을 못 지킨다는 것**이다. m5에서 chat이 요청의
3분의 1인데 llm-d의 chat 달성률이 26.1과 38.6이고 우리는 94.5와 94.9다. **거절률이 그 차이를
만든다** — llm-d 48.5~65.8% 대 우리 17.7~28.5%이고, **admitted는 둘이 비슷하다**(우리
90.0~92.3, llm-d 87.1~95.4). **llm-d는 받아들인 것은 잘 지키는데 받아들이는 양이 절반이다.**

⚠ **같이 적어야 하는 것 셋.** (1) **llm-d의 반복 폭이 크다** — m4에서 12.1점이고 chat이 39.6
에서 7.0으로 갈린다(우리는 1.6~2.1점). 조건마다 예측기를 초기화하고 3분 예열을 주는데도
그렇다. (2) **이것은 정적 조건이고 한 시간 trace가 아니다** — 한 시간의 +24.3과 여기의 +29.0을
"우위가 커졌다"로 읽으면 안 된다. (3) **두 믹스의 도착률이 다르다**(30과 20 req/s. EXP-75가
각 믹스에서 달성률이 90%와 40% 사이에 오도록 고른 값이다).

**② 우리 시스템의 어느 부분이 값을 만드는지가 절반만 갈렸다.** 2026-08-10에 EXP-73이 끝나서
**보유(PEND)와 클래스 선호가 각각 숫자를 갖게 됐다**(§3.4.2). 남은 것은 **게이트에 ablation이
없다는 것**과, **우리와 llm-d의 24.3점 중 대부분이 아직 어느 부분의 것인지 모른다는 것**이다.
그리고 EXP-73이 답한 것은 "세 번째 답이 값을 갖는가"이지 **"거절과 배치가 같은 양을 써야
하는가"가 아니다** — 그 칸(A2a × B3)은 여전히 비어 있다.
→ **닫는 것: 독립 결합 arm**(§5.2의 E2).

⚠ **그리고 EXP-73이 co-design 주장을 약하게 만들었다.** 사전에 적어 둔 규칙은 "둘 다 끈 손해가
각각 끈 손해의 합보다 크면 두 메커니즘이 서로를 돕는다"였는데, 두 판정 도착률에서 **작게**
나왔다(25에서 4.2 대 4.9, 35에서 13.6 대 18.6). **규칙대로 "두 메커니즘이 부분적으로 같은 일을
한다"로 적는다.** 45 req/s에서는 반대(20.8 대 15.2)인데, **판정에 45를 쓰지 않기로 실행 전에
정했으므로 거기에 기대지 않는다.**

**③ 사후에 계산한 정수 배분이 두 조건에서 우리를 이긴다.** §3.3.3. 그리고 그 두 조건에서
우리 반복 폭은 1.5점과 0.5점이라 **편차로 설명되지 않는다.**
→ **닫는 것: 함대 크기를 바꾸는 실험**(§5.2의 E5). 인스턴스가 네 대뿐이면 정수 배분의 단위가
함대의 25%나 되므로, **각 클래스가 몇 대를 갖는가(수준)와 그것을 얼마나 잘게 바꿀 수
있는가(해상도)가 구분되지 않는다.**

**④ PolyServe 이식본에서 원문의 과부하 대응이 셋 다 빠져 있다.** 오토스케일링(제외),
lazy promotion(미구현), DSLO 채점(미사용). **특히 lazy promotion은 우리가 "KV 점유율 17.7%에 대기 큐가 비어 있는 인스턴스"로
보여 주는 바로 그 상태를 없애려고 있는 메커니즘이다.**
→ **닫는 것: 실험이 아니라 서술이다.** 이름을 "고정 함대 위의 정적 클래스 파티션"으로 좁히고,
빠진 셋을 본문에 적는다. lazy promotion 구현은 필터 인터페이스 변경이 필요하므로 지금은
범위 밖으로 명시하는 쪽이 현실적이다.

**⑤ 기준선이 채점되지 않는 축에서 우리보다 4.7배 빡빡한 목표를 쫓고 있다.** §3.1의 `m1f`
비대칭. 그리고 하필 그 클래스(swe)가 우리가 지는 유일한 클래스다.
→ **닫혔다 (EXP-74, 2026-08-10, 3 rate × 2반복).** FluidServe를 `m1f`로 돌리면 swe 달성률이
37.3 → 34.7 / 23.3 → 21.8 / 19.0 → 17.7로 움직이는데, 세 도착률 전부 **사전에 정한 3점 문턱
안**이다. **그러므로 우리가 swe에서 지는 것은 예산 설정 차이가 아니라 정책의 성질이다.**
⚠ 총계는 −2.0 / −3.6 / −2.7로 일관되게 음수이고 45 req/s 하나가 문턱을 넘는다 — **"기준선과
같은 방식으로 예산을 표현하게 하면 1.3~3.6점 잃는다"까지 쓸 수 있고, "민감하다"고 쓰려면
반복을 늘려야 한다.**
⚠ **그 대신 새 질문이 열렸다**: 우리가 swe를 크게 거절하는 이유가 예산 표현이 아니라면
무엇인가. m1에서 이미 54.1%를 거절하고 있었고 m1f에서 59.2%가 된다. **아직 안 쟀다.**

**⑥ 어려움 둘과 셋에 직접 측정이 없다.** §3.2.2의 근거인 EXP-55는 수정 전 워크로드라 인용할
수 없고, §3.2.3의 근거는 **우리 시스템의 반복 간 편차**다 — 자기 약점을 논거로 쓰는 형태다.
→ **닫는 것: EXP-55 재측정(약 8시간)과, 잘 튜닝한 단일 신호 arm이 지는 것을 보이는 실험.**
후자가 없으면 "단일 신호로는 안 된다"는 문장을 쓸 수 없다.

### 5.2 다음 실험 다섯 — 비용과 사전 판정 규칙

정적 조건 하나가 엔진 cold restart 포함 약 13분, 한 시간 trace 조건 하나가 약 70분이다.
**셋(E1의 정찰 pass, E3, 그리고 EXP-73)은 이미 걸려 있거나 돌고 있다.**

#### E1 — 믹스 비율 sweep

- **무엇을 답하나**: 우리 우위가 chat 비중의 함수인가. **§5.1의 ①을 닫는 유일한 실험이다.**
- **조건과 비용**: 믹스 셋(10:2:1은 이미 있다 / 4:2:1 / 1:1:1) × arm 둘(FluidServe, llm-d)
  × 도착률 하나 × 2반복 = **새로 8조건, 약 1.7시간.** 워크로드 설정만 바꾸므로 **코드 0줄**
  이고, 클래스별 출력 길이 분포가 안 바뀌므로 **프로파일도 그대로 쓴다.**
- **사전 판정 규칙**: 1:1:1에서도 우위가 **두 arm 중 큰 반복 폭보다 크면** 결과가 믹스 수준에
  걸려 있지 않다고 쓸 수 있다. **폭 안이면 논문의 주장을 "chat이 요청의 절반을 넘는 믹스에서"
  로 한정해 다시 쓴다.**
- **지금 상태**: 정찰 pass가 **끝났다**(EXP-75, 2026-08-10). 확인 pass의 도착률이 정해졌다 —
  **m4는 30 req/s(offered 68.3), m5는 20 req/s(offered 74.3)**로, 둘 다 사전에 정한 창
  (90%와 40% 사이) 안이다. **남은 것은 llm-d를 같은 두 조건에서 돌리는 것**이고, 그쪽
  드라이버가 워크로드 설정을 상수로 박고 있어 **약 5줄을 고쳐야 한다. 사용자 승인 뒤에 건다.**
- **정찰에서 같이 보인 것**: chat 비중이 내려가면 포화 도착률이 크게 내려간다(m1의 28.1에서
  m4 대략 21~22, m5 대략 17 이하). **정책이 아니라 워크로드가 무거워진 것이다** — 요청당 평균
  출력이 521 → 600 → 644 토큰, 평균 입력이 1,640 → 2,490 → 3,615 토큰이다. 그리고 **chat이
  요청의 3분의 1로 내려가도 우리가 가장 크게 거절하는 클래스는 여전히 swe다**(m5 @ 20 req/s
  에서 chat 94.1, deepresearch 85.8, swe 43.6).

#### E2 — 독립 결합 arm

- **무엇을 답하나**: 거절과 배치가 **같은 양**을 써야 하는가. 분류 표의 A2a × B3 칸이고,
  `fluidserve-design.md` §6.3이 **"논문의 핵심 실험"**이라고 사전 등록한 것이다.
- **조건과 비용**: Go 약 30줄(`--fluidserve-shed-signal=kv:θ` 같은 플래그) + 25·35·45 req/s
  × 2반복 = **6조건, 약 1.3시간.**
- **사전 판정 규칙**: 그 설계 문서가 이미 적어 뒀다 — **"독립 결합 대비 유의미한 격차가
  없으면 co-design 주장을 유지할 수 없다."** 25와 35 req/s에서 판정하고, θ는 그 arm의
  거절률이 대조군의 ±5%p 안에 들도록 예비 조건 하나로 맞춘다. **거절률을 맞춰야 "거절 비율을
  잘 골라서 얻은 점수"라는 반론이 닫힌다.**

#### E3 — FluidServe를 `m1f`로

- **무엇을 답하나**: swe 열의 차이가 정책 때문인가 예산 설정 때문인가. **§5.1의 ⑤를 닫는다.**
- **조건과 비용**: 35·45·55 req/s × 2반복 = **6조건, 약 1.3시간.** 코드 0줄.
- **사전 판정 규칙**: `experiments/EXP-74_swe-budget-symmetry.md` §3에 적어 뒀다. swe
  달성률이 3점보다 크게 움직이면 클래스별 표의 swe 열 **이름에** 설정 차이를 적는다.
- **결과 (2026-08-10)**: **swe가 −2.6 / −1.5 / −1.3으로 세 도착률 전부 문턱 안이다. 닫혔다.**
  총계는 −2.0 / −3.6 / −2.7이다.

#### E4 — 정적 sweep 두 번째 반복

- **무엇을 답하나**: 네 arm의 90% 유지 도착률이 재현되는가. **§5.1의 지금 상태로는 인트로
  그림을 실을 수 없다.**
- **조건과 비용**: PolyServe·Llumnix SLO 8 rate + 나머지 둘의 저부하 4 rate = **24조건,
  약 5.2시간.**
- **사전 판정 규칙**: 그 값이 두 반복 사이에서 **1.0 req/s 안**이면 곡선 그림을 논문에
  싣는다. 더 크면 그 값을 인트로에서 내리고 **총 출력과 goodput의 쌍**을 인트로 수치로

#### E5 — 함대 크기 2대

- **무엇을 답하나**: 정수 배분의 손해가 함대 크기 때문인가. **§5.1의 ③을 닫는다.**
- **조건과 비용**: `DP_SIZE_LOCAL=2`, 도착률 절반, 4 rate × arm 둘(FluidServe, PolyServe)

  정수 배분의 손해가 함대 크기에 반비례한다는 것이 확인된다. 반대로 우위가 줄면 **"큰
  함대에서는 정적 파티션으로 충분하다"는 반론이 살아나고, 그것을 논문에 적어야 한다.**


**안 하기로 권하는 것 둘.** ① **vLLM production stack router 이식** — 분류 표에서 Llumnix와
같은 칸이라 새 축을 만들지 않는다. 논문에는 "A0×B2에는 배포된 라우터가 둘 더 있고 둘 다 이
부하 구간을 평가 대상으로 삼지 않는다"고 한 문장 쓰는 것으로 충분하다. ② **EXP-55 재측정을
지금 넣는 것** — 세 주장이 걸려 있어 크지만 8시간이고 결론이 뒤집힐 것 같지 않다. E1~E3을
먼저 돌리고 그동안 세 주장은 이 절에 내려 둔다.

### 5.3 그 밖에 열려 있는 것 셋

- **Llumnix 부하 균등화가 수정 후 워크로드에서 재측정되지 않았다.** 초고 §3.1이 쓰는 세
  기준선 중 하나인데 evaluation에 없다. 되살리려면 **EXP-54의 임시 포트 고갈 결함을 먼저
  고쳐야 한다**(클라이언트의 서버 종료 키워드 목록에 `cannot assign requested address`와
  `max retries exceeded`를 넣고 러너의 `ip_local_port_range`를 넓힌다). 아직 안 고쳐졌다.
- **게이트웨이 보유 창이 arm마다 35,000 / 5,000 / 0 ms로 셋이다**(FluidServe 계열 / Llumnix
  계열 / llm-d는 Envoy라 붙들지 않는다). 설정 스크립트의 주석은 "다른 정책에는 무해하다"고
  적었는데, Llumnix SLO의 거절이 중앙값 5.23초·최대 6.0초에 몰려 있는 것은 **그 5초 창이
  거절 시점을 정하고 있다는 뜻**이다. 총계를 뒤집을 것 같지는 않지만 **"우리 거절이 더 일찍
  온다"는 문장은 정책이 아니라 설정의 결과일 수 있다.** 12조건이면 갈린다.
- **주 분모에 대한 지시가 문서마다 다르다.** `CLAUDE.md`와 `exp-plot` 스킬은 admitted를
  주 지표로 지목하고, `motivation_v2.md` §1.3·`exp23_rate_sweep.py`·이 문서는 offered를
  쓴다. **거절을 위반으로 세어야 capacity 정의가 성립하므로 offered로 통일하는 것이 맞고,
  그 두 곳을 고쳐야 한다.** 사용자 확인이 필요한 항목이라 여기 적어 둔다.

**그리고 쓰면 안 되는 문장 넷.**

- ❌ **"우리가 SLOs-Serve를 이긴다"** — 그들의 본체(batch 안의 토큰 배분)를 구현하지 않았다.
- ❌ **"기존 시스템의 부하 신호가 부하를 못 잡는다"** — 직접 재지 않았다(위의 5번).
- ❌ **"함대의 절반이 쓰이지 않고 있다"** — 정책마다 남는 자원이 다르다(§3.1.3).
- ❌ **"prefix-aware routing"** — 우리는 목적지 선택을 바꾸지 않고, 켜면 엔진의 hit rate는
  오히려 1.5%p 내려간다. **"prefill 비용을 인스턴스별로 정확히 매긴다"라고 써야 한다.**

# 부록 A. 논문에 그대로 옮길 수 있는 문장

**여덟 중 넷(A5·A6·A7·A8)은 각각 §3.3.2·§3.1.4·§2.3.1·§3.2.1의 첫 문장과 같은 문장이다.**
본문에서 이미 읽었더라도 여기 다시 두는 이유는, **논문으로 옮길 때 필요한 것이 문장 여덟 개가
한자리에 모인 목록**이고, 각 문장 뒤의 "같이 적을 것"이 여기에만 있기 때문이다.

각 문장 뒤에 **캡션이나 각주에 같이 있어야 하는 것**을 적었다.

**A1. 메커니즘 (§3.2.1)**

> An instance produces one token-generation rate at a time, shared by every
> request resident on it. Admitting a request therefore does not consume capacity
> in proportion to that request: it changes the rate every other resident
> receives.

같이 적을 것: 이것은 연속 배칭의 성질이다. **"따라서 그 인스턴스는 새 요청을 받으면 안
된다"는 여기서 따라 나오지 않는다** — 그것은 admission 규칙이 정하고, 명목 예산의
최솟값(50.0 ms)과 남은 예산의 최솟값(68.3~72.7 ms) 중 어느 것으로 재느냐가 갈린다.

**A2. 그래서 용량이 라우터의 함수가 된다 (§3.2.1)**

> Capacity is therefore not additive over requests. It depends on how requests
> are grouped, and the grouping is the router's output.

같이 적을 것: 스텝 법칙 `t = 16.361 + 1.2822e-5·M + 0.07643·n`(R² 0.952, 표본 377,838)의 두
변수가 모두 그 인스턴스에 무엇을 보냈는지로 정해진다는 것.

**A3. 문제가 실제로 있다 (§3.1.1)**

> On the same four engines, the same request mix and the same latency rules, a
> static class partition produces 97% as many output tokens as our policy and
> delivers 6.9 times fewer of them inside their own latency rule.

같이 적을 것: 한 시간 trace, **네 arm 모두 2반복**. 11,145 대 11,501 tok/s, goodput 1,566 대
10,865. **PolyServe는 하나도 거절하지 않는다.**

**A4. 위반의 원인이 미래에 있다 (§3.2.1)**

> A per-token latency budget is violated by requests that arrive after the
> request in question has already been placed. Admission cannot honour such a
> budget by deciding once at arrival; it has to constrain what is placed next.

같이 적을 것: 첫 토큰까지의 시간에는 이 성질이 없다. **이것이 admission과 routing을 같은
결정으로 묶어야 하는 첫 번째 이유다.**

**A5. 판정 조건은 필요조건이고 충분조건이 아니다 (§3.3.2)**

> Testing a candidate instance against the tightest budget resident on it is
> necessary but not sufficient. It says the current placement is bad; what
> placement to build instead is decided by the tie-break among the candidates
> that pass, and every existing system breaks that tie by load.

같이 적을 것: llm-d가 같은 형태의 조건을 갖고도 한 시간 trace에서 **chat 없는 (인스턴스, 시각)
쌍이 0.2%**이고 38.7%를 거절한다는 것(2반복).

**A6. 엔진 계층으로는 못 고친다 (§3.1.4)**

> A deadline-aware engine scheduler recovers 2.8 points inside an instance whose
> queue the router should not have created, in the same session in which the
> placement itself costs 60 points.

같이 적을 것: EXP-62, PolyServe × {FIFO, QoServe}, 45 req/s. **되찾은 2.8점이 전부 chat
클래스의 것**이고 나머지 둘은 이미 99~100%였다. 같은 실험을 Llumnix 위에서 하면 부호가
반대다(−0.9~−1.1).

**A7. capacity의 정의 (§2.3.1)**

> We report the highest offered request rate at which at least 90% of arriving
> requests meet their own per-class latency rule, counting rejections as
> violations, interpolated between the two measured rates that bracket the
> threshold.

같이 적을 것: **거절이 위반으로 세어지므로 거절해서 이 값을 살 수 없다.** 통과 기준을 70·80·90·95%
어디에 그어도 우리가 1위다. ⚠ **90%를 지나는 지점이 반복 1회 구간에 있다.**

**A8. 반대 극단도 답이 아니다 (§3.2.1)**

> Giving each class its own instances removes that failure and introduces a
> different one: the allocation is integral, so a class that needs 2.56 of four
> instances receives one, and the class that needs it is 78.1% of the requests.

같이 적을 것: 그 배분이 **우리와 같은 길이 프로파일에서 유도된다.** 그러므로 "당신들만
워크로드 정보를 갖고 있어서 불공정하다"는 반론이 이 표에 대해서는 성립하지 않는다.

motivation은 **문제가 있고, 그 문제가 라우팅 계층의 것이며, 자연스러운 답 둘이 둘 다
어긋난다**까지만 말한다.
