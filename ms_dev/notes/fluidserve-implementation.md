# FluidServe 구현 기록

> 설계 원안: [fluidserve-design.md](fluidserve-design.md) · 대상 스택: NXC13 k3s, Llumnix,
> 4× vLLM 인스턴스(각 TP2, Llama-3.1-70B), B200×8 · 브랜치: `feat/fluidserve`
> (Agent_applications 쪽도 같은 이름의 브랜치)
>
> 이 파일은 **설계 원안을 실제 코드로 옮기면서 내린 결정과 그 근거**를 시간순으로
> 기록한다. 원안이 `[제안]`/`[미결]`로 남겨둔 자리를 채운 내용이 대부분이다.
> 서술 규칙: 비유를 쓰지 않고 일반적인 기술 용어로 인과를 적는다.

## 0. 목표와 성공 기준

**최종 목표**: 1시간 동적 trace(`dyn60_azure4d`, Azure 모양 rate + 15분 단위 믹스 변화)에서
PolyServe 라우팅을 **SLO attainment와 token goodput 두 지표 모두에서** 상회한다.

**채점 규칙(고정)**

| 클래스 | 규칙 | 근거 |
|---|---|---|
| chat | 평균 TTFT ≤ 5s **및** 평균 TBT ≤ 50ms | EXP-14/17/21과 동일 |
| deepresearch | 평균 TTFT ≤ 10s **및** 평균 TBT ≤ 100ms | 〃 |
| swe | E2E ≤ 30s | 〃 (EXP-17 기준) |

- 집계는 **클래스 등가중(equal-mix)**. fleet 평균은 arm마다 served 요청의 클래스 구성이
  달라져 비교가 성립하지 않는다(EXP-21에서 확인된 문제).
- **거절/미서빙 요청은 위반으로 집계한다.** 기존 `served_rows`는 admission reject를
  분모에서 제외하는데, 그 규칙을 그대로 쓰면 요청을 거절할 수 있는 정책이 자동으로
  유리해진다. 따라서 분모는 **분석 창에 도착한 모든 요청(offered)**으로 정의하고,
  기존 정의(served 기준)는 참고값으로 병기한다.
- token goodput = SLO를 만족한 요청이 생성한 output token만 합산(EXP-17 정의 그대로).

**중간 성공 기준**: 고정 rate smoke test에서 (a) 정책이 기동하고, (b) 라우팅 결정이
설계대로 관측되며, (c) 같은 rate의 PolyServe 대비 열세가 아님.

## 1. 실행 환경이 강제하는 것 (설계 원안과의 차이)

원안은 라우터가 큐를 소유하는 독립 프로세스를 가정한다. 실제 스택은 다음과 같다.

```
client → gateway (요청 보유, 재시도) → POST /schedule → scheduler (인스턴스 1개 반환)
                                                          → gateway가 엔진으로 전달
```

- **스케줄러는 큐를 갖지 않는다.** 요청당 한 번 호출되어 인스턴스 하나를 고르는
  함수다(`DispatchPolicy.Schedule`). 큐를 스케줄러 안에 새로 만들면 게이트웨이와의
  프로토콜을 바꿔야 하고, 그러면 PolyServe arm과 게이트웨이 구성이 달라져 비교가
  오염된다.
- **게이트웨이에 이미 보유-재시도 경로가 있다.** `SchedulerClient.Get()`은 스케줄러가
  `ErrorNoAvailableEndpoint`(HTTP 429)를 반환하면 `wait-scheduling-retry-interval`만큼
  자고 `wait-scheduling-timeout`까지 재시도한다. 요청은 그동안 **어떤 엔진에도
  바인딩되지 않는다.**
- **완료 이벤트가 스케줄러에 오지 않는다.** full-mode에서 `/release`는 전달 실패 시에만
  호출된다(`OnPostRequest`). 정상 완료는 CMS 상태 동기화로만 반영된다.
- **엔진은 요청별 진행도를 보고하지 않는다.** 다만 CMS 상태에 인스턴스 단위로
  `StepId`(엔진의 누적 step 카운터), `NumUsedGpuTokens`, `SchedulerRunningToDecodeRequestsNum`,
  `StepDuration`(직전 step 실행 시간), `NumScheduledPrefillTokens`가 들어 있다.

### 결정 D1 — C7(late binding)은 게이트웨이 보유-재시도로 구현한다

스케줄러가 `PEND`을 표현하는 방법은 429 반환이다. 요청은 게이트웨이에 남고, 엔진
바인딩은 **재시도가 성공하는 순간**에 일어난다. 원안이 요구한 성질(바인딩 지연,
재배치 비용 0, 얕은 엔진 큐)은 그대로 얻는다. 얻지 못하는 것은 라우터가 대기 요청
집합을 한 번에 보고 순서를 정하는 능력이다. 이는 스케줄러가 요청 ID별 최초 관측
시각을 기록해 **대기 시간을 알고 있는 상태로 매 재시도를 판정**하는 것으로 부분
대체한다(아래 C5).

재시도 간격 기본값 1000ms는 이 용도에 너무 크다. FluidServe arm은
`--wait-scheduling-retry-interval=100ms`, `--wait-scheduling-timeout`은 가장 큰 TTFT
예산에 맞춰 12s로 올린다. **PolyServe arm의 게이트웨이 설정은 건드리지 않는다** —
두 arm의 게이트웨이가 달라지므로, 이 차이를 결과 해석에 명시하고, 필요하면
"PolyServe + 같은 재시도 설정" 대조군을 추가한다.

### 결정 D2 — 요청 진행도는 `StepId` 차분으로 복원한다

연속 배칭에서 디코딩 중인 요청은 스케줄되는 매 step마다 정확히 토큰 1개를 낸다.
따라서 어떤 요청이 디코드에 진입한 뒤 엔진이 실행한 step 수가 곧 그 요청이 생성한
토큰 수다. 스케줄러는 dispatch 시점의 `StepId`를 기록해 두고

```
j_r = max(0, StepId_now − StepId_dispatch − prefillSteps(l₀))
prefillSteps(l₀) = ceil(l₀ / max_num_batched_tokens)
```

로 진행도를 복원한다. wall-clock을 쓰지 않으므로 iteration time 변동에 영향받지 않고,
CMS 폴링 지연에도 둔감하다. preemption이 일어나면 과대추정이 되는데, 이는
outflow(완료량) 과대추정 방향이므로 원안의 원칙 4(오차를 보수 쪽으로)와 반대다.
그래서 아래 D3의 대조(reconciliation)로 보정한다.

### 결정 D3 — 레지스트리는 엔진 보고값을 기준으로 대조한다

스케줄러가 유지하는 인스턴스별 요청 목록은 추정값이고, 엔진이 보고하는
`NumUsedGpuTokens`(점유 토큰)와 running 요청 수가 사실이다. 매 스케줄 호출에서:

1. 레지스트리 항목 수가 엔진의 running 수보다 많으면, **진행도가 큰 항목부터**
   제거한다(먼저 끝났을 가능성이 높은 순서).
2. 클래스 생존함수 기준 `S_c(j) < s_min`인 항목은 완료로 간주해 제거한다.
3. 레지스트리 합 `Σ(l₀+j)`와 엔진 보고 `NumUsedGpuTokens`의 비를 drift 지표로
   기록하고, outflow 계산에 쓰는 `w_r`에 그 비를 곱해 규모를 맞춘다.

이 구조에서 레지스트리의 역할은 **점유 토큰의 절대량을 맞히는 것이 아니라, 엔진이
보고한 점유량을 클래스와 진행도별로 배분하는 것**이다. 절대량은 항상 엔진 값을 쓴다.

## 2. 설계 원안의 재구성 3가지

리뷰에서 지적한 세 가지 문제(cap 고정, externality 무력화, 교정 통계량 불일치)를
해결하기 위해 원안의 수식을 다음과 같이 바꾼다. 컴포넌트 구성(C1~C7)과 설계 원칙
(engine agnostic, 정확한 양만 온라인 사용, 분포 측정, 보수 편향)은 유지한다.

### R1 — SLO를 순간 임계값이 아니라 **잔여 예산**으로 표현한다

원안의 `cap_i = f(min TBT among requests)`는 우리 SLO 숫자에서 다음 문제를 만든다.
swe의 tier 키는 TPOT 25ms인데, 이 값은 B200에서 측정된 단독 디코드 ITL 중앙값과
같다. 즉 배치 크기가 1을 넘는 순간 위반이므로, swe 요청 하나가 배치된 인스턴스는
그 요청이 728 토큰을 다 생성할 때까지 cap이 최저값으로 고정되고 다른 요청을 받을 수
없게 된다. 인스턴스 4대 중 일부가 이 상태로 오래 머무르면 fleet 처리량이 그만큼
줄어든다.

그런데 **채점 규칙은 순간 TBT가 아니다**. 세 클래스 모두 실제로는 누적 예산이다.

| 클래스 | 채점 규칙 | 누적 예산으로 환산 |
|---|---|---|
| chat | 평균 TBT ≤ 50ms, 평균 출력 386 | 디코드 총시간 ≤ 19.3s |
| deepresearch | 평균 TBT ≤ 100ms, 평균 출력 275 | 디코드 총시간 ≤ 27.5s |
| swe | E2E ≤ 30s, 평균 출력 728 | TTFT + 디코드 총시간 ≤ 30s |

따라서 요청 r의 **현재 허용 per-token 시간**을

```
allowance_r = (예산_r − 이미 소비한 시간) / (예상 잔여 토큰 수)
```

로 정의한다. 예산을 앞서 쓴 요청은 allowance가 줄고, 여유가 있는 요청은 늘어난다.
`cap_i`는 인스턴스에 올라간 요청들의 allowance 최솟값으로 정한다. 이렇게 하면

- swe가 초반에 빠르게 진행했다면 allowance가 25ms보다 훨씬 커져 cap을 낮추지 않는다.
  (30s − TTFT 1.5s) / 728 ≈ **39ms**가 시작 시점의 allowance이며, 앞부분이 빠를수록
  더 커진다.
- 반대로 예산을 초과하기 시작한 요청은 allowance가 0에 수렴한다. 이때는 cap을 낮추는
  대신 **그 요청을 이미 위반 확정으로 분류하고 cap 계산에서 제외**한다(아래 R1-b).
  이미 SLO를 놓친 요청 때문에 나머지 요청까지 손해를 보는 상태를 피하기 위함이다.

**R1-b 구조적 실현 불가 판정**: allowance가 그 인스턴스에서 요청 혼자 있을 때의
디코드 step 시간보다 작으면, 어떤 배치 구성으로도 만족할 수 없다. 이런 요청은
`best-effort`로 강등해 cap 최솟값 계산에서 빼고, 라우팅에서도 다른 요청을 방해하지
않는 인스턴스로 보낸다. 이것은 PolyServe가 swe에 전용 서버 2대를 주고 그 tier의
attainment가 0에 가까워지는 것을 감수한 것과 같은 판단을, **서버를 전용으로 묶지 않고**
내리는 것이다.

### R2 — capacity 모델에 **prefill 점유율 φ**를 1급 변수로 넣는다

EXP-16 측정: 디코드 step은 17~113ms, full-chunk(8192 토큰) prefill step은 519.7ms로
6~37배다. vLLM V1의 chunked prefill은 대기 중인 prefill이 있으면 매 step에 청크를
싣는다. 따라서 어떤 인스턴스의 **평균 step 시간**은

```
s_p   = min(k, ceil(P_i / chunk))          # 앞으로 k step 중 prefill을 싣는 step 수
mean_step(k) = [ (k − s_p)·t_dec(M) + s_p·t_pre(chunk) ] / k
```

이고, 디코딩 요청이 겪는 평균 TBT가 곧 이 값이다(청크가 실린 step에서도 디코딩
요청은 토큰 1개를 받으므로, 토큰 간격이 그 step 시간이 된다).

이 형태의 장점은 **externality가 별도 장치 없이 같은 식에서 유도된다**는 점이다.
요청 r을 인스턴스 i에 배치하면 `P_i`가 `l₀(r)`만큼 늘어 `s_p`가 `ceil(l₀/chunk)`만큼
증가하고, 그 결과 i에 이미 올라가 있는 모든 요청의 `mean_step`이 얼마나 나빠지는지가
바로 계산된다. 원안의 `cap_if_added`를 따로 추정할 필요가 없다.

`t_dec(M)`는 EXP-11에서 확인된 KV 점유량에 대한 선형 관계를 쓴다(`t_dec = a + b·M`).
`t_pre(x)`는 P4-b에서 유휴 엔진 스윕으로 직접 측정한 `ttft.json`을 그대로 쓴다.

### R3 — 대기(PEND)와 확산(spill)을 명시적으로 비교한다

원안의 판정 순서는 `feasible = {i : headroom_i ≥ cost}` → 그 안에서 externality 반영
점수 최대. 이 순서에서는 tight 요청을 모아둔 인스턴스가 cap이 낮아 headroom이 먼저
마르므로 feasible 집합에서 가장 먼저 빠지고, 결국 tight 요청이 loose 인스턴스로
확산된다. 부하가 올라갈수록 확산이 심해져 원안이 의도한 집중이 반대로 작동한다.
(PolyServe 구현에서 admission이 모든 인스턴스에서 탈락한 뒤 fallback으로 풀려
사실상 무력화된 것과 같은 형태의 문제다.)

그래서 판정을 다음으로 바꾼다.

```
best_now   = argmin_i  degradation(i, r)         # 지금 보내면 fleet에 주는 총 손해
wait_gain  = degradation(best_now, r) − degradation(best_future, r)
if 요청 r의 TTFT 잔여 예산 > 예상 대기시간 and wait_gain > wait_threshold:
        PEND
else:   ROUTE(best_now)
```

`degradation(i, r)`은 R2의 `mean_step` 증가분을 i에 있는 요청들의 allowance 여유로
정규화한 값의 합에, r 자신이 i에서 받을 손해를 더한 것이다. `best_future`는
가장 빨리 여유가 생길 인스턴스의 예측 상태로 평가한다. 즉 **대기 자체가 하나의
선택지로 점수화**되며, 이것이 PEND(=429)의 발생 조건이다.

## 3. 컴포넌트 구현 명세

파일은 모두 `pkg/scheduler/policy/` 아래 `fluidserve_*.go`로 새로 만든다.
기존 파일 수정은 등록(`scheduling_policy_registry.go`), 상수(`pkg/consts`), 설정
플래그(`cmd/config/config.go`)에 한정한다. PolyServe 코드는 건드리지 않는다.

| 파일 | 컴포넌트 | 내용 |
|---|---|---|
| `fluidserve_profile.go` | C1, C3(오프라인) | 클래스 생존함수 + 디코드 step 선형모델 로딩, JSON 스키마 |
| `fluidserve_length.go` | C1 | 온라인 Kaplan-Meier 갱신, `p_c(j,k)` |
| `fluidserve_registry.go` | C2 | 인스턴스별 요청 레지스트리, `StepId` 기반 진행도, 대조 |
| `fluidserve_capacity.go` | C3 | `t_dec(M)` 온라인 적합, `mean_step(k)`, `cap_i`, allowance |
| `fluidserve_flux.go` | C2 | inflow/outflow/proj/headroom |
| `fluidserve_decide.go` | C4, C5 | degradation 점수, ROUTE/PEND 판정, 대기 마감 |
| `fluidserve_tuner.go` | C6 | z_safety 조정, 예측 잔차 감시 |
| `fluidserve.go` | 조립 | 정책 구조체, 필터/셀렉터 어댑터, 메트릭 발행 |

### 설정 플래그

```
--scheduling-policy fluidserve
--fluidserve-profile-path      /profiling/fluidserve.json   # C1+C3 시드
--fluidserve-horizon-steps     100      # k
--fluidserve-z-safety          1.65
--fluidserve-alpha-externality 1.0
--fluidserve-class-budgets     "25:e2e:30000:728,50:decode:19300:386,100:decode:27500:275"
--fluidserve-enable-pend       true     # false면 항상 즉시 배치 (ablation)
--fluidserve-enable-externality true    # ablation
--fluidserve-enable-flux       true     # false면 현재 점유량만 사용 (ablation)
```

`--fluidserve-class-budgets`의 형식은 `tpotSloMs:mode:budgetMs:expectedTokens`이며
`mode`는 `e2e`(TTFT가 예산에 포함) 또는 `decode`(TTFT 별도)다. tier 키가 TPOT SLO인
것은 PolyServe와 동일한 게이트웨이 배관(packed priority)을 그대로 쓰기 위함이다.

### 2026-07-26 — M1 완료: 오프라인 프로파일

생성기 `ms_dev/scripts/gen_fluidserve_profile.py`,
산출물 `deploy/profiling/llama31-70b-b200-tp2/fluidserve.json`.

**(1) 디코드 step 법칙** — EXP-16 step dump의 decode-only step 377,838건, 76개 셀
(셀당 최소 30표본, 셀 중앙값으로 적합):

```
t_dec = 16.361 ms + 1.2822e-5 · M + 7.643e-2 · n      R² = 0.952
        (M = 인스턴스가 보유한 KV 토큰 수, n = 디코딩 요청 수)
상대오차 p50 6.4% / p90 20.5%
```

기존 `tpot.json`의 독립 적합(16.427 / 1.412e-5 / 7.950e-2)과 세 계수가 모두 근접해
서로 교차검증된다. KV 항은 엔진 1대 기준 12.8 ns/token이고, EXP-11이 fleet 합계 KV에
대해 보고한 약 3 ns/token을 엔진 4대로 나눈 값과 일치한다.

**(2) 혼합 step 모델 — 검증 결과 가법 형태로 확정**

prefill 청크를 실은 step의 비용을 두 가지로 놓고 실측 window와 비교했다.

| 형태 | 식 |
|---|---|
| 분리형 | `mean = (1−φ)·t_dec + φ·t_pre(chunk)` |
| **가법형(채택)** | `mean = (1−φ)·t_dec + φ·(t_pre(chunk) + t_dec − c0)` |

window는 **엔진별 step 사슬**을 복원한 뒤 연속 40 step으로 잡고, 측정값은
`(window가 걸친 wall time)/(step 수)`로 구했다(비동기 스케줄러의 run-ahead를
개별 step에 귀속시키지 않기 위함).

| φ | window 수 | 실측 | 가법형(비) | 분리형(비) |
|---|---|---|---|---|
| 0.0 | 4,717 | 21.5 ms | 19.9 (0.96) | 19.7 (0.95) |
| 0.2 | 2,459 | 22.1 ms | 25.0 (1.11) | 23.8 (1.06) |
| 0.4 | 1,050 | 30.1 ms | 36.5 (1.19) | 30.0 (0.99) |
| 0.6 | 36 | 124.6 ms | 109.8 (**0.90**) | 79.1 (**0.66**) |
| 0.8 | 4 | 134.6 ms | 123.2 (**0.89**) | 80.1 (**0.59**) |

가법형을 채택한 이유: prefill을 실은 step은 그 step에서 prefill GEMM과 함께 실행 중인
모든 디코딩 요청의 attention도 수행하므로 두 비용이 더해지고, 고정 오버헤드 `c0`만
한 번 계산된다. `ttft.json`은 유휴 엔진에서 측정돼 디코드 비용이 들어 있지 않으므로
분리형은 간섭이 큰 구간에서 35~40% 과소예측한다. **과소예측은 과잉 admission을 통해
preemption으로 이어지므로 가장 피해야 할 방향**이며(원안 원칙 4), 가법형은 중간
구간에서 11~19% 과대예측하는 대신 그 방향의 오차가 없다.

한계: φ ≥ 0.6 구간의 표본이 40개뿐이다. EXP-16 워크로드에서 prefill 포화 구간이
드물게 나타나기 때문이며, 이 구간의 정확도는 온라인 교정(C3)과 z_safety로 보완한다.

### 2026-07-26 — M2~M4 구현 중 내린 결정

**D4 — 온라인 교정 신호를 바꿨다.** 원래 계획은 CMS 상태의 `StepDuration`
(직전 step 실행 시간)과 `NumScheduledPrefillTokens`를 짝으로 써서
`(점유량, 배치 내 prefill 토큰) → step 시간` 표본을 모으는 것이었다. 그런데
`status_updater.py:145-168`을 보니 이 필드는

- `LLUMNIX_ENABLE_PROFILING`이 켜져 있고 `profiling_id < LLUMNIX_PROFILING_STEPS`인
  동안에만, 그리고
- `num_scheduled_prefill_tokens > 0`, 즉 **prefill을 실은 step에서만**

발행된다. 디코드 step의 비용을 교정하는 데 쓸 수 없다.

대신 **항상 발행되는 두 필드의 차분**을 쓴다.

```
관측 평균 step 시간 = (TimestampMs 증가분) / (StepId 증가분)
```

이 값은 (a) 언제나 얻을 수 있고, (b) 모델이 예측하는 것과 **같은 양**(구간 평균)이며,
(c) M1에서 오프라인으로 검증한 것과 같은 방식이다 — 비동기 스케줄러의 run-ahead를
개별 step에 귀속시키지 않고 구간으로 평균낸다. 디코드 법칙에는 구간 양 끝에서
대기 prefill이 0인 표본만 먹인다.

**함정 하나**: 디코드할 것이 없는 엔진도 step 카운터는 올라가지만 그 사이 시간은
계산이 아니라 대기 시간이다. 그대로 나누면 유휴 인스턴스의 step 시간이 1,476 ms로
보고되어(실제로 라이브에서 관측됨) 안전 루프가 가장 여유 있을 때 후퇴한다. 구간 양
끝에서 디코딩 요청 수가 1 미만이면 표본을 버린다.

**D5 — 판정 전체를 selector에 넣었다.** Llumnix의 필터 구조는 2-pass다: 필터가
인스턴스를 모두 제거하면 `skipWhenFallback()`인 필터를 빼고 다시 돌린다. 즉
**아무도 못 받는 상황에서 제약을 푸는** 구조인데, FluidServe에서 그 상황의 올바른
대응은 제약을 푸는 것이 아니라 요청을 붙잡아 두는 것이다. 또 대기는 인스턴스 하나에
대한 판정이 아니라 전체를 본 뒤에야 내릴 수 있다. 그래서 필터에는 liveness 검사만
남기고(schedulability, staleness) 판정은 selector가 전부 한다. selector가 nil을
반환하면 `executeSchedule`이 nil을 반환하고, `Schedule`이 `ErrorNoAvailableEndpoint`
(HTTP 429)를 내며, 게이트웨이가 요청을 들고 재시도한다. **fallback pass는 필터가
비었을 때만 도는 것이지 selector가 nil을 낼 때는 돌지 않으므로**, 이 구조에서
대기 결정이 뒤집히지 않는다.

**D6 — 게이트웨이 재시도 간격이 곧 재결정 주기다.** 위 구조의 귀결이다. 기본값
1000ms는 인스턴스 상태가 바뀌는 시간 규모(step 20ms 내외, CMS 상태 갱신 500ms)보다
훨씬 거칠다. FluidServe arm에서만 100ms로 낮추고 보유 상한을 12s로 올린다
(워크로드 최대 TTFT 예산 11.8s를 덮기 위함). 다른 정책으로 되돌릴 때 원래 값
(1000ms/5s)으로 복구한다. **arm 사이 설정 차이이므로 실험 문서에 명시**한다.

**D7 — 달성 불가 요청의 분류.** R1-b를 다음 기준으로 구현했다: 요청의 잔여
per-token 허용시간이 **비어 있는 인스턴스에서의 step 고정비용 `c0`(16.4ms)보다 작으면**
어떤 배치 구성으로도 만족할 수 없다. 이 요청은 인스턴스의 cap을 정하는 최솟값
계산에서 제외한다. 물리적 하한을 기준으로 하므로 판정이 임의적이지 않고, 제외하지
않으면 그 요청은 나아지지 않으면서 인스턴스만 새 요청을 못 받게 된다.

**라이브 검증 (2026-07-26)**: 정책 기동 후 실제 요청 3건을 흘려 전 구간 확인.
세 tier 모두 정상 라우팅되고, `scheduler_fluidserve_capacity_correction`이
**0.9998**을 가리켰다 — 오프라인으로 적합한 디코드 법칙이 실행 중인 엔진을 그대로
설명한다는 뜻이고, M1의 적합이 이 클러스터에서 유효함을 라이브로 확인한 것이다.

### 2026-07-26 — 첫 실측(1800 rpm smoke)에서 v1이 진 이유와 수정

**결과**: 클래스 등가중 attainment **FluidServe 33.7 / PolyServe 69.5 / load-balance 22.4**.
총 출력 처리량도 5,613 tok/s로 PolyServe 11,104의 절반이었다.

클래스별로 보면 문제의 성격이 드러난다.

| arm | chat | deepresearch | swe | goodput tok/s | 총 tok/s |
|---|---|---|---|---|---|
| load-balance | 9.3 | 55.3 | 2.5 | 1,408 | 9,042 |
| **PolyServe** | **100** | **100** | 8.5 | 7,422 | 11,104 |
| FluidServe v1 | 33.3 | 36.6 | 31.0 | 1,718 | 5,613 |

FluidServe는 **세 클래스에 손해를 고르게 나눠줬다**. 이것은 분리가 전혀 일어나지
않았다는 신호다. 스케줄러 카운터에서 원인 세 가지를 확인했다.

**결함 1 (핵심) — externality가 요청이 "선언한 예산"만 보고 "가져오는 작업량"을
보지 않았다.** v1의 externality는 `요청의 allowance < 인스턴스의 현재 최솟값`일 때만
과금했다. 그런데 이 워크로드에서 문제를 일으키는 요청은 swe이고, swe의 per-token
예산(30s/520토큰 ≈ 57.7ms)은 chat(50ms)보다 **느슨하다**. 즉 22k 토큰 프롬프트를
들고 와서 chat이 돌고 있는 인스턴스의 다음 step 몇 개를 prefill 청크로 채워
chat 전부를 예산 밖으로 밀어내면서도, **externality는 0원이었다.**

→ **수정**: 이 항을 "이 요청을 넣으면 기존 요청들의 평균 step 시간이 얼마나 늘고,
그것이 각자 남은 여유(allowance − 현재 평균 step)의 몇 배인가"로 바꿨다
(`harmToIncumbents`). 그리고 **이미 예산을 넘긴 요청은 0으로 센다** — 어차피 놓칠
요청이므로 추가 지연은 새로운 손실이 아니고, 그렇게 세면 무거운 작업을 이미 흡수한
인스턴스가 비싸 보여서 그 작업이 다시 fleet 전체로 퍼진다. 이 비대칭이 곧
"무거운 클래스가 몇 대에 모이고 나머지는 깨끗하게 유지된다"를 만들며, 어떤 인스턴스도
사전에 예약하지 않는다.

**결함 2 — 온라인 교정이 prefill 비용을 디코드 법칙에 떠넘겼다.** 교정 계수가
**1.735**까지 올라갔다. 구간에 prefill이 있었는지 판정하는 유일한 근거가 구간
**양 끝**의 대기 prefill인데, 상태 갱신 간격이 500ms이고 그 사이 엔진은 약 25 step을
돈다. 구간 안에서 생겼다 사라진 큐는 보이지 않으므로 그 비용이 디코드 법칙으로
들어갔다.

→ **수정**: 온라인 교정을 **기본 off**(`--fluidserve-enable-online-calibration=false`).
오프라인 법칙은 단일 run이 방문하는 범위보다 훨씬 넓은 구간에서 377,838 step으로
적합했고 독립 적합과 교차검증됐으며 유휴 엔진에서 0.9998로 확인됐다. 구간 내부의
두 비용을 분리할 수 있는 신호가 생기기 전까지는 시드가 더 나은 추정이다.

**결함 3 — 안전 루프가 "과부하"를 "추정이 낙관적이었다"로 오독했다.** v1은 측정된
step 시간을 **현재 예산**과 비교했다. 지속 과부하에서는 무엇을 어디로 보내든 모든
인스턴스가 예산을 넘기므로 이 트리거는 계속 발화하고, 안전계수가 상한 3.0에
고정된다(실측: overshoot rate 1.0, z=3.0). 그 결과 admission이 과도하게 조여져
처리량이 절반으로 떨어졌는데, 그렇다고 누구의 SLO가 지켜지지도 않았다.

→ **수정**: 비교 대상을 **모델이 같은 구간에 대해 예측한 값**으로 바꿨다. 측정치가
예측의 1.5배를 넘는 비율이 신호이며, 이것이 "추정이 낙관적이었다"의 실제 형태다.

부수 수정 2건: (a) 방금 비워진 인스턴스에서 물리 점유가 0으로 보고되어 메모리 용량이
1000배 과대 계산되던 문제(비율 하한 0.01), (b) 점수 정규화 기준을 부호가 바뀌는
`min(capKv, capMem)`에서 항상 양수인 `capMem`으로 변경 — 지연 예산을 어떤 점유에서도
만족할 수 없게 되면 `capKv`가 음수가 되는데, 바로 그 구간에서 순위가 무의미해졌다.

### 2026-07-26 — v2 결과와 v3 변경 (분리를 만드는 힘이 없었다)

**v2 결과**: 등가중 35.3 (v1 33.7에서 소폭 상승, PolyServe 69.5). 클래스별로 여전히
고르다(chat 31.9 / dr 40.0 / swe 34.1). 라이브 카운터가 원인을 정확히 지목했다:

```
tightest_allowance_ms  인스턴스1=48.0  인스턴스2=50.4  인스턴스3=47.3  인스턴스4=49.5
```

**네 인스턴스가 전부 chat 예산에 묶여 있다.** 즉 chat이 4대에 고르게 퍼져 있고,
그래서 swe가 갈 만한 "깨끗한" 인스턴스가 존재하지 않는다. harm 항은 무거운 작업이
여유 있는 요청들을 밟는 것을 막지만, **chat이 swe 있는 인스턴스를 피할 이유**는
만들지 못한다. 그 역할을 하려던 항(binding loss)은 토큰 단위로 계산해 인스턴스
크기로 나눴기 때문에 0.013이었고, [-1,1] 범위인 room 항 옆에서 아무 영향이 없었다.

**v3 변경**

1. **예산 유사도(budget affinity)** — binding loss를 `log(요청 예산 / 인스턴스 현재
   예산)`의 절댓값으로 교체했다. 같으면 0이고 양방향으로 대칭적으로 커진다. 가중치 3은
   "예산이 2배 차이(log 2 = 0.69 → 2.08)면 여유 공간 차이(최대 1)를 이긴다"가 되도록
   잡았다. **아무것도 없는 인스턴스는 제약이 없으므로 mismatch가 0**이고, 따라서 먼저
   도착한 예산의 집이 된다 — 콜드 상태에서 분리가 시작되는 경로다.
2. **비교 기준을 tier의 명목 예산으로** — 살아 있는 잔여 allowance는 요청이 뒤처지면
   움직인다. 인스턴스가 얼마나 더 받을 수 있는지를 볼 때는 그게 맞지만, **어떤 요청들이
   같이 있어야 하는지**를 볼 때는 틀리다. 요청 하나가 뒤처졌다고 그 인스턴스가 다른
   클래스를 서빙하는 것처럼 보이면 안 된다.
3. **대기 문턱 0.5 → 2.0, 안전 루프 완화**(잔차 트리거 1.5→2.0배, 발화 비율 0.10→0.25,
   z 상한 3.0→2.5). v2에서도 z가 상한에 붙어 있었고(잔차 초과 비율 0.2), prefix cache
   때문에 harm이 과대평가되므로 대기가 지나치게 잦았다(route 1,394 대 pend 4,180).

**남아 있는 알려진 편향 — prefix cache**: 요청을 배치했을 때 늘어나는 prefill 작업량을
`프롬프트 전체 토큰 수`로 계산한다. 그런데 이 워크로드는 바이트 동일 replay이므로
첫 순회 이후 프롬프트 대부분이 prefix cache 히트이고, 엔진이 실제로 계산해야 하는
uncomputed 토큰은 훨씬 적다. 따라서 harm 항이 간섭을 **과대평가**하며, 그만큼 대기와
강제 배치가 자주 일어난다. 다만 과대평가 배율이 프롬프트 길이에 비례하므로
**클래스 간 순서(swe ≫ deepresearch > chat)는 보존**되고, 방향도 보수적이다.
정확히 고치려면 배치한 프롬프트 토큰 대비 엔진이 보고한 uncomputed 증가분의 비를
인스턴스별로 추정해야 하는데, 두 값이 서로 다른 요청 집합을 가리켜 잡음이 크다.
현재는 편향으로 기록만 해 둔다.

### 2026-07-26 — v4(best-fit) 역효과와 v5 변경

**v4 결과**: 등가중 35.7 — v3의 43.2보다 **나빠졌다**. 라우팅 집중도도 세 클래스
모두 하락(chat 0.11 / dr 0.04 / swe 0.10, v3는 0.07 / 0.20 / 0.36).

가설은 "클래스마다 인스턴스를 채우면 다른 클래스가 쓸 인스턴스가 비워진다"였는데,
실제로는 **가장 찬 인스턴스가 대개 무거운 클래스를 담고 있는 인스턴스**다(swe는
요청당 KV가 chat의 15배). best-fit이 chat을 그쪽으로 끌어당겼고 harm 항이 만들어 둔
분리가 무너졌다. 되돌렸다.

같은 run이 두 번째 사실도 알려줬다. **가중합으로는 분리를 유지할 수 없다.**
같은 예산을 쓰는 인스턴스라는 사실은 mismatch 항에서 약 0.43인데, 여유 공간 차이는
room 항에서 최대 1.0이다. 즉 단지 더 비어 있다는 이유만으로 다른 예산의 인스턴스로
끌려갈 수 있다.

**v5 변경 2가지**

1. **사전식 순서** — 받을 수 있는 인스턴스들 중에서, 먼저 **예산이 비슷한 그룹**을
   고르고 그 안에서만 여유 공간으로 정렬한다. mismatch를 3개 구간으로 묶어
   (< 0.10 / < 0.40 / 그 이상) 사실상 같은 예산인 인스턴스들을 서로 교환 가능하게 본다.
   경계는 chat↔swe 간격(log 1.154 = 0.14)과 chat↔dr 간격(log 2 = 0.69) 사이에 둔다.
2. **대기 시간 상한** — TTFT 예산의 1/4까지만 기다린다. v4에서 강제 배치 1,979건이
   정상 배치 1,681건보다 많았는데, 기존 조건이 "마지막 순간에 배치해도 첫 토큰을
   시간 안에 낼 수 있는가"만 물었기 때문이다. TTFT 5s에 prefill 80ms면 4.6s까지
   기다리게 되고, 그 시점이면 배치에 성공해도 위반이 확정이다. 즉 그 대기는 기존
   요청을 보호하는 대가로 **이 요청을 확실히 잃는** 거래였다.

**ablation 스위치 노출**: `FS_PEND=false` 등으로 메커니즘을 하나씩 끌 수 있게 했다.
특히 **대기를 끄면 FluidServe는 순수 라우팅**이 되고, PolyServe도 순수 라우팅이므로
그 arm이 두 라우팅 규칙의 동등 비교다(지금 비교는 "라우팅" 대 "라우팅+admission"이다).

### 2026-07-26 — v6/v7: 배정이 안 붙는 진짜 이유는 "기억이 없다"는 것

v1~v5를 통틀어 라우팅 집중도가 chat 0.06~0.11, dr 0.03~0.20에서 벗어나지 못했다.
다섯 가지 다른 순위 규칙에서 같은 증상이 나온다면 원인은 순위 규칙이 아니다.

**진단**: mismatch 항이 비교하는 "인스턴스의 예산"은 `tightestNominal`,
즉 **그 순간 올라가 있는 요청들의 최솟값**이다. 인스턴스가 비면 이 값이 사라지고
다음에 오는 아무 클래스나 그 인스턴스를 차지한다. 30 req/s에서 인스턴스가 잠깐 비는
일은 계속 일어나므로, 배정이 끝내 안정되지 않는다. v5의 사전식 순서가 오히려 나빴던
것도 같은 원인이다 — 빈 인스턴스는 mismatch가 0이라 "같은 예산" 그룹과 동급이 되고,
비어 있으니 여유 공간에서도 이겨서 churn을 가속했다.

**수정(v7)**: 인스턴스마다 **자기가 서빙해 온 예산의 평활값**(dispatch 시점
`log(nominal)`의 EWMA, α=0.02)을 들고, mismatch를 그 값에 대해 잰다.

- 인스턴스가 비어도 유지된다 → 잠깐 빈 chat 인스턴스는 여전히 chat을 끌어당긴다.
- 다른 클래스 몇 건으로는 안 움직이고, 수백 건이 지속되면 옮겨간다
  (이 rate에서 수십 초 규모 = PolyServe의 배정 반응 시간과 같은 차수).
- 아직 아무것도 서빙 안 한 인스턴스는 선호가 없어 무엇이든 받는다(콜드 스타트).

이것은 PolyServe가 "같은 배정이 2회 연속 계산되어야 적용"으로 얻는 안정화를,
이산 배정이 아니라 **연속량**으로 표현한 것이다. 부하가 오르면 선명해지고 내려가면
느슨해지며, 어떤 인스턴스도 예약되지 않는다 — 설계 원안이 "정적 파티션이 아니라
결과로 나온다"고 적은 성질 그대로다.

### 2026-07-26 — v8: 대칭성이 문제였다 (메커니즘 확증), 그리고 남은 격차

v1~v7의 chat 라우팅 집중도: 0.06 / — / 0.07 / 0.11 / 0.06 / 0.05 / 0.06.
**일곱 개의 서로 다른 순위 규칙이 모두 같은 답을 냈다.** 이 시점에서 원인이 순위
규칙이 아니라는 것이 분명해진다.

**구조적 원인**: 그때까지 넣은 모든 항 — headroom(room), harm, budget mismatch,
선호 기억 — 이 전부 **인스턴스에 대해 대칭**이다. 모든 인스턴스가 같은 클래스 혼합을
갖는 상태에서는 각 인스턴스가 모든 요청에게 똑같이 보이므로 어떤 클래스도 어느 쪽으로도
밀리지 않는다. 즉 **균일 혼합이 안정한 고정점**이고, 대칭인 항을 아무리 정교하게
만들어도 거기서 빠져나올 수 없다. v7의 선호 기억이 실패한 것도 같은 이유다 — 균일
혼합에서는 모든 인스턴스의 선호가 같은 값으로 수렴한다.

**수정**: 의도적으로 비대칭인 항 하나(`classShare`, 가중치 1.0). 그 클래스를 이미 더
많이 담고 있는 인스턴스가 그 클래스에게 더 매력적이다. 이것은 명시적 배정이 공급하는
양의 되먹임을 배정 없이 얻는 것이고, 균일 혼합을 **불안정**하게 만든다.

**결과**: chat 집중도 0.057 → **0.409**. 메커니즘은 확증됐다.

**그러나 attainment는 28.6으로 오히려 떨어졌다**(처리량도 5,733 tok/s). 왜인지는
분명하다: 이 항은 **어떤 클래스가 어느 인스턴스에 모이는지**만 정하고,
**그 인스턴스가 그 클래스의 수요를 감당할 수 있는지**는 보지 않는다. chat 10 req/s가
1대에 모이면 그 1대가 감당해야 하는데, 감당 못 하면 chat 전체가 나빠진다.
PolyServe는 관측 수요에서 tier별 서버 수를 유도하므로(`serverSecondsPerRequest` ×
도착률 → 비례 배분) 이 부분이 구조적으로 보장된다. FluidServe에는 대응물이 없다.

**다음 작업의 출발점**: 클래스 점유율 항에 **용량 제약**을 결합해야 한다. 형태는
"그 클래스가 이 인스턴스에서 쓰고 있는 서버-초가 그 클래스 수요의 몫을 넘지 않는 한
끌어당긴다"에 가깝고, 필요한 재료(클래스별 도착률, 요청당 서버-초 비용)는 PolyServe의
`tierRepartitioner`가 이미 계산하는 것과 같다. 즉 **PolyServe의 수요 추정을 파티션이
아니라 라우팅 점수의 한 항으로 쓰는 것**이 자연스러운 다음 단계다.

### 2026-07-26 — 동적 trace 결과와 작업 종료 상태

**결론: 고정 rate와 동적 trace 양쪽에서 PolyServe가 이겼다.**
동적 7분 trace 기준 등가중 attainment **68.5 대 38.2**, token goodput
**7,458 대 1,967 tok/s**. 상세는 EXP-22 문서.

동적 run이 비용값을 했다 — **고정 rate에서는 절대 나타나지 않는 결함**을 드러냈다.
한 인스턴스가 용량의 36배(투영 6,940만 토큰 대 cap 190만)까지 밀리고 iteration이
2,026ms인데도 계속 요청을 받았다. 세 항의 상호작용이 원인이다:

1. 이미 예산을 잃은 요청은 harm에 기여하지 않는다 — **의도된 설계**다(어차피 놓칠
   요청에 대한 추가 지연은 새 손실이 아니고, 그렇게 세면 무거운 작업을 흡수한
   인스턴스가 비싸 보여 분리가 무너진다).
2. 그 클래스를 많이 담은 인스턴스는 share 항이 끌어당긴다 — **의도된 설계**다
   (균일 혼합 고정점을 깨는 유일한 비대칭 항).
3. 이 둘을 막아야 할 여유공간 항이 **−1에서 포화**했다 — **버그**. "용량의 36배
   초과"와 "약간 초과"가 같은 점수가 된다.

셋 중 둘은 의도된 설계이고 버그는 하나뿐인데, 셋이 만나면 폭주가 된다. 포화 하한을
−50으로 내려 고쳤고 재실행에서 28.1 → 38.2로 올랐다.

**남은 격차의 원인(진단 완료, 미구현)**: 분리는 이제 일어나지만 **용량 배분과 맞지
않는다**. share 항은 어느 인스턴스에 모이는지만 정하고 그 인스턴스가 그 클래스의
수요를 감당하는지는 보지 않는다. PolyServe는 관측 수요에서 tier별 서버 수를
유도하므로(`serverSecondsPerRequest` × 도착률 → 비례 배분) 이 부분이 구조적으로
보장된다.

**다음 작업**: PolyServe의 `tierRepartitioner`가 이미 계산하는 수요 추정
(클래스별 도착률 × 요청당 서버-초)을 **파티션이 아니라 라우팅 점수의 한 항**으로
쓴다. 형태는 "이 클래스가 이 인스턴스에서 쓰는 서버-초가 그 클래스 수요의 몫을
넘지 않는 한 끌어당긴다". 코드는 그대로 재사용 가능하다.

**작업 종료 시 클러스터 상태**: 스케줄러 정책은 마지막 실행 arm(fluidserve),
게이트웨이 재시도 100ms/12s. PolyServe로 되돌리려면
`python3 ms_dev/scripts/set_scheduler_profiling.py --policy polyserve`
(게이트웨이 설정도 1000ms/5s로 함께 복구된다).

### 6.2 지금 문제의 정확한 위치 — 별개의 두 가지

동적 7분 trace 기준. **문제 A와 B는 원인이 다르므로 따로 고쳐야 한다.**

**A. 손해를 고르게 나눈다 (등가중 점수의 주손실)**

| | chat | dr | swe | 등가중 |
|---|---|---|---|---|
| PolyServe | **100** | **100** | 5.4 | 68.5 |
| FluidServe | 43.9 | 53.0 | **17.7** | 38.2 |

직접 원인은 **과부하 클래스가 다른 클래스의 인스턴스로 넘치는 것**이다. 점수 산수로
확인된다 — swe 인스턴스가 포화하면 `room`이 하한 −50에 붙어 점수가 −49.2가 되고,
chat 인스턴스는 `harm`이 30이어도 −29.7이라 **chat 인스턴스가 이긴다.**

내가 만든 tension이다: room 하한이 작으면(−1) 한 인스턴스가 폭주하고(용량 36배까지
밀린 사례), 크면(−50) 다른 클래스 인스턴스로 넘친다. PolyServe는 tier 소속이
점수 항이 아니라 **fallback에서도 안 풀리는 필터**라서 둘 다 안 겪는다.

강제 배치(force)가 결정의 **29%**였으므로 이 경로가 전체의 29%에 적용된다.

**B. fleet을 덜 쓴다 (처리량 결손)**

총 5,671 대 9,965 tok/s — 용량의 43%를 안 쓴다. 결정의 53%가 대기.
보수적인 층이 셋 쌓인 결과다:

1. **prefix cache 미반영** — 새 요청의 prefill 작업량을 프롬프트 전체로 charge.
   바이트 동일 replay라 실제론 대부분 캐시 히트. harm 과대 → 대기 과다. **최대 원인.**
2. 완료량을 1.65~2.5σ 낮춰 잡음
3. 예산의 90%까지만 씀

### 6.3 설계 한계인가, 튜닝 문제인가

| 층 | 판정 |
|---|---|
| 신호·추정 (C1/C2/C3) | ✅ **검증됨.** 디코드 법칙 R²=0.952 + 독립 적합과 교차검증, 혼합 step 모델 오차 4~19%, **라이브 엔진 대조 교정계수 0.9998** |
| 결정 규칙 (C4) | ⚠️ **컴포넌트 하나가 빠져 있음** |
| 대기 판정 (C5/C7) | ⚠️ 과보수, 원인은 위 B-1 |
| 파라미터 | ⚠️ 20개, 미튜닝, 반복 측정 없음 |

**빠진 컴포넌트**: 요청 단위 greedy 점수로는 안정적인 분리를 만들 수 없다.
대칭 항만으로는 균일 혼합 고정점을 못 벗어나고(7개 구성으로 실증), 비대칭 항을
넣으면 용량 앵커가 없어 폭주한다. PolyServe는 **수요에서 배정을 계산해 붙잡고
있기 때문에** 둘 다 피한다. 원안의 C3/C4는 용량을 인스턴스 단위로만 다루고,
**클래스 수요 대 인스턴스 용량**을 맞추는 부분이 원안에도 구현에도 없다.

결론: "근본적으로 틀렸다"고 하기엔 추정 계층이 잘 맞고, "튜닝만 하면 된다"고 하기엔
대칭성 문제가 구조적이다. 정확히는 **빠진 컴포넌트 1개 + 미튜닝 파라미터 20개**다.

### 6.4 ⭐ 검증된 사실 — PolyServe의 재분할은 이 워크로드에서 아무 일도 안 한다

`analysis_scripts/request_level/exp22_polyserve_allocation.py`로 재현 가능.
동적 7분 run의 계측:

```
tier  25ms(swe) : t=48s에 2대로 적용된 뒤 459 샘플 동안 변화 0회
tier  50ms(chat): t=48s에 1대,               변화 0회
tier 100ms(dr)  : t=48s에 1대,               변화 0회

같은 기간 관측 수요(서버-초/초)
  swe  6.593 → 55.791  (8.5배 변동)
  chat 0.201 →  1.972  (9.8배)
  dr   0.911 →  5.418  (5.9배)
```

**수요가 6~10배 흔들리고 믹스가 A→C→B→A로 바뀌는 동안 배정은 한 번도 안 움직였다.**

구조적 이유: 인스턴스 4대 + 클래스 3개 + **tier당 최소 1대 보장**이면 3대가 이미
묶이고 자유로운 건 1대뿐이다. 도달 가능한 배정은 `{(2,1,1), (1,2,1), (1,1,2)}`
**3가지뿐**이고, swe의 요청당 서버-초 비용이 나머지의 7~15배라 그 1대는 항상
swe가 가져간다. 세 믹스 각각에 배정 알고리즘을 돌려도 전부 (2,1,1)이다.

| 믹스 (30 req/s) | 수요 D (인스턴스 환산) | 비례 배분 | 최소1 보장 후 |
|---|---|---|---|
| A (1:1:1) | swe 22.1 / dr 3.09 / chat 1.46 | 3/1/0 | **2/1/1** |
| B (6:3:1) | swe 6.63 / dr 2.78 / chat 2.63 | 2/1/1 | **2/1/1** |
| C (1:1:3) | swe 39.8 / dr 1.85 / chat 0.88 | 4/0/0 | **2/1/1** |

**따라서 PolyServe의 68.5는 동적 적응의 성능이 아니라 고정 파티션
swe 2 / chat 1 / dr 1의 성능이다.** 1시간으로 늘려도 이건 안 바뀐다.
"반응 속도로 이긴다"는 가설은 **비교 대상이 없어서** 성립할 수 없다.

### 6.5 그럼에도 그 고정 배정이 등가중 채점에서는 거의 최적이다

mix A에서 chat은 작업량의 5.5%인데 fleet의 25%를 받는다. 낭비로 보이지만,
그 1대를 swe로 옮겨도 swe는 11배 초과가 6.7배 초과가 될 뿐 attainment는 0 근처에
머물고, chat은 100%에서 떨어진다.

```
(100 + 100 + 5) / 3 = 68     대     (70 + 70 + 8) / 3 = 49
```

**감당 가능한 클래스를 완전히 지키고 감당 불가능한 클래스를 버리는 것이 등가중
채점의 최적 전략이고, 최소 1대 보장이 우연히 그것을 구현하고 있다.**
PolyServe의 강점은 "적응"이 아니라 **"두 클래스를 100%로 완전히 격리하는 것"**이다.

### 6.6 FluidServe가 이길 수 있는 경로 (크기 순)

```
필요조건  chat·dr을 PolyServe 수준으로 격리 (43.9/53.0 → 95~100)
          = 강제 배치 경로에서 다른 클래스 인스턴스로 넘치지 않게 하는 것

① swe의 E2E 예산 추적       측정됨: 17.7 대 5.4 (3.3배)          약 +4점
   PolyServe는 swe를 "토큰당 25ms" 순간 임계값으로 다루는데 실제 채점은
   E2E 30초(= 토큰당 57.7ms)다. 그래서 admission이 전부 "steady state"
   사유로 탈락해 무력화됐다(EXP-21). FluidServe는 남은 E2E 예산을 요청마다
   추적하므로 30초 안에 들어올 수 있는 요청을 실제로 구분한다.

   산수: (100 + 100 + 17.7)/3 = 72.6  대  PolyServe 68.5

② 서버 단위보다 잘게 배분     mix B(chat 60%)에서 유효, 1시간 중 15분
   PolyServe는 정수 대수만 줄 수 있다. mix B에서 chat 수요 2.63인데 1대를
   받아 2.6배 초과인데도, (1,2,1)로 가려면 swe를 1대로 줄여야 해서 못 간다.
   FluidServe는 chat 1.4대 + swe 1.8대 같은 배분을 만들 수 있다.

③ 최소 1대 보장 없음          mix C에서 유효하나 작고 위험
   chat이 작업량 2.1%인데 1대를 잡는다. 다만 그 1대를 swe에 줘도 swe는
   못 살고, chat·dr을 한 대에 몰았다가 둘 다 100%를 놓치면 손해다.
   이길 지점이 아니라 조심할 지점.

④ "동적 적응" 자체            ✗ 비교 대상 없음 (§6.4)
```

**1시간 trace가 7분보다 유리한 점**: 콜드 스타트 전이(60초 warmup)가 전체의
14% → 1.7%로 줄고, 선호 EWMA(인스턴스당 ~150 dispatch)와 classShare가 충분히
수렴한다. 지금 38.2에는 시작 전이 오염이 섞여 있다.

**불리한 점**: 믹스 전환 4회마다 클래스 그룹을 다시 형성해야 하는데,
PolyServe는 어차피 안 움직이므로 전환 비용이 0이다. 여기선 PolyServe가 유리하다.

### 6.7 다음 작업 순서 (사용자 확인됨)

```
1. prefix cache 반영
   새 요청의 prefill 작업량을 프롬프트 전체가 아니라 실제 미계산분으로.

2. 강제 배치 경로를 claimed 집합으로 제한
   클래스별 수요 D_c(= 도착률 × 요청당 서버-초, tierRepartitioner가 이미 계산)에서
   k_c = ceil(D_c) 대를 정하고, claimed_c = 그 클래스를 가장 많이 담은 상위 k_c 대.
   feasible한 곳이 없을 때 claimed_c **안에서만** 강제 배치.
   → chat·dr 오염 차단. §6.6의 필요조건. 산수상 가장 큰 이득.

3. share 항에 용량 정지점
   share = (같은 클래스 비율) × max(0, 1 − 그 클래스가 이 인스턴스에서 쓰는 용량 비율)
   → 폭주 방지를 room 하한(−50)에만 의존하지 않게 됨. 하한을 완화할 수 있어
     2번의 오염 압력도 함께 줄어든다.

4. warm start + 1시간 trace로 2-arm 비교
   저부하 10분 preload 후 측정 시작. 구현은 build_dynamic_mix_trace.py의
   warmup 구간을 60초 → 10분으로 늘리고 분석의 WARMUP_S를 맞추면 된다.
   주의 (a) prefix cache/page cache도 데워져 EXP-14/17/21과 절대 수치 비교 불가,
        (b) 그래서 1번을 먼저 고쳐야 함 — warm start는 prefix 히트율을 더 올려
            현재의 미반영 결함을 더 크게 만든다,
        (c) preload와 측정 사이에 엔진 재시작이 들어가면 안 됨.
   진단 가치: 격차가 크게 줄면 시작 전이가 원인, 안 줄면 §6.2-A가 정상상태의 성질.
```

**먼저 볼 만한 것**: 1시간 trace 전에 **mix B만 고정 rate로 15분** 돌려보는 것.
chat 60% 구간에서 PolyServe가 chat에 1대만 주는 게 실제로 얼마나 손해인지,
그게 §6.6-②가 파고들 수 있는 크기인지를 짧게 확인할 수 있다.

있고 나머지 세 대는 완전히 유휴 상태로 27분을 보냈다.** 같은 조건의 PolyServe run은
506초 만에 끝났는데 FluidServe run은 2,080초가 걸렸고, 23,080건 중 12,470건(54%)이
`server terminated during streaming`으로 끝났다 — 클라이언트가 끝까지 답을 못 받은
것이다. PolyServe는 같은 항목이 5,114건(22%)이다.

즉 §6.2에서 "손해를 고르게 나눈다(문제 A)"와 "fleet을 덜 쓴다(문제 B)"로 나눠
적은 두 증상은 **하나의 사건의 두 얼굴**이었다. 결정의 53%가 대기였던 것도, 세 대가
놀고 있는 상태에서 측정된 값이므로 "새 요청의 prefill을 과대 charge해서 보수적"
때문이 아니라 **한 대에 몰아넣고 그 한 대가 감당 못 해서 전부 막힌 것**이다.

또한 §5 마지막의 `roomFloor` 수정(커밋 `eaf9d75`, 2026-07-26 17:24)은 이 run
(01:24)보다 **뒤에** 있다. 즉 **동적 trace에서 roomFloor 수정 이후의 측정은 아직
없다.** §6의 "38.2" 수치는 그 수정 전 바이너리의 결과로 읽어야 한다.

### 7.2 붕괴가 일어나는 산수

점수는
`score = room + 1.0·share − α·(harm + 3·mismatch)`, `room = clamp(headroom/capMem, −50, 1)`.

과부하 구간에서는 **모든 인스턴스가 infeasible**이므로 순위를 정하는 것은 남은 항들이다.
그때 `room`은 전부 크게 음수라 인스턴스 사이 차이가 압축되는 반면, `share`는 [0,1]에
가중치 1로 붙는다. 그리고 `share`는 **양의 되먹임**이다 — 그 클래스를 이미 더 담은
인스턴스가 더 매력적이므로, 한 번 기울면 계속 그쪽으로 간다. 용량 정지점이 없으므로
그 인스턴스가 감당 가능한지는 보지 않는다. 엔진에 한 번 배정된 요청은 회수할 수
없으므로(migration off) 이 되먹임의 결과는 되돌릴 수 없다.

여기에 두 번째 되먹임이 겹친다. 인스턴스의 용량 상한 `capKv`는 그 위에 있는 요청들의
**잔여 예산**에서 나온 `tightestAllowance`로 계산된다. 요청이 늦어지면 잔여 예산이
줄고 → allowance가 줄고 → capKv가 줄고 → feasible이 아니게 되고 → 더 대기하거나 강제
배치되고 → 더 늦어진다. **늦음이 용량을 깎고 깎인 용량이 다시 늦음을 키우는 구조**다.

### 7.3 재설계 — 결정 사다리를 세 개의 단일 양으로 분리한다

가중합 하나로 모든 상황을 정렬하려던 것이 문제였다. 각 단계가 **하나의 양**만 쓰도록
분리하면 가중치가 사라지고, 용량 제약이 선호보다 항상 앞선다.

```
F = { 예산 게이트와 메모리 한도 안에서 이 요청을 받을 수 있는 인스턴스 }

F ≠ ∅          →  ROUTE.  F 안에서 같은 클래스 점유율(share)이 가장 높은 곳,
                          동률이면 여유공간(room)이 큰 곳.
F = ∅, 더 기다릴 수 있음 →  PEND.  게이트웨이가 계속 들고 있는다.
F = ∅, 못 기다림
    ├ 지금 배치해도 자기 SLO를 못 지킴  →  SHED. 즉시 거절한다.
    └ 자기 SLO는 지킬 수 있음           →  FORCE. harm이 최소인 곳에 배치.
```

**(1) 용량 게이트를 잔여 예산이 아니라 공칭(nominal) 예산으로 계산한다.**
`capKv`를 정하는 allowance는 이제 "그 인스턴스에 있는, 아직 가망이 있는 요청들의
**클래스 공칭 예산** 중 최솟값"이다. 잔여 예산은 인스턴스 자신의 지연이 커질수록
작아지는 양이라 §7.2의 두 번째 되먹임을 만든다. 공칭 예산은 클래스의 성질이지
인스턴스 이력의 함수가 아니므로 게이트가 안정하다. 잔여 예산은 **그 요청을 계속
서비스할 가치가 있는지(가망 없음 판정)와 SHED 판정**에만 쓴다 — 원래 그 역할이다.

**(2) share를 feasible 집합 안에서만 적용한다 = 이것이 용량 정지점이다.**
§6.7의 3번("share 항에 용량 정지점")을 별도 항으로 만들 필요가 없다. 선호가
용량 제약을 이길 수 없게 만들면 폭주 자체가 불가능하다. 이 한 줄로
`shareWeight`, `roomFloor`, `mismatch` 항과 그 가중치가 동시에 없어진다.

**(3) infeasible일 때의 순위는 harm 하나로 정한다.**
harm은 "아직 예산이 남은 incumbent들이 잃는 슬랙"이다. 이미 예산을 잃은 요청은
harm에 기여하지 않으므로, 이미 무너진 인스턴스의 harm은 0에 가깝고 깨끗한
인스턴스의 harm은 크다. 따라서 **최소 harm = 이미 그 클래스로 포화된 인스턴스**가
되어, 과부하는 아직 살아 있는 요청을 가장 적게 죽이는 곳으로 간다. §6.7의 2번
(claimed 집합으로 강제 배치 제한)이 노리던 효과를 이미 정의돼 있는 양으로 얻는다.
파티션도, 클래스별 서버 수 계산도 필요 없다.

**(4) SHED — 이것이 없으면 (3)이 다시 폭주한다.**
(3)만 있으면 과부하 요청은 계속 같은 인스턴스로 가고 대기열이 무한히 자란다.
경계를 만드는 것은 거절이다. 거절 조건은 **"지금 가장 좋은 자리에 놓아도 자기
SLO를 못 지킨다"**이다.

- decode 예산 클래스(chat/dr): `대기시간 + 예상 prefill > TTFT 예산`이거나
  배치 후 예측 평균 step이 그 클래스의 per-token 예산을 넘으면 위반 확정.
- E2E 클래스(swe): `대기시간 + prefill + 예상출력 × 예측 step > E2E 예산`이면 위반 확정.

이것이 PolyServe의 admission과 다른 점: PolyServe는 **점유율 임계값**으로 거절한다
(그 요청이 성공했을지와 무관하다). FluidServe는 **그 요청의 예상 결과**로 거절한다.
그래서 거절은 "이미 잃은 요청을 빨리 놓아주어 아직 지킬 수 있는 요청의 자리를
비우는" 행동이 된다.

**(5) 대기 한도를 TTFT 예산에서 직접 유도한다.**
기존 `maxPendFraction=0.25`(TTFT 예산의 25%까지만 대기)의 근거는 "대기가 끝날 때쯤이면
어차피 놓친 요청"이었는데, chat의 채점 규칙은 `TTFT ≤ 5s AND 평균 TBT ≤ 50ms`이므로
4.5초를 기다렸다가 즉시 첫 토큰이 나오면 **위반이 아니다.** 근거가 틀렸으므로
상한을 없애고 `대기한도 = TTFT예산 − 예상 prefill − 여유`만 남긴다. 이러면
게이트웨이의 12초 보유 상한도 스케줄러 판단보다 먼저 걸리지 않도록 올려야 한다.

### 7.5 §6.7의 순서를 바꾸는 근거

1. **prefix cache 반영은 뒤로 미룬다.** 근거였던 "결정의 53%가 대기"는 §7.1에서
   본 대로 세 대가 유휴인 상태에서 나온 값이라 원인 귀속이 틀렸다. 그리고 새 요청의
   한계 prefill 비용은 chat 프롬프트(1,448토큰)면 청크 1개, 즉 지평 100 step 중 1
   step이라 예측 평균 step에 약 1ms를 더한다 — 50ms 예산에서 무시할 크기다. 22k
   프롬프트인 swe만 3청크(≈15ms)로 유의미한데, swe는 대부분 SHED 대상이다.
   재설계 후 다시 측정해서 대기율이 여전히 높으면 그때 손댄다.
2. **claimed 집합(2번)은 §7.3-(3)이 대체한다.** 별도 구현하지 않는다.
3. **share 정지점(3번)은 §7.3-(2)가 대체한다.** 별도 항이 아니라 구조로 들어간다.
4. **warm start + 1시간 trace(4번)는 그대로 유지**하되, 그 앞에 rate sweep을 넣는다
   (§7.6).

### 7.6 실험 설계 — 거절이 있는 정책은 rate를 올려야 차이가 보인다

지금까지의 비교는 단일 rate(1800 rpm) 또는 7분 trace 하나였다. 이 조건에서는
PolyServe의 admission이 거의 발동하지 않는다 — 동적 run에서 PolyServe의 거절은
23,080건 중 **20건**뿐이었다. 즉 지금 비교는 "거절이 없는 PolyServe" 대
"거절이 없는 FluidServe"였고, 두 정책의 admission 계층 차이는 측정된 적이 없다.

**설계**: 고정 rate sweep(예: 1200 / 1800 / 2400 / 3000 / 3600 rpm)을 두 arm에
대해 돌린다. 채점 분모는 offered(도착한 전부, 거절·에러·미완은 위반)로 고정한다.
이렇게 하면
- 낮은 rate: 두 정책 모두 거의 다 지킨다 (차이 없음이 정상)
- 중간 rate: FluidServe가 "지킬 수 있는 부분집합"을 골라 지키는 이득이 나타난다
- 높은 rate: PolyServe는 점유율 임계값으로 거절하거나 대기열에 쌓아 전부 놓치고,
  FluidServe는 자기 SLO 예측으로 거절해 남은 요청을 지킨다

가로축이 rate인 attainment 곡선은 **어느 지점부터 갈라지는지**를 보여주므로,
단일 조건 비교보다 주장이 강하고 재현하기도 쉽다. 이것이 사용자가 지적한
"실험 자체를 유리하면서 더 현실적으로 설계"에 해당한다 — 현실의 서빙 시스템은
과부하에서 요청을 버리지 않고 늦게 주는 쪽이 더 나쁘고(클라이언트는 타임아웃까지
자원을 붙잡는다), offered 분모는 그 비용을 정직하게 반영한다.

## 8. 2026-07-27 — ⭐ FluidServe의 모든 이전 측정이 게이트웨이 워커 5개에 막혀 있었다

### 8.1 증상

v10(1800 rpm, 2분)에서 클래스별로 무엇이 실패하는지 분해했더니 예상과 달랐다.

| | chat TTFT p50 | chat TTFT 충족 | chat TBT p50 | chat TBT 충족 | 완료율 |
|---|---|---|---|---|---|
| **FluidServe v10** | **20.3초** | 16.9% | 20.3ms | 52.2% | 44.8% |
| PolyServe (EXP-21, 같은 rate) | **0.14초** | 100% | 10.9ms | 97.9% | 100% |

**디코드 품질은 문제가 아니었다.** chat의 TBT는 20ms로 예산 50ms 안에 넉넉히 들어
간다. 실패는 전부 **첫 토큰까지 20초**에서 온다. 30초 간격으로 보면 TTFT가 4.2초 →
32.5초 → 54.3초로 자라고, t=150초 이후에는 chat 요청이 첫 토큰을 아예 못 받는다.

### 8.2 어디서 20초가 생기는지 좁혀 들어간 과정

시간이 어디서 사라지는지 후보를 하나씩 지웠다.

1. **클라이언트 큐잉인가** → 아니다. `start_time − job_submit_time`의 중앙값이
   0.1ms다. 클라이언트는 즉시 발신한다.
2. **스케줄러의 보유(PEND)인가** → 아니다. pend 결정은 8,246건인데 재시도 간격이
   100ms이므로 누적 보유 시간은 825초, 240초 run에서 동시 보유 평균 3.4건이다.
   게이트웨이 카운터도 818건이 평균 1,031ms 기다렸다고 보고한다.
3. **스케줄러가 느린가** → 아니다. `request_full_mode_schedule_duration_milliseconds`
   를 직접 긁으면 **호출당 0.109ms**다(3,607호출에 392ms).
4. **엔진 대기열인가** → 아니다. 엔진이 보고한 최대 대기열은 23건, running은
   인스턴스당 14~56건이다. Little의 법칙으로 30 req/s × 20초 = 600건이 어딘가에
   있어야 하는데 엔진에는 130건뿐이다.
5. **그럼 게이트웨이다** → `gateway_pending_requests`가 **515에 고정**되어 있었다.
   PolyServe는 같은 계열이 0~2다.

### 8.3 원인

게이트웨이는 도착한 요청을 버퍼 큐에 넣고 **고정된 수의 워커 고루틴**이 꺼내
처리한다(`--max-queue-size 512`, `--wait-queue-threads 5`). 워커는 그 요청이
엔드포인트를 받을 때까지 붙잡혀 있다 — 즉 `SchedulerClient.Get()`의 보유-재시도
루프 안에서 대기한다.

- 즉답하는 정책(PolyServe 등): 워커 점유 시간이 1ms 미만이므로 5개로 초당 수천 건을
  처리한다. 이 파라미터는 보이지도 않는다.
- **배치를 미루는 정책(FluidServe)**: 워커가 보유 시간 내내 묶인다. 워커가 5개이므로
  **동시에 보유할 수 있는 요청이 5건**이고, 나머지는 512칸 버퍼 큐에 쌓인다. 큐가
  차면 핸들러는 `--wait-queue-interval`(1초) 자고 다시 시도한다.

`gateway_pending_requests = 큐 길이 + 바쁜 워커 수`가 515에 붙어 있었다는 것은
**큐가 내내 가득 차 있었다**는 뜻이다. 요청은 게이트웨이 문 앞에서 수십 초를
기다렸고, 그 시간이 그대로 TTFT가 됐다. 그동안 엔진은 용량의 1/3만 쓰고
스케줄러는 0.1ms에 답하고 있었다.

### 8.4 이것이 무엇을 무효화하는가

**v1부터 v10까지의 FluidServe 측정 전부가 이 제약 아래에 있었다.** 특히:

- "결정의 53%가 대기" → 대기가 많았던 게 아니라, 대기 한 건이 워커 하나를 묶어
  전체 유입을 5건으로 제한했다.
- "fleet을 43% 덜 쓴다" → 스케줄러가 보수적이어서가 아니라 요청이 게이트웨이를
  통과하지 못해서다.
- "PolyServe가 이겼다" → 성립하지 않는다. 한쪽 arm만 게이트웨이 설정과 상호작용해
  유입이 막혀 있었으므로 두 정책을 비교한 것이 아니다.

§7.1에서 본 동적 run의 붕괴(한 엔진에 5,569건)는 별개의 실제 결함이었고 v9에서
고쳤지만, 그 뒤 남은 격차의 해석은 여기서 다시 세워야 한다.

### 8.5 수정

```
--wait-queue-threads  5   → 4096
--max-queue-size      512 → 16384
```

워커는 네트워크를 기다리는 것이지 계산하는 것이 아니므로, 풀 크기는 코어 수가 아니라
**동시에 떠 있을 수 있는 요청 수**에 맞춘다. Go 고루틴 4,096개의 비용은 무시할 수 있다.

**두 arm 모두에 적용한다.** PolyServe는 이 계열이 0이므로 변화가 없지만, 한쪽에만
적용하면 그 자체가 arm 간 설정 차이가 된다.

함께 바꾼 것: FluidServe의 재시도 간격을 100ms → **500ms**로 올렸다.
`--cms-pull-status-interval-ms`가 500ms이므로 결정이 읽는 인스턴스 상태는 500ms마다
갱신된다. 그보다 자주 다시 결정해도 **다른 답이 나올 수 없고** 스케줄링 호출만 는다.
재결정 주기는 상태 갱신 주기와 같아야 한다.

### 8.6 왜 이걸 이제야 찾았나 (같은 실수를 반복하지 않기 위해)

이 결함은 요청 단위 지표에서 "성능이 나쁨"으로만 보인다. attainment는 낮고 goodput은
낮은데, 그 원인이 정책인지 배관인지 구분해 주는 값이 없다. 실제로 찾아낸 것은
**클래스별로 어느 SLO 규칙이 깨지는지 분해**한 순간이었다 — TBT는 멀쩡한데 TTFT만
20초라는 조합은 "라우팅이 나쁘다"로 설명되지 않는다.

그래서 표준 산출물에 넣는다:

- 클래스별 **TTFT 충족률과 TBT 충족률을 따로** 보고한다(합쳐서 attainment 하나로
  내지 않는다).
- `gateway_pending_requests` / `gateway_current_requests`,
  `request_full_mode_schedule_duration_milliseconds`를 수집 목록에 넣는다.
- 엔진 점유(`engine_occupancy.py`)와 나란히 본다. **엔진은 놀고 스케줄러는 빠른데
  지연이 크면, 남는 곳은 배관뿐이다.**

## 9. 2026-07-27 — 배관을 고친 뒤의 결과: 두 지표 모두에서 앞선다

§8의 게이트웨이 워커 풀을 고치고 나서 v11 → v12 두 번의 수정으로 목표에 도달했다.
전부 1800 rpm 고정 rate, 채점 분모는 offered다.

| arm | 등가중 | chat | dr | swe | token goodput |
|---|---|---|---|---|---|
| v10 (배관 막힘) | 41.2 | 37.7 | 47.0 | 39.0 | 2,384 |
| PolyServe (8분) | 68.5 | 100.0 | 100.0 | 5.5 | 7,361 |
| v11 (배관 수정) | 65.1 | 90.4 | 82.7 | 22.2 | 7,373 |
| **v12** | **72.1** | **100.0** | 98.4 | **17.9** | **8,047** |

### 9.1 v11 → v12에서 고친 것

v11에서 남은 결손은 **지각이 아니라 거절**이었다. chat은 거절 5.6% + 지각 4.4%,
dr은 거절 14.6% + 지각 3%다. dr의 예산은 100ms인데 fleet은 32ms로 돌고 있었으므로
dr이 거절될 이유가 없어야 한다.

원인은 v10에서 넣은 incumbent 보호 조건의 적용 범위였다. 인스턴스별 최소 잔여
허용치가 28/37/42/51ms인데 실측 iteration은 32ms였다. 즉 **잔여 허용치가 28ms인
요청 하나가, 이미 자기가 못 지키고 있는 속도로 인스턴스 전체를 묶었다.** 그
인스턴스는 admissible 용량의 1/6만 쓰면서 dr을 거절했다.

보호 조건의 취지는 **위반을 새로 만들지 않는 것**이다. 잔여 허용치가 지금 인스턴스가
내고 있는 속도보다 낮은 요청은 이미 위반 중이고, 새 요청을 거절해도 구제되지 않는다 —
그 요청이 속한 배치는 지금 속도로 계속 돌고, 배치는 그 요청들이 끝나야 줄어든다.
그래서 그런 요청을 한도 계산에서 제외했다(harm 계산은 이미 같은 기준이었다).

### 9.2 왜 이기는가 — 정적 파티션이 표현할 수 없는 상태

PolyServe를 1800 rpm에서 8분 돌리고 엔진 점유를 펴 보면, 인스턴스 두 대가 chat/dr을
**KV 4~11%, iteration 11~16ms**로 서비스하고(예산 50/100ms) 나머지 두 대는 KV 100%에
대기열 857건을 쌓아 swe를 2.9~5.5%만 지킨다. **fleet 메모리의 절반이, 이미 100%인
클래스를 위해 놀고 있다.**

할당 단위가 서버 한 대이므로 "chat 인스턴스가 안 쓰는 여유를 swe에 조금 준다"를
표현할 수 없다. tier당 최소 1대 보장과 정수 배분이 그것을 강제한다.

FluidServe의 할당 단위는 서버가 아니라 **예산 안에서 허용되는 KV**다. v12에서 chat의
실측 TBT는 15.0ms이고 예산은 50ms다 — 그 여유만큼 swe가 같은 인스턴스에 올라가 있다.
이것이 3.3배(17.9% 대 5.5%)의 출처다.

이것을 가능하게 하는 세 가지가 모두 필요했고, 셋 다 설계에 이미 있었다:

1. **feasibility 게이트**가 chat 인스턴스를 45ms 안에 유지한다.
2. **누적 예산** 표현. 11~15ms로 돌던 chat 요청은 예산을 앞당겨 벌어놨으므로 잔여
   허용치가 공칭 50ms보다 크고, 따라서 incumbent 보호가 swe를 막지 않는다.
   순간 임계값으로 SLO를 표현했다면 이 여유를 볼 수 없다.
3. **SHED**가 swe 총 유입을 용량에 맞춰 자른다. 이것이 857건짜리 대기열을 만들지
   않는 이유다. 거절의 65.6%가 swe다.

### 9.3 아직 확정이 아닌 것

- v12는 2분 run, PolyServe는 8분 run이다. 도착 수가 8,107 대 10,477로 다르고
  반복 측정이 없다.
- 그래서 **EXP-23 rate sweep**(두 arm, rate 6점, rate당 8분, 조건마다 엔진 콜드
  재시작)을 돌린다. rate에 따른 곡선은 단일 조건 비교보다 훨씬 강한 근거다.
- 스케줄러 호출 비용이 **호출당 2.05ms**로 PolyServe(0.109ms)의 19배다. 보유 중인
  요청이 재시도마다 이 경로를 다시 타므로, 더 높은 rate에서는 제어평면 자체가
  제약이 될 수 있다. 인스턴스 상태는 500ms마다만 갱신되므로, 요청과 무관한 부분
  (reconcile + flux 구성)을 상태 갱신 단위로 캐시하면 대부분 없앨 수 있다.
  필요해지면 그때 한다.

| 버전 | 고친 것 | 측정된 효과 |
|---|---|---|

### 10.1 제어평면이 병목이 될 수 있다는 것 자체가 발견이다

배치를 미루는 정책은 **보유 중인 요청이 재시도마다 결정 경로를 다시 탄다.**
그래서 스케줄링 호출률이 도착률의 배수가 된다. 3000 rpm에서 호출률이 초당 436회에
달했고, 호출당 3.9ms(PolyServe는 0.109ms)이며 스케줄링은 클러스터 뷰 락 아래에서
직렬화되므로 초당 1.7초 분량의 일이 제시된다 — 포화다. 그러면 요청은 게이트웨이에서
스케줄러를 기다리고, **엔진은 KV 60%에 대기열 없이 놀고 있는데 TTFT가 커진다.**

이것은 "라우팅 정책의 성능"이 아니라 배관이고, 요청 단위 지표만 보면
"높은 rate에서 정책이 무너진다"로 잘못 읽힌다. 구분하려면 반드시
`request_full_mode_schedule_duration_milliseconds`와 엔진 점유를 같이 봐야 한다.

두 가지가 곱해진 결과였다:
1. 결정 자체가 무겁다(인스턴스마다 레지스트리 대조 + flux 구성) → **뷰 캐시**로 해결.
   뷰가 의존하는 것은 엔진이 마지막에 보고한 상태와 그 뒤 이 스케줄러가 배치한 것
   둘뿐이므로, 둘 다 안 변하면 재사용한다. 배치가 뷰를 무효화해야 한다 — 아니면 두
   요청이 서로를 모른 채 같은 용량을 두 번 배정받는다.
2. 가망 없는 요청을 오래 붙들고 있었다 → **대기 마감을 실제 속도로**. 이전에는
   "빈 엔진에서라면 가능한가"를 물었는데, 부하가 용량의 2배인 구간에서 fleet은
   비지 않으므로 그 대기는 전부 낭비되고 끝에 가서 거절된다.

### 10.2 남은 결함 — 보정계수가 도착하는 prefill을 통째로 흡수한다

600 rpm 8분 run에서 보정계수가 1.00 → **1.48**로 꾸준히 올라가고, 거절이 그에
따라 늘어난다(누적 35건 → 598건). fleet이 명백히 한가한데(chat·dr 100%) swe를
12% 거절한다.

원인은 예측이 **지금 큐에 있는 prefill만** 본다는 것이다. `f.meanStep`은 상태
샘플 시점의 `pendingPrefill`로 계산되는데 그 값은 대개 0이다. 실제로는 구간 동안
prefill이 도착했다 처리되므로 실측이 예측보다 크고, 보정계수가 그 차이를 **전체
평균 step에 곱하는 방식으로** 흡수한다. 그러면 KV 항과 배치크기 항까지 같이
부풀어 게이트가 필요 이상으로 조여진다.

**다음 수정(미구현)**: 지평 동안 **도착할** prefill을 투영에 넣는다. 재료는 이미
있다 — 인스턴스별 배치율(레지스트리가 안다)과 prefill 실측 비율(§10 v13에서 도입,
600 rpm에서 0.29로 수렴). 그러면 보정계수는 1 근처에 머물고 "모델이 빠뜨린 항"이
아니라 원래 목적인 하드웨어 드리프트만 추적한다. 이것이 C3의 flux 개념을 디코드
증가분뿐 아니라 **prefill 유입에도** 적용하는 것이고, 원안에 없던 부분이다.

4. 반복 측정. 지금까지 조건당 1회뿐이다. 1800 rpm은 세 번 측정했고 그 산포가

## 11. 2026-07-27 — v16: 도착 prefill을 투영에 넣는다 (§10.2의 수정)

### 11.1 무엇이 틀렸었나

예측이 **순간**을 기술하는데 결정은 **구간**을 필요로 했다. 엔진은 prefill 큐를
상태 갱신 주기(500ms) 안에서 다 비우므로, 샘플링 순간에 읽은 큐 길이는 대개 0에
가깝다. 그런데 지평(100 iteration ≈ 2.5초) 동안 엔진은 그 사이에 도착한 프롬프트에
매 iteration의 실질적인 몫을 쓴다.

이걸 빼놓은 것이 단순히 "예측이 낮다"로 끝나지 않았다. **보정계수가 그 차이를 평균
iteration 전체에 곱하는 방식으로 흡수**하는데, 그러면

- 고정항 `c0`, KV항 `c_kv·M`, 배치크기항 `c_n·n`이 **전부** 같이 부풀고,
- 용량 역산 `maxKvForAllowance`는 예산을 보정계수로 **나누므로**
  (`allowanceMs /= corr`), 허용 점유량이 빠진 prefill이 정당화하는 것보다 훨씬
  많이 줄어든다.

600 rpm 8분 run에서 보정계수가 1.00 → **1.48**로 올랐다. 그때 fleet은 chat·dr이
100%이고 iteration이 13.5ms(예산 50/100ms)였는데, 거절 누적이 35 → **598**로
따라 올랐다. 부하가 클수록 도착 prefill이 많아지므로 왜곡도 커진다 — 1800에서
3600 rpm 사이에 chat이 100 → 78.6 → 70.4 → 53.0으로 무너지는 것이 그 결과다.

### 11.2 수정

이미 측정되고 있는 두 값으로 도착량을 투영한다.

```
horizonMs      = horizon(=100 step) × 그 인스턴스가 내고 있는 실측 iteration 시간
arrivingPrefill = 배치율[tok/ms] × horizonMs × prefill 실측 비율
effectivePrefill = 엔진이 보고한 큐 + arrivingPrefill
```

- **배치율**: 레지스트리가 인스턴스별로 보낸 프롬프트 토큰을 누적하고 있고,
  상태 구간마다 `토큰/경과시간`으로 EWMA한다(가중치 0.05, 정착 약 10초).
- **prefill 실측 비율**: v13에서 도입. 600 rpm에서 0.29로 수렴.
- **실측 iteration 시간**: 지평이 iteration 단위이므로 이걸로 시간 단위로 바꾼다.
  측정 전에는 디코드 법칙으로 대체하는데, 이는 지속시간을 과소평가 → 도착량 과소
  → **새 프로세스가 덜 받는 게 아니라 더 받는 쪽**으로 시작한다.

상한 clamp를 두지 않았다. 용량 모델이 이미 지평 중 prefill을 실은 iteration의
비율을 1로 자르기 때문이다 — 아무리 많이 도착해도 엔진은 iteration당 청크 하나
이상을 흡수할 수 없다.

`effectivePrefill`은 `meanStep`, `capKv`, `evaluate`의 배치 후 상태, TTFT 추정의
대기열 항 **전부**에 쓴다. 한 인스턴스에 대해 서로 다른 두 개의 prefill 개념이
돌아다니지 않게 하려는 것이다.

### 11.3 이것이 설계 원안과의 관계

C3의 flux 개념을 **prefill 유입에도** 적용한 것이다. 원안은 flux를 디코드 증가분
(`n·k`, 산수가 정확하다)에만 적용했다. prefill은 측정된 도착률이 있어야 해서
빠져 있었고, 그 측정이 v13에서 생겼으므로 이제 넣을 수 있다.

### 11.4 실행 전에 적어두는 예상

600 / 1800 / 3000 rpm 세 점을 8분씩 다시 돌린다(`exp23g`).

| 지표 | v15 | 기대 | 아니면 무엇을 뜻하나 |
|---|---|---|---|
| 보정계수(600 rpm) | 1.00 → 1.48로 상승 | **1.2 이하에서 정착** | 여전히 오르면 도착 prefill 말고 다른 미모델링 항이 있다 |
| 거절률(600 rpm) | 12.3% | **< 3%** | 높으면 배치율 추정이 과대 |
| 등가중(600 rpm) | 87.4 (PolyServe 99.3) | **> 95** | |
| 등가중(1800 rpm) | 67.4 (PolyServe 68.5) | **> 70** | |
| chat(3000 rpm) | 70.4 | **> 90** | 안 오르면 3000 rpm의 손실은 게이트가 아니라 다른 것 |
| 등가중(3000 rpm) | 47.2 (PolyServe 61.9) | 55~62 | |

**주의**: 도착 prefill을 넣으면 게이트가 **조여지는** 방향으로도 작용한다(예측이
커지므로). 이득은 보정계수가 1 근처로 내려와 KV·배치항의 과대 팽창이 사라지는
데서 온다. 둘의 순효과가 어느 쪽인지는 측정으로만 알 수 있고, 그래서 세 rate를
같이 본다.

### 11.5 결과 — 추정 계층은 고쳐졌고, 라우팅에 새 힘이 하나 생겼다

v16(첫 시도)은 배치율을 **한 상태 구간의 길이**로 나눴는데, 누적기는 iteration
시간을 잴 수 있었을 때만 비워진다(유휴 인스턴스는 건너뛰고 재시작을 걸친 쌍도
건너뛴다). 그 사이에도 토큰은 계속 쌓이므로 rate가 약 19배로 나왔다 — 도착 투영이
인스턴스당 284,000 토큰(지평 100 step 중 35 step어치)이 되어 600 rpm에서 절반을
거절했다. **v17에서 누적이 실제로 덮는 시간을 누적기 쪽에서 재도록 고쳤다.**
(v16 run `exp23g`는 폐기했다. 이유는 `results/README_exp23g_discarded.txt`.)

**v17, 8분 조건:**

| rpm | PolyServe | v12 | v15 | **v17** |
|---|---|---|---|---|
| 600 | **99.3** | 89.4 | 87.4 | **92.2** |
| 1800 | 68.5 | **70.2** | 67.4 | 62.4 |
| 3000 | **61.9** | 43.5 | 47.2 | **58.5** |

**의도한 것은 정확히 달성됐다.** 1800 rpm run의 계열을 보면 보정계수가 **1.00**에
정착하고(v15에서는 600 rpm에서도 1.48까지 올라갔다), 예측 평균 step이 실측을
따라간다 — 실측이 45.8 → 59.3 → **208.6** → 191.0 → 66.9 → 34.7ms로 4배 이상
움직이는 동안 예측이 47.3 → 50.9 → 123.2 → 105.5 → 51.6 → 40.7로 같이 움직인다.
**모델이 blanket multiplier에 의존하지 않고 상태를 기술하게 됐다.**

3000 rpm에서 43.5 → **58.5**(PolyServe 61.9까지 −3.4)로 좁혔고 goodput도
7,840 → 10,687(PolyServe 11,078)이 됐다. 고부하에서 도착 prefill이 지배적이므로
당연한 결과다.

### 11.6 그런데 1800 rpm에서는 나빠졌다 (70.2 → 62.4)

두 가지가 관찰된다.

1. **도착 prefill은 그 인스턴스의 배치율에 비례하므로, 많이 받은 인스턴스가 더
   비싸진다.** 이것은 물리적으로 옳지만 **부하 분산 힘**으로 작용해서, 클래스
   점유율(share)이 만드는 집중과 정면으로 맞선다. 1800 rpm run에서 네 인스턴스의
   게이트가 전부 50.0ms(= chat 공칭)였다 — **네 대 모두 chat을 담고 있다**는 뜻이고,
   분리가 일어나지 않았다는 뜻이다. v12에서는 chat이 100%였다.
2. **prefill 실측 비율이 부하에 따라 움직인다**: 600 rpm에서 0.24, 1800 rpm에서
   0.35~0.45. 캐시 히트율은 워크로드 성질이지 부하의 함수가 아니어야 한다. 이는
   `notePrefill`의 귀속 편향이다 — 디코드 법칙이 다른 이유로 빗나간 몫까지 prefill로
   귀속되는데, 그 오차는 점유율이 높을수록 커진다(오프라인 적합의 p90 상대오차 21%).
   비율이 부풀면 도착 투영도 같이 부풀어 게이트가 과도하게 조여진다.

**다음 수정 후보(미구현, 근거만 적어둔다)**: 비율 추정을 EWMA 평균이 아니라
**최근 구간들의 최솟값**으로 잡는다. 귀속 편향은 항상 한 방향(더하는 쪽)이므로
최솟값이 가장 덜 오염된 추정이고, 캐시 히트율이 부하와 무관하다는 성질과도 맞다.
단, 이건 아직 측정하지 않은 가설이다.

### 11.7 현재 시점의 판단

- **추정 계층(C3)의 결함은 실제로 고쳐졌다** — 보정계수가 1.00에 정착하고 예측이
  4배 변동을 따라간다는 것이 그 증거다. 이건 되돌릴 이유가 없다.
- **결정 계층에는 새 긴장이 생겼다**: 도착 prefill의 부하 분산 힘 대 클래스 점유율의
  집중 힘. 1800 rpm의 손실이 그 결과다.
- 세 점 평균으로는 v17(71.0)이 v12(67.7)보다 낫고 PolyServe(76.6)보다 낮다.
  1시간 동적 trace는 rate가 넓게 변하므로 **양 끝에서 더 나은 v17이 그쪽에 맞다.**

## 12. 2026-07-27 — 추정기가 자기 출력을 읽으면 안 된다 (v18)

### 12.1 무엇이 문제였나

§11에서 넣은 도착 prefill 투영을 **라우터 자신의 최근 배치율**로 구동했다.

```
arrivingPrefill = dispatchRateOf(인스턴스) × horizonMs × prefill비율
                  └─ "이 스케줄러가 그 인스턴스로 보낸 양 / 시간"
```

이건 루프다. **"얼마나 보낼지"를 정하려고 "얼마나 보냈는지"를 읽는다.**

```
배치율 ↑ → 투영 ↑ → 게이트 조임 → 거절 ↑ → 그 인스턴스로 보내는 양 ↓ → 배치율 ↓ → …
```

이득과 지연이 있고 **바깥에서 잡아주는 관측이 없으므로** 평형점이 여러 개일 수 있다.

### 12.2 실제로 두 개의 평형점에 안착했다

같은 v17 바이너리, 같은 600 rpm, 같은 8분, 조건마다 콜드 재시작.

| | run A (exp23i) | run B (exp23h) |
|---|---|---|
| `arrivingPrefill` | 7~8만에 고착 | 1.7~3.7만에 고착 |
| 예측 평균 step | 58.6~67.8ms | 26.7~41.1ms |
| **실측 평균 step** | **16.9~31.6ms** | **19.9~35.5ms** |
| 예측/실측 | **약 2.4배** | 약 1.1배 |
| 거절 | 799건 | 357건 |
| 등가중 attainment | 82.7 | 92.2 |

**run A는 엔진이 26ms로 도는데 60ms로 예측하고 두 배를 거절했다.**

결정적 단서: **run A는 더 많이 거절했는데 배치율 추정이 더 높다.** 올바른 추정기라면
반대여야 한다. 추정기가 실제 도착량이 아니라 루프의 상태를 재고 있었다는 뜻이다.

3000 rpm에서는 산포가 15.2점(43.4 대 58.5)이었다. **밤새 비교한 버전 간 차이가
전부 이 산포 안에 있다.**

### 12.3 원칙 — 어떤 값이 안전하고 어떤 값이 위험한가

| 값 | 우리 결정의 결과인가 | 외부 관측이 교정해주나 | 판정 |
|---|---|---|---|
| `kvLogical`, `nDecode`, 실측 iteration 시간 | 그렇다 | **엔진이 관측해 돌려준다** | 안전 |
| 물리/논리 KV 비율 | 그렇다 | 엔진이 관측해 돌려준다 | 안전 |
| prefill 실측 비율 | 부분적 | 분자·분모가 같이 움직이는 **비율**이라 결정에 불변 | 안전 |
| **인스턴스별 배치율** | 그렇다 | **없다 — 우리 장부에만 있다** | **위험** |

원칙으로 적어둔다: **컨트롤러의 추정에 컨트롤러 자신의 출력을 넣지 않는다. 넣으려면
그 믿음을 틀렸다고 말해줄 외부 관측이 있어야 한다.** 엔진이 보고하는 양들은 우리
결정의 결과지만 엔진이 사실을 돌려주므로 루프가 닫히지 않는다. 배치 장부는 그렇지 않다.

### 12.4 수정 (v18) — 설계가 아니라 한 입력의 출처

```
arrivingPrefill = offeredRate() / 인스턴스수 × horizonMs × prefill비율
                  └─ "게이트웨이에 도착한 프롬프트 토큰 / 시간", 요청당 1회 집계
```

- **외생**이다. 스케줄러가 무엇을 하든 도착량은 워크로드가 정한다.
- `noteArrival`이 최초 도착에만 새 엔트리를 만드는 성질을 그대로 쓴다. 보유 중
  재시도는 같은 id로 다시 오므로 **재시도를 세지 않는다**. 세면 "오래 붙들수록
  도착률이 높아지는" 또 다른 루프가 된다.
- **모든 인스턴스에 같은 값**이 들어가므로 인스턴스 간 순위를 바꾸지 않는다.
  이것이 두 번째 이득이다 — 인스턴스별 형태는 "많이 받은 곳이 비싸진다"는
  **부하 분산 힘**이었고, 클래스 분리를 만드는 `share`와 정면으로 맞섰다.
  1800 rpm run에서 네 인스턴스의 게이트가 전부 50.0ms(chat 공칭)였다는 것은
  네 대 모두 chat을 담고 있었다는 뜻이고, 분리가 없었다는 뜻이다.
- 코드는 **줄었다**: 맵 3개(`dispatchRate`, `lastDrainMs`, 그리고 rate용 경로)와
  메서드 2개가 없어지고 카운터 하나가 생겼다.

### 12.5 알려진 편향 (숨기지 않고 적어둔다)

과부하에서 **도착률 > 실제 실행될 양**이다. 거절하는 몫만큼 과대추정한다.
그래도 이 형태를 택한 이유:

1. 편향이 **정적**이다(루프가 아니라 상수 배). 보정계수가 흡수할 수 있고, 보정계수는
   정확히 그 용도다. 루프는 보정계수로 못 고친다 — §12.2가 그 증거다.
2. 거절이 0인 저부하에서는 도착 ≈ 배치라 편향이 없다. 편향은 거절이 옳은 구간에서만
   생긴다.
3. 용량 모델이 이미 상한을 갖는다 — 지평 중 prefill을 실은 iteration 비율을 1로
   자르므로 "엔진이 전부 prefill에 묶인다"보다 더 나빠지지 않는다.

### 12.6 그리고 측정 방법이 바뀐다

§12.2가 보여준 산포(9.5~15.2점) 때문에 **조건당 1회 측정으로는 어떤 버전 변경도
판정할 수 없다.** 다음 실험(EXP-24)은 반복 측정이다: 3 rate × 3회 × 2 arm.
반복을 바깥 루프로 돌려서, 기계 상태의 드리프트가 한 조건에만 몰리지 않게 한다.

### 13.3 ⭐ 반증된 설계 가정 — SHED의 전제가 이 워크로드에서 성립하지 않는다

SHED는 이렇게 전제한다:
> 지킬 수 없는 요청을 미리 놓아주면, **그 요청이 쓰려던 용량이 지킬 수 있는 요청에게
> 간다.**

3000 rpm 엔진 점유가 이걸 반증한다.

| | 한 엔진 최대 대기열 | chat | dr |
|---|---|---|---|
| polyserve | **4,296건** | **100.0** | **99.1** |
| fluidserve | **22건** | 55.5 | 78.0 |

**PolyServe는 4,296건을 쌓아놓고도 chat/dr을 완벽하게 지킨다.** 쌓인 건 전부 swe이고,
swe는 별도 서버 2대에 갇혀 있어서 chat/dr 서버가 영향을 안 받기 때문이다.

즉 **swe를 대기열에 쌓아두는 비용이 chat/dr에게 거의 0**이다. 그러면 "거절해서
비워준 용량"의 가치도 0이고, **거절한 요청은 순손실**이다.

§9.2에서 "fleet 메모리의 절반이 놀고 있다"고 지적한 것은 **낭비가 아니라 격리
비용**이었고, 이 워크로드에서는 그 비용이 값어치를 한다. 이 해석을 뒤집는다.

**단, 이건 3000 rpm까지의 얘기다.** PolyServe도 3600 rpm에서 dr 48.8로 무너지고
token goodput이 3000에서 정점을 찍고 꺾인다. **격리가 감당 못 하게 되는 rate가
있고, 거기서는 shedding이 이겨야 한다.** 그래서 EXP-25에 4200 rpm을 넣었다.

### 13.4 ⭐ 새로 특정한 결함 — 거절률이 만드는 두 번째 루프

측정된 모순:
```
fluidserve 3000rpm   실측 iteration p50 = 32.9ms   ← 엔진은 여유롭다
                     게이트 pace 평균   = 61.7ms
                     그런데 54.6% 거절, chat도 44.2% 거절
```

§12.5에서 "정적 편향"이라고 적은 것이 **사실은 되먹임 루프**였다. 정정한다.

**용어 정의** (아래에서 계속 쓴다)
- **투영(projection)** = `arrivingPrefill`. "앞으로 지평(100 iteration ≈ 2.5초)
  동안 이 인스턴스에 prefill 작업이 얼마나 도착할까"를 미리 계산한 토큰 수.
  예측 iteration 시간에 들어가고, 그게 게이트 통과 여부를 정한다.
- **거절률 s** = 도착한 요청 중 SHED로 거절한 비율.

루프:
```
거절률 s ↑
   → 실제로 엔진에서 실행되는 prefill은 (1−s)배인데
     투영은 "도착률" 기준이므로 1/(1−s)배로 과대평가
   → 예측 iteration ↑
   → 게이트 통과 실패 ↑
   → 거절률 s ↑ → …
```

s = 0.55면 투영이 2.2배 과대평가된다. 실측 32.9ms인데 게이트가 61.7ms를 요구하는
상태가 정확히 이 모습이다.

**§12.4에서 도착률을 택할 때 "이 편향은 정적이라 보정계수가 흡수한다"고 적었는데,
그게 틀렸다.** 도착률 자체는 외생이 맞지만, **"도착한 것"과 "실행될 것"의 차이가
곧 우리 결정**이므로 루프가 닫힌다. 용량 모델이 prefill 비율을 1로 자르므로 발산은
안 하고, 대신 **높은 거절률에 안정적으로 눌러앉는다.**

### 13.5 계획된 수정 (미구현) — 엔진이 실제로 하고 있는 prefill 부하를 연장한다

도착률로 투영하지 말고, **엔진이 지금 실제로 수행 중인 prefill 오버헤드를 측정해서
그대로 연장**한다.

```
prefill오버헤드[ms/step] = 실측 평균 step − 디코드 전용 예측     (인스턴스별 EWMA)
예측 평균 step = 디코드 전용 예측 + prefill오버헤드
```

분자는 이미 `capacityModel.notePrefill`에서 계산하고 있다. 새 재료가 필요 없다.

**되먹임 부호가 반대가 된다:**
```
거절 ↑ → 엔진에 도달하는 prefill ↓ → 실측 오버헤드 ↓ → 예측 ↓ → 게이트 열림 → 다시 받음
```
자기교정 루프다. 그리고 §12.3의 원칙을 만족한다 — **엔진이 관측해서 돌려주는 값**이라
잘못된 믿음이 교정된다.

부수적으로 `offeredRate`, `paceMs`, `horizonMs` 경로가 전부 없어져 코드가 또 줄어든다.
새 요청 자신의 prefill charge(`프롬프트 × prefill비율`)는 그대로 둔다.

**실험 중 바이너리를 바꾸면 조건마다 다른 코드가 되므로, EXP-25가 끝난 뒤에 넣는다.**

### 14.1 ⭐ Go bool 플래그가 조용히 반대로 동작했다 (4시간 손실)

`set_scheduler_profiling.py`의 `set_flag`이 플래그를 `["--name", "value"]` 두 토큰으로
넣었다. Go의 `pflag`는 **값을 받는 플래그에만** 분리형을 허용한다. bool에 대해서는
`--flag false`가 **플래그를 true로 설정하고 `"false"`를 위치 인자로** 흘려버린다.

배포 spec에 그대로 남고, rollout도 성공하고, `kubectl get deploy`에도 요청한 대로
보인다. **어디에도 틀렸다는 신호가 없다.**

기본값이 전부 `true`라 정상 run에는 영향이 없었고, ablation을 실제로 돌린 것이
EXP-25가 처음이라 그때 드러났다. 증거(3000 rpm 스케줄러 계열):

```
fluidserve         route=7336  pend=66190  shed=15843  force=881
fluidservenoshed   route=7054  pend=72593  shed=15723  force=1283   ← 껐다는 arm
```

두 arm이 전 rate에서 등가중 1점 이내로 같았다(93.3/94.2, 57.5/58.4, 33.9/34.4,
26.8/26.5). **같은 설정을 두 번 잰 것이다.**

### 14.2 고친 것 셋

1. **`set_flag`이 bool을 `--flag=value` 한 토큰으로 쓴다.** `drop_flags`도 등호형을
   인식하도록 고쳤다.
2. **적용과 반영을 분리해 검증한다.** 스케줄러는 시작 시
   `FluidServe dispatch policy created: horizon … pend=… shed=… affinity=… flux=…`를
   출력한다. **그 줄이 유일한 authority다** — spec을 읽는 것으로는 위 함정을 못 잡는다.
   `verify_effective()`가 적용한 인자와 대조하고, 다르면 **실패로 종료**한다.
   이 검증이 첫 실행에서 바로 걸렸다: `-v 4`에서 그 줄이 몇 초 만에 tail 밖으로
   밀려나 "보고한 적 없음"으로 실패했고, **전체 로그를 읽도록**(`--tail` 없이) 고쳤다.
3. **`arm_of` 정규식.** `exp\d+[a-z]*_`가 `exp25r1_`을 매칭하지 못해 **전체 디렉토리
   이름이 arm 이름**이 됐다. 숫자는 다 맞는데 묶음만 틀리는 종류다.
   `exp[0-9a-z]*_([a-z][a-z0-9]*)_`로 고쳤다.

### 15.1 계산으로 확인한 것 — 게이트는 틀리지 않았다

EXP-24의 3000 rpm 조건을 숫자로 재구성했다.

```
offered  50 req/s x 평균 9,068 tok/req = 453,400 prompt tok/s
인스턴스당                              113,350 tok/s
horizonMs = 100 steps x 32.9 ms       = 3,290 ms
prefillFraction (실측)                 ~= 0.2
arrivingPrefill = 113,350 x 3.29 x 0.2 ~= 74,600 tokens
```

용량 모델은 이걸 horizon 안의 chunk-carrying step 비율로 바꾼다.

```
s_p / k = 74,600 / (8,192 x 100) = 0.091
mixed step = t_pre(8192) + t_dec - c0 = 519.7 + 33 - 16.4 = 536 ms
mean = 0.909 x 33 + 0.091 x 536 = 78.8 ms
```

**게이트가 61.7 ms를 요구하고 엔진이 32.9 ms로 돌던 격차는 전부 이 항이다.**
그리고 이 계산은 **틀리지 않았다**. 엔진 1대의 prefill throughput은
`8,192 / 519.7 ms = 15,763 tok/s`, fleet 4대로 63,000 tok/s인데 offered는
453,400 tok/s다. **7.2배 초과다.** fleet은 실제로 도착하는 프롬프트를 prefill할 수
없고, 모델은 그것을 정확히 감지했다.

즉 v18까지의 거절은 계산 오류의 결과가 아니다. 그런데도 졌다. 이유는 둘로 나뉜다.

### 15.2 손해 1 — 채점 규약 (정책 문제가 아니다)

offered를 분모로 쓰면 **거절은 위반이다.** 54.6%를 거절하면 점수는 45.4%가 상한이다.
거절을 전혀 하지 않는 정책은 이 상한이 없다. PolyServe는 지킬 수 없는 swe를 전부
받아서 swe 전용 서버 2대의 대기열에 쌓고(최대 4,296건), chat/dr 서버는 영향을 받지
않으므로 100%를 유지한다. 등가중 (100 + 99 + 1.5)/3 = 66.8.

**이 규약 아래에서는 admission control이 이길 수 있는 구간이 존재하지 않는다.**
거절한 요청이 "받았으면 늦게라도 완료됐을" 요청인 한, 거절은 순손실로만 계산된다.

사용자 지시로 채점을 바꾼다: **주 지표는 admitted 분모의 SLO attainment이고,
거절률은 별도 곡선으로 같이 보고한다.** 교차검증은 token goodput(SLO를 만족한
요청이 생성한 토큰/초)이 맡는다 — 거절된 요청은 토큰을 만들지 않으므로,
과도한 거절은 goodput에서 반드시 드러난다. offered 분모 attainment는 세 번째
열로 계속 기록한다.

### 15.3 손해 2 — 투영 항이 라우팅 신호가 아니었다 (여기가 진짜 결함)

`arrivingPrefill = offeredRate()/instances x horizonMs x prefillFraction`.

이 값은 **모든 인스턴스에서 같다**(fleet 합계를 인스턴스 수로 나눈 것이므로).
따라서:

- **후보를 정렬하는 데 아무 기여도 하지 못한다.** 모든 후보에 같은 값을 더하면
  순서가 바뀌지 않는다. v16의 주석은 이미 이 사실을 "인스턴스를 서로 이동시키지
  않는 공통 배경 부하"라고 적어 두었다 — 장점으로 적혀 있었지만, 그것은 곧
  **이 항의 유일한 효과가 모든 인스턴스의 게이트를 동시에 조이는 것**이라는 뜻이다.
- **그래서 거절이 클래스를 구분하지 못한다.** 674 토큰짜리 chat 요청도, 22k 토큰짜리
  swe 요청도 같은 74,600 토큰의 배경 prefill을 마주한다. 3000 rpm에서 **chat의 44%가
  거절**된 것이 이 구조의 직접적 귀결이다. PolyServe는 같은 chat을 100% 처리한다.

정책으로서 이것은 명백한 오류다. fleet이 prefill 한계를 7배 초과한 원인은 swe이고,
그 부담을 chat에게 청구할 이유가 없다.

### 15.4 손해 3 — 거절률 되먹임 (§13.5에서 이미 지목)

`offeredRate()`는 **이 정책이 곧 거절할 요청까지 센다.** 거절률 s일 때
`offered = served / (1-s)`이므로, s가 오르면 투영이 커지고, 게이트가 조여지고,
s가 다시 오른다. 양(+)의 되먹임이고 높은 s에서 고정점을 갖는다. 3000 rpm에서
s = 54.6%로 앉은 것이 그 고정점이다.

세션 간 이동(3000 rpm: 45.3 → 33.9 → 28.4)도 여기서 나온다. 고정점의 위치가 초기
과도구간에 의존하기 때문이다.

### 15.5 v19의 수정 — 투영을 엔진이 관측한 prefill duty cycle로 바꾼다

투영 자체를 없앨 수는 없다. 없애면 `noteResidual`의 보정계수가 그 차이를 **평균의
곱셈 인자**로 흡수하고, 곱셈 인자는 KV 항과 배치 항까지 같이 키워서 허용 점유를
빠진 prefill보다 더 크게 깎는다(600 rpm에서 보정계수 1.48까지 올라간 기록이 §11에
있다).

대신 **무엇으로부터 만드는지**를 바꾼다. 상태 간격마다 이미 측정하고 있는 값이 있다:

```
duty_i = (실측 평균 step - 디코드 전용 예측) / 실측 평균 step
```

디코드 법칙이 설명하지 못하는 엔진 시간은 전부 prefill이라는 귀속은
`notePrefill`이 이미 쓰고 있는 것과 동일하다. 다른 점은 **인스턴스별로, 비율로**
보관한다는 것이다. horizon 길이만큼 투영하고 모델이 쓰는 토큰 단위로 되돌린다:

```
arrivingPrefill_i = duty_i x horizonMs / (t_pre(chunk) - c0) x chunk
effectivePrefill_i = max(pendingPrefill_i, arrivingPrefill_i)
```

세 가지 성질이 이전 두 형태와 다르다.

| | 배치율 구동 (v16) | offered 구동 (v18) | duty 구동 (v19) |
|---|---|---|---|
| 되먹임 경로 | 배치 결정 통과 (양) | admission 결정 통과 (양) | **엔진 관측, 음(-)** |
| 인스턴스 구분 | 있음 | **없음** | **있음** |
| 관측으로 교정되나 | 아니오 | 아니오 | **예** |

음의 되먹임인 이유: 많이 청구하면 그 인스턴스에 덜 배치되고, 덜 배치되면 엔진이
prefill에 쓰는 시간이 줄고, 그러면 청구가 줄어든다. 발산하지 않고 수렴한다.

`pendingPrefill`과 **더하지 않고 max를 쓴다.** 지금 큐에 있는 것은 다음 간격에
duty로 관측될 것과 같은 일이므로 더하면 이중 계산이다. 서로 놓치는 경우가 달라서
둘 다 필요하다 — 방금 도착한 버스트는 duty보다 큐에 먼저 나타나고, 상태 조회
사이에 흡수되는 정상 흐름은 큐가 0으로 읽히는 동안 duty에만 나타난다.

### 15.6 없어진 것

- `offeredRate()`가 결정 경로에서 빠졌다. 계측 계열로만 남긴다(그 run이 fleet 용량을
  몇 배 초과했는지 읽는 유일한 계열이다). 파라미터 `fsOfferedWindowMs`,
  `fsOfferedRateAlpha`는 결정에 관여하지 않는다.
- 새로 들어온 파라미터는 `fsPrefillDutyAlpha = 0.1` 하나다. 상태 간격 약 500 ms,
  간격당 약 25 iteration이므로 유효 창은 약 10간격(5초, 250 iteration)이다.
  `noteResidual`의 α=0.002처럼 느릴 필요가 없는 이유는 되먹임의 부호가 반대이기
  때문이다.
- 새 계열 `scheduler_fluidserve_prefill_duty{instance}`를 노출한다. 인스턴스별로
  나뉘는지, 그리고 `arriving_prefill_tokens`가 offered rate를 따라가지 않는지를
  이 두 계열로 확인한다.

### 15.7 검증

- `TestTheProjectionCountsPrefillTheEngineIsObservedCarrying`로 교체했다. 이전 테스트는
  `noteArrival`로 offered rate를 먹여 투영이 커지는지만 봤는데, 새 테스트는 **같은
  디코드 상태의 두 인스턴스 중 하나만 디코드 법칙보다 3배 느리게 돌렸을 때 그
  인스턴스만 청구되는지**를 본다. 이 성질이 곧 v18에 없던 것이다.
- `go test ./pkg/scheduler/policy/` 통과. `TestExecuteMigrations*` 두 개는 패키지

  (개별 실행 시 통과). 이 작업과 무관하다.

### 15.8 예상과 반증 조건

## 16. 2026-07-28 — v20: 다른 클래스가 들고 있는 인스턴스는 늦었다고 해서 공짜가 아니다

### 16.1 EXP-25 r1이 보여준 것 (n=1, 판정은 r2까지 보고)

새 채점(admitted 분모)으로 다시 읽었다. 그러자 그림이 달라진다.

| polyserve | 600 | 99.2 | 99.2 | 0.0 | 4,208 | 100.0 / 100.0 / 97.6 |
| polyserve | 1800 | 68.5 | 68.5 | 0.0 | **7,384** | 100.0 / 100.0 / 5.6 |
| polyserve | 3000 | 67.0 | 67.0 | 0.0 | **11,827** | 100.0 / 100.0 / 1.0 |

**세 가지가 동시에 읽힌다.**

2. **라우팅만 놓고 보면 1800 rpm에서 이긴다** — fs-noshed 76.3 대 polyserve 68.5
   (+7.8). EXP-25 판정표의 "C > A" 구간이 존재한다.
3. **그러나 3000 rpm에서 라우팅이 무너진다** — fs-noshed 46.5 대 67.0. 무너지는
   지점이 명확하다: **chat 54.5%**. PolyServe는 같은 조건에서 chat 100%다.
   admission을 껐는데도 chat이 무너지므로 이것은 거절의 문제가 아니라
   **라우팅이 클래스를 섞는 문제**다.

### 16.2 chat이 무너지는 메커니즘

`harmToIncumbents`는 아직 예산을 만족하고 있는 요청만 센다. 이미 예산을 넘긴 요청은
"더 늦춰도 추가 손실이 없다"는 이유로 제외된다. 이 규칙 자체는 옳고, 의도도 명확했다
— 이미 망가진 인스턴스가 싸 보여야 과부하가 거기로 모이고 나머지가 깨끗해진다.

문제는 **이 규칙에 "누가 망가뜨렸는가"라는 개념이 없다**는 것이다.

```
chat 인스턴스에 swe 요청이 한 번 들어감
  -> 그 인스턴스의 chat 요청들이 예산을 넘김
  -> 넘긴 요청은 harm 합계에서 빠짐
  -> 그 인스턴스의 harm이 0으로 읽힘
  -> 다음 swe 요청도 거기가 가장 싸 보임
  -> chat이 더 무너짐
```

되먹임이 한 방향이고 멈추는 지점이 없다. 3000 rpm에서 chat 54.5%가 이 래칫의
결과다. PolyServe는 chat 서버에 swe를 **애초에 배정하지 않으므로** 이 경로가 없다.

### 16.3 v20 — 인스턴스에 대한 다른 클래스의 청구권을 harm에 넣는다

harm 합계가 놓치는 것은, **인스턴스가 지금 올라와 있는 요청만이 아니라는 것**이다.
그 인스턴스는 거기 모이고 있던 클래스가 **다음에 도착할 자리**이기도 하고, 그 청구권은
현재 점유자들이 예산을 넘겼다고 사라지지 않는다.

```go
if p.cfg.enableAffinity && len(f.live) > 0 {
    harm += (1 - classShare(f, tier)) * fsHarmCap
}
```

- **다른 클래스가 차지한 비율**이 그 청구권의 크기다.
- **한 요청이 받을 수 있는 최대 harm(`fsHarmCap`)과 같은 척도로** 청구한다. 새 상수를
  만들지 않으면서, harm 합계가 구분하지 못하는 인스턴스들을 갈라놓되 실재하는 큰
  차이를 뒤집지는 않는 크기다.
- **빈 인스턴스는 0**이다. 어느 클래스에도 속하지 않았고, 어떤 기준으로 읽어도 가장
  싼 배치다.
- `enableAffinity`로 게이트한다. feasible 집합의 `share` 정렬과 **같은 메커니즘**을
  feasible이 없는 경우로 확장한 것이므로, ablation이 둘을 함께 끄지 않으면 혼합을
  측정하게 된다.

| | 무엇이 문제였나 | 어디서 관측됐나 |

### 16.5 채점 규약 변경과 그에 딸린 구현 결함

`attain()`이 served 열에서도 거절된 요청을 분모에 남겨두고 있었다. 거절된 요청은
first token이 없으므로 `miss`가 참이 되고, 결과적으로 **served 열은 offered 열과
에러 처리만 다른 열이었다.** 2026-07-28 이전에 기록된 모든 "served" 수치는 사실상
offered 수치다.

이제 두 분모를 나란히 출력하고, 같은 행에 거절률을, 옆 열에 token goodput을 둔다.
admitted만 단독으로 읽으면 전부 거절하는 정책이 최고점을 받기 때문이다.

## 17. 2026-07-28 — 여유 HBM을 빌려주는 안에 대한 검토 (측정 기반)

엔진별 KV 사용률과 preemption 횟수:

| polyserve | 8001 | 42.9% | 84.0% | 90.7% | 0 | 84.7% |
| polyserve | 8002 | 86.9% | 99.9% | **100.0%** | **302** | 66.8% |
| polyserve | 8003 | 85.7% | 99.9% | **100.0%** | **247** | 66.6% |
| fluidserve | 8000~8003 | 7.1~7.5% | 10.5~12.2% | 12.6~15.2% | **0** | 63.6~65.5% |
| fs-noshed | 8000~8003 | 50.9~60.0% | 99.5~99.6% | 100.0% | 56~76 | 60.5~67.0% |

### 17.1 조건은 실재한다 — 그리고 그 대가가 처음으로 수치로 나왔다

PolyServe는 **swe 서버 2대를 KV 100%까지 채워 8분에 549회 preempt**하면서, 같은 시각
chat 서버(8000)의 HBM을 **75~88% 비워 둔다.** 사용자가 말한 상황이 정확히 이것이다.

preemption 1회의 비용을 계산한다. vLLM V1의 기본 preemption은 recompute이고, swe
요청의 평균 입력은 22,474 토큰, 그 엔진의 prefix hit이 66.8%이므로 재계산량은 약
7,460 토큰이다. `t_pre(8192) = 519.7 ms`에서 토큰당 0.063 ms이므로 약 470 ms.

```
549회 x 470 ms = 258 초
8분 조건 x 엔진 2대 = 960 엔진-초
=> swe 서버 2대 시간의 약 27%가 재계산이다
```

**§13에서 "PolyServe가 4,296건을 쌓아두고도 chat/dr을 100%로 지킨다"고 적었을 때,
그 대기열의 대가가 무엇인지는 몰랐다. 이것이 그 대가다.** swe 달성률이 1.0%인 이유의
일부가 여기 있다.

### 17.2 그런데 제안된 형태 그대로는 성립하지 않는다

**실행 중인 요청의 KV는 매 step 전부 읽힌다.** attention이 그 요청의 전체 KV를
참조하므로, 일부를 다른 인스턴스에 두면 step마다 원격 읽기가 필요하다. 30 ms 예산의
step에서 이건 불가능하다. 즉 **"실행 중인 요청의 KV를 남의 HBM에 둔다"는 형태는
성립하지 않는다.**

성립하는 형태는 **실행 중이 아닌 요청**의 KV를 두는 것이다. 그게 바로 preemption된
요청이고, 위 수치가 그것이 실재함을 보여준다.

### 17.3 세 가지 실현 경로와 각각의 장벽

**(a) migration을 preemption 백스톱으로 쓴다.** Llumnix에 인스턴스 간 KV 전송이 이미
있다(`LLUMNIX_ENABLE_MIGRATION`, 현재 실험에서는 0으로 꺼 둠). 쫓겨날 요청을 버리는
대신 여유 있는 인스턴스로 옮긴다.

- 전송량: 7,460 토큰. Llama-3.1-70B TP2에서 토큰당 KV는 80층 x 8 KV head x 128 x 2 x
  2바이트 = 320 KB이므로 약 2.4 GB. NVLink면 수 ms, IB면 100 ms 수준 — **어느 쪽이든
  470 ms의 재계산보다 싸다.**
- **장벽**: 옮겨간 요청은 그 인스턴스에서 **실행된다.** 목적지가 chat 서버(8000)라면
  chat의 45 ms 예산이 깨진다. FluidServe의 게이트가 바로 이것을 막는 규칙이다.
  즉 이 경로는 "메모리는 남는데 지연 예산은 안 남는" 인스턴스에는 못 쓴다.

**(b) 원격 HBM을 swap tier로 쓴다 (제안의 정확한 형태).** 쫓겨난 요청의 KV를 peer의
HBM에 **주차만** 한다. 주차된 요청은 디코드 배치에 없으므로 그 인스턴스의 step 시간을
전혀 늘리지 않는다 — **지연 예산을 소비하지 않고 메모리만 쓴다.** (a)의 장벽이 없다.

- **장벽**: 엔진 기능이다. vLLM의 preemption은 recompute 아니면 host swap이고,
  "peer GPU로 swap"은 없다. 컨트롤 플레인에서 할 수 있는 일이 아니라 엔진 변경이다.
- 다만 FluidServe는 **빌려줄 수 있는 양을 이미 계산하고 있다**: `capKv`(지연 한계)와
  `capMem`(메모리 한계) 중 `capMem - capKv`가 양수인 부분이 곧 "실행에는 쓸 수 없지만
  주차에는 쓸 수 있는 메모리"다. 엔진이 받아주기만 하면 스케줄러 쪽 신호는 있다.

**(c) 애초에 preemption을 만들지 않는다.** FluidServe는 3000 rpm에서 네 엔진 모두
**preemption 0회**다(KV 7.1~7.5%). 메모리 게이트가 작동하고 있다는 뜻이다. PolyServe가
지불하는 27%를 FluidServe는 지불하지 않는다 — 대신 거절률로 지불한다.

### 17.4 결론과 순서

- **(b)가 제안의 정확한 형태이고 유일하게 장벽이 논리적이지 않은 경로**지만, 엔진
  변경이 필요하므로 컨트롤 플레인 연구의 범위 밖이다. 나중에 할 일로 남긴다.
- **당장 쓸 수 있는 것은 (c)의 관점 전환이다.** 지금까지 "PolyServe는 격리 대가로
  메모리 절반을 논다"고 적었는데, 실제로는 **격리 대가로 549회의 재계산을 지불한다.**
  이건 FluidServe가 지불하지 않는 비용이고, goodput 비교에서 우리 쪽 논거가 된다.
  §13.3에서 "swe를 쌓아두는 것이 chat/dr에게 거의 비용이 아니다"라고 적은 것은
  **chat/dr에 대해서만 맞고, swe 자신에 대해서는 틀렸다.**
- 따라서 EXP-27에서 **preemption 횟수를 표준 관측 항목에 넣는다.** 지금까지 한 번도
  보지 않았다.

### 17.5 부수적으로 드러난 것 — prefix hit rate가 정책에 따라 다르다

PolyServe는 클래스를 고정 배정하므로 chat 서버가 chat 프롬프트만 보고, 그래서
94.5%까지 올라간다. FluidServe는 네 엔진이 전부 64~65%로 같다 — **클래스가 섞여

### 19.2 원인 — `prefillSteps`의 `math.Ceil`

```go
return math.Ceil(pendingTokens / chunk)
```

올림은 **한 iteration에 대해서는 옳다** — chunk를 싣거나 안 싣거나 둘 중 하나다.
그러나 이 값은 **100 iteration의 지평 전체에 걸친 개수**다. 100 step 동안 chunk를
싣는 step이 1.4개일 것이라는 기댓값은 1.4이지 2가 아니다.

여분 0.6 step이 예측 평균에 더하는 양:

```
(t_pre(8192) − c0) × 0.6 / 100 = (519.7 − 16.4) × 0.006 = 3.0 ms
```

**그 3.0 ms가 45 ms 게이트를 넘느냐 마느냐를 갈랐다.** 그리고 t=540의 행이 논증 없이
그것을 보여준다: arriving이 0.85 chunk로 떨어져 올림이 한 step을 더하지 않게 되자
예측이 41.0 ms로 내려가고 인스턴스가 다시 admissible이 된다.

### 19.3 수정 — 한 chunk를 넘을 때만 소수를 유지한다

```go
if pendingTokens <= chunk { return 1 }
return pendingTokens / chunk    // 올림하지 않는다
```

**두 갈래인 이유는 호출부와 짝이 맞아야 하기 때문이다.**

| pending | 호출부의 단가 `prefillStepMs(min(pending, chunk))` | 개수 | 청구 |
|---|---|---|---|
| ≤ chunk | 부분 chunk의 실제 비용 `t_pre(pending)` | 1 | `t_pre(pending) − c0` ✓ |
| > chunk | 온전한 chunk 비용 `t_pre(chunk)` | `pending/chunk` | `(pending/chunk)(t_pre(chunk) − c0)` ✓ |

한 chunk 이하에서 개수까지 소수로 만들면 **같은 일을 두 번 할인**한다(단가가 이미
부분 chunk 기준이므로). 한 chunk를 넘으면 단가가 온전한 chunk이므로 개수가 소수를
져야 한다. 이렇게 두면 양쪽 구간 모두 실제로 있는 일만큼 청구하고, 정확히 한 chunk
지점의 불연속도 사라진다.

검증 수치(실측 값 기준): 2400 rpm은 pending 2,053 = 0.25 chunk라 변화 없음(양쪽 다
1 step, 단가가 부분 chunk). 4800 rpm은 pending 11,478 = 1.40 chunk라 청구가
2 × 503.3 = 1,006.6 ms에서 1.40 × 503.3 = 705 ms로 내려가고, 예측 평균이 3.0 ms
낮아져 게이트 아래로 들어간다.
