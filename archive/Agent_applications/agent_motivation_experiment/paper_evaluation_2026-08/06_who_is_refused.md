# A6 — 두 정책이 서로 다른 클래스를 거절한다

**2026-08-21. 재분석만 했다.** 그림 `paper_figures/eval_who_is_refused.pdf`,
스크립트 `fig_eval_who_is_refused.py`. 데이터 `static_sweep_clean_2026-08`(8 도착률 × 2반복).

## 1. 무엇을 물었나

[A5](05_per_class.md)가 클래스별 결과를 냈고, 그것이 바로 부르는 질문이 **"결국 어떤 클래스를
버려서 이기는 것 아닌가"**다. **그 질문의 답은 '그렇다, 양쪽 다 버리고, 무엇을 버릴지가
다르다'이고, 그것이 두 설계의 차이를 점수가 아니라 결정으로 말한다.**

먼저 손실이 어디로 가는지 갈랐다 — 클래스마다 도착을 100%로 놓고 **지킴 / 거절 / 미완료**로
나누면 **양쪽 다 손실이 거의 전부 거절**이다(우리 agent 45 req/s에서 거절 73% 미완료 0%,
llm-d chat 45 req/s에서 거절 90% 미완료 0%). **그러므로 거절률이 옳은 축이다.**

## 3. ⚠ 어느 쪽도 클래스 이름을 부르는 규칙을 갖고 있지 않다

**이것이 예산에서 따라 나온 결과이지 누가 준 선호가 아니다.**

- **우리**: agent 클래스는 **전체 시간 30초**로 채점되고, 부하가 걸리면 **어느 인스턴스에서도
  30초 안에 끝낼 수 없게 되는 첫 예산**이다. 판정 조건이 그것을 거절한다.
- **llm-d**: 예측 지연과 예산의 차(headroom)로 거르는데, **chat의 50 ms가 셋 중 가장 빡빡하므로
  headroom이 가장 먼저 음수가 된다.**

> **그러므로 이 그림은 "두 시스템이 무엇을 선호하도록 만들어졌나"가 아니라 **"각자의 admission
> 규칙이 무엇을 함의하나"**를 보여준다. 논문에 그렇게 적어야 한다** — 우리가 chat을 지키도록
> 튜닝했다고 읽히면 안 된다.

## 4. 캡션에 반드시 들어가야 하는 것 셋

1. **llm-d의 거절은 러너가 라벨링한 대로 세었다.** 그 arm 거절의 96~100%가 429가 아니라
   **KV 문턱 경로의 HTTP 500**으로 도착한다. 그것을 admission 결정으로 볼지 실패로 볼지가
   **그 arm의 admitted 달성률을 크게 바꾼다.** 이 그림은 **어느 쪽이든 아무것도 만들지 못한
   요청을 세므로 영향받지 않는다.**
2. **2반복이고 llm-d의 10 req/s가 불안정한 칸**이다(0.0~12.4%).
3. agent 클래스는 **어느 arm이든 전체 시간 30초로 채점**된다.

## 5. 이 문서가 말하지 않는 것

- **우리가 agent를 거절하는 것이 옳은 결정인지 말하지 않는다.** agent가 요청의 7.7%이므로
  총계에는 유리하지만, **배포하는 사람이 그 거래를 고른 것이 아니다.**
- **어느 판정이 agent를 거절하는지 정확히 짚지 않는다.** 예산이 원인이라는 것은 유도이고,
  확인하려면 shed 자리에서 `best.meanAfter`와 계산된 마감을 한 번 내보내면 된다
  (STATUS의 열린 항목 6번).
