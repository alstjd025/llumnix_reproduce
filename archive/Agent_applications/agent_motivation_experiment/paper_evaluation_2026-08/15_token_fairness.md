# A8 — fairness를 요청이 아니라 토큰으로 다시 재면

**2026-08-22. 재분석만 했다.** 스크립트 `analysis_scripts/request_level/eval_token_fairness.py`,
표 `results/aggregate_analysis/paper_eval_2026-08/token_fairness.csv`.
데이터: 고정 세트의 FluidServe·llm-d 32 run (8 도착률 × 2반복).

## 0. 왜 (사용자 가설, 2026-08-22)

요청 단위로 보면 우리는 agent를 64~82%, llm-d는 chat을 86~93% 거절해서 서로 다른 클래스를
희생하는 것으로 보인다(A6). **그런데 클래스의 요청 크기가 크게 달라서**(agent 입력 ~5.6k 토큰,
chat ~0.7k) 요청 단위 76.9/15.4/7.7%가 **입력 토큰 단위로는 약 30/40/30**이다. agent 요청
하나의 거절이 chat 여러 개 값의 용량을 돌려주므로, **토큰으로 재면 대우가 엇비슷할 수 있다**는
가설. 거절 행의 100%에 입력 토큰이 기록돼 있어 분모가 완전하다.

## 1. 입력 토큰 수용률 — 요청 단위 거절률의 토큰판

`받아들인 입력 토큰 / 도착한 입력 토큰`, 클래스별 (2반복 min–max, 괄호는 요청 단위 거절률):

**FluidServe**

| req/s | chat | deepresearch | **swe(agent)** |
|---|---|---|---|
| 35 | **77** (거절 14%) | **78** (15%) | **28-30** (64-65%) |
| 45 | 59-61 (28-31%) | 63-64 (27-28%) | **20-23** (70-75%) |
| 70 | 37-39 (51-52%) | 40-41 (49-50%) | **14-15** (80-82%) |

**llm-d**

| req/s | **chat** | deepresearch | swe |
|---|---|---|---|
| 35 | **36-46** (55-62%) | 64-75 (28-39%) | 64-74 (23-36%) |
| 45 | **9-14** (86-93%) | 69-72 (30-36%) | 63-69 (30-34%) |
| 70 | **9-15** (87-92%) | 42-48 (48-59%) | 28-36 (63-67%) |

**읽기 셋:**

- **가설이 맞는 부분**: FluidServe에서 **chat과 deepresearch는 토큰 단위로 사실상 동일한
  대우를 받는다**(35 req/s에서 77 대 78, 70에서 37-39 대 40-41). 요청 단위로도 비슷했지만
  토큰으로 보면 더 정확히 같다.
- **가설이 틀리는 부분**: **swe의 불이익은 토큰 단위에서도 그대로 남고, 오히려 조금 더
  심해진다.** 35 req/s에서 요청 수용률은 35~36%인데 토큰 수용률은 28~30% — **같은 클래스
  안에서도 큰 요청을 우선적으로 거절한다**는 뜻이다(입력이 클수록 얹은 뒤 pace 교란이 커서,
  B4의 기제와 정합).
- **대칭 비교**: 각 arm이 가장 깎는 클래스의 토큰 수용률이, 45 req/s에서 우리 swe 20-23%
  대 llm-d chat **9-14%**다. **최소 클래스 기준(max-min)으로는 토큰 단위에서도 우리가 덜
  깎는다.** 다만 35 req/s에서는 llm-d의 세 클래스가 36~75로 우리(28~78)보다 고르다 —
  구간에 따라 갈린다.

## 2. ⚠ 새로 나온 것 — goodput 토큰 배분의 "공정한 기준선" 자체가 30/40/30이 아니다

`도착 입력 토큰의 몫 → SLO를 지킨 출력 토큰의 몫`:

| | chat | deepresearch | swe |
|---|---|---|---|
| **아무도 거절 안 하는 10 req/s (양쪽 arm 동일)** | 30 → **64** | 40 → **29** | 30 → **7** |
| FluidServe @45 | 30 → 71-73 | 40 → 24-26 | 30 → **3** |
| llm-d @45 | 30 → **13-27** | 40 → **59-73** | 30 → 14 |

> **거절이 0인 지점에서 이미 64/29/7이다.** 입력 토큰당 출력 토큰이 클래스마다 크게 달라서
> (chat은 0.7k 넣고 415개 생성, swe는 5.6k 넣고 495개) **"입력 몫 = 출력 몫"은 이 워크로드에서
> 애초에 성립할 수 없는 기준**이다. 그러므로 goodput 몫의 공정성은 30/40/30이 아니라
> **무거절 기준선 64/29/7에 대해** 읽어야 한다.
> 그 기준으로: 우리는 45 req/s에서 chat +8, dr −4, **swe 7 → 3 (절반)**. llm-d는 chat
> **64 → 13-27 (최대 5분의 1)**, dr 29 → 59-73 (2배 이상), swe 7 → 14 (2배).

## 3. 토큰 달성률 ≈ 요청 달성률 — 헤드라인은 단위에 강건하다

`SLO를 지킨 출력 토큰 / (도착 수 × 그 클래스의 실측 평균 출력)`으로 재면(거절된 요청의 못 만든
출력은 클래스 평균으로 추정 — 추정임을 명시한다), **모든 칸에서 요청 단위 달성률과 1~4점
안에서 같다**(예: FluidServe 45 req/s에서 chat 65-70 대 66-70, swe 21-26 대 22-26).
**클래스 안의 크기 편차가 달성 여부와 거의 무관하다**는 뜻이고, **논문의 달성률 표는 단위
선택에 의존하지 않는다** — 그 자체로 보고할 가치가 있는 강건성 검사다.

## 4. 논문에 쓰는 문장

1. **A6의 결론은 토큰 단위에서도 유지된다** — 두 정책이 서로 다른 클래스를 깎고, 각자가
   깎는 클래스의 토큰 수용률이 45 req/s에서 20-23%(우리 swe) 대 9-14%(llm-d chat)다.
2. **다만 "우리는 30%의 트래픽을 버린다"는 요청 단위의 과장이다** — agent는 요청의 7.7%,
   입력 토큰의 30%, **무거절 상태에서도 goodput 출력 토큰의 7%**다. 어느 분모로 말하는지
   반드시 붙인다.
3. goodput 몫의 공정성은 **무거절 기준선(64/29/7) 대비 이동**으로 보고한다 — 30/40/30 대비로
   보고하면 거절이 없어도 "불공정"으로 읽힌다.

## 5. 말하지 않는 것

- **거절된 요청의 못 만든 출력은 추정이다**(클래스 평균). 요청별 실제 값은 존재하지 않는다.
- 낭비(수용했으나 위반한 요청의 토큰)는 여기서 가르지 않았다 — EXP-78 §7.6의 낭비율이 그 축이다.
- 한 시간 trace에서는 안 쟀다.
