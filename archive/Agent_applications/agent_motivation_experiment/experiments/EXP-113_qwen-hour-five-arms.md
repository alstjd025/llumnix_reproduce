# EXP-113 — 다섯 컨트롤플레인, Qwen2.5-72B, 한 시간 mix-shift trace

**2026-09-03 ~ 04.** 두 번째 모델에서 정적 sweep 없이 **한 시간 실험만** 한다(사용자 결정).
묻는 것은 **"용량 대비 같은 자리에서 정책 순위가 유지되는가"** 다.

## 1. 도착률을 왜 낮췄는가

원본 trace `dyn60_shift_m2Am1B_b1045` 는 Llama-3.1-70B 의 용량에 맞춰 만들어진 것이다.
같은 파일을 Qwen 에 그대로 쓰면 다른 실험이 된다:

| | Llama (무릎 28.4) | Qwen (무릎 18.3) |
|---|---|---|
| 평균 부하 | 27.4 req/s = **0.96×** | 27.4 req/s = **1.50×** |
| 무릎 위에 있는 시간 | **45%** (27/60 분) | **78%** (47/60 분) |
| 최대 부하 | 1.59× | 2.46× |

Llama 에서 이 trace 는 **용량 언저리를 오가며 절반쯤을 과부하로 보내도록** 설계됐고, 그
전환에서 정책이 어떻게 반응하는지가 이 실험이 보는 것이다. 78% 가 과부하이면 과소부하
구간이 사라지고 모든 arm 이 내내 거절하거나 백로그를 쌓는 한 종류의 상태만 재게 된다.

→ **`traces/scale_trace.py --factor 0.644 --down-method thin`** 으로 도착을 솎아냈다.
배수는 EXP-112 가 잰 90% 교차점의 비(18.3/28.4)다. **시간 축과 버스트 위치는 그대로**
두고 도착만 줄인다(늘리면 93 분이 되어 믹스 전환 일정까지 바뀐다).

결과(`_q064`): 도착률 **7.0~29.6 req/s**, 평균 **17.3 = 0.95× 무릎**, 최대 1.62×, 무릎 위
**44%** — Llama 에서의 원본과 같은 자리다. 클래스 믹스도 보존됐다(chat 65.4 → 65.2 /
deepresearch 21.5 → 21.6 / swe 13.0 → 13.2%). 63,437 건(원본 98,649).

⚠ **두 열은 위치만 공유한다.** 요청 수가 63.4k 대 98.0k 이므로 **개수는 비교할 수 없고
비율과 초당 값만** 비교한다.

## 5. 이번에 고친 계측·도구 결함

1. **`exp41_dynamic_timeline.py` 의 패널 A 가 "all N arms see the same trace" 를 조건 없이
   찍고 있었다.** 세트 B 에서는 거짓이다. 이제 **그려진 곡선에서 판정**한다. 처음 넣은
   판은 존재하지 않는 변수를 참조해 **항상 "같다"로 떨어지는 무늬만 수정**이었고, 다시
   고쳤다. 그리고 그 검사가 세트 A 에서 참을 냈을 때 오탐인 줄 알고 완화하려 했으나
   **재 보니 오탐이 아니었다**(③ 의 vLLM router). 문구를 `REALISED ARRIVALS DIFFER` 로
   바꿨다 — trace 파일이 아니라 실제로 보내진 도착이 다르다.
2. **`traces/scale_trace.py` 가 솎아낸 뒤 다시 첫 도착을 0 으로 맞춘다.** 첫 도착이 솎여
   나가면 살아남은 도착이 전부 앞으로 밀리는데 phase·segment 라벨은 행을 따라가므로
   warmup 과 믹스 전환 일정이 시계와 어긋난다. `thin` 에서만 생기고 고쳤다. ⚠ 처음
   이 결함의 증거로 든 "경계가 60.05 → 59.95 로 옮겨졌다"는 **오진이었다** — 그것은
   모든 축소 trace 가 받는 입력 재기준 0.1197 s 와, 원본 경계 행이 솎여 나가 다음 measure
   행이 첫 행이 된 것이다. 이번 배수에서는 첫 도착이 살아남아 문제의 뺄셈이 0 이었다.
3. **러너가 워크로드의 `class_plan_file` 과 `--trace-file` 이 다르면 시작을 거부한다**(각

4. **러너 템플릿이 trace 옆의 `.plan.json` 을 읽는다.** 축소판 계획을 축소된 CSV 에서 다시

## 6. 실행에서 걸린 것

- **정상으로 돌던 run 을 내가 죽였다.** 드라이버를 "명령줄에 스크립트 이름이 있는
  프로세스"로 셌는데 **bash 가 fork 한 서브셸이 같은 명령줄을 갖는다.** 하나짜리 실행이
  둘로 읽혔고 측정 4 분 시점에 죽였다. **드라이버는 세션·프로세스 그룹 리더만 센다**
  (PPID 1 또는 PGID==PID). 부분 run 둘은 `excluded_runs.tsv` 에 있다.
- **감시를 하네스가 추적하지 않는 형태로 띄우면 알림이 오지 않는다.** EXP-111·112 의
  감시는 종료를 제대로 감지해 파일에 썼는데 나에게 전달되지 않았다.
- vLLM router 는 83 분 걸렸다(다른 arm 70 분). 거절하지 않아 백로그가 쌓이고 유한한
  drain 을 다 쓴다. **미리 95 분을 이상 판정선으로 정해 두었고** 그 안이었다.

## 9. 클래스 분리 지표 (2026-09-04)

`analysis_scripts/request_level/separation_measures.py` 를 열 run 에 돌렸다. 재는 것은
**각 클래스가 실제로 몇 대의 인스턴스에서 돌았는가**이고, 지표는 `N_eff = 1/Σ sᵢ²`
(창별 중앙값, 4.0 = 네 대에 고름, 2.0 = 두 대, 1.0 = 한 대)다. 최다 점유율은 바닥이
1/N 이라 두 대 전용 구성을 50% 로 읽으므로 헤드라인으로 쓰지 않는다.

| arm (r1 / r2) | chat | deepresearch | swe |
|---|---|---|---|
| FluidServe | 1.50 / 1.50 | 3.28 / 3.32 | 2.74 / 2.65 |
| PolyServe | 1.00 / 1.00 | 2.00 / 2.00 | 1.73 / 1.67 |
| Llumnix SLO | 3.85 / 3.85 | 3.83 / 3.80 | 2.34 / 2.94 |
| vLLM router | 2.94 / — | 2.93 / — | 1.12 / — |

**두 반복이 소수 둘째 자리까지 맞는다.** PolyServe 는 정적 파티션이라 chat 1.00,
deepresearch 2.00 으로 설계값이 그대로 나오고, Llumnix SLO 는 3.8 대로 사실상 섞으며,
