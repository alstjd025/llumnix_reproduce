# EXP-87 — 첫 토큰 마감을 feasibility에 넣으면 무엇이 달라지는가

**2026-08-18 작성. 6조건 실행 전이다.** 진단의 정본은
`results/aggregate_analysis/tail_2026-08-16/27_waiting_selects_bad_placements.md`와
`28_backlog_at_placement.md`, 계획은 `ms_dev/notes/tail-plan.md` §7·§7.1.

## 1. 무엇을 고치는가

배치 결정은 이 순서다(`fluidserve.go:1302-1360`).

```
best = 정렬된 첫 후보
1. if best.feasible          → route.  여기서 return
2. if canWait(best, req)     → pend (붙들고 재시도 주기 뒤 다시)
3. if best.missesOwnBudget   → shed (거절)
4. else                      → force
```

`feasible`은 네 조건이고 **전부 토큰당 속도와 KV**다 — `unpredictable`, `overGate`,
`overIncumbents`, `overMemory`. **"이 요청이 자기 TTFT 예산 안에 첫 토큰을 받는가"를 묻는 항이
없다.** 그 질문을 하는 검사(`waited + c.prefillMs > req.ttftSloMs`)는 `missesOwnBudget` 안에
있고 **3번에서만 읽히므로, 1번에서 끝나면 실행되지 않는다.**

**측정된 결과**(`28`, 45 req/s, 조인율 100%): 3,024~3,528 ms 붙들린 deepresearch 요청이
**76,813~87,845 토큰의 prefill 줄**을 가진 인스턴스로 route된다. 그 인스턴스는 토큰당
65.6~70.0 ms를 내고 허용치가 100 ms이므로 **feasible하다.** 첫 토큰까지 실측
**12,610~13,199 ms**, 예산 10,000 ms. **줄 88,000 토큰 ÷ 배치후 11,000 ms = 약 8,000 토큰/초**
이고 실측 인스턴스당 prefill 처리율이 8,882~9,289 토큰/초이므로 **배치후 시간은 그 줄이다.**

`c.prefillMs`는 **그 줄을 이미 값매긴다**(`prefillEstimateMs`의 `queued` 항) — 약 11,000 ms다.
그러니 3번이 실행됐다면 `3,300 + 11,000 = 14,300 > 10,000`으로 **버렸을 것이다.**

> **틀린 것은 계산도 값도 아니다. 맞게 계산된 값을 쓰는 맞는 검사가 도달하지 않는 경로에 있다.**

## 2. 변경 — 접속사 하나. 새 상수도 문턱도 없다

```go
c.missesTtftDeadline = p.missesTtftDeadline(req, c)
overDeadline := p.cfg.deadlineFeasible && c.missesTtftDeadline
c.feasible = !unpredictable && !overGate && !overIncumbents && !overMemory && !overDeadline
```

- `missesTtftDeadline`은 **기존 `missesOwnBudget`에서 마감 부분만 떼어낸 것**이고,
  `missesOwnBudget`이 그것을 부르므로 **정의가 하나만 남는다.**
- 비교에 쓰이는 세 양(`waited`, `c.prefillMs`, `req.ttftSloMs`)이 **전부 이미 계산돼 있다.**
- **`--fluidserve-deadline-feasible`, 기본 `false`.** 값이 아니라 켬/끔이고 ablation을 위해 있다.
- **불가 사유 카운터에 `reason="deadline"`을 추가**했다 — 조건이 실제로 걸리는지 보는 유일한 방법.

**⚠ TTFT 갈래만 넣는다. swe(E2E)는 이번에 바뀌지 않는다.** E2E 갈래는 디코드 전체
(`expectedToks × meanAfter`)를 같이 지므로 함께 넣으면 **두 클래스를 한 번에 바꾸는 것**이 되고,
그것이 A1/A2에서 지적된 문제다. **swe가 그대로인 것이 이 실험의 대조군 역할을 한다** — 노린
클래스만 움직이고 안 노린 클래스는 안 움직인다는 것이 결과의 신뢰도다.
**⚠ swe에도 결국 적용해야 한다(사용자 지시, 2026-08-18). 같은 원리를 한 줄 더 적용하는 것이고
별도 실험으로 잰다.**

## 5. 사전 등록 — 예상과 반증

| 양 | 예상 | 반증 |
|---|---|---|
| **`infeasible_total{reason="deadline"}`** | **0보다 크다** | **0이면 조건이 안 걸린 것이고, 그러면 아래 무엇도 해석하면 안 된다** |
| deepresearch 거절률 | 오른다 | 안 오르면 route가 shed로 안 바뀐 것 |
| **deepresearch TTFT p90** (지금 16,477~16,829 ms, 예산 10,000) | **크게 내려간다** | 이것이 결함의 직접 표적이다 |
| **deepresearch 누적 deadline 달성률, 모든 도착** (35에서 59.8~61.8, 45에서 48.8~50.8) | **오른다** — 비운 용량이 같은 인스턴스의 다른 deepresearch에 간다 | **주 판정.** 안 오르면 비운 용량이 안 쓰인 것 |
| token goodput | 오른다 | |
| **chat** | **안 나빠진다.** 예산 5,000 ms에 `prefillMs`가 약 500 ms, 줄이 0이라 안 걸린다 | 나빠지면 예상 못 한 상호작용 |
| **swe** | **안 움직인다** (E2E 갈래를 안 넣었으므로) | 움직이면 변경이 의도한 범위를 넘은 것 |
| 함대 배치 | 같이 낸다 | deepresearch 배치가 줄면 전용 인스턴스가 안 생길 수 있고, 그러면 효과의 일부가 배치 변화다 |

**성공의 정의**: `reason=deadline` > 0 **그리고** deepresearch의 모든 도착 분모 달성률이 반복 폭
밖으로 오르고 **그리고** chat과 swe가 반복 폭 안에서 유지될 것.

⚠ **모든 도착 분모에서는 route-후-실패와 거절이 둘 다 위반이므로 그 지표가 안 움직여도
이상하지 않다.** 그때는 **admitted 달성률과 token goodput**이 판정이고, 쓸 수 있는 문장은
**"약속을 더 지키게 됐다"**이지 "더 많이 처리했다"가 아니다.

## 6. 결과 — **효과가 반복 폭 안이다. 채택하지 않는다** (2026-08-18 18:14 KST, 6/6)

처리군 2반복, 대조군은 EXP-82의 같은 도착률 2반복. 표의 범위는 두 반복의 min–max.

### 6.1 관문 검사는 통과했다 — 조건은 확실히 걸린다

`infeasible_total{reason="deadline"}`이 **25 req/s에서 708건(불가 사유의 1.1%),
35에서 7,259건(4.8%), 45에서 17,343건(8.3%)**이다. **부하와 함께 커지고, 그것이 진단과
일관된다** — 저부하에서는 prefill 줄이 짧아 `waited + prefillMs`가 예산 안이고, 고부하에서
줄이 5만~8.8만 토큰이 되면 걸린다. **조건은 문제가 있는 곳에서만 작동했다.**

### 6.2 그런데 결과가 안 움직인다

| 45 req/s | 처리군 (2반복) | 대조군 (2반복) |
|---|---|---|
| **deepresearch TTFT p90** (표적) | **16,424~16,527** | 16,477~16,829 |
| deepresearch 거절률 | 27.5~30.2 | 28.5~30.2 |
| deepresearch 달성률 | 51.2~53.7 | 52.1~54.2 |
| chat 달성률 | 64.6~67.3 | 66.7~70.3 |
| 전체 goodput | 12,846~13,251 | 13,165~13,737 |

**모든 칸이 대조군 반복 폭과 겹치거나 그 안이다.** 35 req/s도 같다(deepresearch TTFT p90
11,976~14,000 대 13,285~13,437, 달성률 67.6~67.7 대 65.5~67.3). 25 req/s에서 deepresearch가
조금 나아 보이지만(달성률 96.7~99.1 대 95.0~95.7) **그 구간은 조건이 1.1%만 걸리는 곳이고
대조군 폭이 0.7점이라 판정에 쓰지 않는다.**

**사전 등록한 성공의 정의**(`reason=deadline` > 0 **그리고** deepresearch 달성률이 반복 폭 밖으로
오르고 **그리고** chat·swe 유지)에서 **두 번째 조건이 충족되지 않았다. 채택하지 않는다.**

### 6.3 반복 1만 보고 세운 두 가설이 반복 2와 카운터로 반증됐다

실행 중에 chat이 나빠 보였고(반복 1에서 −2.9~−3.5점) 두 가지 원인을 세웠는데 **둘 다 틀렸다.**

- **"deepresearch가 다른 인스턴스로 밀려 KV로 chat을 막는다"** — `reason=memory`가 대조군
  19.1~20.5%, 처리군 18.1~18.2%로 **오히려 낮다.** 절대 건수도 같은 자릿수다. 반증.
- **"막힌 요청이 더 오래 붙들려 게이트웨이를 점유한다"** — 45 req/s에서 pend가 대조군
  17,065~19,353, 처리군 19,569로 **폭 안**이고, 도착당 호출 수 1.79~1.90 대 1.91, 평균 대기
  1,535~1,590 ms 대 1,630 ms로 **거의 그대로**다. 반증.
- **그리고 chat 자체가 반복 2에서 반대로 움직였다** — 35 req/s에서 처리군 달성률이
  81.6과 86.6이다(대조군 84.5~85.1). **처리군 안의 반복 간 폭이 5.0점으로 대조군의 0.6점보다
  훨씬 크다.** 즉 "chat이 나빠졌다"도 성립하지 않는다. **반복 1만 보고 방향을 말한 것이
  잘못이었다.**

### 6.4 왜 조건이 걸리는데 결과가 안 바뀌는가 — 이것이 남는 질문이다

45 req/s에서 17,343건이 이 조건으로 막혔는데 **route가 13,327~13,363으로 대조군
13,623~14,159의 폭 근처이고 shed도 폭 안이다.** 즉 **막힌 요청이 결국 배치된다.**

가장 단순한 설명은 **조건이 배치를 막는 것이 아니라 늦춘다**는 것이다. deepresearch가 갈 수
있는 곳은 게이트가 100 ms인 인스턴스 한 대뿐이고(EXP-84), 그 인스턴스의 prefill 줄은 계속
차고 빠진다. 줄이 잠깐 짧아지는 순간 `waited + prefillMs`가 예산 안에 들어가 통과한다.
**막을 곳은 있는데 갈 곳이 없으므로, 요청은 조금 뒤 같은 곳으로 간다.**

⚠ **이것은 관측과 모순되지 않는 설명이고 측정된 인과 사슬이 아니다.** 직접 확인하려면 막힌
요청이 그 뒤 어디로 갔는지와 그때의 줄 길이를 봐야 하고, 하지 않았다.

### 6.5 그래서 무엇이 남는가

**`28`의 진단은 여전히 유효하다** — 배치 후 시간이 그 인스턴스의 prefill 줄이라는 것은
측정된 사실이고(줄 88,000 토큰 ÷ 배치후 11,000 ms = 약 8,000 토큰/초, 실측 처리율
8,882~9,289 토큰/초와 일치), `feasible`이 그 줄을 안 본다는 것도 코드가 그렇다.

**틀린 것은 처방이다.** 그 인스턴스를 잠시 막는 것으로는 안 되고, **그 클래스에 갈 곳을
만들어야 한다.** 그것은 EXP-84가 남긴 요구 조건과 같은 자리다 — **"한 클래스가 함대의 얼마를
자기 예산으로 gate하게 허용할 것인가"**를 정책이 정해야 하고, 그 양이 코드에 없다.

### 6.6 처리

- **플래그는 코드에 남긴다. 기본값 `false`이므로 아무 동작도 바뀌지 않는다.** 제거하면 이 측정을
  재현할 수 없고, 위 요구 조건을 다루는 다음 시도에서 다시 필요할 수 있다.
- **`reason="deadline"` 카운터도 남긴다** — 켜지 않으면 0이고, 켰을 때 조건이 걸리는지를 보는
  유일한 방법이다.
- **swe(E2E 갈래)는 넣지 않는다.** 넣을 이유였던 효과가 TTFT 갈래에서 확인되지 않았다.
  사용자 지시(2026-08-18)는 유효하되 **그 처방이 값을 낸다는 것이 먼저 보여야 한다.**
- **바이너리는 되돌린다** — `bin-backup/scheduler-exp07.pre-exp87`(`45f25640`)이 아니라, 플래그가
  기본 false인 새 바이너리(`89d9593b`)를 그대로 둔다. **동작이 동일하고 카운터가 추가되어 있다.**
