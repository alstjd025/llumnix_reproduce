# EXP-132 — 한 시간 trace 위의 FluidServe 변형 셋

실행 전에 씀. 2026-09-13 KST.

## 1. 무엇을 묻는가

EXP-131이 **정적 35 req/s**에서 여섯 요소를 하나씩 빼서 각각의 몫을 쟀다. 이 실험은
그중 **믹스가 15분마다 바뀌는 한 시간 trace에서만 물을 수 있는 것 셋**을 묻는다. 세
질문 모두 심사에서 나올 반론에 대응한다.

1. **요청 하나하나의 출력 길이를 완벽히 알면 얼마나 좋아지는가** — 우리를 Scorpio
   (요청마다 100-bin 분류기), AdaGen(DistillBERT 회귀, 정확도 76.4%), SLOs-Serve
   (디코드 길이를 정확히 안다고 가정)와 비교할 때, *"FluidServe가 이긴 것은 정보에서
   유리했기 때문이 아니냐"* 또는 그 반대로 *"정보에서 불리한데도 이겼다"* 중 어느
   쪽인지를 정하는 실험이다.
2. **클래스 선호가 믹스가 움직이는 동안에도 값을 하는가** — 정적에서는 35 req/s에서
   +3.3~+5.6점, 45 req/s에서 +9.1~+11.4점(EXP-131, 각 3·2 반복)이었다. 믹스가
   15분마다 바뀌면 선호가 만든 분리가 매번 새로 만들어져야 하므로, 정적에서 잰 값이
   그대로 남는지는 별개의 질문이다.
3. **클래스별 길이 분포를 추적하는 것 자체가 값을 하는가** — 위 1이 *"클래스보다 더
   세밀하면"*을 묻는다면 이것은 *"클래스보다 덜 세밀하면"*을 묻는다. 셋을 같이 놓으면
   **요청 단위 / 클래스 단위 / 전체 하나**의 세 점이 되어 축 하나가 완성된다.

## 2. 대조군 — 다시 돌리지 않는다

**EXP-109의 `fsv3capgnofrct75`, 한 시간 mix-shift trace, 2 반복.** 두 run은
`260831_2015_exp109r1_fsv3capgnofrct75_shift`와
`260901_1514_exp109r2_fsv3capgnofrct75_shift`다. (세 번째로 잡히는
`260901_0602_exp109r2_...`는 두 러너가 한 함대를 나눠 쓴 55초짜리이고
`excluded_runs.tsv`에 등록되어 있다. 집계에서 뺀다.)

⚠ **아래는 t75 규칙(TTFT 7 초 + 토큰당 75 ms)으로 낸 값이다.** 처음 적은 판은 swe 를
기본값인 E2E 30 초로 채점했고 그래서 swe 가 33.9 / 33.1, 모든 도착이 74.2 / 73.5 로
적혀 있었다. §6 머리에 경위가 있다. **이 표는 EXP-109 문서의 표와 자리마다 일치한다.**

| | r1 | r2 | 폭 |

나중에 추가된 정상 run 도 놓친다), 클래스별 점수를 `one_run` 이 쓰는 것과 **같은 met/cutoff
정의에서 묶어서** 내므로 총계와 어긋날 수 없다.

## 3. 처리군 셋

전부 대조군의 설정을 그대로 쓰고 **정확히 한 가지만** 바꾼다. `set_arm`을 불러
확인했다(누출 없음).

| arm | 바꾼 것 하나 |
|---|---|
| `orct75` | `--fluidserve-oracle-length=true` **와** `--fluidserve-oracle-flux=true`, 그리고 러너가 요청마다 `len:<n>` 힌트를 싣는다 |
| `noafft75` | `--fluidserve-enable-affinity=false` |
| `flatlent75` | `FS_PROFILE_DIR=llama31-70b-b200-tp2-flatlen` — 세 클래스가 결정적 길이 532 토큰 하나를 공유하는 프로파일 |

### 3.1 오라클이 왜 플래그 둘인가

길이 예측은 정책 안에서 **다섯 자리**에 들어간다. 하나라도 클래스 곡선에 남겨 두면
그 arm이 무엇을 잰 것인지 말할 수 없다.

| 자리 | `oracle-length` | `oracle-flux` |
|---|---|---|
| 도착한 요청의 청구(`costOf`의 `expectedToks`) | ✅ | |
| 마감 판정의 잔여 디코드 | ✅ | |
| registry가 들고 있는 남은 토큰 수 | ✅ | |
| `outflow` — 상주 요청이 지평 안에 끝나 KV가 빠질 확률 | | ✅ 확률 대신 **0 또는 1** |
| `inflow` — 상주 요청이 지평 동안 더 만들 토큰 | | ✅ 무조건 `지평` 대신 **`min(남은 길이, 지평)`** |

`outflow`가 0/1이 되면 분산이 0이 되어 `z=1.65` 안전 여유도 함께 사라진다. 완전한
정보에는 안전 마진이 필요 없다는 뜻이고 의도한 동작이다.

### 3.2 ⚠ 오라클 arm의 한계 — 요청 다섯 중 넷에 대한 오라클이다

표는 `260831_2015_exp109r1_fsv3capgnofrct75_shift`의 완주 요청 79,100건으로 만들었고
(잘린 요청 560건은 뺐다 — 잘린 요청의 `output_tokens`는 길이가 아니라 하한이다),
**같은 조건의 다른 반복에 대해 79.7%를 덮는다**(chat 84.7 / deepresearch 67.7 /
swe 74.5). 출력을 실제로 낸 요청만 보면 86.0%다. 못 덮는 20%는 **거절됐거나 시작되지
않아 길이가 존재하지 않는 요청들**이고, 같은 조건의 run으로 만든 표로는 원리적으로
채울 수 없다.

표가 답한 67,820건에서는 **정확 일치 94.0%, 중앙 절대오차 0 토큰, p90 0**이다.

**표에 없는 요청은 두 플래그 모두에서 클래스 분포로 되돌아간다.** 따라서 이 arm은
"완전한 오라클"이 아니라 **"요청의 80%에 대한 오라클"**이고, 결과를 상한으로 읽을
때 그만큼 보수적으로 읽어야 한다.

### 3.3 ⚠ 오라클 arm만 클라이언트 경로가 다르다

EXP-64에서는 **두 arm 다** 표를 실었고 스케줄러 플래그만 달랐다 — 표를 만드는
실수가 두 arm이 *보낸 것*을 다르게 만들 수 없도록 한 설계다. 여기서는 대조군이
이미 디스크에 있는 EXP-109의 run이고 그것은 표 없이 돌았으므로, **오라클 arm은
스케줄러가 읽는 방식뿐 아니라 러너가 보내는 payload에서도 대조군과 다르다.**
`user` 역할 메시지 한 줄(`len:<n>`)이 추가되므로 prefill 토큰 수가 요청마다 몇 개
늘어난다. 두 arm을 비교하는 모든 자리에 이 문장을 적는다.

### 3.4 flat 프로파일이 정확히 무엇인가

`deploy/profiling/llama31-70b-b200-tp2-flatlen/fluidserve.json`. 세 클래스가 전부:

```
mean     = 532                       ← EXP-109 반복1 완주 79,100건의 믹스 가중 평균 531.5
grid     = [0, 531, 532, 100000]
survival = [1.0, 1.0, 0.0, 0.0]      ← 531토큰까지 전부 생존, 532에서 전부 종료
```

그래서 `completionProb(j,k)`가 `j+k ≥ 532`이면 1, 아니면 0이 되고
`expectedRemaining(j) = 532 − j`가 된다. **tier 키(25/50/100)는 유지한다** —
`fluidserve_profile.go`가 클래스를 그것으로 인덱싱하므로 바꾸면 클래스가 사라진다.
`ttft.json`·`tpot.json`은 **그대로 복사했다** — 엔진과 하드웨어의 성질이지 워크로드의
성질이 아니므로 같이 바꾸면 한 번에 두 가지를 바꾸는 것이 된다.

**코드 경로는 대조군과 완전히 같다.** 바뀌는 것은 읽는 JSON 하나뿐이다.

## 4. 판정 규칙 — 실행 전에 정한다

**모든 arm이 1 반복이다.** 대조군 두 반복의 폭이 모든 도착에서 0.7점이지만, 이
저장소가 이 워크로드에서 관측한 반복 간 이동의 상한은 **4.6점**이다. 1 반복짜리
점 하나를 2 반복 평균과 비교하는 것이므로 다음과 같이 정한다.

| 차이 | 읽는 법 |
|---|---|
| \|Δ\| < 1.0점 | **차이 없음.** 대조군 자신의 반복 폭 안이다 |
| 1.0 ≤ \|Δ\| < 3.0점 | **판정하지 않는다.** 반복을 늘려야 말할 수 있다 |
| \|Δ\| ≥ 3.0점 | **실재하는 차이로 읽는다.** 다만 1 반복이므로 방향만 말하고 크기는 범위로 말한다 |

주 지표는 **모든 도착(all arrivals)**이고, **admitted와 거절률과 token goodput을
반드시 같이 적는다**(admitted만 읽으면 전부 거절하는 정책이 최고점을 받는다).

### 4.1 arm별 사전 예측과 반증 조건

**`orct75` — 예측: 차이 없음(\|Δ\| < 1.0).**

근거는 EXP-64다. 정적 35 req/s에서 오라클의 몫이 **−0.2점**이었고(처리군 자신의
반복 폭 3.7), 도착률 넷 전부에서 3점 안이며 부호가 두 번 뒤집혔다. 그때는 커버리지가
99.2%로 지금(79.7%)보다 높았는데도 그랬다.

**그런데 EXP-64와 다른 것이 둘 있다.** ⑴ 그때는 `oracle-flux`가 없어 **KV 투영은
여전히 클래스 곡선**이었다. ⑵ 그때는 정적이었고 v0.2였다. EXP-131이 **지평을 100에서
25~50으로 줄이면 7.3~10.2점이 오른다**는 것을 쟀고 그 기전이 `costOf`의 선청구이므로,
**투영 항이 정확해지는 것은 EXP-64가 재지 않은 축이다.**

- **반증(좋아지는 쪽)**: 모든 도착이 **+3.0점 이상** 오르면 "요청 단위 길이 진실은
  값을 한다"가 되고, 그러면 **우리가 정보에서 불리하지 않다는 논증을 쓸 수 없다.**
  그 경우 EXP-64의 −0.2와 왜 갈리는지를 `oracle-flux`의 유무로 분해해야 한다
  (`oracle-length`만 켠 조건을 하나 더 돌린다).
- **반증(나빠지는 쪽)**: **−3.0점 이하**로 나빠지면 그것도 결과다 — 정확한 정보가
  해를 끼친다는 뜻이고, 가장 그럴듯한 기전은 `outflow`가 0/1이 되어 **안전 여유가
  사라지고 공제가 커져 preemption이 는다**는 것이다(EXP-131에서 공제가 클수록
  preemption이 늘고 점수가 떨어지는 것을 h=250·500에서 봤다: 516·671회). 그러면
  preemption 횟수가 대조군보다 눈에 띄게 커야 한다. 그렇지 않으면 이 설명은 틀렸다.

**`noafft75` — 예측: 3점 이상 나빠진다.**

정적 35 req/s에서 +3.3~+5.6점(3 반복)이고 한 시간 trace는 도착률이 10~45 req/s를
오가므로 45 근처 구간(+9.1~+11.4)이 섞인다. 다만 **믹스가 바뀌는 동안에는 선호가
만든 분리가 매번 새로 만들어져야 하므로** 정적만큼 나오지 않을 수 있다.

- **반증**: **\|Δ\| < 1.0**이면 "클래스 선호는 정적에서만 값을 한다"가 되고, 그러면
  논문에서 선호를 설계의 기여로 세울 때 **도착률과 믹스 안정성을 조건으로 달아야
  한다.** 그 경우 `separation_measures.py`의 창별 `N_eff`로 두 arm의 분리가 실제로
  다른지 먼저 확인한다 — 분리가 같은데 점수만 같다면 선호가 애초에 분리를 만들지
  않은 것이다.

**`flatlent75` — 예측: 나빠진다. 크기는 모른다.**

클래스별 길이 분포를 하나로 뭉개면 deepresearch(평균 984.8)를 532로, swe(494)를
532로 본다. deepresearch를 **1.85배 짧게** 보므로 그 클래스의 요청이 지평 안에 끝날
것으로 잘못 예측되어 **`outflow`가 과대**해지고, 그러면 자리가 있다고 판단해 더
받아들이다가 KV가 차서 preemption이 는다.

- **반증(차이가 없으면)**: **\|Δ\| < 1.0**이면 **"클래스별 길이 분포를 추적하는 것은
  값을 하지 않는다"**가 되고, 이것은 설계에 대한 강한 음성 결과다. `orct75`도 차이가
  없으면 **길이 예측의 세밀도라는 축 전체가 이 시스템의 성능과 무관**하다는 뜻이고,
  논문은 그것을 숨기지 말고 적어야 한다 — 우리 기여가 길이 예측이 아니라 다른 곳에
  있다는 주장이 오히려 강해진다.
- 기전 확인: 나빠지면 **deepresearch의 클래스별 점수가 가장 크게 떨어져야 하고**
  preemption이 늘어야 한다. 그렇지 않으면 위 설명은 틀렸다.

### 4.2 유효성 검사 — 판정 전에 통과해야 한다

1. **네 엔진이 전부 요청을 처리했는가.** 라우팅이 함대를 잘라도 달성률에서는
   정책이 못하는 것처럼 보인다(EXP-114).
2. **도착이 98,240 ± 200건인가.** 대조군 두 run이 98,240과 98,211이다. 크게 적으면
   부하 생성기가 먼저 무너진 것이다.
3. **`metrics.csv`가 헤더만 있고 `shards/`가 남아 있지 않은가** — 병합 전에 죽은
   run의 표식이다.
4. **두 run의 창이 겹치지 않는가** (`metrics.csv`의 `start_time` 최소·최대).
5. **`orct75`에서 힌트가 실제로 전달됐는가.** 스케줄러의 시작 줄이
   `oraclelen=true, oracleflux=true`이고, 그 조건의 입력 토큰 수가 대조군보다
   요청당 몇 토큰 많아야 한다. 같으면 힌트가 payload에 안 실린 것이다.
6. **`flatlent75`에서 스케줄러가 flat 프로파일을 읽었는가.**
   `set_scheduler_profiling.py`가 찍는 `profile tables from ...flatlen` 줄과,
   그 조건의 `--polyserve-tier-decode-tokens`가 `25:532,50:532,100:532`인 것.

#### ⚠ 기전은 세우지 않는다 — 확인한 것과 확인 못 한 것

*(아래는 preemption 을 오라클의 효과로 읽고 있던 동안 한 확인이다. 위 절에서 그 귀속을
철회했으므로 이 절이 답하려던 질문 자체가 없어졌다. 그래도 남겨 둔다 — `oracle-flux` 가
투영을 어느 방향으로 움직이는지는 그 자체로 알아야 하는 사실이고, 실제로 사전에 적어 둔
방향과 반대였다.)*

세운 가설은 *"`oracle-flux` 가 방출 공제를 키워 정책이 자리를 과대평가하고, 그래서 더
받아들이다가 KV 가 차서 preempt 한다"* 였다. **그 방향이 아니다.**

- **투영은 오히려 더 보수적이 됐다.** 정책이 투영한 KV 점유율(부하 구간, 살아 있는
  인스턴스만)이 오라클 arm 에서 p50 0.95·0.98·0.47·0.44, p90 **1.07·1.05**·1.00·0.49 인데
  대조군은 p50 0.86·0.40·0.88·0.37 / 0.40·0.86·0.86·0.37, p90 이 **1.00 을 안 넘는다.**
  이유는 계산하면 나온다: 상주 요청의 대부분은 남은 길이가 지평 100 보다 길므로
  **오라클에서는 `completionProb` 가 0 이 되는데 클래스 생존곡선은 모든 상주에게 0 보다
  큰 확률을 나눠 준다.** 즉 오라클은 방출 공제를 **줄인다**. `inflow` 쪽은 남은 길이가
  100 을 넘는 요청에서는 `min(remaining, 100) = 100` 이라 바뀌지 않는다.
- **그런데 admission 은 거의 그대로다.** 거절 사유별로 `cannot_meet` 17,227(대조군
  16,989·17,873), `no_feasible` 2,755(2,560·2,390). **투영이 보수적이 됐는데 거절이 안
  늘었다는 것은 메모리 항이 판정을 쥐고 있지 않다는 뜻**이고, 이것은 EXP-131 이 정적
  35 req/s 에서 잰 것(구속하는 것은 gate 이고 잔액·메모리는 거의 단독으로 거절하지
  않는다)과 같은 방향이다.
- **실제 디코드 중 토큰 수는 오히려 조금 낮다** — p90 이 876k·868k·904k·386k 로 대조군의
  929k·954k·935k·384k 보다 낮다.
- **집중도는 조금 올랐다** — 완료 요청의 `N_eff = 1/Σs²` 가 2.85 이고 대조군은 3.05·3.25,
  top-1 share 가 51.1% 대 44.4~48.6% 다. 이것만으로 네 배를 설명하기에는 작다.

**남는 설명은 "후보 정렬이 바뀌어 같은 수의 요청이 다른 인스턴스로 갔다"인데, 그것을
이 run 의 시리즈로는 확인하지 못했다.** 기전을 세우려면 dispatch 로그를 요청 단위로
붙여 **같은 도착이 두 arm 에서 어느 인스턴스로 갔는지**를 비교해야 하고, 그것은 아직
안 했다. 그 전까지는 **사실만 적는다: 점수는 안 움직였고 preemption 은 네 배다.**

#### 이 결과가 논문에 대해 말하는 것

**요청 단위 길이 예측은 이 시스템에서 성능을 사지 못한다.** EXP-64 가 정적 네 도착률에서

양이 줄어드는 것이다.** 거절률 총계가 19.9~20.6% 에서 22.3% 로 오르고 goodput 이 2.0~2.5%
떨어지는 것이 같은 사실의 다른 표현이다.

**왜 그런가.** 인스턴스의 허용 속도(gate)는 **지금 그 인스턴스에 있는 요청들의 명목 예산 중
가장 빡빡한 것**으로 정해진다. 클래스를 섞으면 chat 이 하나라도 올라간 인스턴스는 gate 가
chat 의 50 ms 가 되므로, **그 인스턴스는 무엇을 더 받든 50 ms 를 지킬 수 있어야 하고 따라서
덜 받는다.** 선호는 같은 클래스를 같은 인스턴스에 모아 이 상호 제약을 줄이는 장치이고,
끄면 그 제약이 함대 전체에 퍼진다.

#### swe 만 방향이 다르다 — 그리고 그것이 위 설명의 확인이다

swe 는 met 이 안 움직이는데(65.6~67.2 → 65.8) **내역이 바뀐다: 거절이 2.2~3.7 점 늘고
위반이 2.3~2.4 점 준다**(7.5·7.6 → 5.2). 그래서 **admitted 가 89.6~89.9 에서 92.6 으로
오른다.**

**받아들여져 완주한 요청의 토큰당 시간이 그 이유를 직접 보여 준다:**

| arm | chat (예산 50) | deepresearch (예산 100) | **swe (예산 75)** |
|---|---|---|---|
| 대조군 r1 | p50 43.6, p90 45.2 | p50 71.1, p90 74.7 | p50 **70.7**, p90 75.0 |
| 대조군 r2 | p50 43.5, p90 45.2 | p50 71.2, p90 74.6 | p50 **70.7**, p90 75.1 |
| noafft75 | p50 43.5, p90 45.2 | p50 63.9, p90 72.5 | p50 **64.5**, p90 73.6 |

**선호를 켜면 swe 가 swe 끼리 모이고, 그 인스턴스의 gate 는 swe 자신의 75 ms 가 된다
(× 0.90 = 67.5 ms). 그래서 swe 는 자기 예산의 가장자리에서 돈다 — p50 70.7, p90 75.0 이
예산 75 에 붙어 있다.** 선호를 끄면 swe 가 chat 이 있는 인스턴스에도 앉고 그 인스턴스는
chat 의 50 ms 로 페이싱되므로 **swe 가 자기가 필요로 하는 것보다 빨리 돈다**(p50 64.5).
deepresearch 도 같은 이유로 71.1~71.2 에서 63.9 로 내려간다.

**즉 클래스 선호는 예산이 느슨한 클래스에게서 "이웃이 주는 여유"를 빼앗는다.** 그것이
swe 의 위반을 7.5% 에서 5.2% 로 줄일 수 있었던 여유이고, 대신 선호는 그 대가로 함대가
더 많이 받아들이게 한다. **이 실험에서는 후자가 더 크다** — 세 클래스 전부 거절이 줄고
chat 이 요청의 65% 이므로.

#### EXP-131 의 반증 조건에 걸린다

EXP-131 이 **정적** 35 req/s 에서 클래스 선호의 몫을 **+3.3~+5.6 점**(3 반복), 45 req/s 에서
**+9.1~+11.4 점**(2 반복)으로 쟀다. 사전 예측은 *"3 점 이상 나빠진다"* 였고 반증 조건은
*"1.0 미만이면 정적에서만 값을 한다"* 였다. **결과 1.4~2.2 점은 그 둘 사이이므로 판정하지
않는다** — 그러나 **정적에서 잰 값보다 확실히 작다.** 한 시간 trace 의 도착률은 10~45 req/s
를 오가고 45 근처가 섞여 있으므로, 정적 45 의 +9.1~+11.4 가 그대로 들어 있었다면 훨씬 크게
나왔어야 한다.

⚠ **논문에서 클래스 선호를 기여로 세울 때 "정적 35 req/s 에서 +3.3~+5.6 점" 이라고만 쓰면
안 된다.** 그 수치는 **믹스가 고정된 조건의 것**이고, 믹스가 15 분마다 바뀌면 같은 메커니즘이
1.4~2.2 점을 번다. 둘을 같이 적거나 한 시간 수치를 헤드라인으로 쓴다. **1 반복이므로 크기는
범위로만 말한다.**

#### 아직 확인하지 않은 것

*"선호가 만든 분리가 실제로 줄었는가"* 를 `separation_measures.py` 의 창별 `N_eff` 로
확인해야 한다. 위 기전은 **gate 가 무엇으로 정해지는가**와 **관측된 토큰당 시간**으로
세웠고 그 둘은 일치하지만, **분리 자체의 크기는 재지 않았다.**

`separation_measures.py`(창별, 요청→엔진 조인 100%):

| | chat 이 없는 (인스턴스, 시각) 쌍 | 4 대 중 chat 없는 인스턴스 | 한 인스턴스가 드는 실질 클래스 수 |
|---|---|---|---|
| 대조군 r1 / r2 | 52.4% / 53.2% | **2.1** | 1.46 / 1.44 (천장 1.89) |
| `noafft75` | 44.9% | **1.8** | 1.46 |
| `orct75` | 54.2% | 2.2 | 1.43 |

**클래스 선호를 꺼도 네 대 중 1.8 대가 여전히 chat 을 하나도 들지 않는다. 선호가 더하는 것은
0.3 대다.** 나머지는 판정 조건 자체가 만든다 — chat 을 하나라도 든 인스턴스는 그 클래스의
50 ms 예산에 묶여 새 요청을 덜 받으므로, chat 이 저절로 뭉치고 다른 인스턴스가 비워진다.
**이것은 설계가 주장하는 것 그대로이고**(격리를 구성하지 않고 결과로 얻는다), **명시적 선호는
그 위에 얹는 작은 항이라는 것이 여기서 정량적으로 나왔다.**

**한 인스턴스가 드는 실질 클래스 수는 1.46 대 1.46 으로 완전히 같다** — 선호를 꺼도 인스턴스
쪽에서 본 혼합도는 안 바뀌고, 바뀌는 것은 **클래스가 몇 대에 퍼지는가**다(chat 1.60 → 2.00,
deepresearch 3.16 → 3.66, swe 3.28 → 3.76). 그리고 **배치가 3 배 더 자주 움직인다**(최다 보유
인스턴스가 바뀌는 횟수 시간당 10.5~12.9 → 38.9).

### 6.6 오라클이 왜 아무것도 사지 못하는가 — 구속하지 않는 항의 입력이다

**허용 속도 게이트는 출력 길이를 쓰지 않는다.** 게이트는 지금 그 인스턴스에 있는 요청들의
**명목 예산 중 가장 빡빡한 것**(클래스마다 고정된 상수)과 **투영된 평균 step 시간**으로
정해진다. 출력 길이는 **KV 청구(`costOf`)와 방출 공제(`outflow`)**로만 들어가고 그 둘은
메모리 판정에 쓰인다.

그런데 **EXP-131 이 구속하는 것은 게이트라고 이미 쟀다**: 게이트 여유를 0.90 → 1.00 으로
풀면 18.8~24.2 점이 움직이는데, 잔액 조건은 단독 거절이 0.0~2.7% 이고 빼도 0 점이다.
이번 run 에서도 거절 사유 분포가 대조군과 거의 같다(`cannot_meet` 17,227 대 16,989·17,873,
`no_feasible` 2,755 대 2,560·2,390).

**즉 요청마다 완벽한 길이를 줘도 결정을 내리는 항에는 닿지 않는다.** 이것은 실패가 아니라
논문에 쓸 수 있는 결과다 — 우리 기여가 길이 예측이 아니라는 것의 직접 증거이고, Scorpio
(요청마다 100-bin 분류기)·AdaGen(DistillBERT 회귀 76.4%)·SLOs-Serve(디코드 길이를 정확히
안다고 가정)와 비교할 때 **정보 우위/열위로 설명되는 구도가 아니라는 것**을 말한다.

⚠ **메모리 항이 구속하는 함대에서는 다를 것이다.** EXP-114 가 8 인스턴스 8B 함대를 메모리
구속으로 판정했다. 그것이 요청 단위 길이 정보가 값을 할 조건이고, 이 실험은 그 조건이 아니다.
