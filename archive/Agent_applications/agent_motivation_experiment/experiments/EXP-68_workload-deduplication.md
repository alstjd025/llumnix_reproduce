## 1. 무엇을 고쳤나

`run_experiment.py:_worker_main`이 워커별로 데이터셋을 나누는 줄을 갖고 있고 주석에 이유까지
적혀 있는데(*"Disjoint-ish slice per worker so streams differ (reduces exact-duplicate
prefix-cache masking)"*), 조건이 `isinstance(dataset, list)`이고 mixed 워크로드의
`load_dataset`은 dict를 돌려주므로 **한 번도 실행된 적이 없다.**

측정된 결과: **모든 프롬프트가 정확히 12.00번씩** 나갔고, 사본 12개가 **2.1초 안에**,
연속 사본은 **0.11초** 간격으로 도착했다(99.9%가 1초 이내).

| 고친 것 | 어디 |
|---|---|
| 클래스별 리스트를 워커 조각으로 자른다. **자랐는지 안 잘랐는지를 매번 출력한다** | `mixed_request_level_poisson/workload.py` `create_task_pool` |
| `num_conversations` 1,000 → **10,000** | `mix_short_m1_balanced.json`, `mix_short_m1_slofair.json` |

10,000인 이유: 70 req/s에서 chat이 25,896건을 뽑는데 10,000 대화가 약 33,540건을 주므로
워커당 조각 2,795건 대 뽑는 양 2,158건이 되어 **한 바퀴도 안 돈다.** 8,000이면 1.04배로
아슬아슬하다. 표본은 **고정 시드로 섞은 뒤 앞에서 N개**라 1,000 집합이 10,000 집합의
앞부분이고 앞 1,000개의 task id도 그대로다.

  측정 주행과 **같은 프롬프트 열**을 보내게 됐다. 더 데워질 수도 있고(같은 프롬프트), 덜

  측정한다** — 측정 주행의 첫 1분 hit rate를 나머지와 비교하면 크기가 나온다.

| | 8002 | 229 | 44.8% | 1.0 |
| | 8003 | 199 | 50.6% | 0.8 |
| **llm-d** | 8000 | 74 | 36.2% | 0.4 |
| | 8001 | 95 | 46.8% | 0.2 |

**① llm-d는 함대를 채우지 않는다.** 네 엔진의 실행 배치 합이 318인데 우리는 775로 2.4배다.
엔진 사이도 고르지 않아 45에서 104까지 2.3배 벌어지고, 8002는 이 구간의 **5.7%를 배치 5건
미만**으로 보낸다. 거절률 78.8%가 "받을 수 없어서 거절한다"가 아니라 **받을 수 있는 엔진을
비워 둔 채 거절한다**는 것이 여기서 보인다. 함대 디코드가 llm-d 5,000~10,000 대 우리
15,000~19,000 토큰/초인 것이 같은 이야기다.

**② 우리 쪽 비대칭은 종류가 다르다 — 유리한 관측이 아니다.** 엔진 8000이 **KV 99.5%로 포화**
상태에서 요청 20.3건을 큐에 세워 두는 동안 나머지 셋은 44~51%에 큐가 1건 미만이다. 한
인스턴스가 메모리로 막혀 있고 셋은 여유가 있다. EXP-67b가 infeasible 사유의 92~96%가
gate라고 알려 준 것과 같은 방향을 가리킨다 — **`gateSlack`·`ownBudgetGate` 축을 다시 볼
값어치가 있다는 근거가 하나 더 늘었다.**

**③ 클래스 분리는 워크로드 수정 뒤에도 남아 있다** (`separation_3300.csv`, 55 req/s).
클래스가 실제로 몇 개 인스턴스에서 도는지(`1/Σs²`, 창별 중앙값)가 **우리 2.93 대 llm-d
3.60**이고, 인스턴스 하나가 몇 개 클래스를 드는지가 **1.34 대 2.13**(도착 구성이 정하는
상한은 1.55 대 2.59)이다. 수정 전 EXP-66에서 70 req/s의 2.41 대 3.75와 같은 방향이다.

### 8.2 판정 규칙에 대한 답

- **H1 통과** — 엔진 prefix hit rate가 두 arm 다 내려갔다. 수정 전 llm-d 93.5% / FluidServe
  75.1%였던 것이 **37.7~38.9% / 22.5~38.7%**다. 수정이 결정 경로에 도달했다.
- **H2 통과** — llm-d의 우위가 줄어든 정도가 아니라 **부호가 바뀌었다.** 요청 단위로 수정 전
  EXP-66의 45/55 req/s가 llm-d 기준 **+0.2 / +13.0**이었는데 지금은 **−34.5 / −27.3**이다.
  `llmd-baseline.md` §9.11(llm-d의 우위가 prefix 재사용에서 왔다)이 확증됐고 철회할 것이 없다.
- **H3** — 대조군 `fluidserve`를 새 워크로드에서 재지 않아 **답할 수 없다.** prefix 인식의
  이득이 얼마나 남았는지는 조건 6개를 더 돌려야 한다(§9).
- **H4** — task당 유효 엔진 수는 아직 계산하지 않았다. 두 반복이 다 있으므로 실행만 하면 된다.

### 8.3 이 표를 읽을 때 같이 봐야 하는 것 넷

1. **EXP-66과 나란히 놓을 수 없다.** 워크로드가 2026-08-08 11:00에 바뀌었다. 절대값이
   양쪽 다 내려간 것(35 req/s에서 우리 100.0 → 77.6, llm-d 94.8 → 42.9)은 정책이 나빠진
   것이 아니라 프롬프트 재생이 사라져 엔진이 실제로 계산해야 하는 prefill이 늘어난 것이다.
2. **swe의 SLO 분해가 arm마다 다르다** — 우리는 m1 + `25:e2e:30000`, llm-d는 m1f의
   2,500/52다. **swe는 llm-d가 덜 거절하는 유일한 클래스다**(두 반복 평균 거절률 36.8 /
   36.4 / 59.5% 대 우리 54.1 / 73.3 / 77.8%). 그 클래스가 하필 두 arm이 다른 예산을 받는
   클래스이므로, **swe 열 하나로 어느 쪽이 낫다고 쓰면 안 된다.**
3. **llm-d 클라이언트는 거절을 `is_rejected`와 `is_error`에 둘 다 세운다.** 채점표의
   `rej`와 `err` 열이 같은 요청을 두 번 보고하는 것이고 점수는 OR이라 영향이 없다.
   진짜 오류는 여섯 조건 합쳐 `400 Bad Request` 두 건뿐이다.
4. **부분 완료로 잘린 요청(cutoff)이 두 arm에서 비대칭이다.** 결과가 정해지지 않았으므로
   양쪽 분모에서 빠지는데 우리 쪽이 1.6~1.9%로 llm-d의 0.5~1.0%보다 많다. **전부 실패로
   세는 최악의 경우에도 우위가 유지된다**: +34.7 / +34.5 / +27.3 → **+33.7 / +33.7 /
   +26.7점.**

### 8.4 무릎이 어디로 갔나

수정 전에는 45 req/s가 교차점이었고 35 이하에서 우리가 100.0이었다. **지금은 35에서 이미
77.6이므로 무릎이 35보다 아래로 내려갔다.** 세 rate가 전부 무릎 오른쪽이라 이 sweep은
"포화에서 누가 더 잘 버티는가"를 재고 있고 "무릎이 정확히 어디인가"는 재지 않는다.
그것을 알려면 **25 req/s 이하를 추가로 재야 한다**(§9).
