# EXP-122 (설계 노트) — KV 투영의 도착 항, per-instance 도착률로

**아직 구현 안 함. 2026-09-10에 측정으로 방향이 열렸다는 것까지가 여기 적힌 것이다.**
실험이 아니라 **설계 근거의 보관소**이고, 걸기 전에 §5의 사전 등록을 채운다.

## 1. 고치려는 것

```go
f.inflow  = f.nDecode * horizonSteps                 // 상주 요청들이 100 step 동안 만들 토큰
f.outflow = p.expectedOutflow(f.live, horizonSteps)  // 끝나서 회수될 토큰 (평균 − 1.65σ)
f.proj    = f.kvLogical + f.inflow - f.outflow
// admit if proj + costOf(req) <= capMem
```

**horizon 동안 새로 배치될 프롬프트에 해당하는 항이 없다.** 실측(8×8B 한 시간, 인스턴스·horizon당):

| | 실측 | 모델 |
|---|---|---|
| 생성 | +38,781 | inflow +41,505 |
| **새로 배치된 프롬프트** | **+133,565** | **항 없음** |
| 회수 | −173,317 | outflow −129,219 |
| **합** | **−971** | **−87,735** |

**빠진 항이 모델이 계산하는 드레인 전체보다 1.5배 크다.** ⚠ 그리고 `outflow`는 **25% 과소**
(실제 회수의 0.73~0.745배)라 **그것만 고치면 오차가 커진다.** 두 오류가 상쇄 중이다.

## 2. 닫힌 후보 둘 — 다시 시도하지 않는다

### 2.1 `pendingPrefill`을 더한다 — **이중 청구다**

`kvLogical`은 엔진의 `running`·`waiting` 리스트를 돌며 **prefill이 끝났는지 보지 않고**
`req.num_tokens`를 통째로 더한다. `pendingPrefill`은 **같은 리스트**의 미계산 잔량을 더한다.

실측 확인 셋: in-flight prefill 개수 == in-flight decode 개수가 **스크레이프의 99.8~100.0%**,
`scheduler_waiting_to_decode_requests ÷ 엔진 num_requests_waiting` 중앙값이 큐가 찬 조건에서
**0.98~0.99**, 그리고 결정적으로 **`kvLogical + pendingPrefill`이 +64,385(한 시간 r1) /
+91,340(210 req/s) 과대예측한다** — 겹치지 않으면 넘칠 수 없다.

**그리고 사후적이다** — 엔진 대기 큐가 도착 대비 100 req/s에서 1.8%, 210 req/s에서 63.7%로,
**풀이 이미 찬 뒤에만 커진다.** 유일하게 선행인 성분(우리가 보냈고 엔진 미보고)은
**도착의 0.2~1.2%, 여섯 run 전부 중앙값 0**이라 의미가 없다.

### 2.2 함대 offered 도착률 ÷ N — **부하 구간에서 무너진다**

잔여 도착과의 상관이 100 req/s에서 +0.883인데 **210에서 +0.153, 한 시간에서 +0.098/+0.120**이다.
**항이 중요하지 않은 곳에서만 통한다.** 이유: 인스턴스별 offered 몫의 p10~p90 폭이 0.19인데
중앙값 몫이 0.057이라 **함대 도착률이 어느 인스턴스에 떨어지는지를 말해주지 않는다.**

## 3. ⚠ 2026-09-10에 내가 한 번 잘못 보고한 것

"인스턴스 자신의 배치율이 외생 신호보다 3~4배 잘 맞는다(+0.442~+0.498)"고 적었는데,
**그 상관은 `[t, t+H]`의 도착 토큰과 `[t, t+H]`의 도착 개수 사이의 것**이다
(`an.py:36-37`의 `arr`과 `narr`이 같은 창이다). **거의 항등식이고 판정 시점 이후의 정보를 쓴다.**
예측기로 쓸 수 없다. 철회한다.

## 4. 열려 있는 방향 — **지연 상관을 재니 성립한다** (2026-09-10 측정)

민성님 제안: **`[t−H, t]`에 이 인스턴스가 받은 양으로 `[t, t+H]`에 받을 양을 예측한다.**
판정 시점에 알 수 있는 정보만 쓴다. 인스턴스별, 부하 창, 도구 `scratchpad/pp/lag.py`:

| run | 인스턴스별 상관 min / **p50** / max | 직전값을 그대로 쓸 때 MAE ÷ 예측대상 평균 |
|---|---|---|
| 8×8B 한 시간 r1 | +0.431 / **+0.760** / +0.938 | **0.30** |
| 8×8B 한 시간 r2 | +0.507 / **+0.711** / +0.934 | 0.32 |
| 4×70B 한 시간 | +0.560 / **+0.755** / +0.856 | 0.30 |

**평활 창을 늘리면 좋아지고 10 horizon(약 40초)에서 포화한다:**

| 평활 (horizon) | 1 | 3 | 5 | **10** | 20 |
|---|---|---|---|---|---|
| r1 상관 p50 | +0.760 | +0.805 | +0.822 | **+0.830** | +0.820 |
| MAE ÷ 평균 | 0.30 | 0.26 | 0.25 | **0.24** | 0.25 |

**20에서 다시 나빠진다** — 잡음 감소와 반응 지연의 상충이 데이터에 그대로 보이고 최적이 5~10이다.

→ **도착은 horizon 단위로 백색이 아니다. per-instance 추정기가 성립한다.**

## 5. 설계할 때 반드시 다룰 것 넷

**⑴ 자기참조.** 이 추정기는 우리 자신의 배치를 되먹인다. 부호는 음성 되먹임이고 그것이
원하는 조절이지만(많이 받은 인스턴스가 더 청구되어 덜 받게 된다), **이득과 지연이 문제다.**
이 저장소가 이미 시간 척도를 안다 — step 보정의 `fsCorrectionAlpha`가 0.02(τ≈6초)에서
계수가 1.2~2.4를 오가며 admission을 끌고 다녔고 **0.002(τ≈1분)에서 안정**됐다.
**위 측정의 최적 평활 5~10 horizon(20~40초)이 그 척도와 같은 자릿수다.**
⚠ 앞선 시도가 "인스턴스 자신의 배치율"로 **같은 바이너리 두 run이 8점 떨어진 곳에 앉았다**
(`fluidserve.go:1130-1155`). 그것은 첫토큰 예측용이었고 목적이 다르지만, **경고로 유효하다.**

**⑵ 문턱을 같이 유도해야 한다.** 항을 더하면 좌변이 커지고, `capMem`을 안 움직이면 그것은
조이는 것이다. **2026-09-10에 조이는 변경이 세 번 다 무너졌다**(level test offered 70.2 → 28.7,
0.85 → 34.9, 첫토큰 수정 admitted 90.0 → 73.3). `capMem = 0.95 × pool`은 **편향된 `proj`에
맞춰 암묵적으로 교정된 값**이고, 그 증거가 함대가 실제로 앉는 자리가 물리 풀의 0.977~0.979라는
것이다. **⚠ 다만 이 항은 균일하지 않다** — 많이 받는 인스턴스에서 크고 그곳이 과다 수용이
일어나는 곳이다. **실패한 셋은 전부 균일했다.** 그래서 다를 수 있고, 그것이 이 후보의 근거다.

**⑶ `outflow`의 25% 과소를 같이 고칠 것인가.** 지금은 두 오류가 상쇄한다. **도착 항만 넣으면
`outflow`의 과소가 그대로 남아 순 편향이 반대로 간다.** 둘을 같이 움직이거나, 하나만 고칠
근거를 적어야 한다.

**⑷ 오프라인 평가의 한계.** 위 상관은 **현재 정책이 만든 배치열**에서 잰 것이다. 항을 켜면
평형이 옮겨가고 그 평형에서의 상관은 모른다. **오프라인으로는 못 답한다.**

## 6. 걸기 전에 할 오프라인 검사

`kvLogical`(= 아무 투영도 안 함)이 지금 **여섯 run 전부에서 최선**이고 편향이 ±2,500 토큰이다
(MAE 37,365, `proj`의 94,273 대비 2.52배 우세). **새 후보의 통과 기준은 `kvLogical`을 이기는
것**이다. 후보:

```
proj_new = kvLogical + inflow − outflow + smooth_k(직전 horizon들의 배치 프롬프트 토큰)
```

`k` = 1 / 3 / 5 / 10 / 20을 쓸고, 각 `k`에 대해 **MAE·편향·과소예측 비율**과
**작동점을 유지하는 `memorySafety`**를 낸다. 그 값이 실측 preemption 시작점
(물리 풀의 0.973~0.998, 0.973 아래 10,646 구간에서 0건) 안에 들어오는지가 ⑵의 답이다.
