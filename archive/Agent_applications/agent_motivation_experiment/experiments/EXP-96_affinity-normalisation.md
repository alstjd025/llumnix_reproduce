# EXP-96 — 클래스 선호의 정규화를 고치고, 제대로 작동할 때 이득이 있는지 본다

**2026-08-24 저녁 작성, 실행 전.** 사용자 지시로 코드를 고쳐 돌린다.

## 1. 무엇이 결함인가

`classShare` (`fluidserve.go:2042`)는 **같은 tier 상주 수 ÷ 그 인스턴스의 전체 상주 수**다.
**비율이라 1.0에서 포화한다.**

| 인스턴스 | 지금 (`share`) | 고친 것 (`count`) |
|---|---|---|
| chat 100개 중 80개 | 80/100 = **0.80** | 80/80 = **1.00** |
| chat 1개 중 1개 | 1/1 = **1.00** ← 이긴다 | 1/80 = **0.0125** |
| chat 0개 | 0 | 0 |

정렬 점수가 `w·share + (1−w)·room`이고 배포값 `w=1.0`이므로 **`share`만** 본다. 그래서
그 클래스가 지배적인 인스턴스들이 **전부 정확히 1.0으로 동률**이 되고, 그러면 4단계 동률
깨기가 결정한다:

```go
if c[a].room != c[b].room { return c[a].room > c[b].room }   // free space가 '많은' 쪽
```

**즉 더 빈 쪽으로 보낸다. 채우는 것이 아니라 퍼뜨린다.** 같은 함수의 주석은 *"한 인스턴스를
한 클래스로 더 못 받을 때까지 채우는 것이 분리를 만들고, 멈추는 것은 feasibility"*라고
적혀 있어 **코드와 주석이 어긋난다.**

### 1.1 이 설명을 뒷받침하는 측정 (전부 재분석, 클러스터 안 씀)

정본 `results/aggregate_analysis/overservice/mechanism.md`.

| 관측 | 값 |
|---|---|
| s0(chat 93%)에서 share 1위가 **정확히 동률**인 chat 배치 | **45.7%** — 같은 순간 **개수로는 1.2%** |
| 동률일 때 붙는 인스턴스 수 | 정확히 **2.00** (순수 인스턴스 둘) |
| chat 배치가 share 1위로 간 비율 / **개수 1위**로 간 비율 (s0) | 64.6% / **40.1%** |
| chat 상주 인스턴스 수 (선호 켬) | chat 93%에서 **2.91**, chat 33%에서 **2.94** — **비중과 무관** |
| chat 배치 N_eff | 5초~180초 전 척도에서 **2.0~2.5로 평평** (채우다 멈추는 것이 아니라 정상상태 분산) |

⚠ **share는 배치 시각의 상주 집합으로 재구성한 것이고 정책은 자기 registry를 센다.** 방향은
튼튼하지만 45.7%·64.6% 같은 숫자 자체는 그렇지 않다. **그래서 이번에 카운터를 넣었다.**

## 2. 코드 변경 — 판정 로직은 한 줄도 안 건드렸다

바이너리 **`8faedded3da20e2b3b30cff8832e5b98`**, 백업 `bin-backup/scheduler-exp07.pre-exp96`
(= `89d9593b`). 파드에서 `md5sum /proc/1/exe`로 확인했다.

### 2.1 `--fluidserve-affinity-metric=share|count` (기본값 `share` = 종전 동작)

`count`는 **후보 중 최대 개수로 나눈다**. 포화하지 않으면서 **0~1에 머물러 `room`과 같은
눈금**을 유지한다(가중합이 뜻을 가지려면 두 양이 commensurable해야 한다는 코드 주석의 조건).
`w=1`이면 **그 클래스를 가장 많이 든 인스턴스가 이기고, feasibility가 멈출 때까지 계속 이긴다.**

유닛 테스트 다섯을 새로 넣었고 **결함을 재현하는 테스트가 포함된다**
(`TestShareMetricPrefersTheNearlyEmptyInstance`: 1/1이 80/100을 이긴다).

### 2.2 카운터 셋 — 재구성 없이 결정 경로를 직접 센다

`countSortPath`가 정렬 직후에 부른다. **후보에 이미 있는 값만 읽고 아무 결정도 안 바꾼다.**

| 시리즈 | 무엇 |
|---|---|
| `scheduler_fluidserve_sort_tie_total{width}` | 최상위 점수를 공유한 **feasible 후보 수**. `width=1`이면 점수가 정했고, `>1`이면 **`room` 동률 깨기가 정했으며 그 수가 몇 대 중에서 골랐는지** |
| `scheduler_fluidserve_topshare_total{outcome}` | `taken` / `tie` / `blocked` / `passed_over` — share 1위가 선택됐는지, 아니면 왜 아닌지 |
| `scheduler_fluidserve_topshare_blocked_total{reason}` | 그 1위를 막은 판정 조건(`gate`/`incumbents`/`memory`/`unpredictable`), 후보의 저장된 값으로 재계산 |

`passed_over`(1위가 feasible인데 안 뽑힘)는 정렬상 일어날 수 없지만 **가정하지 않고 따로 센다.**

## 3. 조건

정적 **m1**, **25 req/s**(선호의 이득이 이번 세션에서 깨끗하게 나온 유일한 지점)와
**45 req/s**, 조건당 8분, **2반복**. **세 arm 전부 새 바이너리로 돈다.**

| arm | `enable-affinity` | `affinity-metric` | 정렬 점수 (w=1) |
|---|---|---|---|
| `fsnoaff` | **false** | (계산 안 됨) | `room`만 — 선호 꺼짐 |
| `fspfx` | true | **share** | 지금 배포된 것, 결함 있는 정규화 |
| **`fscount`** | true | **count** | **고친 정규화** |

3 arm × 2 rate × 2반복 = **12조건, 약 3.4시간.**

⚠ **arm이 셋이어야 하는 이유**: 둘만 돌리면 "고친 것이 나빠졌다"가 나왔을 때 **원래 선호가
나빴던 건지 수정이 나빴던 건지 구별할 수 없다.** 세 비교가 세 질문에 대응한다 —
`fsnoaff` 대 `fscount`가 **원래 질문**("제대로 작동하면 이득이 있는가"),
`fspfx` 대 `fscount`가 기제 확인, `fsnoaff` 대 `fspfx`가 어제 값의 재현.

## 4. 가설과 반증 조건 — 실행 전 확정

주 지표는 요청 단위 **offered** 달성률.

**H1 (주 판정, 원래 질문)**: 25 req/s에서 **`fscount` − `fsnoaff`가 `fspfx` − `fsnoaff`(어제
+3.0점)보다 크다.**
- **확인**: 차이가 **+3.0점을 2.0점 이상 넘는다**(즉 +5.0점 이상), 반복 범위 비겹침.
- **반증**: `fscount`가 `fspfx`보다 **낮다.** 그러면 **분리를 제대로 해도 이 워크로드에서는
  값이 없다**가 확정되고, 그것은 지금 논문 주장(계층 분포를 수요에 맞추는 것이 목적이고
  최적점은 워크로드가 정한다)을 **직접 뒷받침한다.**
- 문턱 2.0점의 근거: 25 req/s의 이번 세션 반복폭이 0.4~0.5점이다.

**H2 (기제, 이것이 실패하면 H1을 해석할 수 없다)**: `sort_tie_total{width>1}`의 비율이
**`fspfx`에서 높고 `fscount`에서 1~2%로 떨어진다.**
- **반증**: `fscount`에서 5%를 넘게 남는다 → **정규화에 대한 이해가 틀렸다.**

**H3 (계측 검증)**: `fspfx`가 새 바이너리에서 **25 req/s 96.1점을 3점 안으로 재현한다.**
- **반증**: 3점 밖 → 바이너리 교체가 무해하지 않았고, 이번 결과를 어제와 나란히 못 놓는다.

**부수 관측 (가설 아님)**: `topshare_blocked_total{reason}` — shift trace의 s1~s3에서 1순위로
안 가던 **34~45%**가 어느 판정 조건 때문인지가 **처음으로 직접** 보인다. 지금은 "동률이
아니므로 infeasible일 것"이라는 소거법으로만 안다.

## 6. 결과 — 첫 시도가 계측을 잃었고, 다시 돌린 8조건이 H1을 반증했다

### 6.0 ⚠ 첫 시도(EXP-96)는 카운터를 전부 잃었다

Go에 시리즈를 넣는 것만으로는 수집되지 않는다. **러너의 `llumnix_metrics.py`가 시리즈 이름
화이트리스트로 거른다.** 스케줄러는 내보내고 수집기가 버렸다. **성능 지표는 정상이라 로그만
봐서는 멀쩡해 보였고, 4조건이 돌 때까지 몰랐다.** `CLAUDE.md` 함정 B에 등록했다(커밋 `69eeb04`).

다시 돌린 것이 **EXP-96B**이고 셋을 고쳤다: 수집기 등록, **체인에 2분짜리 smoke 검사**(카운터가
디스크에 닿는지 `grep`으로 확인하고 아니면 즉시 중단 — 통과: 각 189 샘플), 그리고 **arm을 둘로
줄였다.** `fspfx`(지금 방식)는 이 바이너리에서 코드 경로가 안 바뀌고 어제 EXP-94가 같은 세션에서
두 도착률 × 2반복으로 쟀으므로 그 값을 쓴다.

### 6.1 성능 — H1 반증. 고쳐도 저부하에서 같고 고부하에서 나쁘다

| 25 req/s | 반복별 | 평균 | 폭 | 거절 | goodput | 메모리 탈락 |
|---|---|---|---|---|---|---|
| 선호 끔 | 93.1 / 93.8 | 93.5 | 0.8 | 2.7% | 11,544 | 0.0% |
| **선호 켬 (고친 방식)** | 96.1 / 96.1 | **96.1** | **0.1** | 2.1% | 11,884 | 0.9% |
| 선호 켬 (지금 방식) | 96.4 / 95.9 | **96.1** | 0.5 | 1.9% | 11,862 | 0.5% |

| 45 req/s | 반복별 | 평균 | 폭 | 거절 | goodput | 메모리 탈락 |
|---|---|---|---|---|---|---|
| 선호 끔 | 68.0 / 63.6 | 65.8 | 4.4 | 28.4% | 13,860 | 4.6% |
| **선호 켬 (고친 방식)** | 62.4 / 62.2 | **62.3** | 0.3 | 33.2% | 13,369 | **17.8%** |
| 선호 켬 (지금 방식) | 67.5 / 63.7 | 65.6 | 3.7 | 29.4% | 13,950 | 10.0% |

- **25 req/s: 두 방식이 96.1로 같다.** 선호의 이득은 둘 다 **+2.6점**. H1이 요구한
  "고친 쪽이 2.0점 이상 더 번다"가 **성립하지 않는다(차이 −0.0).**
- **45 req/s: 고친 쪽이 3.3점 나쁘고 반복 범위가 겹치지 않는다**(62.2~62.4 대 63.7~67.5).
  그리고 **메모리 사유 탈락이 10.0% → 17.8%로 뛴다.**

> **정규화는 진짜 결함이었지만 성능의 원인은 아니었다. 모으는 힘을 키우면 그만큼 KV가 더 빨리
> 찬다** — 어제부터 확립된 기제가 정렬을 고치자 더 선명해졌다.

### 6.2 ⚠ 카운터가 내 가설을 반증했다 — 동률은 원인이 아니다

고친 방식, 2반복 평균:

| | **진짜 동률(width≥2)** | 1순위 뽑힘 | **1순위 막힘** | 막은 사유 |
|---|---|---|---|---|
| 25 req/s | **0.16%** | 58.1% | **41.7%** | gate 52% / memory 37% / incumbents 11% |
| 45 req/s | **0.07%** | 52.3% | **47.2%** | gate 55% / memory 42% / incumbents 3% |

**동률은 0.1% 수준이다.** `mechanism.md`가 재구성으로 낸 **"chat 93% 구간에서 45.7% 동률"은
방법이 틀렸다** — 정책의 registry가 아니라 클라이언트 상주 기록으로 share를 만들었다.
⚠ **단 그 재구성은 한 시간 trace의 chat 93% 구간이고 이 측정은 정적 m1이다. 같은 조건이
아니므로 완전한 반증은 아니고, EXP-97이 그 구간을 카운터와 함께 잰다.**

**진짜 원인은 1순위가 막히는 것이다 — 42~47%.** 그리고 막는 것은 **속도 게이트가 절반,
메모리가 37~42%**다. **모으려는 인스턴스가 이미 가득 차 있다.**

⚠ `passed_over`가 0.1~0.5% 나온다. 정렬상 일어날 수 없어야 하는데 0이 아니다 — 카운터가
share 최댓값을 **모든 후보**에서 찾는데 정렬은 feasible을 먼저 두므로 생기는 경계 사례로 보이나
**확인하지 않았다.**

### 6.3 H3(계측 검증) 통과

새 바이너리의 `fspfx`가 첫 시도에서 25 req/s에 96.7을 냈고 어제 값이 96.4/95.9다. **0.3~0.8점
차이로 바이너리 교체가 이 도착률에서 무해하다.**

### 6.4 그래서 남는 문장

**클래스 선호가 이 워크로드에서 총계를 못 바꾸는 이유는 정렬 규칙이 아니라 자원이다.** 모으려는
인스턴스가 42~47%의 경우에 이미 속도나 메모리로 막혀 있고, 정렬을 고쳐 모으는 힘을 키우면
고부하에서 메모리 탈락이 10.0%에서 17.8%로 늘어 오히려 3.3점을 잃는다.

이것은 `overservice/README.md`가 세운 주장 — **목적은 계층 분포를 tier별 디코드 수요에 맞추는
것이고 최적점은 워크로드가 정한다** — 을 **정렬을 고친 상태에서도 뒷받침한다.**
