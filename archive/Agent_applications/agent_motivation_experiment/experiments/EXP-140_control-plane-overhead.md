# EXP-140 — 제어평면이 결정 하나에 쓰는 시간, 그리고 그것이 부하에 따라 어떻게 자라나

**2026-09-18. 계측을 먼저 고쳐야 했고, 그 과정에서 수치 두 개를 철회한다.**

## 1. 왜

논문의 오버헤드 절에 쓸 숫자가 없었다. 스케줄러에 `request_full_mode_schedule_duration_milliseconds`
가 이미 있었지만 **쓸 수 없는 지표였다**(§2).

물어야 할 것은 둘이다. **결정 하나가 얼마나 드는가**, 그리고 **그것이 부하에 따라 어떻게 자라나.**
두 번째가 중요한 이유는 결정 비용이 구조상 `O(함대가 들고 있는 요청 수)`이기 때문이다 —
판정 경로에서 `f.live`를 순회하는 곳이 다섯이다(`fluidserve.go` :1273, :1384, :2497, :2661,
:2674). 그리고 **결정은 단일 락 뒤에서 직렬로 처리되므로**(`DefaultAllowConcurrentScheduling
= false`, `scheduling_policy.go` :246-251) 제어평면의 한계가 `1 / 결정 시간`이다.

## 2. ⚠ 철회 하나 — 기존 계측은 평균을 말하지 않는다

`metrics.Histogram("..._milliseconds").ObserveInt(time.Since(startTime).Milliseconds())` 는
**정수로 내림한다.** 1 ms 미만은 전부 0으로 기록되므로 `sum/count` 는 평균이 아니라
**"1 ms 를 넘은 결정의 비율"** 이다.

> **철회**: 이 지표로 읽은 "요청당 평균 0.009~0.015 ms (9~15 µs)"는 **평균이 아니다.**
> EXP-139 run 들에서 그 값은 결정의 0.9~1.5% 가 1 ms 를 넘었다는 뜻이고, 참 평균은
> 0 에서 1 ms 사이 어디든 될 수 있다. 실측은 **169~272 µs** 로, 그 수치는 **11~19 배 과소**였다.

## 3. 무엇을 넣었나

| 시리즈 | 감싸는 구간 |
|---|---|
| `request_full_mode_schedule_duration_microseconds` | 락 + CMS 조회 + 뷰 변환 + 정책 |
| `request_policy_decide_duration_microseconds` | **`p.schedule()` 만** |

**둘로 나눈 이유**: 락·CMS 조회·뷰 변환은 **세 정책이 똑같이 내는 Llumnix 의 비용**이다. 그것까지
우리 오버헤드로 보고하면 공유 인프라 값을 우리 앞으로 다는 것이 된다.

**이름에 단위를 넣고 기존 시리즈를 남겼다** — 같은 이름으로 단위만 바꾸면 디스크의 모든 옛 run 과
1,000 배 차이로 한 열에 섞인다.

⚠ `llumnix_metrics.py` 화이트리스트에도 넣었다. Go 에만 추가하면 조용히 유실된다(EXP-96).
짧은 조건 하나로 실제 저장을 확인한 뒤 본 조건을 걸었다.

바이너리 **`9e8f68b6`**(= `063e1c85` + 위 두 계측). 백업 `bin-backup/scheduler-exp07.pre-exp140`.

## 4. 조건

Llama-3.1-70B ×4 TP=2, **배포 설정(k=1.0)**, 조건당 8분.

| | 도착률 | 목적 |
|---|---|---|
| EXP-140 A | 600 rpm (10 req/s) | 동시 요청 1~176 을 두껍게 |
| EXP-140 B | 2100 rpm (35 req/s) | 동시 요청 1~808 |
| EXP-140b | 2100 rpm, **`-v 0`** | §6 의 비교 |

**도착률을 쓸지 않았다.** 재려는 축은 도착률이 아니라 **동시 요청 수**이고, 한 조건이 스스로
그 축을 훑는다 — 스크레이프가 1초 간격이라 조건당 약 500 쌍이 나오고, 함대가 비어서 차오르는
동안 동시 요청이 0 에서 정상상태까지 지나간다. 8 도착률은 같은 축을 더 비싸게 얻는 것이다.

## 5. 결과 — 비용은 거의 전부 상수항이다

조건 **안에서** 본 기울기(조건 사이를 비교하면 조건 효과와 동시성이 섞인다):

| 조건 | 동시 요청 범위 | 기울기 | 절편 |
|---|---|---|---|
| 10 req/s | 1~176 | **+11.9 µs / 100 건** | 289 µs |
| 35 req/s | 1~808 | **+10.0 µs / 100 건** | 205 µs |

두 조건이 독립적으로 거의 같은 기울기를 준다. **상주 요청 하나를 만지는 데 약 100 ns**이고
(`f.live` 를 다섯 번 순회하니 회당 20 ns), 동시 요청이 800 건이어도 가변항은 **+80~96 µs** 로
기저의 30% 다. **`O(live)` 항이 원래 싸다는 것이 부하 둔감함의 절반이다.**

⚠ 두 조건을 **합쳐서** 적합하면 R=0.148 로 기울기가 안 보인다. 낮은 구간이 600 rpm run 에서,
높은 구간이 2100 rpm run 에서 오기 때문이다. **조건과 설명변수가 섞이면 조건 안에서 본다.**

## 6. ⚠ 나머지 절반은 로깅이었다 — 두 번째 철회

코드에 250 µs 짜리 상수를 만들 반복이 없다(`maxKvForAllowance` 는 반복 없는 닫힌 식이다).
남은 후보는 로깅이었다: 스케줄러가 **`-v 4`** 로 돌고, `filters.go` 에 V(3) 이 19 개,
`scheduling_policy.go` 에 V(4) 이 17 개 있으며, **필터는 후보 인스턴스마다** 평가된다. klog 는
**프로세스 전역 뮤텍스를 쥔 채 stderr 에 blocking write** 를 한다.

같은 조건에서 `-v` 만 바꿔 쟀다(동시 요청 중앙값 740 대 738 로 같은 자리):

| 스케줄러 | 결정 수 | 결정 전체 | 정책만 |
|---|---|---|---|
| `-v 4` | 24,747 | **320 µs** | **272 µs** |
| `-v 0` | 29,669 | **192 µs** | **169 µs** |
| 차이 | | **−127 µs (−40%)** | **−103 µs (−38%)** |

> **철회**: `-v 4` 에서 잰 290~320 µs 는 **디버그 설정의 산물이다.** 보고할 값은 `-v 0` 의
> **192 µs (정책 169 µs)** 다.

**EXP-114 와 같은 기전의 두 번째 사례다.** 그때는 게이트웨이의 `-v 3` 이 토큰 경로에 있어
130 req/s 에서 달성률이 40.9 → 98.7 로 바뀌었다. 이 저장소는 스케줄러의 `-v 4` 가 로그를 1분
만에 회전시킨다는 것은 알고 있었지만 **결정 경로의 비용에 들어간다는 것은 보지 않았다.**

## 7. 보고할 수치

| | |
|---|---|
| 결정 전체 (락 + CMS 조회 + 뷰 변환 + 정책) | **192 µs** |
| **정책만** | **169 µs**, 전체의 88% |
| 공유 인프라 | 23 µs |
| 동시 요청에 대한 기울기 | +10~12 µs / 100 건 (⚠ `-v 4` 에서 잰 값) |
| 직렬 한계 `1/T` | 약 **5,200 결정/s** |
| 관측된 최고 결정률 | 199/s (70 req/s), 한계의 **3.8%** |

**결정 횟수가 도착보다 빨리 는다**(EXP-108 rate sweep, 기존 데이터): 도착 7 배(10→70 req/s)에
결정 22 배(9.0→199.4/s), 도착당 판정 0.9 → 2.9. **그런데 결정 하나의 비용은 25 req/s 위에서
안 자란다** — admission 이 상주 집합을 752~803 에 묶으므로 `O(live)` 항에도 상한이 생긴다.
**부하가 늘 때 자라는 것은 비용이 아니라 횟수다.**

도착당 판정은 **FluidServe 1.4~1.8, PolyServe 2.0~2.1, Llumnix SLO 3.6~3.8** 이다(EXP-139).

## 8. 남은 것

1. **기울기를 `-v 0` 에서 다시 잰다.** 위 기울기는 `-v 4` 값이고, 로깅이 고정 비용이므로
   기울기 자체는 영향을 덜 받았을 것이나 확인하지 않았다.
2. ⚠ **바이너리가 `9e8f68b6` 으로 바뀌어 있다.** EXP-139 반복 2 를 이어서 돌 때는
   `063e1c85`(백업에 있다)로 되돌리거나, 계측판으로 통일하고 그 사실을 적어야 한다.
   추가된 것은 결정마다 히스토그램 관측 두 번이다.
3. **모든 성능 실험은 `-v 4` 에서 측정했다.** 로깅이 결정마다 127 µs 를 먹었지만 70 req/s
   에서도 한 코어의 2.5% 이고 네 정책이 같은 조건이었으므로 비교는 공정하다. 다만
   **오버헤드 수치는 `-v 0` 에서 따로 쟀다는 것을 밝힌다.**
