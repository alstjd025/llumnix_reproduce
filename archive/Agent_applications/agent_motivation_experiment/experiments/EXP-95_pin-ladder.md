# EXP-95 — 클래스 선호가 푸는 엔진이 한 대뿐인 것이 한계인가

**2026-08-24 05:00 KST 작성, 실행 전.** EXP-94 뒤에 이어서 돈다(체인 PID 699984가 EXP-94의
PID 638604를 `kill -0`으로 기다린다).

## 1. 왜 이 실험인가

밤사이 다섯 축 병렬 분석에서 **선호의 이득이 모호하지 않은 축은 하나, 함대 구조**였다.
정본은 `results/aggregate_analysis/exp93_affinity/README.md`.

- 선호를 켜면 **엔진-초의 25.9%·28.2%가 chat의 50 ms보다 느슨한 속도로 돈다**(끄면 6.3%·6.8%,
  차이 20.5점 대 최대 반복폭 2.23).
- **chat이 요청의 93%인 구간에서 선호는 27.7%·28.3%에 도달하는데 feasibility 검사만으로는
  정확히 0.00%다.** → **chat이 다수일 때 엔진 한 대를 chat에서 자유롭게 만드는 유일한 기제다.**
- ⚠ 그런데 **푸는 엔진이 한 대뿐이다** — 세 엔진이 엔진-초의 **71.9~74.1%에서 chat에 묶여 있다.**
- ⚠ 그리고 **자유로워진 대가 가장 한가한 대다**: 상주 요청으로 가중하면 차이가 20.5점이 아니라
  **12.7점**이고, chat 93% 구간에서는 시간 기준 28.0점이 **작업 기준 2.85~3.15%**로 줄어든다.

**그러므로 물어야 할 것**: 한 대라는 상한이 이득을 막는 것인가. 막는 것이라면 **두 대를 강제로
비우면 선호보다 좋아져야 한다.** 아니라면 한계는 다른 데 있고, 가장 유력한 후보는 선호가
pace 탈락을 KV 탈락으로 옮기는 거래(−6.1 대 +6.1점)다.

블록은 이미 들어와 있게 하려는 것이다.

## 3. 가설과 반증 조건 — 실행 전 확정

주 지표는 요청 단위 **offered** 달성률.

**H1 (한 대 상한이 한계다)**: 45 req/s에서 **`fspinc2`가 `fspfx`를 2.0점 이상 앞서고, 두 반복
모두 그렇고, 동시에 엔진-초의 90% 이상에서 두 대가 chat 없이 유지된다.**
- **반증**: 그렇지 않다. 그러면 **구조를 키워도 성능이 되지 않고**, §1의 구조적 결과를 성능
  주장으로 바꿀 수 없다.
- 문턱 2.0점의 근거: m1 45 req/s의 세션 내 반복폭이 최대 2점이다(EXP-56, arm당 3반복).

**H2 (계측 검사, 가설이 아니라 도구 점검)**: `fspinc3`(강제로 한 대)와 `fspfx`(결과적으로 약
한 대)가 **두 도착률 모두에서 2.0점 이내**여야 한다.
- **어긋나면 사다리를 "chat 없는 엔진 수"로 읽을 수 없다** — 강제한 구조와 emergent 구조가
  다른 물건이라는 뜻이고, H1의 해석이 무효가 된다. **이 검사가 실패하면 H1을 보고하지 않는다.**

**H3 (기제)**: 사다리를 따라 **메모리 사유 탈락 비중이 단조 증가**한다(`fsnoaff` < `fspfx` ≈
`fspinc3` < `fspinc2` < `fspinc1`). 이것이 성립하면 "분리를 키우면 KV 압박이 커진다"가
확정되고, H1이 반증될 때의 이유가 된다.
- **반증**: 단조가 아니다.

**H4 (앵커)**: `fspinc1`은 나빠야 한다 — chat이 만드는 출력 토큰이 엔진 약 2.5대 분량이라
한 대로는 굶는다. **`fspinc1`이 `fspfx`보다 나쁘지 않으면 사다리 자체를 의심해야 한다**(핀이
실제로 후보를 거르고 있는지).

### 5.1 ⚠ 내 채점 오류 하나 — H1의 유효성 조건을 잘못 구현했다

H1은 *"`fspinc2`가 `fspfx`를 2.0점 이상 앞서고, **두 대가 엔진-초의 90% 이상 chat-free**"*였다.
자동 채점이 그것을 **(엔진, 창) 쌍 전체의 90%**로 읽어 50.0%를 미충족으로 판정했는데,
**엔진 넷 중 둘을 핀으로 비우면 그 값의 최대치가 정확히 50%다.** 의도한 뜻(비워진 두 대가
자기 창의 90% 이상에서 chat-free)으로는 **100%로 충족**이다. **문턱이 산술적으로 불가능하게
적혀 있었다.**

바로잡으면: `fspinc2` 64.9 대 `fspfx` 59.7 = **+5.2점**, 두 arm의 반복 범위가 겹치지 않는다
(63.0~66.7 대 59.5~59.8). **H1의 수치 조건은 충족된다.**

### 5.2 그런데 H2(계측 검사)가 실패했다 — 그래서 사다리를 "엔진 수"로 읽지 않는다

`fspinc3`(강제로 한 대 비움) 53.5 대 `fspfx`(결과적으로 비움) 59.7 = **6.2점**, 문턱 2.0 초과.
**실행 전에 "이 검사가 실패하면 H1을 보고하지 않는다"고 적었고 그대로 한다.**

이유가 실제 구조에서 보인다 — **`fspinc3`는 한 대가 아니라 약 1.8대를 비운다**(chat 없는
엔진-창 44.6%, 기대 25%). **chat이 허용된 세 대를 다 쓰지 않는다.** 그러므로 `fspinc3`는
`fspfx`의 구조적 대응물이 아니고, 사다리의 축은 "허용한 엔진 수"가 아니다.

**실제로 달성된 chat-free 비율로 다시 세우면**(1.8 → 23.2 → 44.6 → 50.0 → 75.0%) 달성률은
**65.7 → 59.7 → 53.5 → 64.9 → 36.1로 단조가 아니다.** 중간에서 내려갔다 올라온다.
**EXP-94의 세기 축이 45 req/s에서 U자였던 것과 같은 모양이고, 두 실험이 서로 다른 손잡이로
같은 비단조를 만들었다.** 기제는 없다.

### 5.3 H3 반증, H4 통과, P1 틀림

**H3**: 메모리 탈락이 사다리를 따라 8.1 → 18.9 → 19.5 → 16.6 → 4.2%로 **단조가 아니다.**
가운데가 최대이고, `fspinc1`이 가장 낮은 것은 **54.2%를 거절해서** 애초에 KV를 안 쓰기 때문이다.

**H4 통과 — 사다리 자체는 신뢰할 수 있다.** `fspinc1`이 36.1점으로 파국이고(대조군 59.7),
클래스별로 **chat 27.3 / deepresearch 90.5**다. **다수 클래스를 엔진 한 대에 강제로 묶으면
그 클래스가 굶고 소수 클래스가 남은 자리를 다 쓴다.** 핀이 실제로 후보를 거른다는 증거이기도
하다(기동 줄 `classpin=50:0`, chat-free 75.0%).

**P1 틀림.** a7의 두 체제 분류에서 유도한 *"`fspinc2`가 `fspfx`를 못 이긴다"*가 틀렸다 —
+5.2점 이겼다. **실행 전에 정한 대로, a7이 m1 45 req/s에 적용된다는 전제를 다시 봐야 한다.**
⚠ 다만 H2가 실패했으므로 **이 반증도 "핀 구조와 emergent 구조가 다른 물건"이라는 사실 위에
있다** — `fspinc2`가 이긴 것이 "두 대를 비워서"인지 "핀이 chat을 두 대에 균등하게 강제해서"인지
구별되지 않는다. 후자라면 그것은 a7과 무관한 별개의 기제다.

### 5.4 지금 쓸 수 있는 것

- **다수 클래스를 한 대에 묶으면 파국이다**(36.1 대 59.7, chat 27.3 / dr 90.5). 정적 분할을
  세게 하는 방향에 대한 직접 반례이고 반복 둘에서 재현된다.
- **핀으로 강제한 분리는 선호가 만드는 분리와 같은 물건이 아니다** — 같은 "한 대"를 지정해도
  실제로는 1.8대가 비고 성능이 6.2점 다르다.
- **m1 45 req/s는 블록 사이에 7.9점 흔들린다.** 이것이 이 저장소의 다른 결론들에 걸린다.

**쓸 수 없는 것**: 사다리를 "chat-free 엔진 수 대 성능" 곡선으로 읽는 것, `fspinc2`의 +5.2점을
"분리를 키우면 좋아진다"로 읽는 것, U자의 기제.
