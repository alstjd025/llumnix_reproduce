# EXP-27 — swe 입력을 줄이고, 믹스를 입력 토큰 기준으로 정의한다

**상태**: 실행 중 (2026-07-28 04:40 KST 시작, 약 3.9시간). 세션 접두사 `exp27r1`
**스크립트**: `k8s/exp07/run_exp27_mixsweep.sh`
**브랜치**: llumnix `feat/fluidserve` (v19+v20), Agent_applications `feat/fluidserve`

## 1. 왜 이 실험인가 — 지금까지 정적 파티션은 움직일 필요가 없었다

EXP-21~25는 전부 **요청 수 기준 1:1:1** 믹스로 측정했다. 그런데 클래스별 평균 입력이
chat 674 / dr 4,055 / swe 22,474 토큰이므로, 요청 수가 같으면 **입력 토큰의 82.6%가
swe 하나**에 몰린다. PolyServe의 수요 추정은 요청당 server-seconds에 도착률을 곱한
것이고 swe의 요청당 비용이 chat의 약 32배이므로, 어떤 비율을 줘도 수요가 swe에
지배된다.

`allocateServers`를 오프라인으로 재현해 확인했다(프로파일 테이블을 그대로 읽어
`serverSecondsPerRequest`와 largest-remainder 배분을 재구현; 스크립트는
scratchpad에 있고 결과만 옮긴다).

| swe 입력 | 믹스 (요청 수) | 입력 토큰 비율 chat/dr/swe | 배정 (swe/chat/dr) |
|---|---|---|---|
| 22,474 | 1:1:1 | 2 / 15 / 83 | **2 / 1 / 1** |
| 22,474 | 33:6:1 (토큰 1:1:1) | 32 / 35 / 33 | 1 / 2 / 1 |
| 22,474 | 8:1:1 (토큰 1:1:4) | 17 / 13 / 70 | **2 / 1 / 1** |
| **6,812** | 10:2:1 (토큰 1:1:1) | 31 / 37 / 31 | **2 / 1 / 1** |
| **6,812** | 40:2:1 (토큰 4:1:1) | 64 / 19 / 16 | 1 / 2 / 1 |
| **6,812** | 6:1:2 (토큰 1:1:4) | 19 / 19 / 63 | **2 / 1 / 1** |

즉 **믹스를 입력 토큰 비율로 정의하면 배정이 실제로 움직인다.** 요청 수로 정의하는
한 움직이지 않는다. 이것이 EXP-26(엔진을 3대로 줄여 격리를 불가능하게 만든다)을
하지 않고도 같은 질문에 답할 수 있는 방법이다.

## 2. 워크로드 변경 — swe 입력 22,474 → 6,812 토큰

`workloads/codingagent_request_level_poisson/build_short_transcript.py`가 기존
transcript를 변환해 만든다. 재실행 가능하고, 결과 파일은 git 대상이 아니다.

```
records                 1500
system prompt tokens    14,481 -> 4,047
conversation ratio      0.3694
mean input tokens       22,474 -> 6,812   (p10/p50/p90 = 4,227 / 6,569 / 9,578)
structural prefix share 81.5% -> 78.9%
```

**보존한 것과 그 이유**

| 보존 | 이유 |
|---|---|
| prefix 구조 | 모든 변환이 메시지 내용의 순수 함수라, 변환 전에 접두사를 공유하던 두 레코드는 변환 후에도 **동일한 토큰 접두사**를 공유한다. radix cache가 보는 공유 패턴이 규모만 줄어든 채 유지된다. 측정된 구조적 prefix 공유율 81.5% → 78.9% |
| 메시지 수와 역할 | 같은 agent job의 call 1, 2, 3 사이 접두사 관계가 유지된다 |
| 각 메시지의 끝 | 긴 메시지는 **가운데를 잘라낸다**. 모델이 응답할 stage 지시문이 마지막 user 메시지의 끝에 있으므로, 뒤를 자르면 모델이 하는 일 자체가 바뀌고 출력 길이도 바뀐다 |
| 길이 분포의 형태 | system 외 메시지에 단일 비율을 적용 |

**system prompt는 토큰 오프셋으로 자르지 않고 섹션을 골라 남겼다**(Role Definition /
General Principles / Tool Usage Instructions / Output Format Specifications + 마무리
문단). 실제 coding agent의 system prompt가 역할·도구·출력 형식으로 구성된다는 점에서
4,047 토큰은 현실적인 범위 안이고, 문장 중간에서 잘린 프롬프트를 남기지 않는다.

**보존하지 않은 것**: `baseline_ttft_s` / `baseline_tbt_mean_ms` / `baseline_e2e_s`는
원본 긴 프롬프트의 단독 실행 시간이며 짧은 버전에 대해 틀리다. Llumnix 믹스 실행은
`--disable-timeouts`로 `job_timeout_sec`을 0으로 만들고 절대 SLO 임계로 채점하므로
아무도 읽지 않는다. 스키마를 유지하기 위해 필드는 남기고 `baseline_valid: false`를
찍는다.

**KV hit rate가 비현실적으로 높아지지 않는가**: 반대다. 원본이 81.5%로 더 높았고,
그 대부분(14,481/22,474 = 64.4%)이 **모든 요청이 공유하는 하나의 system prompt**에서
왔다. 짧은 버전은 78.9%로 약간 낮다.

## 4. 채점 규약을 바꾼다

지금까지는 **offered 분모**만 봤다(거절·에러·미완을 전부 위반으로). 그 규약에서는
거절하는 정책이 거절하지 않는 정책을 이길 수 있는 구간이 원리적으로 없다.

이제 **두 분모를 나란히 보고한다.**

| | 정의 | 무엇을 왜곡하나 |
|---|---|---|
| **admitted** (주 지표) | 분모 = 시스템이 받아들인 요청 | 단독으로 읽으면 전부 거절하는 정책이 최고점을 받는다 |
| offered | 분모 = 도착한 모든 요청 | 어차피 못 지킬 요청을 거절해도 손실로 계산한다 |

**단독으로 읽지 않기 위한 두 개의 동반 지표**: 거절률(클래스별)과 token goodput.
거절된 요청은 토큰을 만들지 않으므로 과도한 거절은 goodput에서 반드시 드러난다.
목표는 **admitted 기준 모든 rate에서 90% 이상, 동시에 goodput이 PolyServe 이상**이다.

> 구현 결함 하나를 같이 고쳤다. `attain()`이 served 열에서도 거절된 요청을 분모에
> 남겨두고 있었다(거절된 요청은 first token이 없으므로 `miss`가 참). **2026-07-28
> 이전에 기록된 "served" 수치는 전부 사실상 offered 수치다.**

## 5. 설계

```
rep(바깥) x mix(3: m1/m2/m3) x arm(2: polyserve/fluidserve)
rates 1200 / 2400 / 4800 rpm, 조건당 8분, 조건마다 엔진 콜드 재시작
1 rep = 6 셀 x 3 rate x 약 13분 = 약 3.9시간
```

- **반복이 바깥 루프**다. EXP-24에서 세션 내 산포 0.2점, 세션 간 이동 5점이 측정됐고,
  EXP-25에서는 admission을 끈 arm의 반복 간 반폭이 23.6점까지 나왔다.
  arm을 바깥에 두면 그 산포가 arm 효과로 읽힌다.

**rate 1200/2400/4800의 근거 — 별도 calib를 돌리지 않은 이유.** PolyServe의 수요
모델은 chat의 용량을 실측보다 낮게 잡는 것이 이미 알려져 있어(3000 rpm에서 chat
100% 달성) 그 모델로 rate를 정할 수 없다. 대신 **디코드 법칙에서 직접 계산**했다.
짧은 swe에서 m1의 요청당 평균 KV는 약 1,864 토큰이므로

```
step = c0 + c_kv*B*KV + c_n*B = 16.4 + 0.106 B  ms
chat의 50 ms 예산  ->  B <= 317
엔진당 처리량      =  317 / 50 ms = 6,340 출력토큰/s
4대 / 평균 출력 395 토큰  ->  64 req/s = 약 3,850 rpm  (m1의 포화점)
```

같은 계산이 m2에 4,330 rpm, m3에 3,078 rpm을 준다. 세 믹스가 3,000~4,300 사이에
모이므로 **한 rate 리스트(1200 저부하 / 2400 중간 / 4800 과부하)가 셋을 다 커버한다.**
polyserve arm 자체가 calib 역할을 하므로 별도 조건에 시간을 쓰지 않는다.

### 워크로드가 설계대로 나왔다

| 클래스 | 요청 수 | 실측 입력 평균 | 실측 출력 평균 | 설계값 |
|---|---|---|---|---|

| deepresearch | 2,952 | 4,074 | 278 | 4,055 |
| swe | 1,488 | **5,930** | **523** | 6,812 (tiktoken 기준) |

- 요청 비율 10 : 1.98 : 1 — m1 목표(10:2:1)와 일치.
- 실현 입력 토큰 비율 32.2 / 39.1 / 28.7% — 목표 31/37/31%와 일치.
- swe 입력이 5,930으로 설계값 6,812보다 13% 낮은 것은 **토크나이저 차이**다.
  생성 스크립트는 cl100k_base로 세고 실측은 서버 쪽 계정이다. 5,930은 사용자가
  제시한 5~7k 범위 안이다.
- **출력 길이가 안 변했다**: swe 523, 원본 transcript의 기록값 평균 560. 메시지를
  가운데에서 자르고 끝의 지시문을 보존한 설계가 의도대로 동작했다는 확인이다.
  뒤를 잘랐다면 모델이 하는 일이 바뀌어 출력 길이가 달라졌을 것이다.

### ⭐ PolyServe의 파티션이 움직인다 — 그것도 예상보다 강하게

옛 워크로드에서 재분할은 **459 샘플 동안 변화 0회**였다. 같은 코드가 이 워크로드에서는
**한 조건 안에서 13회** 바꾼다. 기동 과도구간을 뺀 정상 상태만 보면:

```
t(s)   swe(25) chat(50) dr(100)
  79      2       1       1
 140      1       2       1     <- 이동
 170      2       1       1     <- 30초 만에 복귀
 322      1       2       1
 342      2       1       1     <- 20초 만에 복귀
 433      1       1       2     <- 세 번째 배정
 453      2       1       1     <- 20초 만에 복귀
```

**믹스가 고정인데도 배정이 세 가지 구성 사이를 오간다.** 원인은 수요 추정의 잡음이다.
같은 조건에서 관측된 수요 진폭:

```
 25ms(swe)  min 0.035  median 1.458  max 2.380   (68.7배)
 50ms(chat) min 0.064  median 1.285  max 1.866   (29.3배)
100ms(dr)   min 0.663  median 0.987  max 1.434   ( 2.2배)
```

세 tier의 median 수요가 1.458 / 1.285 / 0.987로 **거의 같다**. 이것이 토큰 비율로
믹스를 정의한 직접적 결과다 — 그리고 largest-remainder 배분은 수요가 비슷할 때
경계에 놓이므로, EWMA(α=0.5)가 도착 잡음을 따라가는 것만으로 정수 배정이 뒤집힌다.

**즉 정적 파티션의 문제는 "느리게 따라간다"가 아니라 "균형점에서 진동한다"이다.**
migration이 꺼져 있으므로 tier가 바뀐 서버는 옛 tier의 in-flight 요청을 끝까지 들고
있고, 20~30초마다 그 상태가 반복된다. EXP-28이 인위적으로 만들려던 조건이
**고정 믹스에서 저절로 발생**하고 있다.

단, 이 조건은 부하가 낮다(KV 1.5~9%, 최대 대기열 8). **진동이 비용을 발생시키는지는
2400/4800 rpm 조건을 봐야 판정된다.** 낮은 부하에서는 두 클래스를 동시에 들어도
예산이 남기 때문이다.

### 확인 필요 — prefix hit rate가 93.8~96.4%로 높다

네 엔진 모두 94% 이상이다. 이것은 워크로드 단축 때문이 아니라 **literal replay와 낮은
부하의 조합**이다: 1,500개 transcript와 1,000개 대화를 순환 재생하는데 KV가 1.5~9%밖에
안 차서 캐시가 아무것도 축출하지 않는다. 옛 워크로드에서도 KV 압력이 없던 엔진은
94.5%였고, 압력이 있던 엔진만 66%로 떨어졌다.

**높은 rate 조건에서 이 값이 떨어지는지 확인해야 한다.** 전 rate에서 95%면 이 실험의
prefill 비용이 비현실적으로 작다는 뜻이고, 그때는 풀 크기를 키우는 것(transcript
레코드 수, 대화 수)을 검토해야 한다.

| fluidserveflat | `FS_CLASS_HARM=false` (v19만) | v20의 기여. damage 추정이 "아직 예산을 지키는 incumbent의 합"으로 되돌아가, 자기 클래스가 이미 늦기 시작한 인스턴스가 0으로 읽힌다 |

`FS_AFFINITY=false`와 별개의 스위치인 이유: affinity는 feasible 집합의 정렬을
끄는데, **v20이 작동하는 영역은 feasible이 하나도 없는 영역**이라 그 정렬은 애초에
실행되지 않는다. 한 스위치로 재면 둘의 합을 보고하게 된다.

바이너리는 `scheduler-exp07-v20a`(스위치 포함)이고, 스크립트가 설치 후
**파드 안에서 `md5sum /proc/1/exe`를 읽어 실행 중인 바이너리를 대조**한다.
파일 시각이나 spec으로는 잡히지 않는 실패를 잡는 유일한 방법이다.

## ⭐ 중간 관측 6 — 등가중 집계가 이 믹스들에서는 오도한다. 채점을 하나 더 붙인다

m2의 4800 rpm에서 **두 집계 방식이 정반대를 가리킨다.**

| m2 4800 rpm | 등가중(클래스) | 요청당 | goodput | chat / dr / swe |
|---|---|---|---|---|
| polyserve | **71.7** | **22.3** | 5,709 | 15.1 / 100.0 / 100.0 |
| fluidserve | 57.5 | **53.9** | **10,902** | 52.7 / 79.9 / 40.1 |
| **차이** | **PolyServe +14.2** | **FluidServe +31.6** | **FluidServe 1.9배** | |

원인은 산술이다. **m2는 요청의 93%가 chat**이고 dr 4.7%, swe 2.3%다.
PolyServe는 chat을 15.1%로 떨어뜨리면서 dr/swe를 100%로 지킨다. 등가중은
`(15.1+100+100)/3 = 71.7`로, **트래픽의 4.7%와 2.3%를 지닌 두 클래스에게 93%를 지닌
클래스와 같은 발언권**을 준다. 요청당으로 세면 `0.930×15.1 + 0.047×100 + 0.023×100
= 22.3`이다.

**등가중은 믹스가 요청 수 기준 1:1:1이던 동안에는 요청당 집계와 같은 값이었다.**
EXP-21~25가 그 조건이었기 때문에 하나만 보고해도 문제가 없었다. 믹스를 토큰 비율로
정의하면서 클래스별 요청 수가 40배까지 벌어졌고, 그 순간부터 둘은 다른 값이다.

**둘 다 보고한다. 어느 쪽도 단독으로는 옳지 않다.**

| | 무엇을 답하나 | 무엇을 가리나 |
|---|---|---|
| 등가중 (클래스) | 굶는 서비스 tier가 있는가 | 지배적 클래스가 굶어도 건강한 소수 클래스 둘 뒤에 숨는다 |
| 요청당 | 트래픽의 몇 %가 약속받은 것을 받았나 | 지배적 클래스가 건강하면 굶는 소수 클래스가 묻힌다 |

**token goodput은 이 선택에 의존하지 않는다**(정의상 요청 수로 가중된다). 그리고
m2 4800에서 goodput은 FluidServe 1.9배로 요청당 집계와 같은 방향을 가리킨다.

### 판정

- **저부하 회귀 없음(필수 조건) 통과** — 20·40 req/s 모두 100.0 ±0.0

- **90% 목표는 용량 이내(60 req/s까지) 달성**, 80 req/s만 3점 미달
- **네 지표 × 네 rate 전부 우세** — offered 분모로도 등가중으로도

### 사전 등록 지표 하나가 틀렸다

"pend가 85.5%에서 크게 떨어지면 귀속이 맞다"고 적어뒀는데 **안 떨어졌다**(84.4%).
그런데 결과는 크게 좋아졌다. **보유의 양이 아니라 보유를 언제 끝내는가**가 문제였고,
60 req/s에서는 78%를 보유하면서 98.9를 낸다. 중간 지표를 결과의 대리로 삼은
두 번째 실패다(첫 번째는 §pass 2의 "3.0 ms가 전부"였다).

### 60 req/s를 넣은 것이 결정적이었다

goodput이 **60에서 21,468로 정점**을 찍고 80에서 18,767로 내려온다. 디코드 법칙에서
계산한 m1의 포화점이 약 64 req/s이므로 **모델과 측정이 맞는다.** 40과 80만 봤으면
이 봉우리를 못 봤고, "용량까지는 전부 지키고 초과분만 거절한다"는 형태도 확인하지
못했을 것이다.

PolyServe는 이 형태가 없다 — **40 req/s(용량의 62%)부터 평평**하다. 남은 38%는
하드웨어가 없어서가 아니라 라우팅이 못 쓰는 것이다.
