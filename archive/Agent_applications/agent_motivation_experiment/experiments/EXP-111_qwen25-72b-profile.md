# EXP-111 — Qwen2.5-72B-Instruct 로 모델을 바꾸고 오프라인 프로파일을 다시 재다

**2026-09-03.** 두 번째 모델에서 FluidServe 를 재기 위한 준비 단계다. 결과 자체는
정책 비교가 아니라 **엔진과 모델의 성질** 이고, 그 위에서 도착률 격자와 예산을 정한다.

## 1. 무엇을 바꿨고 무엇이 그대로인가

| | 이전 | 지금 |
|---|---|---|
| 모델 | `meta-llama/Meta-Llama-3.1-70B-Instruct` | **`Qwen/Qwen2.5-72B-Instruct`** |
| `max_model_len` | 40,960 (우리가 정한 천장) | **32,768** (모델의 `max_position_embeddings`, 선택이 아님) |
| 함대 | 4 인스턴스 × TP=2, 8× B200 | 같음 |
| 워크로드 | `mix_short_m1_t75.json` | 같음 |

**32,768 이 워크로드를 자르지 않는다**: 세 클래스를 통틀어 한 요청의 최대가 입력 16,696 +
출력 7,830 = **17,588 토큰**(EXP-110 의 10 req/s run)이라 1.9 배 여유가 있다.

**swe transcript 는 다시 만들지 않는다.** 그것은 입력이고, 두 토크나이저가 같은 내용을
사실상 같은 개수로 센다 — 400 건 표본에서 **Qwen/Llama 토큰 수 비가 중앙값 0.999, 범위
0.995~1.037** 이다(둘 다 영어·코드에 맞춘 BPE, 어휘 128k 대 152k). `recorded_input_tokens`
도 그대로 쓸 수 있고, 인용할 때 **Llama 토크나이저로 잰 값** 이라는 것만 밝힌다.

## 2. 모델 정체가 적혀 있는 자리는 일곱 곳이고 다섯은 어긋나도 조용하다

`ms_dev/scripts/switch_model.py` 를 만들어 표 하나에서 여섯을 설정하고 **엔진에게 직접
물어 확인** 한다. 여섯은 LWS 의 `llumnix.io/model` 라벨, `vllm serve` 의 모델 인자, 엔진의
`--max-model-len`, `TP_SIZE`/`DP_SIZE_LOCAL`, **게이트웨이의 `--tokenizer-path`**, 게이트웨이의
`--max-model-len` 이다. 다섯째가 가장 위험하다 — 게이트웨이는 그 토크나이저로 프롬프트
토큰 수를 세어 스케줄러에 넘기므로, 옛 모델의 것을 남겨 두면 **모든 prefill 추정이 틀리고
어떤 로그도 그 사실을 말하지 않는다.**

일곱째는 `ms_dev/scripts/set_scheduler_profiling.py` 가 프로파일 디렉토리를
`llama31-70b-b200-tp2` 로 고정하고 있던 것이다. 기본값은 그대로 두고 **`FS_PROFILE_DIR`**
로 바꿀 수 있게 했고, **어느 디렉토리를 읽었는지 찍게** 했다.

⚠ **아직 남은 것**: 러너 템플릿 **15 개**에 `--model meta-llama/Meta-Llama-3.1-70B-Instruct`
가 하드코딩돼 있고 그 값이 요청 payload 로 그대로 간다(`run_experiment.py:1239`). 프로파일용
`runner-exp111.template.yaml` 만 치환자 `__MODEL__` 로 바꿨다. **본 sweep 을 걸기 전에
드라이버가 쓰는 템플릿을 전부 고쳐야 하고, 안 고치면 모든 요청이 없는 모델을 이름으로 부른다.**

## 3. 측정 방법

- **`ttft.json`** — `measure_ttft_sweep.py`, 유휴 엔진에 한 번에 한 요청, 20 개 길이 × 5 반복.
  반복마다 새로 뽑은 임의 토큰이라 prefix cache 가 개입하지 않는다.
- **`tpot.json`, `fluidserve.json`** — `run_exp111_profile.sh` 가 **10 · 20 · 30 · 45 · 60 req/s
  × 5 분**, 엔진은 `llumnix_sched.InstrumentedScheduler`(정렬은 stock vLLM 과 동일, 계측만
  추가), 라우팅 정책은 **`load-balance`**. FluidServe 로 돌리면 지금 만들고 있는 표를 필요로
  하는 순환이 생긴다. 도착률을 넓게 편 이유는 **KV 항과 배치 항이 포화에서 공선성을 갖기**
  때문이다(EXP-16 1 단계가 한 포화 도착률에서만 재어 VIF 약 11 이었다).
  step dump 총 **177,820 step**, decode-only **160,565 step**, 38 셀.

## 4. 결과 — 엔진 물리는 거의 같고, 출력 길이가 크게 다르다

**prefill step 비용은 전 구간에서 4.5% 이내로 같다** (1~65,536 토큰, Qwen/Llama 비 0.94~1.05).
80 층에 hidden size 가 비슷해 prefill FLOPs 가 거의 같다.

**decode step law** `t = c0 + c_kv·M + c_n·n` (M = 인스턴스가 든 KV 토큰 수, n = 디코드 중인
요청 수):

| 항 | Llama-3.1-70B | Qwen2.5-72B | 비 |
|---|---|---|---|
| `c0` (ms) | 16.361 | **18.125** | 1.108 |
| `c_kv` (ms/토큰) | 1.2822e-05 | **1.3325e-05** | 1.039 |
| `c_n` (ms/요청) | 0.07643 | **0.05672** | 0.742 |
| R² | 0.952 | **0.978** | |

`tpot.json` 격자 247 셀을 셀마다 비교하면 비의 p10/p50/p90 = **0.83 / 1.04 / 1.21** 이다.

**출력 길이는 크게 늘었다** (완주한 요청만; 잘린·거절된·오류 요청은 생성기가 제외한다):

| class | Llama mean / p50 / p90 | Qwen mean / p50 / p90 | mean 비 |
|---|---|---|---|
| chat | 428 / 389 / 766 | **519 / 484 / 1020** | **1.21** |
| deepresearch | 985 / 973 / 1246 | **1826 / 1809 / 2394** | **1.85** |
| swe | 494 / 486 / 645 | **1006 / 977 / 1518** | **2.04** |

출력 상한 4,096 에 닿은 요청은 **0.01~0.21%** 뿐이라 분포가 상한에 눌리지 않았다.
표본 수는 chat 16,277 / deepresearch 2,290 / swe 1,438 이다(Llama 표는 훨씬 많은 run 을
합친 것이라 n 이 백만 단위다 — **표본 수가 다르다는 것을 인용할 때 같이 적는다**).

## 5. 그래서 무엇이 달라지는가

**① 용량이 약 3분의 2로 준다.** 믹스 가중 평균 출력이 519 → 758 토큰(×1.461)이고 decode
step 시간이 ×1.04 이므로 요청 하나가 요구하는 디코드 작업이 **×1.52**, 초당 처리 가능한
요청 수는 **×0.66** 이다.
→ **무릎 추정**: FluidServe 28.0 → **약 18.4 req/s**, llm-d 19.9 → **약 13.1 req/s**.
→ **지금 정적 격자(10·15·20·25·35·45·55·70)를 그대로 쓰면 무릎 아래 점이 두세 개뿐** 이고
나머지가 전부 깊은 과부하에 놓인다. 격자를 왼쪽으로 옮겨야 한다.
⚠ **이 18.4 는 프로파일에서 유도한 추정이지 측정이 아니다.** 격자를 확정하기 전에 몇 점을
실제로 재서 무릎을 확인한다.

**② per-token 약속이 뜻하는 실제 소요 시간이 늘어난다.** 예산 자체(chat 50 / swe 75 /
deepresearch 100 ms per token)는 **속도에 대한 약속** 이므로 모델이 바뀌어도 그대로 두는 것이
맞지만, 평균 출력 길이에 곱하면 뜻이 달라진다:

| class | Llama | Qwen |
|---|---|---|
| chat (5 s + 50 ms/tok) | 26.4 s | **31.0 s** |
| swe (7 s + 75 ms/tok) | 44.0 s | **82.5 s** |
| deepresearch (10 s + 100 ms/tok) | 108.5 s | **192.6 s** |

→ v0.4 에서 swe 를 전체 시간에서 per-token 형태로 바꾼 이유가 여기서 값을 한다 — 전체 시간
30 초로 채점했다면 Qwen 의 swe 는 평균조차 지킬 수 없는 약속이 됐을 것이다. **다만 논문에
쓸 때는 "같은 per-token 약속이 이 모델에서는 평균 82.5 초를 뜻한다"를 같이 적어야 한다.**

## 6. 이번에 걸린 것

- **`local rps=$1 rpm=$((rps * 60))`** — bash 는 한 줄 전체를 먼저 확장하므로 산술식이
  아직 없는 `rps` 를 읽고 `set -u` 로 죽는다. 두 문장으로 나눈다.
- **`kubectl apply` 에 살아 있는 객체를 그대로 넣으면 `resourceVersion` 이
  `last-applied-configuration` 주석에 박힌다.** 그 뒤 그 필드를 (올바르게) 빼고 apply 하는
  도구가 3-way merge 에서 **그 필드를 지우라는 지시** 를 만들어 LWS 가
  `resourceVersion: Invalid value: 0` 으로 거부한다. `switch_model.py` 가 서버 관리 필드를
  벗기도록 고쳤고, 낡은 주석은 지웠다.
- **그 실패를 드라이버가 무시했다** — 호출이 파이프라 상태가 grep 의 것이 된다. 지금은
  `PIPESTATUS` 로 읽어 중단하고, **엔진이 실제로 `InstrumentedScheduler` 인지 확인한 뒤에만**
  부하를 보낸다.
- **"네 포트가 답한다"는 준비 검사가 아니다** — 교체 직전의 옛 파드가 답하면 그대로 통과한다.
  실제로 10 초 만에 통과해 옛 모델을 가리켰다. **서빙하는 모델 이름까지 확인한다.**
