# EXP-135 — 클래스별 인스턴스 상한을 한 시간 trace 에서 뺀다

2026-09-14 KST. EXP-134 의 직접 후속이고, **채택 결정이 내려진 자리에서 다시 잰 것**이다.

## 1. 왜

EXP-134 가 **정적 35 req/s** 에서 상한 하나만 빼면 **+10.3~+12.5 점**이라고 쟀다. 그런데
EXP-107 은 상한을 그 셀에서 채택하지 않았다 — 근거는 **이 한 시간 mix-shift trace 의
재분배**였고, chat 이 많은 구간에서 deepresearch 가 8~12 점 올랐다는 것이었다. **정적 한 셀은
그 양을 재지 않는다.** 그래서 같은 한 플래그 변경을 이 trace 에서 2 반복 돌렸다.

## 2. 설정

`nocaphour` = 배포 설정(`fsv3capgnofrct75`)에서 `--fluidserve-class-instance-cap=false`
**하나만**. arm 정의를 대조군과 diff 해서 다른 항목이 `FS_INSTANCE_CAP` 하나뿐인 것을
확인했다. 대조군은 **EXP-109 의 2 반복**(디스크에 있다, 다시 안 돌렸다).
채점 `FS_SWE_TBT_MS=75`.

## 3. 결과 — **총점은 안 움직이고, deepresearch 가 잃는다**

| | 대조군 r1 / r2 | 상한 제거 r1 / r2 | 판정 |
|---|---|---|---|
| 모든 도착 | 78.5 / 77.8 | **78.5 / 78.4** | **−0.1 ~ +0.7, 차이 없음** |
| admitted | 98.3 / 98.3 | 98.6 / 98.5 | 차이 없음 |
| 거절률 | 19.9 / 20.6% | 20.2 / 20.2% | 차이 없음 |
| goodput | 11,521 / 11,465 | 11,463 / 11,425 | −0.4 ~ −0.8%, 차이 없음 |

**클래스별 (모든 도착)**

| | 대조군 r1 / r2 | 상한 제거 r1 / r2 | 차이 |
|---|---|---|---|
| chat | 84.3 / 83.1 | 84.8 / 84.9 | +0.5 ~ +1.8 |
| **deepresearch** | 68.0 / 69.1 | **66.0 / 65.7** | **−2.0 ~ −3.4** |
| swe | 67.2 / 65.6 | 67.4 / 66.8 | −0.4 ~ +1.2 |

**두 arm 의 deepresearch 구간이 겹치지 않는다**(대조군 68.0~69.1, 처리군 65.7~66.0).
판정 문턱 1.0/3.0 을 걸치므로 **크기는 판정하지 않지만 방향은 분명하다: 상한을 빼면
deepresearch 가 잃고 chat 이 조금 얻는다.** 그것이 EXP-107 이 상한을 채택한 이유다.

**믹스 단계별 deepresearch** (EXP-107 이 근거로 삼은 양)

| arm | m2 (chat 93%) | A (36%) | m1 (75%) | B (61%) |
|---|---|---|---|---|
| 대조군 r1 / r2 | 90.9 / 99.8 | 61.6 / 62.5 | 91.2 / 91.6 | 60.7 / 61.5 |
| 상한 제거 r1 / r2 | 92.4 / 90.1 | 61.6 / 61.5 | 90.2 / 84.5 | 56.3 / 58.4 |

⚠ **단계별 값은 반복 간 편차가 크다** — 대조군 자신이 m2 에서 90.9 와 99.8 로 8.9 점,
처리군이 m1 에서 90.2 와 84.5 로 5.7 점 벌어진다. **단계 하나를 근거로 삼으면 안 된다.**
읽을 수 있는 것은 **B 구간(chat 61%)에서 네 값이 60.7·61.5 대 56.3·58.4 로 겹치지 않는다**는
것뿐이고, 나머지 세 구간은 편차 안이다.

## 4. 그래서 상한은 무엇인가

**두 실험을 같이 읽으면 일관된 그림이 나온다.**

| | 상한을 빼면 |
|---|---|
| **정적 35 req/s** (부하가 계속 걸린다) | **+10.3 ~ +12.5 점.** 거절이 절반이 되고 admitted 는 그대로 |
| **한 시간 trace** (평균 27.4 req/s, 절반이 무릎 아래) | **0 점.** 대신 deepresearch 가 2.0~3.4 점 잃는다 |

**상한은 용량을 대가로 클래스 보호를 사는 장치다.** 그 대가는 **용량이 구속할 때만** 청구된다
— 정적 35 req/s 는 계속 구속하므로 10~12 점을 물고, 한 시간 trace 는 절반의 시간이 무릎
아래이므로 물지 않는다(EXP-70 이 이 시스템의 무릎을 28.1 req/s 로 쟀고 trace 의 평균 도착률이
27.4 req/s 다).

**따라서 EXP-107 의 채택은 이 trace 에서 유효하고, EXP-134 의 결과는 그것을 뒤집지 않는다.**
바뀌는 것은 **무엇을 같이 적어야 하는가**다.

## 5. 논문에 같이 적어야 하는 것

1. **상한의 비용은 도착률의 함수다.** "상한이 deepresearch 를 보호한다"만 적으면 안 되고,
   **지속 부하에서는 10~12 점을 문다**는 것을 같이 적는다. 심사에서 정확히 그 자리를 친다.
2. **한 시간 trace 의 총점으로 상한을 정당화할 수 없다** — 총점은 0 이다. 정당화하는 것은
   **deepresearch 의 2.0~3.4 점**이고, 그것은 클래스별로 봐야 보인다.
3. **가능한 개선**: 상한의 한도가 수요에서 유도되는데(`capmult=3.0`), **지속 부하에서 너무
   빡빡하다.** 도착률이나 거절률에 반응하게 만들면 두 조건 모두에서 이길 수 있다. 아직 안 쟀다.

## 6. 남은 것

- **도착률 축**: 상한의 비용을 25·35·45·55 req/s 에서 재면 곡선이 되고, 언제부터 물기
  시작하는지가 나온다. 2 arm × 4 rate × 2 반복 ≈ 3.5 시간.
- **`capmult` 축**: 3.0 을 4.0·6.0 으로 올리면 정적에서의 비용이 얼마나 줄고 한 시간에서의
  보호가 얼마나 남는지.
