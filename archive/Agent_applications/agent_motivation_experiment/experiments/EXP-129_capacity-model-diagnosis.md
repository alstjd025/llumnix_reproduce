# EXP-129 — Qwen2.5-14B 8인스턴스 함대의 decode step 법칙이 왜 맞지 않는가

작성 2026-09-12. 클러스터를 건드리지 않고 이미 저장된 step dump만 읽어서 한 분석이다
(분석 당시 `bench-runner-exp111`이 돌고 있었다).

## 0. 무엇을 물었나

용량 모델이 쓰는 decode step 법칙은

    t = c0 + c_kv * M + c_n * n      (M = 그 인스턴스가 들고 있는 KV 토큰 수, n = decode 중인 요청 수)

이고, `ms_dev/scripts/gen_profiling_from_stepdump.py`가 step dump에서 이 계수를 적합한다.
Llama-3.1-8B에서는 R2 0.980 / 셀별 상대오차 중앙값 8.0%, Qwen2.5-72B에서는 R2 0.978인데
**Qwen2.5-14B에서는 R2 0.80 / 상대오차 중앙값 57.5%**이고 데이터를 네 배로 늘려도 그대로였다.

네 가지를 물었다. ⑴ prefill 간섭 항을 넣으면 예측이 되는가, ⑵ `interval_ms`가 정말 그 step의
계산 시간인가 아니면 엔진이 step을 돌지 않은 시간까지 포함하는 벽시계 간격인가, ⑶ 앞뒤가 모두
decode-only인 구간으로 제한하면 고원(plateau)이 사라지는가, ⑷ batch 100~250에서 도는 정책이
쓸 수 있는 `tpot.json`을 어떻게 만드는가.

**먼저 기준선을 그대로 재현했다.** 같은 스크립트의 `decode_cells` + `fit_decode_model` 경로로
Qwen2.5-14B는 R2=0.8004 / p50 57.5% / p90 77.6% (셀 50개, decode-only step 1,326,131건),
Llama-3.1-8B는 R2=0.9800 / p50 8.0% / p90 13.4% (셀 57개, 1,101,148건)이 나왔다. 문제 제기에
적힌 수치와 소수점까지 같으므로 **아래 분석은 같은 양을 보고 있다.**

사용한 데이터: Qwen2.5-14B는 `results/*exp129[pq]_r*_rpm_*`의 10개 run(도착률 5~160 req/s,
step 기록 1,391,918건), Llama-3.1-8B는 `results/*exp114prof_r*_rpm_*`의 5개 run(도착률 20~200
req/s, 1,191,503건)이다. 두 함대 모두 8인스턴스 × TP=1이고 워크로드 입력 분포가 같다.

새로 만든 분석 코드는 `analysis_scripts/exp129_stepdump_linked.py`(엔진별 step 사슬 복원)와
`analysis_scripts/exp129_decode_model_candidates.py`(후보 모델 적합)다.

## 1. `interval_ms`는 무엇을 재는가 (질문 2)

### 1.1 정의 — 벽시계 간격이 맞다

`patches/vllm-sched/llumnix_sched.py`의 `InstrumentedScheduler.schedule()`이 만든다.

```
t0 = time.perf_counter_ns()          # schedule() 진입
...
out = super().schedule()
t1 = time.perf_counter_ns()
...
interval_ms = (t0 - last) / 1e6      # last = 직전 step의 t0
```

즉 **연속한 두 `schedule()` 진입 시각의 차이**이고, GPU 타이머가 아니다. 이 간격 안에서
엔진이 무엇을 했는지는 이 값만으로 알 수 없다. 클래스 주석도 "enter-to-enter gap"이라고
적고 있고, 생성 스크립트의 모듈 docstring도 async scheduling에서 이 값이 이봉분포라고
경고해 두었다.

### 1.2 한 칸 어긋나 있다 — row k의 `interval_ms`는 step k−1의 일을 잰다

간격의 시작점이 **직전** step의 진입 시각이므로, `interval_ms[k]`가 덮는 구간에서 엔진이
실행한 것은 step k−1의 배치다. 그런데 `decode_cells`는 `interval_ms[k]`를
`prefill_tokens_step[k]`로 거른다. **한 칸 어긋난 짝을 맺고 있다.**

측정으로 확인했다. decode-only인 행만 놓고, 이웃 중 정확히 한쪽만 prefill인 경우를 갈랐다
(batch를 통제했고, 괄호 안은 표본 수).

| 구분 | Qwen2.5-14B 중앙값 | Llama-3.1-8B 중앙값 |
|---|---|---|
| A 앞뒤 모두 decode-only | 6.71 ms (1,219,586) | 4.50 ms (986,625) |
| B **직전** step이 prefill | 66.50 ms (26,530) | 11.21 ms (47,560) |
| C **직후** step이 prefill | 51.98 ms (26,316) | 9.26 ms (47,526) |

batch를 통제하면 갈림이 분명하다. Qwen에서 B/A는 batch 구간별로 1.24~2.45인데 **C/A는
0.98~1.20**이고, Llama에서도 B/A 1.00~2.26 대 C/A 0.96~1.01이다. **직전 step이 prefill이면
느려지고 직후 step이 prefill인 것은 거의 영향이 없다** — `interval_ms[k]`가 step k−1을 잰다는
뜻이다.

이것이 기존에 "느린 decode step은 41.0%가 prefill step에 인접해 있다"로 관측된 것의 정체다.
인접이 아니라 **직전**이고, 방향이 있다.

### 1.3 여덟 엔진이 한 파일에 섞여 쓴다

`SCHED_STEP_LOG`는 파드 환경변수 하나이고 `vllm serve`가 for 루프로 **여덟 번 독립 실행**되므로
(LWS `neutral`의 vllm 컨테이너 명령, `DP_SIZE_LOCAL=8`, `TP_SIZE=1`, 인스턴스마다
`CUDA_VISIBLE_DEVICES` 하나), 여덟 프로세스가 같은 경로를 `open(path,"a")`로 열고 쓴다.
`step` 값 1이 파일에 8번 나오고 한 step 값의 최대 중복도가 8이다. `_last_enter_ns`와 `_step`은
클래스 속성이라 프로세스마다 따로이므로 `interval_ms` 자체는 각 엔진에서 올바르지만,
**파일에서 바로 앞줄이 같은 엔진의 직전 step이라는 보장이 없다.** 로그 파일은 1초마다 도는
배출 스레드가 프로세스별 덩어리로 쓰므로 파일 인접은 대체로 같은 엔진 안이지만 경계에서 깨진다.

생성 스크립트는 이것을 알고 `link_chains`로 사슬을 복원한다. 다만 그 판정이
`|t_wall[예측 직전] − t_wall[후보]| < 2 ms`인데, `t_wall`은 `super().schedule()`이 끝난 뒤
찍는 `time.time()`이고 `interval_ms`는 진입 시각 기준이라 **잔차가 `|t_schedule[k] −
t_schedule[k−1]|`이 된다.** 그래서 스케줄링 시간이 출렁이는 **부하가 높은 step만 골라서**
연결에 실패한다. 실측 연결률이 80.0~100.0%였고 도착률 45 req/s에서는 엔진 여덟에 대해
사슬이 4,469개로 부서졌다.

`t_wall − t_schedule_us`로 진입 시각을 복원해서 `entry[k−1] = entry[k] − interval_ms[k]`로
맞추면 잔차가 시계 지터 수준이 된다. 허용오차를 0.5 ms로 좁히고도 **연결률 98.6~100%**,
같은 run의 사슬이 4,469개에서 426개로 줄었다. 아래 분석은 전부 이 복원된 사슬을 쓴다.

⚠ 사슬이 부서지면 **사슬의 첫 행은 "뒤에 prefill이 없다"로 보이므로 가짜 pure-decode 구간을
만든다.** 아래 §2의 표는 사슬 경계에서 반경만큼 떨어진 행만 센다.

### 1.4 그런데 이 값은 엔진이 토큰을 내놓는 속도와 정확히 일치한다

엔진 자신이 보고하는 `vllm:inter_token_latency_seconds`(sum/count 델타)와 대조했다. 이 값은
**토큰 가중**이고 `interval_ms`의 단순 평균은 **step 가중**이라 그대로 비교하면 2.3배까지
어긋난다(도착률 15 req/s에서 46.69 대 20.53). 같은 가중으로 맞추면
`Σ(interval_ms × n_decode) / Σ n_decode`가 되고,

**15개 run 전부에서 비가 1.00~1.01이다** (Qwen 10개, Llama 5개; 예: Qwen 45 req/s에서
엔진 89.59 ms 대 89.46 ms, Llama 200 req/s에서 35.84 대 35.83).

서로 다른 두 계층(스케줄러 안의 파이썬 계측과 vLLM 자신의 카운터)이 독립적으로 같은 값을
말한다. 그러므로 `interval_ms`는 **엔진이 토큰 하나를 더 내놓는 데 걸리는 실제 주기**이고,
`tpot.json`이 예측하려는 양이 바로 그것이므로 **표를 만드는 데 쓰기에 올바른 양이다.**

### 1.5 밝히지 못한 것

**그 주기 안에서 GPU가 계산을 하고 있었는지, 무언가를 기다리고 있었는지는 이 데이터로 가를 수
없다.** 수집된 엔진 메트릭에는 GPU 쪽 시간 계열이 하나도 없다(`engine_*.jsonl`에 있는 것은
TTFT/ITL/e2e/queue/prefill/decode의 요청 단위 시간, 토큰 카운터, preemption, prefix cache 뿐이고
`vllm:model_forward_time` 류는 수집 목록에 없다). 따라서 아래에서 "고원"이라고 부르는 것이
계산 시간인지 대기 시간인지는 **미해결**이다. 다만 §1.4 때문에 **그것이 무엇이든 토큰 생산
속도로는 실재한다.**

간접 증거 둘만 적어 둔다.
- `t_schedule_us`(schedule() 안에서만 잰 순수 CPU 시간, 모델과 무관한 같은 코드)의 중앙값은
  두 함대가 batch를 맞추면 비가 0.89~1.32로 비슷하다. 호스트 CPU가 통째로 굶고 있는 상태는
  아니다. 다만 **p90은 Qwen batch 180~259에서 6,276 µs로 Llama의 1,177 µs보다 5.3배**이고
  batch 260 이상에서는 11,982 대 2,723이다. KV 할당기가 포화 근처에서 더 많은 일을 하는
  모습과 맞지만 확인하지는 못했다.
- async scheduling의 run-ahead로 생긴다는 ~0.5 ms 모드는 **실제로 없다**. decode-only step 중
  0.5 ms 미만이 Qwen 0.000% / Llama 0.000%, 2 ms 미만이 0.083% / 0.019%다(최솟값 각각
  0.983 ms, 1.014 ms). 즉 스케줄러 루프는 사실상 항상 무언가에 묶여 있다.

## 2. 고원은 prefill 간섭이 아니다 (질문 3)

### 2.1 앞뒤가 모두 decode-only인 구간으로 제한해도 남는다

각 행에 대해 **같은 엔진의 사슬 안에서** 앞으로도 뒤로도 r개 step이 모두 decode-only인 경우만
골랐다(사슬 경계에서 r 이상 떨어진 행만 센다). 단위는 중앙값 ms, 괄호는 표본 수.

Qwen2.5-14B:

| batch | r≥1 | r≥2 | r≥4 | r≥8 | r≥16 |
|---|---|---|---|---|---|
| 20-39 | 10.5 (23,127) | 10.2 (19,810) | 10.0 (14,543) | 9.6 (7,850) | 9.4 (2,162) |
| 40-59 | 47.8 (5,692) | 45.1 (3,776) | 39.7 (1,452) | **16.0 (208)** | — |
| 60-79 | 61.6 (6,253) | 58.5 (3,799) | 53.1 (1,163) | 47.0 (110) | — |
| 80-119 | 72.1 (10,389) | 68.8 (5,178) | 61.7 (822) | — | — |
| 120-179 | 71.2 (9,748) | 67.4 (4,183) | 59.6 (472) | — | — |
| **180-259** | **86.5 (32,183)** | **86.5 (18,740)** | **90.1 (7,502)** | **92.0 (1,814)** | **84.2 (190)** |
| 260+ | 86.5 (13,320) | 84.8 (8,714) | 84.4 (4,191) | 85.0 (1,224) | 95.4 (157) |

Llama-3.1-8B는 같은 표에서 반경에 거의 반응하지 않는다(batch 180-259: 16.9 → 16.6 → 16.8 →
16.8 → 16.5).

**답: 사라지지 않는다.** batch 180 이상에서는 연속 8 step 이상 순수 decode인 구간에서도
92.0 ms이고(표본 1,814), 같은 조건의 Llama는 16.8 ms다. batch 40~179에서는 반경을 늘리면
값이 내려가지만 표본이 빠르게 마르고(batch 80~179는 r≥8에서 30건도 남지 않는다), 그 구간에서는
prefill step이 항상 8 step 안에 한 번은 들어온다는 뜻이다.

### 2.2 회복은 Llama에서 2 step, Qwen 고batch에서는 일어나지 않는다

직전 prefill step에서 몇 step 떨어졌는지(d)로 본 중앙값 ms:

| | d=1 | d=2 | d=3-4 | d=5-8 | d=9-16 | d=17-32 |
|---|---|---|---|---|---|---|
| Llama batch 180-259 | 16.8 | 28.0 | 16.1 | 16.3 | 16.5 | 16.8 |
| Qwen batch 40-79 | 75.3 | 63.9 | 59.3 | 55.1 | 47.1 | 17.0 |
| Qwen batch 180-259 | 108.8 | 91.2 | 83.8 | 86.1 | 92.1 | 96.3 |

Llama는 d=3에서 이미 바닥에 돌아온다(async scheduling의 파이프라인 깊이와 맞는다). Qwen은
batch 40~79에서 약 20 step에 걸쳐 천천히 내려가고, **batch 180 이상에서는 내려가지 않는다.**

### 2.3 다른 엔진 탓이 아니다

같은 노드의 다른 일곱 엔진이 동시에 prefill을 얼마나 하고 있는지를 100 ms 창으로 세어
(자기 사슬의 기여는 뺐다) 자기 batch를 통제하고 보면, Qwen batch 180-259에서 다른 엔진의
prefill 토큰이 0 / 1~2,000 / 2,000~10,000 / 10,000~30,000일 때 중앙값이
**90.1 / 84.2 / 86.3 / 87.7 ms**다. 단조 증가가 없다. Llama도 마찬가지다(17.1 / 17.0 / 16.7 /
15.9). **호스트를 공유해서 생기는 간섭이라는 설명은 이 데이터로 지지되지 않는다.** 여덟
인스턴스는 vLLM의 data-parallel 랭크가 아니라 각자 GPU 하나를 쥔 독립 `vllm serve`이므로
step 동기화도 없다.

### 2.4 preemption도 아니다

`vllm:num_preemptions_total` 델타로 다시 셌다. `exp129q_r20`은 **preemption 0건**, 생성 토큰
3,784,971개인데 엔진이 보고한 ITL이 65.33 ms다. `exp129q_r30`도 0건에 82.91 ms다. 고원은
preemption이 전혀 없는 조건에서 이미 완성되어 있다.

## 3. 실제로 일어나는 일 — batch 48 부근의 불연속

반경 4 이상 떨어진 pure decode step만 놓고 batch를 잘게 나눈 Qwen2.5-14B의 중앙값이다.

| batch | 표본 | 중앙값 ms | p25 | p75 | KV 총량 중앙값 |
|---|---|---|---|---|---|
| 20-23 | 9,174 | 9.2 | 8.6 | 11.0 | 58,576 |
| 24-27 | 3,890 | 10.4 | 9.4 | 21.8 | 71,508 |
| 28-31 | 3,687 | 12.8 | 9.7 | 26.3 | 83,188 |
| 32-35 | 1,874 | 25.0 | **10.9** | **41.6** | 97,243 |
| 40-43 | 755 | 41.0 | **11.9** | **55.0** | 99,302 |
| 56-63 | 1,508 | 55.2 | 43.3 | 67.6 | 174,033 |
| 96-127 | 4,174 | 69.2 | 57.1 | 83.3 | 360,397 |
| 200-239 | 8,011 | 86.2 | 69.2 | 112.9 | 806,238 |
| 280-399 | 3,599 | 83.7 | 68.3 | 105.2 | 837,037 |

세 가지가 보인다.

1. **batch 24에서 56 사이에 불연속이 있다.** 10 ms 대에서 55 ms 대로 올라간다.
2. **그 전이 구간의 분포가 이봉이다.** batch 32~35에서 p25가 10.9인데 p75가 41.6이고,
   batch 28~47을 모아 보면 8~12 ms에 32%, 35 ms 이상에 32%가 쌓인 두 덩어리다. 비용이
   완만히 오르는 것이 아니라 **두 상태 사이를 오간다.**
3. **불연속 위쪽은 거의 평평하다.** batch 96에서 384로 네 배가 되는 동안 69.2 → 83.7 ms,
   21% 증가에 그친다. 같은 구간에서 Llama는 9.7 → 25.2 ms로 batch에 거의 비례한다.

두 상태는 **한 엔진 안에서 섞이지 않는다.** 해당 batch 구간 step이 50건 이상인 사슬 46개 중
두 모드가 각각 15% 이상 나타난 사슬은 2개뿐이다. 한 엔진은 한동안 빠른 상태이거나 한동안 느린
상태다.

**빠른 쪽은 정상 상태가 아니라 과도 상태였다.** batch 40~79에서 20 ms 미만인 step 1,263건 중
1,225건이 도착률 80·120·160 req/s run의 **run 시작 후 64~67초 지점**에 몰려 있다. 함대가
채워지는 동안 batch가 그 구간을 스쳐 지나가는 순간이다. 도착률 15·20 req/s에서 같은 batch는
run 시작 후 158~214초 지점이고 47~62 ms다. 그러므로 "같은 batch인데 도착률이 높으면 빠르다"는
관측은 **도착률의 효과가 아니라 램프업 과도 구간을 본 것**이다.

한 엔진의 궤적으로도 같은 것이 보인다(`exp129q_r20`, 60 step씩):

```
  t=184.6s  batch 17  KV  47,430  prefill step 1/60   decode 중앙값 10.1 ms
  t=185.3s  batch 19  KV  59,694  prefill step 6/60   decode 중앙값 21.8 ms
  t=187.3s  batch 31  KV  75,350  prefill step 13/60  decode 중앙값 71.2 ms
  t=228.6s  batch 85  KV 161,404  prefill step 11/60  decode 중앙값 71.2 ms
```

전이 뒤에는 KV가 그 전의 세 배가 되어도 값이 거의 그대로다.

**셀 안의 산포도 크다.** 생산 파이프라인이 쓰는 (batch, 요청당 토큰) 셀에서 batch 96 이상인
셀들의 p10/중앙값이 0.60~0.67, p90/중앙값이 1.47~1.65다. Llama의 같은 셀들은 0.85~0.91과
1.20~2.51이다. **(batch, KV)만의 함수인 어떤 모델도 Qwen의 한 step을 ±40% 안으로 맞출 수
없다는 뜻이다** — 셀 하나 안에서 그만큼 흩어져 있다.

그리고 **run 안에서 시간에 따라 올라간다.** batch 180 이상만 놓고 run 시작 후 60~120 /
120~180 / 180~300초로 나누면 도착률 120에서 87.3 → 101.0 → 127.7 ms, 도착률 160에서
87.3 → 93.0 → 141.8 ms다. batch가 같은데도 뒤로 갈수록 느려진다.

### 3.1 원인은 밝히지 못했다

batch 48 부근에서 63 ms짜리 계단이 생기고 그 위가 평평하다는 것은 **배치 크기에 거의 무관한
고정 비용이 어느 문턱 위에서 켜진다**는 모양이다. 같은 함대·같은 워크로드·같은 계측에서
파라미터가 1.75배인 관계의 Llama-3.1-8B가 batch 180~259에서 16.8 ms일 때 Qwen2.5-14B가
92.0 ms인 것(5.5배)은 모델 크기로 설명되지 않는다.

모양이 맞는 후보는 있다. CUDA graph가 어느 크기 위에서 안 쓰이고 eager로 떨어지면 커널 실행
오버헤드가 붙는데 그 비용은 **배치 크기에 거의 무관**하다. 그러나 **확인하지 못했다.**
"capture size 목록에 40, 48, 56 … 512가 들어 있다"는 것은 설정이지 런타임에 graph가 실제로
쓰였다는 증거가 아니다(설정 파일이 존재한다는 것이 그것이 쓰인다는 뜻이 아니다). 엔진의 기동
로그는 `results/` 아래에 보관되지 않고 컨테이너 로그는 회전하므로 지난 run에 대해서는 확인할
방법이 없다.

**다음에 엔진을 띄울 때 기동 직후 로그를 파일로 받아** `Capturing CUDA graphs` /
`graph capturing finished` / eager 폴백 메시지와 실제 capture size 목록을 읽는 것이 이것을
가르는 가장 싼 검사다. 같은 자리에서 attention backend 선택 줄도 같이 읽는다.

## 4. 후보 모델들 (질문 1)

생산 파이프라인과 **같은 공간**에서 적합했다 — (batch, 요청당 토큰) 셀 중 decode-only step이
30건 이상인 셀 하나가 표본 하나이고 목표는 그 셀의 `interval_ms` 중앙값이다. 그래야 Llama의
8.0%와 직접 비교된다.

⚠ **추가 항은 전부 step 수나 토큰 수로 셌고 벽시계 시간으로 세지 않았다.** "최근 벽시계 시간
중 prefill에 쓴 비율"로 정의한 duty는 `interval_ms`로 만들어지는데 그것이 회귀의 목표값이므로,
그런 항을 쓴 적합은 순환논법으로 좋은 점수를 낸다.

### 4.1 자기 표본 위에서

Qwen2.5-14B (셀 50개, step 1,323,899건):

| 모델 | R2 | p50 | p90 | 비고 |
|---|---|---|---|---|
| A `c0 + c_kv·M + c_n·B` (현행) | 0.8002 | 57.5% | 77.5% | 기준선 |
| B A + 직전 32 step의 step당 평균 prefill 토큰 | 0.8801 | 26.4% | 44.8% | 개선하지만 부족 |
| C A + 직전 32 step 중 prefill이었던 비율 | 0.8807 | **8.3%** | **65.7%** | 중앙값만 좋고 꼬리가 나쁘다 |
| D C + 회복항 `exp(−d/8)` | 0.9296 | 35.8% | 97.4% | **실패** |
| E 멱법칙 `exp(a)·B^b·T^c` | 0.7857 | 35.5% | 96.7% | 실패 |
| F A를 pure decode step만으로 적합 | 0.8233 | 48.1% | 67.7% | 거의 나아지지 않는다 |
| G A + `A0·sigmoid((B−48)/8)` | **0.9918** | **4.3%** | **13.4%** | 통과 |

Llama-3.1-8B (셀 57개): A가 0.9800 / 8.0% / 13.4%, C가 0.9840 / 4.1% / 12.8%,
G가 0.9838 / 2.6% / 10.2%다.

**실패한 것들을 그대로 적는다.**
- **D는 R2가 0.9296으로 가장 높게 올라가는데 상대오차 중앙값은 35.8%로 C보다 나쁘다.**
  계수도 `c_p`가 −69.38로 부호가 뒤집히고 VIF가 11.1과 9.9다. prefill 비율과 회복항이 같은
  것을 두 번 세고 있어서 서로 상쇄한다. **R2만 보고 골랐으면 이것을 골랐을 것이다.**
- **C는 중앙값 8.3%로 겉보기에 기준을 통과하지만 p90이 65.7%다.** 아래 교차검증에서 더 나쁘게
  드러난다.
- **F가 가장 중요한 음성 결과다.** 직전 prefill에서 4 step 이상 떨어진 step만으로 다시
  적합해도 48.1%에 그친다. **pure decode run만 모아서 표를 만들면 된다는 방법은 통하지
  않는다.**
- B는 Llama에서 VIF가 `c_n` 103.5, `c_p` 58.8로 터진다. 그 함대에서는 batch와 prefill 토큰이
  거의 같은 것을 말한다.

### 4.2 도착률을 통째로 빼는 교차검증

한 run(= 한 도착률)을 빼고 적합해서 그 run의 셀로 채점했다. 자기가 본 셀을 다시 채점하는
문제를 피하려는 것이다.

| | A p50 평균 | C p50 평균 | G p50 평균 |
|---|---|---|---|
| Qwen2.5-14B (10 폴드) | 58.9% | 30.9% | **5.9%** |
| Llama-3.1-8B (5 폴드) | 8.7% | 6.1% | 3.2% |

C는 폴드별 p90이 46.7%에서 **443.7%**까지 튄다. G의 문턱 `B0`는 10 폴드 중 8번 48이 뽑혔다.

`B0`를 §3에서 측정한 전이 위치인 48로 **고정하고**(폴드마다 다시 고르지 않고) 다시 돌리면
Qwen의 폴드별 중앙 상대오차가 2.6~10.2%, 평균 6.5%다. 전체 데이터 적합은

    t = 6.452 + 1.6056e-05·M + 0.0243·B + 62.93·sigmoid((B−48)/8)   [ms]

이고 자기 표본에서 p50 4.3% / p90 13.4%다.

### 4.3 G를 믿으면 안 되는 이유 두 가지

**첫째, 절대 오차가 SLO 예산만 하다.** 홀드아웃 폴드에서 셀 하나의 최대 절대 오차가
22.4 ~ 59.9 ms다(10 폴드 중 8 폴드가 22 ms 이상). 같은 검사에서 Llama는 0.5 ~ 6.7 ms다.
chat 클래스의 토큰당 예산이 50 ms인데 예측 오차가 그만큼이면 admission 판정에 쓸 수 없다.
폴드별 p90도 6.1%에서 264.2%까지 벌어진다.

**둘째, 운영 구간에서 평평해서 정책에 줄 정보가 없다.** 적합된 계수로 요청당 KV 3,300 토큰을
가정하면 batch 100/150/200/250에서 77.0 / 81.0 / 84.8 / 88.7 ms이고 **요청 하나를 더 받는
한계 비용이 0.077 ms**다. 모델이 "batch 100이든 250이든 한 명 더 받는 것은 공짜"라고 말한다.
그런데 admission 정책이 이 표에 묻는 것이 정확히 그 한계 비용이다. 적합이 잘 되는 이유가
**측정된 표면이 실제로 평평하기 때문**이므로, 적합 품질을 올려도 정책이 쓸 신호는 생기지 않는다.
(계수가 말하는 평평함은 측정과 맞다 — batch 96에서 384까지 74.8 → 90.6 ms, 요청당 0.055 ms다.)

**질문 1의 답: prefill 간섭 항으로는 안 된다.** 최선인 C가 교차검증 중앙값 30.9%에 p90이
최대 443.7%다. 기준(Llama에서 8.0%)을 넘는 것은 prefill 항이 아니라 **batch에 대한 포화 항**
(G, 교차검증 5.9%)인데, 그것은 간섭을 모형화한 것이 아니라 §3의 불연속을 계단 함수로 베낀
것이고 위의 두 이유로 용량 모델로는 쓸 수 없다.

## 5. 권고 — 쓸 수 있는 `tpot.json`을 어떻게 만드나 (질문 4)

### 5.1 지금 당장은 표를 만들 수 있다. 적합이 나쁜 것이 표를 막지 않는다

중요한 사실이 하나 있다. `fill_grid`는 **측정된 셀을 그대로 쓰고**(`source: "measured"`),
모델은 측정되지 않은 셀을 채울 때만 쓴다. 그러므로 R2 0.80은 **채워 넣은 셀의 품질**에 대한
것이지 정책이 실제로 질의하는 셀에 대한 것이 아니다.

파이프라인을 그대로 돌려서 확인했다(스크래치 디렉토리에 출력했고 배포 경로는 건드리지 않았다).
정책이 도는 batch 100~250 · 요청당 2,048~4,096 토큰 구간의 격자점이 **전부 측정된 셀**이다.

| batch | 요청당 토큰 | p50 ms | 표본 | 출처 |
|---|---|---|---|---|
| 96 | 2048 / 4096 | 74.82 / 77.60 | 6,395 / 6,940 | 측정 |
| 128 | 2048 / 4096 | 77.70 / 78.08 | 4,745 / 11,884 | 측정 |
| 192 | 2048 / 4096 | 78.75 / 81.01 | 5,812 / 19,013 | 측정 |
| 256 | 2048 / 4096 | 86.37 / 95.80 | 6,686 / 52,158 | 측정 |
| 384 | 2048 / 4096 | 91.60 / **138.81** | 3,517 / **0** | 측정 / **모델** |

isotonic 보정은 71개 셀을 최대 1.97 ms(9.5%) 움직였고, Go의 `InterpolationPredictor` 의미를
replay하는 검증에서 모든 질의가 해결됐다.

그러므로 **명령은 이것이다** (모델·하드웨어 문자열과 타임스탬프만 이 함대의 것으로 바꾼다):

```bash
python3 ms_dev/scripts/gen_profiling_from_stepdump.py \
  --results-glob 'Agent_applications/agent_motivation_experiment/results/*exp129[pq]_r*_rpm_*/server_metrics/sched_steps.jsonl' \
  --out-dir deploy/profiling/qwen25-14b-b200-tp1 \
  --model Qwen/Qwen2.5-14B-Instruct \
  --hardware "B200 x1 (TP1) x8" \
  --timestamp "<생성 시각>"
```

`fluidserve.json`의 `classes[]`는 이 모델의 출력 길이 분포로 따로 다시 만들어야 한다
(`ms_dev/scripts/gen_fluidserve_profile.py`). **모델을 바꾸면 세 파일을 전부 다시 잰다.**

### 5.2 그러나 그대로 배포하면 안 되는 이유와, 먼저 할 일

표는 나오지만 **그 표가 인코딩하는 것은 원인을 모르는 고원**이다. 배포 전에 둘을 한다.

1. **batch 48의 계단이 배포 결함인지부터 가른다 (§3.1).** 엔진을 다음에 띄울 때 기동 직후
   로그를 파일로 받아 CUDA graph capture 목록과 eager 폴백 여부, attention backend 선택 줄을
   읽는다. **만약 결함이면 고친 뒤 다시 재야 하고, 지금 표를 배포하면 결함을 물리 법칙으로
   굳혀서 정책이 그것을 최적화하게 된다.** Llama-3.1-8B가 같은 함대·같은 워크로드에서
   batch 180~259에 16.8 ms인데 파라미터 1.75배인 Qwen2.5-14B가 92.0 ms인 것은 모델 크기로
   설명되지 않으므로, 결함일 확률을 낮게 잡을 근거가 없다.
2. **batch 384 / 요청당 4,096 칸을 손으로 막는다.** 그 칸만 모델이 채웠고 값이 138.81 ms인데
   바로 옆 측정값들이 86~96 ms다. 적합이 나쁜 것이 정확히 이 칸으로 새어 들어온다. 격자를
   batch 384까지로 자르거나, 그 칸을 이웃 측정값에서 외삽한 값으로 대체한다.

### 5.3 표를 쓸 때 같이 기록해야 하는 것

- **이 함대의 decode step 시간은 batch 96~384에서 요청당 0.055 ms밖에 오르지 않는다.** 즉
  이 표로 계산한 "요청을 하나 더 받으면 토큰당 시간이 얼마나 늘어나는가"는 거의 0이다.
  용량 판정이 사실상 KV 한계에만 걸리게 되므로, 이 함대에서 나온 결과를 다른 함대의 결과와
  같은 표에 놓을 때 그 점을 밝힌다.
- **셀 하나 안의 산포가 p10/중앙값 0.60~0.67, p90/중앙값 1.47~1.65다.** p50 한 값으로
  예측하면 개별 step에서 40~65% 틀린다. Llama 함대(0.85~0.91 / 1.20~2.51)보다 훨씬 넓다.
- **같은 batch에서도 run이 진행되면 값이 오른다**(도착률 160에서 87.3 → 93.0 → 141.8 ms).
  표는 run 전체의 중앙값이므로 후반부를 과소예측한다.

### 5.4 추천하지 않는 것

- **pure decode run만으로 적합하기**: §4.1 F가 48.1%로 거의 나아지지 않는다. 고원이 prefill
  간섭이 아니기 때문이다(§2).
- **prefill 간섭 항 추가**: §4의 B·C·D 전부 기준에 못 미치거나 불안정하다.
- **모델을 쓸 수 없다고 선언하기**: 정책이 질의하는 셀이 전부 측정되어 있으므로 과한 결론이다.
  문제는 적합이 아니라 **측정된 표면 자체가 이상하다는 것**이고, 그것은 적합을 바꿔서 풀 수
  없다.

## 6. 이 문서가 밝히지 못한 것

1. **고원이 GPU 계산 시간인지 대기 시간인지.** 수집된 엔진 메트릭에 GPU 쪽 시간 계열이 없다
   (§1.5). 토큰 생산 속도로 실재한다는 것만 확인했다(§1.4).
2. **batch 48 계단의 원인.** CUDA graph 폴백은 모양이 맞는 후보일 뿐이고 확인하지 못했다.
   엔진 기동 로그가 보관되지 않아 지난 run으로는 확인할 방법이 없다(§3.1).
3. **왜 같은 batch에서 run 후반이 더 느린가**(§3 마지막). 메모리 단편화, KV 재사용률 변화,
   전력·발열 중 어느 것도 이 데이터로 가릴 수 없다.
4. **Qwen2.5-72B가 왜 멀쩡한지.** 그 함대가 잘 적합된다는 것은 문제 제기에서 주어진 사실로
   받았고 직접 재확인하지 않았다. 72B는 TP 구성이 달라서 batch 48 부근의 같은 문턱을 지나지
   않을 수 있는데 확인하지 않았다.
5. **§1.2의 한 칸 어긋남을 고치면 Llama의 표가 얼마나 달라지는지.** Llama에서는 회복이 2 step
   이라 영향이 작을 것으로 보이지만(§2.2) 표를 다시 만들어 대조하지는 않았다. 이 어긋남은
   `decode_cells`에 그대로 남아 있고 이번에 고치지 않았다.
