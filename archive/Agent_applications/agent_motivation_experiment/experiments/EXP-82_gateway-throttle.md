## 1. 무엇을 고치려는 것인가

부하 생성기는 **서버가 보낸 이벤트가 클라이언트에 도착한 시각의 간격**을 기록하고 그것을
토큰당 시간이라고 부른다(`agent.py`의 `inter_arrival_ms`). 이 값은 보통 엔진이 토큰을 만든
간격과 같지만, **여러 이벤트가 전송 계층에서 묶여 한꺼번에 도착하면** 첫 이벤트에 간격이 몰리고
나머지는 0에 가깝게 기록된다.

**실측**: Llumnix 게이트웨이를 지나는 네 arm(`fspfx`·`polyserve`·`slo`·`vllmcache`)에서 chat
간격의 **12.5~17.2%가 5 ms 미만**이고 1분위가 **0.02 ms**다. Envoy를 지나는 `llmdslo`는
**0.04~0.06%**, 1분위 **15.98~17.07 ms**다. 디코드 step 하나가 약 16 ms 이상이므로 **0.02 ms는
실제 생성 간격일 수 없다.**

**원인은 클라이언트가 아니다.** 고정된 80 run 전부가 같은 클라이언트 클래스, 같은 읽기 루프,
같은 `/v1/completions`, 같은 네 vLLM 엔진을 쓴다(`llmdslo`의 `envoy_access.log`로 확인).
게이트웨이는 이벤트마다 정상적으로 flush한다(`gateway_service.go:236-237`,
`sse_reader.go:112-141`).

**원인은 게이트웨이 컨테이너가 CFS CPU 할당량을 다 써서 커널에 정지당하는 것이다.**
`cpu.max`가 `800000 100000`(100 ms 주기에 8코어)인데 Go가 스레드 수를 호스트 CPU 72개로 잡는다.
할당량이 떨어지면 **다음 주기 경계까지 컨테이너 전체가 멈추므로 살아 있는 모든 스트림이 동시에
얼었다가 동시에 풀린다.**

| 증거 | 값 |
|---|---|
| 묶음 시작점의 동시성 (Fano factor) | **23.688** (시각을 어긋나게 한 대조군 1.077) |
| 한 정지에서 같은 2 ms 구간에 재개되는 스트림 | 살아 있는 chat 스트림 약 78개 중 **76개** |
| 정지 해제 시각이 100 ms 격자에 맞는 정도 | **R = 0.915** (잡음 바닥 0.024; 250 ms·1000 ms 격자는 R≈0.03) |
| 파드의 throttle 누적 | `nr_throttled` 1167, `throttled_usec` 1,869,468,589 (= 전체 시간의 18.7%) |
| 대조 | Envoy는 **같은 노드에서 같은 8코어 제한**인데 묶임이 없다 |

**묶음의 산수가 닫힌다**: 묶음 크기 N에서 묶음 앞 간격 ÷ step = 2.29 / 3.18 / 4.05 / 4.94 / 5.79
(N=2..6)이고 묶음 안 토큰당 폭 ÷ step = 1.17 / 1.08 / 1.05 / 1.03 / 1.01이다. **그 N개 토큰은
정상 속도로 만들어졌고 전달만 함께 됐다.** 묶음이 6~7에서 멈추는 것도 정지가 100 ms 주기를 못
넘기 때문이다(정지 길이 중앙값 49.9 ms, p90 84.7 ms).

## 2. 이것이 무엇을 오염시켰나 — 세 가지, 전부 확인됨

1. **요청 안의 분위수.** `tbt_p90_ms`가 이 결함이 가장 크게 부풀리는 값이다. 10 req/s에서
   보정하면 **42.42 → 27.30 ms**.
2. **엔진 step 시간 복원.** 토큰 도착 시각을 엔진별로 묶어 step 경계를 복원한 값이 오염됐다 —
   정지 하나가 진짜 step N개를 하나로 합치기 때문이다. `fspfx`의 긴 step이 엔진 쌍 사이에서
   **우연의 7.2~12.2배로 동시 발생**하고(관측 15.5~37.3% 대 기대 1.9~3.2%), **40~65%가 독립적으로
   검출한 정지 사건 안에서 끝난다.** `llmdslo`는 각각 **0.0~1.9배, 0.0~1.4%**다.
3. **그리고 오염보다 큰 문제가 하나 더 있었다 — 비교 대상이 틀렸다.** 어젯밤 표는 **우리의 가장
   바쁜 엔진을 llm-d의 가장 한가한 엔진 둘과** 짝지었다. llm-d의 바쁜 엔진 둘(8001·8003)은
   9.6%와 11.1%인데 표에서 빠져 있었다.

**보정하고 같은 기준(엔진 자신의 `num_requests_running` 기준 가장 바쁜 엔진)으로 다시 놓으면:**

| | fspfx (보정) | llmdslo | 반복 폭 |
|---|---|---|---|
| 중앙값 2배 초과 step | 10.4 / 12.1 → **11.3%** | 11.1 / 8.4 → **9.8%** | 1.7 / 2.7 |
| 그 step들이 먹는 시간 | 25.2 / 28.2 → **26.7%** | 44.9 / 37.9 → **41.4%** | 3.0 / 7.0 |

> **차이가 사라진다.** 7~8점이 1.5점이 되어 반복 폭보다 작고, 시간 비중에서는 **부호가 뒤집힌다.**
> **"도착을 모으면 step이 길어진다"는 기제 결론은 성립하지 않는다.** 오염이 2.1점, 엔진 선택
> 오류가 6.7점을 설명한다.

**오염되지 않고 남는 것**: 집중 그 자체(엔진 자신의 게이지로 우리 바쁜/한가한 비 **6.2~7.7배**,
llm-d **1.06~2.6배**), **preemption 0건**, 큐 깊이 거의 0. 엔진이 직접 내보내는 값
(KV 점유·배치 크기·큐 깊이·preemption)은 클라이언트 도착 시각을 거치지 않으므로 전부 깨끗하다 —
**게이트웨이가 멈춰 있는 동안에도 엔진은 계속 돌고 계속 보고한다.**

## 3. 무엇을 바꾸고 무엇은 안 바꾸는가

**바꾸는 것: 환경변수 하나.** `kubectl -n llumnix set env deploy/gateway GOMAXPROCS=16`.
16을 고른 이유는 여유를 두기 위해서다(사용자 지시) — 목표는 스레드 수가 할당량의 9배인 상태를
없애는 것이지 8로 조이는 것이 아니다. **코드·워크로드·정책 설정은 하나도 안 바꾼다.**

적용 확인: 파드 `gateway-fbbbd6f9f-dwcjj`에서 `GOMAXPROCS=16`, `cpu.max` 그대로,
카운터는 새 파드라 0에서 시작.

총계 지표에 대해서만 쟀다. 같은 세션 안의 짝은 그 미지수를 없앤다.

## 5. 사전 등록한 판정 — 실행 전에 적는다

### 5.1 게이트 조건 (25 req/s, `fspfx` 하나) — 이것이 통과해야 나머지 31조건을 돈다

| | 변경 전 실측 | 통과 기준 |
|---|---|---|
| 5 ms 미만 간격 비율 | **14.11%** | **5% 미만** (기대는 1% 미만) |
| 간격의 1분위 | **0.02 ms** | **약 16 ms** (llm-d는 17.07) |
| 요청 내 `tbt_p90_ms` 중앙값 | 42.42 (10 req/s) | 보정으로 얻은 값 27.30 근처 |

**반증 조건**: 5 ms 미만이 5%를 넘게 남으면 **스레드 수 불일치가 원인이라는 설명이 반증된다.**
그러면 남은 후보는 `TimeoutReader.Read`가 **토큰마다 goroutine 하나와 24시간 타이머 하나를
만드는 것**이고(8분 run 하나에 타이머 약 220만 개), 그것은 코드 변경이라 별도 판단이 필요하다.
게이트가 실패하면 체인은 **그 조건 하나만 남기고 멈춘다.**

### 5.2 변하면 안 되는 것 — 이것이 흔들리면 이 실험은 같은 시스템을 잰 것이 아니다

**토큰당 시간의 평균은 전달이 묶이는 것과 무관하다**(전체 디코드 시간 ÷ 토큰 수이고, 이미
엔진 자신의 카운터와 1~2% 안에서 일치한다). 따라서 **SLO 달성률·거절률·token goodput·첫 토큰
시간·전체 시간이 반복 폭 안에서 그대로여야 한다.**

대조할 값(고정된 sweep, 요청 단위 offered 달성률 / goodput / 거절률):

| req/s | `fspfx` | `llmdslo` |
|---|---|---|
| 25 | 95.7 / 11,771 / 2% | 72.4 / 9,397 / 22% |
| 35 | 77.6 / 13,147 / 16% | 42.9 / 8,295 / 52% |
| 55 | 48.3 / 13,184 / 46% | 21.0 / 7,168 / 77% |

⚠ **반복 폭을 넘는 이동이 있으면 그 자체가 결과다** — 게이트웨이가 전체 시간의 18.7%를 멈춰
있었으므로, 그것이 없어지면 **게이트웨이의 보유-재시도 경로를 쓰는 FluidServe에서 처리량이
올라갈 수 있다.** 그 경우 이 실험은 "측정을 고친 것"이 아니라 **"시스템을 고친 것"**이 되고,
**고정된 sweep의 수치를 전부 다시 매겨야 한다.** 어느 쪽인지는 달성률이 말해 준다.

### 5.3 이 실험이 처음으로 가능하게 하는 것

**모든 토큰 간격을 통째로 모은 분위수(p50·p90·p95·p99·p99.9)를 두 arm 사이에서 비교하는 것.**
지금까지는 네 arm에만 있는 결함 때문에 불가능했다. 참고로 오염된 상태의 25 req/s 값은
p50 29.51 대 28.45, p90 **100.42 대 40.71**, p95 157.42 대 118.20, **p99 391.54 대 412.53**이다 —
**p99에서는 이미 우리가 낫다.**
