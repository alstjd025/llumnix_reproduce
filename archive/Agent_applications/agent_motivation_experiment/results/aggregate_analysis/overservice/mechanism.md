# 클래스 선호가 왜 약하게만 작동하는가 — 코드와 측정을 맞춰 본 결과

**2026-08-24 오후. 클러스터를 쓰지 않았다.** `README.md`(과잉 서비스)의 후속이고, 그 문서의
결론 하나를 뒤집는다. 사용자 질문 셋에서 출발했다.

## 1. ⚠ 정정 — "chat은 디코드 수요의 61.6%이므로 2.46대가 필요하다"는 틀렸다

`README.md` §0.2에 적은 계산은 **디코드 토큰 비중 × 엔진 수**였다. 그것은 **모든 클래스가 엔진
한 대에서 같은 속도로 토큰을 낸다**고 가정한 것이고, 클래스마다 요청당 KV가 6~9배 다르므로
틀렸다. 사용자가 "chat은 짧으니 더 뭉칠 수 있지 않나"라고 지적한 그대로다.

배치 상한을 pace와 KV 둘 다로 잡고 다시 계산하면(step 모델 `16.36 + 1.282e-5·kv + 0.0764·n`,
KV 용량 776k~845k — 두 독립 추정):

| 클래스 | 요청당 KV | pace가 허용 | **KV가 허용** | 실제 배치 | **그때 step** | 예산 | 대당 토큰/초 | 막는 것 |
|---|---|---|---|---|---|---|---|---|
| chat | 728 | 334 | 1,066 | **334** | 45.0 ms | 50 | 7,421 | **pace** |
| deepresearch | 4,299 | 560 | **181** | **181** | **40.1 ms** | 100 | 4,501 | **메모리** |
| swe | 6,460 | 223 | **120** | **120** | **35.5 ms** | 57.7 | 3,385 | **메모리** |

25 req/s m1에서 필요한 엔진: **chat 1.01대**, dr 0.83대, swe 0.28대 (합 2.11 / 4대).
**제 2.46대는 2.4배 과대였다.**

### 1.1 그리고 이 정정이 과잉 서비스의 해석을 뒤집는다

위 표의 `그때 step` 열이 결정적이다. **dr만 있는 엔진도 40.1 ms로 돈다** — 자기 예산 100 ms의
절반이다. **chat과 섞여서가 아니라, KV가 배치를 181에서 막아 pace 한계(560)에 도달하기 전에
멈추기 때문이다.** waste로 환산하면 1 − 40.1/100 = **0.60**이고 실측이 **0.44~0.55**다.

> **`README.md` §2.1의 "포화인데도 dr을 두 배 속도로 서비스한다 — 섞여 있어서다"를 철회한다.
> 분리해도 그대로다.** dr을 전용 엔진에 놔도 KV가 먼저 차서 40 ms로 돈다. **분리는 dr의 과잉
> 서비스를 회수할 수 없다.**

⚠ dr이 pace 한계에 걸리려면 KV 용량이 **2.41M 토큰**이어야 하는데 두 추정 모두 그 3분의 1이라,
어느 추정을 써도 결론이 같다.

## 2. chat 상주 인스턴스 수는 chat 비중과 무관하다

shift trace, 5초 창, 엔진 4대, 각 arm 2반복:

| 구간 | **선호 켬** | 선호 끔 |
|---|---|---|
| s0 chat 93% | **2.91 / 2.88** (4대 전부인 창 40%) | 4.00 / 4.00 (100%) |
| **s1 chat 33%** | **2.94 / 2.96** (4대 전부인 창 **0%**) | 3.54 / 3.44 |
| s2 chat 77% | 3.06 / 2.80 | 3.88 / 3.98 |
| s3 chat 60% | 2.99 / 2.91 | 3.59 / 3.51 |

**요청의 3분의 2가 사라져도(93% → 33%) chat이 차지하는 엔진 수가 2.91 → 2.94로 안 준다.**
정적 m5에서 잰 것(EXP-92)이 동적 trace에서도 그대로다.
**선호를 끈 쪽은 오히려 비중을 따라간다**(4.00 → 3.54) — 도착이 적으면 우연히 비는 대가 생긴다.

**그래서 "chat이 줄어드는 구간이 오면 선호의 효과가 커지는가"의 답은 아니오다.** 구간별 효과가
s0 +0.9, s1 +1.2, s2 +2.1, s3 +1.3으로 **chat이 가장 적은 구간이 가장 크지 않다.**

## 3. 그 이유가 코드 한 곳에 있다 — `classShare`가 비율이고 동률이 free space로 떨어진다

`classShare` (`fluidserve.go:2042`)는 **같은 tier 상주 수 ÷ 전체 상주 수**다. **비율이라 1.0에서
포화한다.**

- chat 100개 중 80개 → **0.80**
- chat 1개 중 1개 → **1.00** → 이긴다
- 완전히 빈 인스턴스 → `len(f.live)==0`이라 **0**을 반환하므로 맨 뒤다

문제는 빈 인스턴스가 아니라 **거의 순수한 인스턴스끼리 구별이 안 되는 것**이고, 그때
`sortCandidates`의 4단계가 결정한다:

```go
c.headroomAfter = min(f.capKv, f.capMem) - newKv     // 남는 KV
c.room          = c.headroomAfter / capMem           // 물리 KV 용량으로 정규화, 0~1
...
if c[a].room != c[b].room {
    return c[a].room > c[b].room     // free space가 '많은' 쪽을 앞으로
}
```

**`room`은 토큰 예산이 아니라 KV다** — 이 요청을 놓은 뒤 남는 KV를 그 인스턴스의 물리 KV
용량으로 나눈 값이고, 인스턴스 크기가 달라도 같은 뜻이 되도록 비율로 쓴다(코드 주석).

> **chat이 지배적인 인스턴스가 둘 이상이면 점수가 모두 1.0으로 동률이 되고, 그러면 비어 있는
> 쪽으로 보낸다. 채우는 것이 아니라 퍼뜨린다.**

**이것이 같은 함수의 주석과 어긋난다.** 주석은 *"한 인스턴스를 한 클래스로 더 못 받을 때까지
채우는 것이 분리를 만들고, 멈추는 것은 feasibility"*라고 적는데, **비율 + free space 동률 깨기는
채우기가 아니라 지배된 인스턴스들 사이의 부하 분산이다.**

### 3.1 측정 넷이 이 설명과 맞는다

| 관측 | 설명 |
|---|---|
| chat이 비중과 무관하게 약 3대 (§2) | 지배된 인스턴스 3대가 동률이 되어 그 안에서 균등 분산 |
| **share 1위 적중 64.6%인데 개수 1위 적중 40.1%** (s0) | 점수가 개수를 안 보므로 개수 1위와 자주 어긋난다 |
| N_eff가 5초~180초 전 척도에서 2.0~2.5로 평평 | 채우다 멈추는 것이 아니라 **정상상태 분산**이라 시간 척도에 안 변한다 |
| s0에서 share 1위가 **정확히 동률**인 배치가 **45.7%** (개수로는 1.2%) | chat이 93%면 여러 인스턴스가 정확히 `1.0`이 되어 **선호가 사실상 꺼진다** |

### 3.2 1순위로 안 가는 이유가 구간마다 다르다

chat 배치가 그 순간 share 1위 인스턴스로 간 비율 (선호 켬 / 끔):
s0 64.6 / 29.0, s1 56.0 / 34.5, s2 65.9 / 30.4, s3 54.9 / 32.7 (무작위면 25%).

정렬은 **feasible 집합 안에서만** 하고 w=1이면 share가 유일한 기준이므로, **1위가 feasible이면
반드시 거기로 간다.** 그러니 안 간 34~45%는 둘 중 하나다:

⚠ **처음에는 "1·2위 share 차이가 0.02 미만"으로 셌는데, 코드는 `sa != sb`, 즉 정확한 float
일치를 요구한다.** 사용자가 "실수 단위라 동률이 나올지 모르겠다"고 지적해 정확한 비교로 다시 쟀다.
`classShare`는 **두 정수의 비**이므로 여러 인스턴스가 정확히 `1.0`(상주가 전부 그 클래스)이 되면
완전히 같아진다.

| 구간 | **share 1위 정확 동률** | 동률 인스턴스 수 | **개수 1위 동률** | 원인 |
|---|---|---|---|---|
| **s0 chat 93%** | **45.7%** | 2.00 | **1.2%** | **동률 → free space로 떨어짐** |
| s1 chat 33% | 0.9% | 2.00 | 0.1% | **1위가 infeasible** |
| s2 chat 77% | 4.9% | 2.00 | 0.1% | 1위가 infeasible |
| s3 chat 60% | 0.0% | — | 0.1% | 1위가 infeasible |

> **비율은 s0에서 45.7%가 구별 불가인데 개수는 1.2%뿐이다. 정규화를 개수로 바꾸면 동률이 사실상
> 사라지므로, 동률 깨기의 방향(빈 쪽 선호)은 정규화의 증상이지 독립된 결함이 아니다.**
> ⚠ **그러나 s1~s3에서는 동률이 0~4.9%뿐이므로, 거기서 1순위로 안 가는 34~45%는 정규화를 고쳐도
> 안 바뀔 수 있다.** 남은 후보는 "1위가 infeasible"인데 아직 직접 확인하지 못했다.

> **어제 "chat 93% 구간에서 선호가 엔진-초의 27.7~28.3%를 비운다"고 인용한 그 구간이, 정작
> 선호가 가장 안 작동하는 구간이다.** 거기서 생기는 분리는 선호가 아니라 free space 정렬
> (=부하 분산)이 만들었을 수 있다.

## 3.3 ⚠ 2026-08-24 밤 정정 — §3.1·§3.2의 동률 수치는 재구성이 틀린 것이었다

EXP-96이 카운터를 넣어 **정렬이 실제로 어디서 갈렸는지를 직접 셌다**(정적 m1, 2 arm × 2 도착률
× 2반복). 결과가 위 §3.2의 표를 뒤집는다.

| | **진짜 동률 (width≥2)** | 1순위 뽑힘 | **1순위 막힘** | 막은 사유 |
|---|---|---|---|---|
| 25 req/s | **0.16%** | 58.1% | **41.7%** | gate 52% / memory 37% / incumbents 11% |
| 45 req/s | **0.07%** | 52.3% | **47.2%** | gate 55% / memory 42% / incumbents 3% |

**동률은 0.1% 수준이다.** 위에서 "s0에서 45.7%가 정확한 동률"이라고 적은 것은 **share를 정책의
registry가 아니라 클라이언트 상주 기록으로 재구성한 탓**이고, 두 계수가 다르다(배치됐지만 첫
토큰 전인 요청, 보유 중인 요청).

> **그러므로 §3의 설명 중 "동률이 free space로 떨어져 퍼뜨린다"는 부분은 성립하지 않는다.
> 정렬이 1순위로 안 가는 진짜 이유는 42~47%에서 그 1순위가 infeasible이기 때문이고, 막는 것은
> 속도 게이트가 절반, 메모리가 37~42%다. 모으려는 인스턴스가 이미 가득 차 있다.**

⚠ **완전한 반증은 아니다.** 위 카운터는 **정적 m1**이고 §3.2의 45.7%는 **한 시간 trace의
chat 93% 구간**이다. 같은 조건이 아니므로 그 구간을 카운터와 함께 재는 EXP-97이 답한다.

**그리고 정규화 자체는 실제로 결함이 맞았다** — 고쳐서 돌린 EXP-96B에서 정렬이 실제로 다르게
동작한다. 다만 **성능은 저부하에서 같고(96.1 대 96.1) 고부하에서 3.3점 나쁘며, 메모리 탈락이
10.0%에서 17.8%로 는다.** **결함이었으나 성능의 원인은 아니었다.**

## 4. `harm`이 무엇인가, 그리고 스위치의 실제 범위

`harmToIncumbents` (`fluidserve.go:1872`): `delta = meanAfter − meanBefore`일 때, 상주 요청마다
`h = delta / (그 요청의 남은 허용치 − meanBefore)`를 상한 `fsHarmCap`으로 자른 뒤 합한 값.
**"이 배치가 늘리는 시간이 각 상주 요청의 남은 여유의 몇 배인가"의 합**이다.

**쓰이는 곳은 `sortCandidates`의 3단계, 즉 infeasible 후보들끼리의 순서**다. feasible한 곳이
없으면 가장 덜 망가뜨리는 곳에 강제 배치(`force`)하는데 그때 쓴다.

**클래스 항이 붙어 있는 이유**(같은 함수 주석): 이미 예산을 넘긴 요청은 `slack ≤ 0`이라 합에서
빠지므로, **자기 클래스가 망가지기 시작한 인스턴스가 "비용 0"으로 읽혀 외부 작업을 더 끌어들이고
그래서 더 망가지는 되먹임**이 생긴다. 실측으로 3000 rpm에서 chat이 54.5%까지 떨어졌다.

⚠ **그런데 우리 모든 arm이 `FS_CLASS_HARM=false`로 고정돼 있다.** harm의 클래스 항은 **어차피
항상 꺼져 있었고**, `--fluidserve-enable-affinity=false`가 추가로 끄는 것은 사실상 **정렬의
`share`뿐**이다. "그 플래그가 두 곳을 동시에 끈다"는 서술을 이렇게 좁혀야 한다.

## 5. 고칠 방향 둘 — 다만 아직 고치자고 하면 안 된다

- **동률 깨기를 뒤집는다**: 지배된 인스턴스끼리는 **free space가 적은 쪽**(더 찬 쪽)을 먼저.
  그러면 주석이 말하는 "채우기"가 실제로 일어난다.
- **share 대신 개수**를 쓴다: 무거운 chat 인스턴스가 infeasible해질 때까지 계속 이긴다.

⚠ **둘 다 코드를 읽고 세운 설명이고, 결정이 실제로 그 경로로 나는지는 확인하지 않았다.**
확인에 필요한 것은 카운터 한 줄이다 — **"score가 동률이라 room으로 떨어진 횟수"**와
**"1순위가 infeasible이라 2순위로 간 횟수"**. 지금 `V(5)` 로그에만 있고 수집되지 않는다.

## 6. 재구성 오차 — 위 수치 전부에 걸린다

share를 **배치 시각의 상주 집합**으로 다시 만들었는데, 정책이 쓰는 share는 **자기 registry가
세는 값**이다(배치했지만 첫 토큰 전인 요청, 보유 중인 요청의 계수가 다르다). **방향은 튼튼하지만
"53.5%", "64.6%" 같은 숫자 자체는 그렇지 않다.**
