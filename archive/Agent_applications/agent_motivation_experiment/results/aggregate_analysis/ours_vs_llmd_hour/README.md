# 지금 버전의 FluidServe 대 llm-d — 한 시간 믹스 이동 trace

두 arm만 있다. `exp98_caps/`는 **변경의 사슬**을 읽는 세트이고 여기는 **두 시스템**을 읽는
세트다. 한 그림이 두 질문을 다 들면 어느 쪽도 잘 답하지 못한다.

| arm | 무엇 | run |
|---|---|---|
| **FluidServe (current)** | 클래스 선호를 개수로 순위, 보정 계수를 인스턴스별로, 메모리 판정이 `min(capKv, capMem)` | EXP-98, 2반복 |
| **llm-d** | 자체 endpoint picker의 예측 지연 라우팅 | EXP-93, 2반복 |

⚠ **두 arm은 세션이 다르다.** 아래 차이들은 두 arm의 반복 폭보다 훨씬 크므로 그 단서로
무효가 되지 않지만, **같은 그림에서 더 작은 차이를 읽을 때는 성립하지 않는다.**

⚠ **llm-d의 엔진 귀속은 Envoy access log에서 온다**(`llmd_engine_map.py`, 99.94% 매칭).
그 arm은 Llumnix 스케줄러를 거치지 않아 `scheduler_dispatch.log`에 아무것도 안 남긴다.

**세 문장으로 읽으면:**

**① chat에서 압도한다.** 거절을 37%p 덜 하면서 달성률이 41점 높고 goodput이 1.8배다.
규칙을 지키고 완주한 chat 요청이 **26,469건 더 많다.**

**② deepresearch에서는 llm-d가 낫다.** 우리가 덜 거절하는데(30.3 대 37.7%) **받아들인 것을
덜 지킨다**(80.5 대 **99.9**). llm-d는 그 클래스를 더 거절하고 남은 것을 사실상 전부 지킨다.
지킨 건수로 1,342건 적고 goodput으로 414 tok/s 적다.

**③ swe는 사실상 같다.** 모든 차이가 작다.

**총계로는 거절을 절반 이하로 하면서 달성률 +25.9점, goodput +33%, 지킨 요청 +51%다.**

## 엔진 배치가 정반대다

| | 엔진별 요청 수 | 엔진별 admitted 달성률 | chat 토큰당 (ms) | 불균형 |
|---|---|---|---|---|
| FluidServe | 15,477 / 26,869 / 12,007 / 25,598 | 96.4 / 98.6 / **72.1** / 98.9 | 44.7 / 43.8 / 42.6 / 43.6 | **65.55배** |
| llm-d | 12,337 / 13,277 / 13,886 / 13,605 | 92.4 / 93.2 / 92.4 / 91.1 | 39.9 / 39.6 / 40.2 / 39.1 | **1.79배** |

**llm-d는 네 엔진에 거의 완벽하게 균등하게 나누고 chat 토큰당 시간을 40 ms 아래로 유지한다.
우리는 극단적으로 불균등하고 한 엔진(deepresearch가 43%)의 달성률이 72.1로 낮다.**
**그런데 총 처리량은 우리가 1.4배다** — llm-d는 그 균등함을 거절로 산다.
